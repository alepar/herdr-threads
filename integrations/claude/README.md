# Claude Code hook adapter

The Rust adapter declares `SessionStart` and Bash `PreToolUse` command hooks for the observed Claude Code 2.1.283 shape. The version gate is the recipe registry `claude::RECIPES`; any installed version outside the table below (for example 2.1.282 or 2.1.287) is refused with an actionable message naming the supported recipes, as is an empty version string (the caller observed no version from the installed executable): `claude::check_version` returns it, and every production entry (`parse_event`, `parse_versioned_event`, `encode_lifecycle_response`, `encode_tool_response`) returns it as `ContextError::UnsupportedVersion`, never a bare `Invalid`. `claude::declared_hook_groups` is the single source of those groups, and `declared_hooks` builds its hook object from them. Setup consumes that declaration: `plan_claude` composes every declared group into a caller-supplied JSON settings file, and the owned user-level setup (`install_user_settings(SettingsKind::ClaudeUser, ..)`) installs every declared group into the user's `settings.json` with an exact ownership manifest. Setup installs these hook groups, in declaration order:

- `SessionStart`: no matcher, command hook, timeout 10
- `PreToolUse`: matcher `Bash`, command hook, timeout 10

## Permission allow rule

The owned user-level setup (`herdr-threads setup claude`, library `install_user_settings(SettingsKind::ClaudeUser, ..)`) installs the hook groups into `$CLAUDE_CONFIG_DIR/settings.json` (default `~/.claude/settings.json`), beside the hooks already there (such as Herdr's own SessionStart `herdr-agent-state.sh`), and one permission allow rule in the same file's `permissions.allow`:

```
Bash(herdr-threads *)
```

**What it allows.** Claude Code may run, without asking, any single Bash command whose first word is exactly `herdr-threads`, with any arguments. That covers every subcommand of this CLI: reading threads and the inbox, accepting invitations, ACKing messages, posting and replying, and also the operator subcommands (`setup`/`unsetup`, `daemon ...`, `doctor`). Anyone who can make the agent want to run a `herdr-threads` command, including peer text the agent reads, can therefore get it run without a prompt; the commands act only on this plugin's own state for the caller's pane. The space before `*` is a word boundary, so `herdr-threadsX` does not match. It does not cover a different program invoked by path (`/usr/local/bin/herdr-threads ...`), and it does not cover anything chained after the command: Claude Code checks each segment of a compound command (`;`, `&&`, `||`, `|`, command substitution) separately, so `herdr-threads inbox && rm x` still needs approval for `rm x`.

**Why.** The hook tells the top-level agent to run plugin-authored *ready commands* (`herdr-threads --state-dir S read T --recent 20`, `... accept T`, `... accept-required T --invitation I --requirement R --revision N`, `... ack MSG`, `... inbox`, `... pending-receipts`, `... thread list --seat S`, `... daemon health`). Their argv0 is always the bare program name (`cli::hook::CLI_ARGV0`), never an absolute path, so this one rule covers them; the binary must be on the agent's `PATH`. Without a rule, print mode denied the model's first ready command ("This command requires approval") in [native Claude demo 2](../../docs/evidence/native-claude-demo-2/report.md) (P6). The rule is `claude::HERDR_THREADS_ALLOW_RULE`. The test `owned_claude_allow_rule_covers_every_ready_command_form` renders every ready-command form with the hook's own renderer and checks each against a model of Claude's documented Bash rule matching (`claude::bash_rule_covers`: `*` matches anything, the match is against the whole command, and a compound command is never covered). The `Bash(<program> *)` form itself was observed to allow a quoted-argument command in print mode (`Bash(echo *)`, claude-285 capture run3b); a live run with this exact rule is still owed to the next native demonstration.

**Retired rule.** Earlier setups installed `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` (`claude::CALLER_CONTEXT_ALLOW_RULE`) for the `updatedInput` rewrite prefix. The production hook never rewrites commands (it emits context only), so that rule allowed nothing the plugin runs; setup no longer installs it.

Ownership follows the hook groups:

- The manifest records the rule with a fingerprint. Only the declared rule, or the retired export rule in a manifest an earlier setup wrote, is ever treated as owned, so a manifest cannot direct removal of another user rule.
- If the settings file already allows the identical rule, setup does not add a second copy. It records the rule as `pre_existing`, and unsetup leaves it in place.
- `unsetup claude` removes an owned rule. When nothing else changed, the file is restored byte for byte. After unrelated edits, removal is structural: it removes one occurrence of the owned rule, and drops an `allow` array or `permissions` object that became empty only if the recorded baseline did not hold it. A rule that is already gone does not block unsetup.
- Setup never re-adds a recorded rule that was removed by hand. Re-running `setup claude` then refuses with status 1 and names the rule; run `unsetup` and set up again.
- **Upgrade.** An installation recorded with the retired export rule is reported `installed: no` with `allow_rule.ownership: superseded` and a note. Re-running `setup claude` removes the owned export rule (a copy the user held before setup stays) and adds `Bash(herdr-threads *)`, through the same crash-safe prepared-intent path used for hook upgrades: the manifest records the retired rule as `superseded_permission` until the upgrade is final, so an interrupted upgrade resumes or unsetups cleanly. A retired rule already removed by hand does not block the upgrade. `unsetup` of an installation that was never upgraded removes its owned export rule.
- An installation recorded before any rule existed is reported `installed: no` (`allow_rule.ownership: not_recorded`); re-running `setup claude` adds the rule. A legacy installation without an installation ID must be removed and set up again.
- `setup`, `setup-status`, and `doctor` report `allow_rule.rule`, `allow_rule.ownership` (`owned`, `pre_existing`, `not_recorded`, or `superseded`), `allow_rule.present`, and for `superseded` an `allow_rule.note`. `unsetup` reports `allow_rule: removed`, `left_pre_existing`, or `not_recorded`. "Installed" requires the declared rule to be present.

The public `plan_claude` proposal (private `--settings` JSON) composes hook groups only and adds no rule. Setup changes no other permission rule and no file other than that `settings.json` (plus its private manifest under `<state>/setup/`). The hook command records the Herdr instance (`--state-dir`, `--host-endpoint`), and in any Claude session that is not a pane of that instance it exits 0 at once with no output. A Claude session with another `CLAUDE_CONFIG_DIR`, or `--setting-sources` without `user`, does not load the hooks; such a launch can add the owned file explicitly with `--settings <that settings.json>` (the native demo driver does this for its scratch setup).

## Supported versions

| Recipe | Installed versions | Evidence | Evidence scope |
| --- | --- | --- | --- |
| `claude-hooks-2.1.283` | closed interval [2.1.283, 2.1.286] (exactly those four patch releases) | [`claude-probe.md`](../../docs/compatibility/claude-probe.md), [`claude-lifecycle-probe.md`](../../docs/compatibility/claude-lifecycle-probe.md), [`claude-284-hook-capture`](../../docs/evidence/claude-284-hook-capture/report.md), [`claude-285-hook-capture`](../../docs/evidence/claude-285-hook-capture/report.md), [`claude-286-hook-capture`](../../docs/evidence/claude-286-hook-capture/report.md) | 2.1.283: Bash PreToolUse input and `updatedInput` rewrite observed; SessionStart startup/clear/resume input observed. 2.1.284: SessionStart startup/resume and root/subagent Bash PreToolUse input captured and parsed unchanged; hook-output application unverified. 2.1.285: the same input captured and parsed unchanged; in print mode root Bash `updatedInput` was executed and SessionStart/PreToolUse `additionalContext` delivered. 2.1.286: the same input and print-mode output application, re-captured with the 2.1.285 method. Model receipt unsupported for all four, so daemon health reports `harness.claude = unsupported` |

A new version is added to this recipe only with captured evidence that its payloads parse unchanged; a version whose payloads differ gets its own recipe and `InputSchema` variant.

`inspect_user_settings` reports an installation that lacks any declared group, such as a Bash-only installation recorded under an earlier declaration, as not installed; re-running setup upgrades it to the current declaration. The planner itself performs no writes. Apart from the one owned allow rule above, setup never changes native permission rules. Installing a hook proves neither native observation nor model-visible delivery: the caller still supplies the hook command, and no installed application entry point is qualified here.

`SessionStart` accepts the observed `startup`, `clear`, and `resume` sources. The production hook (`herdr-threads hook claude`) emits context only; the `updatedInput` transport below (`claude::encode_tool_response`) is kept, with its tests, as the verified adapter shape but **is not used in production**, and a future caller would also need a permission rule for its export prefix. Bash `PreToolUse` can return an invocation-scoped caller token through `updatedInput.command` and compact `additionalContext`; the original command is retained verbatim after the export prefix, and all other tool input keys are copied. The output contains no `permissionDecision`. Both encoders parse the hook input, require a caller-observed installed version covered by a recipe (2.1.283, 2.1.284, 2.1.285 or 2.1.286), and return `{}` for child callbacks (a present `agent_id` with `agent_type`), so a child gets no transport or check-in prompt on either path. Empty check-in output returns `{}`.

Budgets are per field. `additionalContext` must fit `min(max_bytes, 4096)` bytes as JSON-escaped in the envelope; the echoed command in `updatedInput` never counts against it. `updatedInput` is bounded by the native input limit (hook input and command at most 65,536 bytes each), so long commands keep their transport. An oversized hint returns `TooLarge` whatever the command length and is never silently dropped; the caller can re-encode with an empty hint to keep the transport. A `SessionStart` response is a pure hint, so its whole envelope must fit the hint budget.

`additionalContext` has a fixed, plugin-authored instruction section followed by one `untrusted_peer_data:` JSON string. The fixed section carries the shared top-level instruction, including the required-invitation `accept-required` procedure, and the child restriction. Peer text is stripped of control characters and appears only in the data section.

Claude Code 2.1.284 support is limited to input parsing. A 2.1.284 capture (binary SHA-256 `50a14c2f50f56668380fdda490167f1d3630d5cc18fb8aed3073c2c7ea7314fe`) recorded SessionStart startup and resume, root Bash PreToolUse, and subagent Bash PreToolUse stdin. These are committed under `tests/fixtures/claude-2.1.284/`, and each parses unchanged: Startup, Tool/TopLevel (the rewrite keeps `tool_input.description` in `updatedInput`), Resume, and Tool/Subagent (`{}`). The payloads add keys the adapter does not read (`permission_mode`, `prompt_id`, `tool_input.description`, and the resume cost/cache fields) and carry no native event ID. Hook output application is still pending native verification: whether 2.1.284 honours `updatedInput` or `additionalContext` has not been observed. The clear, compact and permission-denial paths, and coexistence with user-global hooks, are also unobserved for 2.1.284.

Claude Code 2.1.285 (binary SHA-256 `51f09bd1e021d9fa8a1864c179799bd37cb39962a937935c5cf6823398e86db4`) was captured the same way. The four input payloads have the same keys and types as 2.1.284 and are committed under `tests/fixtures/claude-2.1.285/`, where each parses unchanged. A third print-mode run had the hooks return the adapter-shaped output. The transcript recorded both `additionalContext` markers as `hook_additional_context` attachments, and the model repeated them. The rewritten root Bash command executed with the exported token (`ctx=ctx_probe-…`), with `description` preserved. The adapter's own encoder reproduces that exact `updatedInput` (fixture 05). One operational constraint: 2.1.285 permission-checks the *rewritten* command. With only `Bash(echo *)` allowed, the `export HERDR_THREADS_CALLER_CONTEXT=…` prefix was denied as a separate operation. An unattended session therefore needs an allow rule covering that prefix; `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` was sufficient. Still unobserved for 2.1.285: clear/compact, interactive permission prompts, coexistence with user-global hooks, the Herdr pane, and a qualified model-receipt gate.

Claude Code 2.1.286 (binary SHA-256 `75e3016e9d2570767b08e43a7467d4817a4f149232c169ca295f2c95fef21433`) was captured with the 2.1.285 method (`claude-286-hook-capture`). The four input payloads have the same keys and value types as 2.1.285, the hook environment names are identical, and the payloads are committed under `tests/fixtures/claude-2.1.286/`, where each parses unchanged. The adapter-shaped output run behaved as on 2.1.285: both `additionalContext` markers were recorded as `hook_additional_context` attachments, the rewritten root Bash command executed (`ctx=ctx_probe-c286f4`) with `description` preserved when `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` was allowed, and it was denied as a separate operation under `Bash(echo *)` alone. The adapter's encoder reproduces that exact `updatedInput` (fixture 05). The same paths as for 2.1.285 remain unobserved.

The [installed lifecycle capture](../../docs/compatibility/claude-lifecycle-probe.md) shows native startup, clear, and resume input and private settings composition. The [Bash probe](../../docs/compatibility/claude-probe.md) shows command rewriting reaching the matching tool invocation. Neither capture proves model receipt, explicit accept/ACK, SQLite receipt rows, installed application entry point, compaction behavior, or all launch modes. Those remain native integration gates under the superseding cooperative trust direction in ht-910.
