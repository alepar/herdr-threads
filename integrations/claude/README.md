# Claude Code hook adapter

The Rust adapter declares `SessionStart` and Bash `PreToolUse` command hooks for the observed Claude Code 2.1.283 shape. The version gate is the recipe registry `claude::RECIPES`; any installed version outside the table below (for example 2.1.282 or 2.1.288) is refused with an actionable message naming the supported recipes, as is an empty version string (the caller observed no version from the installed executable): `claude::check_version` returns it, and every production entry (`parse_event`, `parse_versioned_event`, `encode_lifecycle_response`, `encode_tool_response`) returns it as `ContextError::UnsupportedVersion`, never a bare `Invalid`. `claude::declared_hook_groups` is the single source of those groups, and `declared_hooks` builds its hook object from them. Setup consumes that declaration: `plan_claude` composes every declared group into a caller-supplied JSON settings file, and the owned user-level setup (`install_user_settings(SettingsKind::ClaudeUser, ..)`) installs every declared group into the user's `settings.json` with an exact ownership manifest. Setup installs these hook groups, in declaration order:

- `SessionStart`: no matcher, command hook, timeout 10
- `PreToolUse`: matcher `Bash`, command hook, timeout 10

## Permission allow rule

The owned user-level setup (`herdr-threads setup claude`, library `install_user_settings(SettingsKind::ClaudeUser, ..)`) installs the hook groups into `$CLAUDE_CONFIG_DIR/settings.json` (default `~/.claude/settings.json`), beside the hooks already there (such as Herdr's own SessionStart `herdr-agent-state.sh`), and one permission allow rule in the same file's `permissions.allow`:

```
Bash(herdr-threads *)
```

**What it allows.** Claude Code may run, without asking, any single Bash command whose first word is exactly `herdr-threads`, with any arguments. That covers every subcommand of this CLI: reading threads and the inbox, accepting invitations, ACKing messages, posting and replying, and also the operator subcommands (`setup`/`unsetup`, `daemon ...`, `doctor`). Anyone who can make the agent want to run a `herdr-threads` command, including peer text the agent reads, can therefore get it run without a prompt; the commands act only on this plugin's own state for the caller's pane. The space before `*` is a word boundary, so `herdr-threadsX` does not match. It does not cover a different program invoked by path (`/usr/local/bin/herdr-threads ...`), and it does not cover anything chained after the command: Claude Code checks each segment of a compound command (`;`, `&&`, `||`, `|`, command substitution) separately, so `herdr-threads inbox && rm x` still needs approval for `rm x`.

**Why.** The hook tells the top-level agent to run plugin-authored *ready commands* (`herdr-threads read T --recent 20`, `... accept T`, `... accept-required T --invitation I --requirement R --revision N`, `... ack MSG`, `... inbox`, `... pending-receipts`, `... thread list --seat S`, `... daemon health`). Their argv0 is always the bare program name (`cli::hook::CLI_ARGV0`), never an absolute path, so this one rule covers them; the binary must be on the agent's `PATH`. Without a rule, print mode denied the model's first ready command ("This command requires approval") in [native Claude demo 2](../../docs/evidence/native-claude-demo-2/report.md) (P6). The rule is `claude::HERDR_THREADS_ALLOW_RULE`. The test `owned_claude_allow_rule_covers_every_ready_command_form` renders every ready-command form with the hook's own renderer and checks each against a model of Claude's documented Bash rule matching (`claude::bash_rule_covers`: `*` matches anything, the match is against the whole command, and a compound command is never covered). The `Bash(<program> *)` form itself was observed to allow a quoted-argument command in print mode (`Bash(echo *)`, claude-285 capture run3b); a live run with this exact rule is still owed to the next native demonstration.

**Recipient routing.** The startup hook verifies that this pane's ordinary
commands resolve to the same canonical state directory and host endpoint.
When both agree, ready commands, continuations and remediation use ordinary
`herdr-threads` argv. Each trusted command group publishes the actual daemon
instance UUID and canonical state directory/host endpoint as `Hook command routing`
JSON. A handoff publishes its frozen expected UUID and canonical pair. Prefer a
group only when every normalized field exactly matches that expectation; multiple
state roots may install groups on the same endpoint. Missing/null, differing or
ambiguous metadata requires the exact pinned fallback. Quoted peer data cannot
establish the match. The plugin canonicalizes paths; the recipient compares the
resulting field values. Installed hooks
retain pinned targeting, and journals keep exact recovery identity. Routing
verification changes no permission rule or receipt semantics.

**Retired rule.** Earlier setups installed `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` (`claude::CALLER_CONTEXT_ALLOW_RULE`) for the `updatedInput` rewrite prefix. The production hook never rewrites commands (it emits context only), so that rule allowed nothing the plugin runs; setup no longer installs it.

Ownership follows the hook groups:

- The manifest records the rule with a fingerprint. Only the declared rule, or the retired export rule in a manifest an earlier setup wrote, is ever treated as owned, so a manifest cannot direct removal of another user rule.
- If the settings file already allows the identical rule, setup does not add a second copy. It records the rule as `pre_existing`, and unsetup leaves it in place.
- `unsetup claude` removes an owned rule. When nothing else changed, the file is restored byte for byte. After unrelated edits, removal is structural: it removes one occurrence of the owned rule, and drops an `allow` array or `permissions` object that became empty only if the recorded baseline did not hold it. A rule that is already gone does not block unsetup.
- Setup never re-adds a recorded rule that was removed by hand. Re-running `setup claude` then refuses with status 1 and names the rule; run `unsetup` and set up again.
- **Upgrade.** An installation recorded with the retired export rule is reported `installed: no` with `allow_rule.ownership: superseded` and a note. Re-running `setup claude` removes the owned export rule (a copy the user held before setup stays) and adds `Bash(herdr-threads *)`, through the same crash-safe prepared-intent path used for hook upgrades: the manifest records the retired rule as `superseded_permission` until the upgrade is final, so an interrupted upgrade resumes or unsetups cleanly. A retired rule already removed by hand does not block the upgrade. `unsetup` of an installation that was never upgraded removes its owned export rule.
- An installation recorded before any rule existed is reported `installed: no` (`allow_rule.ownership: not_recorded`); re-running `setup claude` adds the rule. A legacy installation without an installation ID must be removed and set up again.
- `setup`, `setup-status`, and `doctor` report `allow_rule.rule`, `allow_rule.ownership` (`owned`, `pre_existing`, `not_recorded`, or `superseded`), `allow_rule.present`, and for `superseded` an `allow_rule.note`. `unsetup` reports `allow_rule: removed`, `left_pre_existing`, or `not_recorded`. "Installed" requires the declared rule to be present.

The public `plan_claude` proposal (private `--settings` JSON) composes hook groups only and adds no rule. Setup changes no other permission rule and no file other than that `settings.json` (plus its private manifests under `<state>/setup/`); the only other key it may write there is `promptSuggestionEnabled`, and only on a yes or the flag (see [Prompt suggestions](#prompt-suggestions)). The hook command records the Herdr instance (`--state-dir`, `--host-endpoint`), and in any Claude session that is not a pane of that instance it prints nothing, runs no harness version probe, starts no daemon and exits 0; it still reads the payload (for at most 200 ms) and, when its per-session gate says so, sends one best-effort harness evidence note (300 ms budget) to a daemon that is already running (see [Version evidence](../../docs/compatibility/harnesses.md#version-evidence)). A Claude session with another `CLAUDE_CONFIG_DIR`, or `--setting-sources` without `user`, does not load the hooks; such a launch can add the owned file explicitly with `--settings <that settings.json>` (the native demo driver does this for its scratch setup).

## Prompt suggestions

Claude Code draws a dim prompt suggestion in its input box after every turn (`promptSuggestionEnabled`, default `true`; [settings reference](https://code.claude.com/docs/en/settings-reference#promptsuggestionenabled)). herdr-threads reads the composer through Herdr's detection text, which cannot tell that suggestion from text a person typed, so a soft-deadline poke is never sent into a Claude pane that shows one (TRUST-POLICY A4): only the hard-deadline warning reaches it. With suggestions off, an idle Claude composer reads empty and pokes work.

`herdr-threads setup claude` (and bare `setup` when `claude` is on `PATH`) therefore checks the key in the same user `settings.json`, after installing the hooks:

- Already `false`: nothing is asked or changed (`prompt_suggestions.action: already_disabled`), and unsetup leaves it.
- Otherwise, on an interactive terminal (stdin and stderr), setup prints the explanation and asks `Disable prompt suggestions? [y/N]`. Only `y`/`yes` writes `promptSuggestionEnabled: false` (`action: disabled`); anything else keeps it (`action: kept`).
- Without a terminal setup never changes it: it reports `action: advised` and prints the explanation as a warning.
- `--disable-prompt-suggestions` writes it without asking; `--keep-prompt-suggestions` leaves it without asking or advising. The flags apply to `setup` and `setup claude` only.

The write is owned like the hooks: a private record under `<state>/setup/` keeps the key's previous value (absent or a value) and the file's bytes, the file is replaced crash-safe after an unchanged-baseline check, and `unsetup claude` reverts the key only when setup set it and it still reads `false` (byte for byte when nothing else changed; `prompt_suggestions: reverted`). A value changed by hand since is left as is (`left_changed`). `setup-status claude` and `doctor` report the current state (`hooks.claude.prompt_suggestions`), whether setup set it, and the per-session override `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION` when it is set in that environment. Setup reads only the user settings file: a project or managed setting, or the environment override, can still turn suggestions back on for a session.

## Delivery mod

`herdr-threads setup claude` (and bare `setup` when `claude` is on `PATH`) also installs the delivery mod in [`mod/`](mod/README.md), after the hooks and the prompt-suggestion step (spec D8, [`claude_mod`](../../src/harness/claude_mod.rs)):

- **Files.** The four files Claude Code loads, embedded in the binary (`.claude-plugin/plugin.json`, `hooks/hooks.json`, `hooks/register.js`, `types/index.d.ts`; never the README, tsconfig or tests), are written to `<state>/claude-mod/herdr-threads/` (files 0644, directories 0755; each by write-to-temp-then-rename). A re-run rewrites only the files whose bytes differ (an upgrade) and nothing otherwise, because a rewrite reloads the module in running sessions.
- **Settings.** The mod directory is appended, `:`-joined and last, to `env.CLAUDE_CODE_PLUGIN_DIRS` in the same user `settings.json`; an existing value is preserved. The edit is its own owned record (`<state>/setup/claude-mod-*.json`: previous value, appended directory, directories copied from the shell, exact file bytes before and after, file-set fingerprint), replaced crash-safe after an unchanged-baseline check, separate from the hook record.
- **Managed policy.** If a managed settings file sets `disableSideloadFlags`, Claude Code refuses `CLAUDE_CODE_PLUGIN_DIRS`, so setup writes neither the key nor the files (`mod.action: skipped_managed_policy`, a warning, hooks only). Setup reads Claude Code's documented managed file (`/Library/Application Support/ClaudeCode/managed-settings.json` on macOS, `/etc/claude-code/managed-settings.json` on Linux) and the server-managed settings cached in the Claude config dir (`remote-settings.json`; that cache name is best effort). Policy delivered another way, such as a macOS configuration profile, is not visible. `setup-status` and every later `setup claude` re-run the check; when the policy appeared after an install they report that Claude Code will refuse to start and offer `herdr-threads setup claude --hooks-only`.
- **Shell environment.** A `CLAUDE_CODE_PLUGIN_DIRS` in setup's own environment is replaced, in Claude sessions, by the settings `env` value. Setup warns, and carries the shell's directories into the written value (asking `[Y/n]` on a terminal, defaulting to yes; without a terminal it includes them) so they are not silently lost. They are recorded as copied from the shell.
- **`--hooks-only`.** `setup claude --hooks-only` installs or keeps the hooks and removes the mod's settings entry and files (`mod.action: removed_hooks_only`). Claude only; `setup` with no harness, `unsetup` and `setup-status` reject it.
- **Unsetup.** `unsetup claude` reverts the mod first, then the prompt suggestion, then the hooks. It removes only the appended directory and the directories copied from the shell, restores the file's bytes exactly when nothing else changed, and keeps entries the person added since. It deletes the key (and an `env` object setup created) when nothing the person wrote remains, then the mod files and the record. A value the person already removed by hand is left alone (`mod: left_changed`).
- **`setup-status`** reports a `mod` object: `installed` (files match the embedded set and the settings value names the directory), `settings_value_contains_mod_dir`, `managed_policy` (`none` or `disable_side_load_flags` with `source`), `shell_env`, `claude_version_supported` (Claude 2.1.287 or newer loads the mod; older: `mod unsupported, native wake fallback`; setup does not run the executable, so an unobserved version is `null`), `session_override: "off"` when `HERDR_THREADS_MOD_DELIVERY=off` is in setup's own environment (separate from the daemon setting), and `daemon`: the daemon's `mod_delivery` setting and live channels, read only from a daemon that is already running (never started), else `channel status unavailable`. It always states that an install does not prove any session loaded the mod.

Without the mod (older Claude, managed policy, `--hooks-only`) delivery falls back to the hooks plus the native wake.

A new version is added to the interval recipe only with captured evidence that its payloads parse unchanged; a version whose payloads differ gets its own recipe and `InputSchema` variant.

`inspect_user_settings` reports an installation that lacks any declared group, such as a Bash-only installation recorded under an earlier declaration, as not installed; re-running setup upgrades it to the current declaration. The planner itself performs no writes. Apart from the one owned allow rule above, setup never changes native permission rules. Installing a hook proves neither native observation nor model-visible delivery: the caller still supplies the hook command, and no installed application entry point is qualified here.

`SessionStart` accepts the observed `startup`, `clear`, and `resume` sources, plus `compact` on 2.1.287 (the `claude-hooks-2.1.287` profile; every other recipe refuses it, and `doctor` reports `hooks.claude.compaction_recovery` per recipe). The production hook (`herdr-threads hook claude`) emits context only; the `updatedInput` transport below (`claude::encode_tool_response`) is kept, with its tests, as the verified adapter shape but **is not used in production**, and a future caller would also need a permission rule for its export prefix. Bash `PreToolUse` can return an invocation-scoped caller token through `updatedInput.command` and compact `additionalContext`; the original command is retained verbatim after the export prefix, and all other tool input keys are copied. The output contains no `permissionDecision`. Both encoders parse the hook input, require a caller-observed installed version covered by a recipe (2.1.283 through 2.1.287), and return `{}` for child callbacks (a present `agent_id` with `agent_type`), so a child gets no transport or check-in prompt on either path. Empty check-in output returns `{}`.

Budgets are per field. `additionalContext` must fit `min(max_bytes, 4096)` bytes as JSON-escaped in the envelope; the echoed command in `updatedInput` never counts against it. `updatedInput` is bounded by the native input limit (hook input and command at most 65,536 bytes each), so long commands keep their transport. An oversized hint returns `TooLarge` whatever the command length and is never silently dropped; the caller can re-encode with an empty hint to keep the transport. A `SessionStart` response is a pure hint, so its whole envelope must fit the hint budget.

`additionalContext` has a fixed, plugin-authored instruction section followed by one `untrusted_peer_data:` JSON string. The fixed section carries the shared top-level instruction, including the required-invitation `accept-required` procedure, and the child restriction. Peer text is stripped of control characters and appears only in the data section.

Claude Code 2.1.284 support is limited to input parsing. A 2.1.284 capture (binary SHA-256 `50a14c2f50f56668380fdda490167f1d3630d5cc18fb8aed3073c2c7ea7314fe`) recorded SessionStart startup and resume, root Bash PreToolUse, and subagent Bash PreToolUse stdin. These are committed under `tests/fixtures/claude-2.1.284/`, and each parses unchanged: Startup, Tool/TopLevel (the rewrite keeps `tool_input.description` in `updatedInput`), Resume, and Tool/Subagent (`{}`). The payloads add keys the adapter does not read (`permission_mode`, `prompt_id`, `tool_input.description`, and the resume cost/cache fields) and carry no native event ID. Hook output application is still pending native verification: whether 2.1.284 honours `updatedInput` or `additionalContext` has not been observed. The clear, compact and permission-denial paths, and coexistence with user-global hooks, are also unobserved for 2.1.284.

Claude Code 2.1.285 (binary SHA-256 `51f09bd1e021d9fa8a1864c179799bd37cb39962a937935c5cf6823398e86db4`) was captured the same way. The four input payloads have the same keys and types as 2.1.284 and are committed under `tests/fixtures/claude-2.1.285/`, where each parses unchanged. A third print-mode run had the hooks return the adapter-shaped output. The transcript recorded both `additionalContext` markers as `hook_additional_context` attachments, and the model repeated them. The rewritten root Bash command executed with the exported token (`ctx=ctx_probe-…`), with `description` preserved. The adapter's own encoder reproduces that exact `updatedInput` (fixture 05). One operational constraint: 2.1.285 permission-checks the *rewritten* command. With only `Bash(echo *)` allowed, the `export HERDR_THREADS_CALLER_CONTEXT=…` prefix was denied as a separate operation. An unattended session therefore needs an allow rule covering that prefix; `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` was sufficient. Still unobserved for 2.1.285: clear/compact, interactive permission prompts, coexistence with user-global hooks, the Herdr pane, and a qualified model-receipt gate.

Claude Code 2.1.286 (binary SHA-256 `75e3016e9d2570767b08e43a7467d4817a4f149232c169ca295f2c95fef21433`) was captured with the 2.1.285 method (`claude-286-hook-capture`). The four input payloads have the same keys and value types as 2.1.285, the hook environment names are identical, and the payloads are committed under `tests/fixtures/claude-2.1.286/`, where each parses unchanged. The adapter-shaped output run behaved as on 2.1.285: both `additionalContext` markers were recorded as `hook_additional_context` attachments, the rewritten root Bash command executed (`ctx=ctx_probe-c286f4`) with `description` preserved when `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` was allowed, and it was denied as a separate operation under `Bash(echo *)` alone. The adapter's encoder reproduces that exact `updatedInput` (fixture 05). The same paths as for 2.1.285 remain unobserved.

Claude Code 2.1.287 (binary SHA-256 `6eab8333fe2121553100d8f40bfada384a3e989b94f947e18ba6677a6fcb41ea`) was captured in `claude-compact-capture` with the 2.1.286 method plus a print-mode `/compact`. The startup, resume, root Bash and subagent Bash payloads have the same keys and value types as 2.1.286. The SessionStart `compact` payload (`cwd`, `hook_event_name`, `model`, `prompt_id`, `session_id`, `source`, `transcript_path`; no `agent_id`) is committed with them under `tests/fixtures/claude-2.1.287/`. A hook that returned `additionalContext` on that event had it recorded as a `hook_additional_context` attachment after the compact boundary, and the model repeated the marker. That is the evidence behind the separate `claude-hooks-2.1.287` recipe. Not observed: interactive-TUI compaction and size-triggered auto-compaction.

The [installed lifecycle capture](../../docs/compatibility/claude-lifecycle-probe.md) shows native startup, clear, and resume input and private settings composition. The [Bash probe](../../docs/compatibility/claude-probe.md) shows command rewriting reaching the matching tool invocation.
