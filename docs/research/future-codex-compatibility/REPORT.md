# Future Codex compatibility and constrained daemon communication

Research date: 2026-10-03. Product baseline: `0d70765e` (public v0.1.0). Installed binary observed: Codex CLI 0.160.0, macOS arm64, SHA-256 `112fae7a5a1223e673c8a1791d32338f37df8b527ff1159bb8adac6c4dbf1b4b`. This is a design checkpoint and empirical research, not a claim that a native Codex 0.160.0 agent has registered, received a wake, or ACKed a receipt.

## Executive summary

The launch refusal is caused by an exact-version gate on the **sandbox socket allowance**, not the hook admission ladder. Herdr-threads admits new Codex hook schemas by fingerprint or an explicitly labeled optimistic recipe, but `codex_sandbox_socket` withholds the networking allowance unless the version string is 0.159.2 or 0.159.3. Launch then reports `Unsupported` before starting the agent. That gate addresses a real safety risk: the allowance sets `sandbox_workspace_write.network_access=true`, and the scoped proxy must still enforce its default-deny policy. An unknown version supplies neither evidence of incompatibility nor evidence that this policy holds. [Local setup code](../../../src/cli/setup.rs), [launch code](../../../src/cli/launch.rs), [official Codex security guidance](https://learn.chatgpt.com/docs/agent-approvals-security?trk=article-ssr-frontend-pulse_little-text-block).

A bounded, no-model check of the installed 0.160.0 binary in a private `CODEX_HOME` used the same three socket keys as setup. The owned allowed socket connected. An owned second Unix socket, an owned loopback TCP listener, and external TCP each failed at `connect` with `EPERM`. Unsandboxed controls connected to all four. Each `codex sandbox` child returned in about 44–48 ms on this machine. A private mock Responses provider then drove real native `codex exec` and interactive TUI tool calls under the same session policy overrides/cwd. Native exec's full output and the TUI's function-call output captured by that provider showed the allowed socket connected, other network targets denied, the two exact journal roots writable, and a sibling path denied. The result establishes **native exec and TUI tool-sandbox behavior for this binary and these test configurations**; it does not prove the effective policy of every project, managed requirements layer, or Linux build. [Debug probe](evidence/probe-codex-160.py), [native probe](evidence/native_exec_probe.py), [transcript](evidence/probe-results.txt), [OpenAI sandbox implementation](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs).

The near-term product direction is a capability proof for the *selected executable and effective policy*, with explicit positive and negative controls, bounded cleanup, and a cache keyed by those inputs. A conclusive result can replace the version-string gate for one **managed launch** after target-pane executable identity is established; it cannot authorize a global setup allowance for every Codex session. Failure or inconclusive evidence should describe the actual communication or policy-validation condition, not declare an unseen Codex version unsupported. The existing Unix socket transport remains the cheapest integration path. A stdio MCP bridge is a plausible durable alternative if a separately tested lifecycle can preserve the daemon's canonical decisions and receipt provenance. Loopback is not a default-deny workaround; filesystem mailboxes require a larger, carefully constrained protocol redesign. [Official network policy](https://learn.chatgpt.com/docs/config-file/config-reference), [official MCP support](https://learn.chatgpt.com/docs/extend/mcp?surface=app&translationFallback=pt-BR), [trust policy](../../../TRUST-POLICY.md).

## Scope and method

Questions: what rejects 0.160.0; how to replace the exact-version proof without broadening networking; whether another transport avoids version churn; and how doctor, setup, and launch should speak about evidence. I read the repo's launch, setup, Codex config and version-state code, its earlier 0.159.3 evidence, TRUST-POLICY, current official OpenAI documentation and Codex source, plus relevant upstream bug reports. I then ran a private no-model probe of the installed binary. Claims below are classified as measured, documented, inferred, or proposed. The linked ledger contains the source and claim records.

The probes did not use the user's real Codex configuration or the shared Herdr daemon. They bound private sockets, used isolated homes, and removed scratch directories. They did not grant persistent network permission. The direct external-TCP baseline succeeded on this run, but the policy-denial result rests on `EPERM` and controlled local positives, rather than on `curl` failure (which could result from DNS or a remote outage). The first attempt to bind sockets inside this agent's outer sandbox failed `EPERM`; the recorded runs used an unsandboxed *outer test runner* to create listeners, while the **tool children** ran under Codex's workspace-write sandbox. The mock provider supplied tool calls without a model account and was stopped afterward. [Probe transcript](evidence/probe-results.txt).

## Findings

### 1. Two different compatibility decisions were conflated in the baseline

The hook ladder already distinguishes listed, schema-matched, optimistic, below-floor and known-broken versions. Its manifest/state layer distinguishes locally verified, known broken, and unseen observations. Unknown future versions are therefore not inherently refused. The separate socket gate compares only `SANDBOX_MEASURED_VERSIONS`; setup omits an allowance on other versions, warns about an existing `network_access=true` allowance, and launch refuses when workspace-write needs it. At baseline, the error code and text made a policy-evidence gap look like a Codex capability verdict. The follow-on in this branch uses a typed unvalidated-policy reason and a `Conflict` launch precondition instead, without changing the gate. [Admission code](../../../src/harness/admission.rs), [state code](../../../src/harness/state.rs), [socket gate](../../../src/cli/setup.rs), [launch code](../../../src/cli/launch.rs).

The old version set should remain **historical evidence** for those two builds, not be a growing allowlist and not become a fallback that silently treats later builds as broken. Explicit known-broken hook evidence remains authoritative for hooks; a sandbox probe cannot rehabilitate a known-broken hook contract. Conversely, a hook schema match cannot prove network isolation. This separation matches the existing manifest's contract-specific status rules. [Manifest code](../../../src/harness/manifest.rs), [0.159.3 probe](../../../docs/evidence/codex-1593-sandbox-probe/README.md).

### 2. The current socket policy is supported but conditional

Official Codex documentation says the command network proxy starts only when network access is on, defaults to no allowed domains and no allowed Unix sockets, and uses explicit socket `allow` entries. It also says the proxy does not cover MCP, browser, app or other hosted tool connections. The repo's setup adds the daemon socket and two narrowly scoped client journal writable roots; the daemon's database and instance root remain outside the writable roots. Codex's macOS Seatbelt source constructs a restricted Unix socket policy from the configured allowlist and emits socket-specific rules. [Security guidance](https://learn.chatgpt.com/docs/agent-approvals-security?trk=article-ssr-frontend-pulse_little-text-block), [configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Seatbelt source](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs), [local config writer](../../../src/harness/codex_config.rs).

This is not a cross-platform guarantee. A reported Linux Codex issue shows an `AF_UNIX` creation denial before the configured allowlist can be checked. Another upstream issue shows a macOS named-permissions profile accepting socket configuration without passing it into the Seatbelt policy; the debug `--allow-unix-socket` flag works there, but the issue reports that flag is unavailable to interactive TUI. The installed 0.160.0 debug command also advertises `--allow-unix-socket`. In our 0.160.0 test, that flag let the allowed Unix socket connect with `network_access=false`, with the other targets denied. A named profile using `network.enabled=false` plus an exact socket entry still denied the allowed socket, confirming the reported gap for the selected 0.160.0 binary. The debug flag is a useful diagnostic, **not a managed TUI fix**. [Linux report](https://github.com/openai/codex/issues/39140), [macOS profile report](https://github.com/openai/codex/issues/25416), [debug CLI source](https://github.com/openai/codex/blob/main/codex-rs/cli/src/debug_sandbox.rs), [probe transcript](evidence/probe-results.txt).

### 3. Capability proof must bind to policy, not a version string

A candidate proof should launch the **selected absolute Codex executable** under `codex sandbox`, an isolated home, and the proposed exact allowance, then test: (a) controlled unsandboxed connects succeed; (b) the intended socket succeeds in the sandbox; (c) a second owned Unix socket and owned loopback listener fail with recognizable policy denials; (d) direct external TCP fails with policy denial; (e) proxy HTTP returns a recognizable deny if an online target is used, but that result alone cannot pass the proof; (f) writable roots permit only the intended journal paths and deny sibling/daemon-state writes. One deadline and child-process cleanup must bound every phase. [Previous 0.159.3 probe](../../../docs/evidence/codex-1593-sandbox-probe/README.md), [0.160.0 probe](evidence/probe-results.txt), [journal write probe](../../../docs/evidence/codex-sandbox-writes-probe/README.md).

The probe must describe its scope. A private debug sandbox can establish behavior of the selected executable under its supplied configuration; it cannot establish that a later TUI/exec invocation loaded identical layers. Codex supports user and trusted-project configuration, CLI overrides, and managed requirements. The gate must therefore either inspect/construct the **effective** policy for each managed launch, or say that an unknown external launch policy is unvalidated. A cache key needs binary content identity, platform/architecture, socket path, canonical journal roots, the effective relevant configuration and requirements/profile/CLI override fingerprint, and probe protocol version. A version string alone is insufficient. Cache writes should be atomic/private, never become daemon authority, and invalidate on any key change. A later real `transport_denied` is negative operational evidence for that invocation, even if an earlier probe passed; it should be recorded separately from hook-contract known-broken evidence. [Config layering](https://learn.chatgpt.com/docs/config-file/config-basic), [advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced), [local manifest](../../../src/harness/manifest.rs), [trust A2](../../../TRUST-POLICY.md).

### 4. Transport alternatives have different boundaries

| Candidate | Status and default deny | Fit with daemon/provenance | Latency, lifecycle, platforms, cost |
|---|---|---|---|
| Existing exact Unix socket through proxy | Officially documented policy; empirically passed in 0.159.2/.3 and debug 0.160.0 on macOS. Needs proof per effective policy; reported Linux gap. | Directly reuses current framed daemon protocol and A2 canonical decisions. | Lowest adoption cost and request latency; setup owns config; daemon socket stable across restarts. Probe/cache maintenance cost. |
| Debug `--allow-unix-socket` with network off | Empirically works for 0.160.0 `codex sandbox`; upstream issue says unavailable to TUI. | Direct client unchanged when usable. | Good one-off diagnostic, not a general managed-agent transport. Mac-specific evidence; test other platforms. |
| Named permission profile with scoped Unix socket | Officially documented, but macOS propagation bug is reported; actual TUI route remains unproved. | Direct client unchanged if fixed upstream. | Could eventually avoid proxy `network_access=true`; do not adopt until TUI and negative controls pass on target builds. |
| Loopback TCP/proxy | Codex docs can allow scoped local destinations, but default local/private networking is blocked; a listener/port exception is still a network grant. | Requires a new daemon listener or bridge and equivalent boot/seat framing. | Port allocation, race, exposure and cleanup costs; no demonstrated lower churn than Unix socket. Not a near-term bypass. |
| Stdio MCP server or host-side broker | Official Codex supports local stdio MCP servers; the command proxy does not filter MCP. A broker may use the existing socket to reach the daemon from the host process, but its sandbox placement needs a private TUI/exec check. | A bridge can forward to the canonical daemon, but tools must pass cooperative caller claims and never synthesize ACK/check-in or decide seats itself. | Extra process per session, tool schema and trust/config lifecycle, reconnect and cleanup design; model tool use changes. Plausible durable route after a focused prototype. |
| Host-side hook/helper communication | Codex hooks already launch configured helper commands and can provide context; this is a supported lifecycle surface, while using it as a bidirectional transport is unproved. Hook trust and firing behavior remain separate requirements. | A helper can ask the canonical daemon for context, but hook output cannot serve as a receipt or canonical authority. | Low request latency when fired, but lifecycle depends on hook events, and silent/noninteractive operation needs separate validation. Configuration and platform behavior can churn with hooks. |
| Filesystem mailbox | Ordinary file I/O could avoid socket permission, but this is a proposed product protocol, not Codex transport support. | Daemon must remain sole decision maker; requests need atomic journals, replay IDs, response correlation, deadlines and boot fencing. Files are hints under A2. | Polling/latency and crash cleanup cost; writable-root and symlink scope remain; broad redesign. |

The stdio alternative deserves a separate prototype: configure a scratch MCP server, verify whether Codex starts it outside the command sandbox, identify exactly what the model can call, then forward a read-only `health` operation to an isolated daemon. Add a mutation only after proving the client can pass explicit seat/session/expected boot information and the daemon remains the sole decision maker. This is a proposed experiment, not measured here. [Official MCP docs](https://learn.chatgpt.com/docs/extend/mcp?surface=app&translationFallback=pt-BR), [proxy scope](https://learn.chatgpt.com/docs/agent-approvals-security?trk=article-ssr-frontend-pulse_little-text-block), [trust policy](../../../TRUST-POLICY.md), [client protocol](../../../src/client/service.rs).

## Recommended implementation plan

**Checkpoint decision:** preserve the existing transport and make any managed-launch authorization depend on a matched executable and policy, not just the debug probe. The native 0.160.0 result now covers one explicit `-C` cwd and session policy config. A further product prerequisite emerged while inspecting launch: `setup::observe_with_cache` witnesses a binary resolved in the CLI process, while Herdr's `agent start --kind codex` invokes its canonical `codex` through the **target pane shell** and offers no absolute executable selector. The existing `SystemShellProbe` starts a separate local interactive shell; it does not witness that target shell's executable. Herdr's `pane run` can potentially observe target-shell resolution, but a separate witness command and canonical `agent start` are not atomic: prompt hooks, PATH changes or shell replacement can alter the resolution between calls. The required supported path is a guarded absolute-executable `agent.start` with expected content identity checked at submission, or an equivalent atomic binding proved by Herdr. An explicit `-C` resolves cwd ambiguity but not this executable ambiguity. Until then, launch must report missing validation input, not call an unknown Codex version incompatible. [Launch observer](../../../src/cli/launch.rs), [native policy](../../../src/harness/launch.rs), [Herdr agent-start help, observed 2026-10-03](evidence/herdr-agent-start-help.txt).

The following is the supported staged sequence:

1. Add a reusable, no-model sandbox probe module/runner under `src/harness/` (or a small helper binary) that receives an absolute Codex path, proposed exact socket and roots, and a deadline. Reuse the existing temporary-home/test-support process ownership pattern. Its output is a typed `Passed`, `Failed { capability, observation }`, or `Inconclusive { stage, reason }`, with timestamp, binary digest, platform, config digest and probe version. Match exact errno/policy signatures and controlled positives; never pass on an offline `curl` failure. Ensure all listeners and child processes stop on timeout. Test the probe against the installed 0.160.0 and a synthetic sandbox command that deliberately permits unintended TCP to prove the negative control catches a regression.
2. Resolve the launch's selected executable and effective sandbox policy. Require an explicit `-C /absolute/project/path` in the initial slice, and reject caller profile/sandbox overrides that would change the measured policy. Use a guarded absolute-executable start primitive with expected content identity checked at submission, or another Herdr facility that proves the same atomic binding; a preceding `pane run` resolution alone is diagnostic. Compare its digest with the probe binary. Build a **session-scoped, explicit policy** and verify argv/config precedence for `codex exec` and TUI in private homes, including trusted-project config and managed requirements. If the binary or layers cannot be matched, leave the result inconclusive for that launch and keep the allowance uninstalled; report the condition. Decide separately how manual launches can use a global allowance safely after an update. A cached debug result alone must never claim all manual sessions safe.
3. Replace `CODEX_SANDBOX_MEASURED_VERSIONS` as the **managed-launch** acceptance decision with the typed proof, keyed by the complete identity above. Keep the old versions as historical evidence only. Managed launch should permit a new version on conclusive proof, refuse a measured policy failure, and report an unmeasured/inconclusive policy state with a concrete re-probe or manual diagnostics command. Global setup must keep its separate, stricter gate until effective-policy coverage across sessions is established. A pre-existing allowance whose cached identity no longer matches gets a **policy validation needed** warning; no automatic widening, deletion, or danger-full-access. Keep hook admission and known-broken checks independent.
4. Coordinate wording and JSON fields with doctor-redesign and cli-help-research: `hook_admission`, `socket_policy_validation` (`measured_pass`, `measured_fail`, `inconclusive`, `not_run`), provenance (`debug_sandbox` versus `native`), selected binary digest and effective-policy digest. Do not label `not_run` as unsupported. Launch errors name the unmet socket validation or real `transport_denied`; doctor `--debug` may expose probe stages. Preserve concise default output.
5. Regression tests: newer unlisted version that passes; same version with changed binary/config/roots that re-probes; known-broken hook version that remains refused despite sandbox pass; allowed socket positive and controlled denied targets; proxy disabled/unrestricted-network synthetic failure; timeout/child cleanup; stale cache; installed allowance after binary update; real EPERM after prior pass. Run focused all-feature tests, clippy, fmt, default-feature check, and scoped leak check. A native no-model 0.160.0 `exec`/TUI validation in a private server/home is required before claiming managed use rather than debug-sandbox compatibility.

The probe's 44–48 ms children suggest a short fast path on this machine, but hashing a 241 MB binary, constructing a faithful config, and cold startup may dominate. Measure p50/p95 cold/warm setup and launch before choosing cache lifetime. Offline operation should work from locally valid evidence; a missing/inconclusive proof should neither require the internet nor be relabeled as an unsupported version. [Probe transcript](evidence/probe-results.txt), [binary observer](../../../src/harness/codex.rs).

## Limitations and caveats

The 0.160.0 debug and native runs used scratch homes and a mock provider, not the user's full effective configuration or a real model. The native runs did recheck journal writable roots, but did not validate Linux, an MCP bridge, Codex hook trust, promptless managed wake/ACK, or the target-pane executable identity of a Herdr managed launch. Native exec captured its full result directly; the TUI's result was truncated in the viewport but captured in full as a function-call output by the private mock provider. Upstream GitHub issue reports describe reproducible failures but are not authoritative statements that every version/platform still fails. Official documentation describes intended configuration semantics; the local empirical result is narrower. A first attempt under this research agent's outer sandbox could not bind its listeners, showing why the probe must distinguish an unavailable test environment from target Codex incompatibility. [Probe transcript](evidence/probe-results.txt), [Linux issue](https://github.com/openai/codex/issues/39140), [macOS profile issue](https://github.com/openai/codex/issues/25416).
