# Integration alternatives: message injection and wake (2026-10-23)

Summary of a survey of twelve competing agent-messaging tools against herdr-threads at `main` `2de3da1c4`, across seven harnesses. The question was the same for every cell: how a peer message gets into the target model's context (injection), and how an idle agent is made to act on it (wake). The goal is to find better integration surfaces and flaws in ours.

- Date: 2026-10-23. Clones were shallow, read-only and never executed; each report pins its commit.
- Tags: claims below inherit the **VERIFIED** / **INFERRED** / unknown tag of the report they cite. This file adds no new evidence. Where a line rests on an inference, it says so.
- Harnesses we support: Claude Code (`claude`), Codex CLI (`codex`), Hermes Agent (`hermes`), Antigravity CLI (`agy`). Harnesses we hope to support: Goose (`goose`), Pi (`pi`), OpenCode (`opencode`).
- Layout: `primers/<harness>.md` (the harness's own surfaces), `alternatives/<tool>/{overview,<harness>}.md` (one tool per harness), `ours/<harness>.md` (herdr-threads per harness), `comparison/<harness>.md` (mechanism table, differences, pro/con, flaws, ranked ideas). The full list is at the end.

## 2. Profiles

**agent-talk (primary).** A skills-plus-scripts plugin for end-to-end-encrypted agent messaging through an untrusted relay, using the `retalk` CLI. Each user runs a background follower that polls the relay (60 s by default) into a spool. Most of the logic is prose skills that tell the model which `retalk` commands to run. Injection: a plugin monitor on Claude; `SessionStart`/`UserPromptSubmit` context plus a `Stop` block on Codex; in-process `promptAsync`/`sendMessage` extensions on OpenCode and Pi. Elsewhere the model pulls. It has no priorities and no ACK: the relay deletes a message on read. It is the only cross-machine and cross-owner design in the set. [overview](alternatives/agent-talk/overview.md)

**Cotal (primary).** "Open pub/sub standard for AI agents" on NATS + JetStream, with a 662 KB wire spec, a delivery daemon, a manager that spawns agents, and a hosted cloud in alpha. It is a much larger orchestration platform than herdr-threads. Connectors: a Claude mod (`$.session.append` mid-turn, `$.prompt.submit` with the whole batch when idle) and a managed hook seat; Codex through a private `app-server` it owns (`turn/start`, `turn/steer`); OpenCode through `prompt_async` to an owned `serve`; Hermes through a gateway platform adapter (refused on 0.22+); Pi through an extension `sendMessage` steer. Strongest delivery proof in the set: a host row uuid with a stored-text match on Claude, and `message_start`/`context`/`after_provider_response` on Pi. Every directed message wakes. [overview](alternatives/cotal/overview.md)

**agmsg (primary).** A cross-agent messaging skill over one local SQLite file, built from bash scripts. It is very active (PR #1727, 357 open issues) and ships a **Herdr terminal driver**. Delivery modes per harness: Claude Monitor-tool watch or `Stop` block; Codex `Stop` block plus `PostToolUse`; agy PTY supervisor or headless worker; and the beta agmsgd daemon, which uses Claude's native cross-session socket and `codex queue`. Its `poke` wakes through `herdr agent prompt` with an ANSI composer read. Messages are marked read on display. Bodies are unbounded, and on Pi that loses the head of a long inbox to Pi's 50 KB bash truncation. [overview](alternatives/agmsg/overview.md)

**ruflo (primary).** A very large "agent meta-harness" around Claude Code and Codex: about 314 MCP tools, about 60 plugins, Claude mods, vector memory and swarms. It is not a peer-messaging system between long-lived sessions. One lead session spawns children (Claude Agent Teams, headless `claude -p`/`codex exec`) and coordinates them through file mailboxes drained by rename (`team_inbox`). It has no cross-session wake. Much of the multi-host comms is still at the ADR stage. Its useful contributions are small: a Codex `hooks/list` trust test and an ADR-486-style `{supported, why}` capability report. [overview](alternatives/ruflo/overview.md)

**hcom.** The closest relative in scope and technique. Every agent runs inside an hcom PTY proxy that scrapes the screen. In-turn delivery goes through hooks (Claude and Codex `PostToolUse` on any tool plus `UserPromptSubmit`; agy `ephemeralMessage`; Hermes `transform_tool_result`; OpenCode and Pi plugins). The Claude wake is a mod `$.prompt.submit('<hcom>')`, which is our mechanism family. hcom ACKs on evidence of admission (the frame is seen in a model request) rather than on emission. It piggybacks pending mail on every hcom command and classifies unknown agents as `adhoc`. Every message wakes. [overview](alternatives/hcom/overview.md)

**mcp_agent_mail.** "Gmail for coding agents": an MCP server with Git-backed Markdown mail plus SQLite FTS, file-reservation leases and a human overseer UI. It is pull-only (`fetch_inbox`) with explicit `acknowledge_message`. Its only push is a count-only Bash `PostToolUse` reminder at most every 120 s. The Python version is superseded by a Rust one. The license rider means ideas only, never code. [overview](alternatives/mcp-agent-mail/overview.md)

**agentchattr.** A Slack-like FastAPI chat server plus MCP. An @mention makes a per-agent wrapper paste a fixed "use mcp to read #channel" prompt into that agent's own tmux session, and the model pulls through `chat_read`. It has no busy gate and no draft guard. Its Enter can approve pending tool calls on Goose and OpenCode. [overview](alternatives/agentchattr/overview.md)

**cross-agent-teams-mcp (xats).** A Node MCP daemon with `(device, team, name)` seats. Per-harness wake transports: Claude dev channel, Codex `app-server` `thread/resume`+`turn/start`/`turn/steer`, OpenCode/Kimi HTTP `prompt_async`, and a tmux paste fallback behind a 2 s screen-quiet guard. Wakes carry a ≤200-char hint and bodies are pulled through `get_inbox`, which gives the sender a real read receipt. Its CHANGELOG documents production pane theft from the shared Codex app-server env, which is our pane-identity risk too. [overview](alternatives/cross-agent-teams-mcp-jtianling/overview.md)

**agent-peers-mcp (mikez93 fork).** A loopback HTTP + SQLite broker with one MCP server per session. It prepends a `[PEER INBOX]` block to every one of its own tool results and confirms delivery on the next call. Idle wakes: a Codex `turn/start` on a private app-server, a Claude **`asyncRewake` Stop hook** (exit 2 with a bodyless reminder) and Hermes host RPC on a patched host. It is macOS/launchd-centric and a personal tool. [overview](alternatives/agent-peers-mcp-mikez93/overview.md)

**Cyclops.** A Rust daemon on tmux control mode with a durable NDJSON mailbox. It pastes a one-line "doorbell" and the model claims the body. It has 52 data-only detection manifests and SGR-byte composer rules that tell a dim suggestion from a draft, and it ACKs on an exact-match `UserPromptSubmit` echo. It is the closest analogue in host model and draft care. It is small and inactive since 2026-09. [overview](alternatives/cyclops/overview.md)

**open-cross-session (ocs).** A single-binary CLI with no hooks and no MCP. Every carrier is a harness-native input API: Claude's UDS cross-session inbox, `codex queue` and `turn/steer`, ChatGPT Desktop IPC, Hermes gateway `prompt.submit {queued}`, Pi `sendMessage`, and agy headless `-p`, with cmux keystrokes as the last resort. The body is the wake payload, bounded at 4 KiB inline. Several of these carriers are private protocols that it labels "may break". [overview](alternatives/open-cross-session-ocs/overview.md)

**CAO (awslabs).** A supervisor/worker orchestrator (`cao-server` plus an MCP `handoff`/`assign`/`send_message`) that launches CLIs in tmux or **Herdr** panes (experimental) and consumes `pane.agent_status_changed`. It delivers by pasting the whole body as a user turn at an idle boundary. It marks DELIVERED before the paste and has no draft guard. Its Herdr backend shows what we would hit: an unknown Herdr kind gets only a 30 s reconcile sweep. [overview](alternatives/cli-agent-orchestrator-cao-awslabs/overview.md)

Patterns across the matrix (INFERRED from the comparison files):

- **Only herdr-threads has a non-waking delivery class.** Every alternative that can wake at all wakes on every message, or on every directed message (Cotal); the pull-only ones (mcp_agent_mail, ruflo) never wake. Our priority/threshold contract is unique, and it is the reason we cannot copy "the wake is the delivery" designs as-is.
- **Few tools hold a wake for a human draft**: herdr-threads (`$.prompt.read()` in the mod, plain composer text elsewhere), Cyclops (SGR bytes), hcom's PTY typing gate (VT dim detection plus a user-activity cooldown; default on Codex and agy, opt-in on Claude) and agmsg's manual `poke` (two styled snapshots about 1 s apart, which its own code says narrows but does not close the window). The rest paste blind. Sources: [hcom overview](alternatives/hcom/overview.md) delivery §1, [agmsg overview](alternatives/agmsg/overview.md) "Draft protection", [comparison/claude.md](comparison/claude.md) D13.
- **The field has converged on in-process harness APIs where they exist**: `sendMessage` on Pi, `promptAsync` on OpenCode, the app-server on Codex. On those harnesses, keystroke designs are strictly worse (they approve permission dialogs, clobber drafts, or lose an Enter).
- **Only herdr-threads confirms that an injected agy step landed** (transcript `SYSTEM_SDK` scan). Only hcom ACKs on admission on Hermes and OpenCode.
- **On Goose nobody has a Goose-specific integration**, us included: the alternatives offer only generic paths (MCP or shell pull, blind tmux paste), Cyclops ships the only Goose artifact (a hook-only plugin with an "UNVERIFIED" manifest), and nobody uses MOIM, ACP or `AGENT_SESSION_ID` ([comparison/goose.md](comparison/goose.md) §1). On Hermes 0.22.1+ classic CLI, nobody has a working wake.

## 5. Our flaws, ranked by severity
