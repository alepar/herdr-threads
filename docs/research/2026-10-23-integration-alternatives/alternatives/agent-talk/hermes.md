## Support status

**agent-talk does not support Hermes Agent.** It has no adapter, no plugin, no hook, no install instructions and no mention of Hermes.

Evidence:
- `grep -rniI 'hermes\|nous'` over the clone, excluding `.git`, returns 0 hits. VERIFIED.
- GitHub code search, 2026-10-23: `hermes repo:xhluca/agent-talk` returns 0 and `hermes repo:xhluca/retalk` returns 0. Issue search `hermes repo:xhluca/agent-talk` returns 0. VERIFIED (`gh api search/code`, `search/issues`).
- The README lists the supported agents as "Six: **Claude Code, OpenAI Codex, Google Antigravity, pi, opencode, and GitHub Copilot.**" (`README.md:362-364`). The auto-receive table covers the same six (`README.md:215-229`). VERIFIED.
- The canonical "Adapt to your host agent" session rule names codex, agy, pi, opencode and copilot as the non-Claude hosts and gives each an install translation. Hermes is not among them (`skills/init/SKILL.md:52-72`). VERIFIED. The rule's generic translations still apply to any host: `AskUserQuestion` becomes a plain-text question, and the monitor and `CLAUDE_SESSION_ID` session map are skipped outside Claude Code (`skills/init/SKILL.md:56-67`). VERIFIED.

A Hermes user could still use agent-talk, because its core is a set of agentskills-style `SKILL.md` files that drive a CLI. That would be a "generic" (pull-only) host like Copilot or agy, and the user would have to do the install by hand. The rest of this report describes what would happen in that case and how agent-talk's mechanisms map onto Hermes surfaces. Unless a statement is tagged otherwise, it is INFERRED from the two sources and was not observed.

## Injection mechanism

### What agent-talk would use on Hermes: pull through the terminal tool (generic path)

- **Exact mechanism.** The `receive` skill tells the model to run `retalk receive --peer <peer> --save --dir "<user>/identity" --passphrase-path "<user>/passphrase"`. The output is NDJSON `{"id","from","name","text"}` and is "auto-acked" (`skills/receive/SKILL.md:99-104`, VERIFIED). On Hermes the model would issue this through the `terminal` tool, and the records would reach the model as that tool's result. Only the model can trigger it.
- **When it fires.** Only when the user asks, or when the model decides to check mail. The Copilot doc, the closest generic host, says: "The agent checks for new messages when asked, or at the start of a turn if configured to do so" (`docs/copilot-auto-receive.md:113-115`, VERIFIED). agent-talk ships nothing that makes the check happen at turn start on any generic host. That part rests on the model following the skill.
- **Gateway shift.** On Hermes 0.22.1 and later the `terminal` tool runs in the shared gateway process, not in the pane (primer section 1, VERIFIED from `hermes:hermes_cli/gateway_agent.py:1-6`). This barely affects agent-talk, because every command names its identity explicitly with `--dir "<user>/identity"`. The design reason given is that "Claude Code starts a fresh shell per command and an environment variable cannot reliably carry "who am I"" (`docs/README.md:16`, VERIFIED). Identity therefore never depends on the pane's environment or process tree. INFERRED: agent-talk is immune to the `HERDR_PANE_ID`-inheritance breakage that the primer flags for herdr-threads (primer section 12.1).
- **Payload and framing.** The payload is raw NDJSON in the tool result. The skill then has the model re-render the exchange as a markdown transcript: `### 💬 <peer>`, `**📥 bob** · 14:32`, quoted bodies, both directions, "plus a little recent context from both sides (~1–3 prior turns)" pulled from the spool and sent copies. It must be "Real text, never summaries or counts" (`skills/receive/SKILL.md:33-57`, `skills/init/SKILL.md:20-23`, VERIFIED).
- **Size bounds.** agent-talk sets none. VERIFIED by absence in `skills/receive/SKILL.md`. On Hermes the terminal tool output "is auto-truncated with the full text saved to a file" (`hermes:tools/terminal_tool.py:177`, VERIFIED; I did not look up the exact cap, so it is unknown). INFERRED: a large `retalk receive` batch is shortened in context, while the relay has already deleted it on delivery. The model then has to read the spill file or use the `history` skill.
- **Dedupe and ack.** These happen only at the transport: the relay deletes each message on delivery (`docs/README.md:22`, a claim about retalk, VERIFIED only as a doc statement). No application or reader ACK exists (overview, "Delivery guarantees"). One-shot pull needs no consumer-side dedupe, because a message can be read only once.

### Push consumers that exist for other harnesses, and how each maps onto Hermes

agent-talk's push design is the same on every harness: a background follower writes one spool per session, and a harness-specific consumer reads it (overview, "Injection mechanisms"). None of these consumers targets Hermes. Here is how each would fare if pointed at it.

| agent-talk consumer | Hermes analogue | Fit |
|---|---|---|
| Claude plugin monitor `monitors/monitors.json` + `bin/inbox-monitor.sh` (spool lines become harness notifications) | none. Hermes has no monitor or plugin-notification surface that reaches the model. MCP `notifications/message` goes only to `agent.log` (primer section 8, `hermes:tools/mcp_tool_health.py:73-97`, VERIFIED) | Not portable |
| Codex `extensions/codex/inbox-hook.py` on `SessionStart` / `UserPromptSubmit` (`additionalContext`) | Shell hook `pre_llm_call` in `config.yaml` `hooks:` (primer section 3). Hermes says `UserPromptSubmit` "is intentionally not a separate Hermes event — `pre_llm_call` fires at the same place" (`hermes:website/docs/user-guide/features/hooks.md:2053`, VERIFIED) | Portable with changes, see below |
| Codex `Stop` hook `{"decision":"block","reason":…}` (block-and-continue after mid-turn arrival, `extensions/codex/inbox-hook.py:189-201`, VERIFIED) | `pre_verify` accepts the same Claude Stop shape (`hooks.md:1934-1936`, VERIFIED), but it fires only at the edited-code verify gate and is capped by `agent.max_verify_nudges` (default 3) (primer section 2.2) | Mostly not portable. It works only on turns that edited code |
| pi `pi.sendMessage(…, {triggerTurn:true})` / opencode `client.session.promptAsync` (`extensions/inbox-monitor.ts:69-78`, `extensions/opencode/inbox-monitor.ts:82-91`, VERIFIED) | Python plugin `ctx.inject_message(content, session_key=…)` (primer section 4) | The best structural match, but agent-talk has no Python plugin |

**The Codex hook would not run on Hermes unchanged.** There are three concrete breaks, all INFERRED from the cited code:
1. **Output shape.** `inbox-hook.py` prints `{"hookSpecificOutput":{"hookEventName":…,"additionalContext":…}}` for the context events (`extensions/codex/inbox-hook.py:203-213`, VERIFIED). A Hermes shell hook's stdout must be a JSON object, and for `pre_llm_call` only a non-empty string `context` key is read (`hermes:agent/shell_hooks.py:664-666,672-682`, VERIFIED; a plain string is accepted only from Python plugin callbacks, primer section 2.2). Claude-style aliases are listed only for block, modify and continue (`hooks.md:1919-1936`, VERIFIED). The context would be dropped silently ("any empty / non-matching output is fine", `hooks.md:1938`).
2. **Opt-in by environment.** The hook returns early unless `AGENT_TALK_CODEX_SPOOLS` is set in its own environment (`extensions/codex/inbox-hook.py:49-51,175-176`, VERIFIED). Under the v0.22.1+ gateway, shell hooks are children of the gateway, and pane variables reach a session only through the allowlisted `client_env` (a fixed toolchain/behaviour list plus `terminal.client_env_passthrough`), which is "bound for its turns only, never written to the gateway's `os.environ`" (`hermes:agent/session_client_env.py:1-5,22-29`, VERIFIED). The shell-hook subprocess env is built from the gateway's `os.environ` (`hermes:agent/shell_hooks.py:505-507`, `hermes:tools/environments/local.py:393`, VERIFIED). So a per-pane `AGENT_TALK_*` variable never reaches the hook, even if passthrough-listed (INFERRED from those two reads); only a value in the gateway's own launch environment would, and that is shared by every session. The workable key is the hook's stdin `session_id` (`hermes:agent/shell_hooks.py:3,97`, VERIFIED), which the Codex script ignores ("we do not need it", `inbox-hook.py:178`, VERIFIED).
3. **Consent.** Gateway sessions never prompt for shell-hook consent. The user needs `hooks_auto_accept: true`, `--accept-hooks`, `HERMES_ACCEPT_HOOKS=1` or a manual allowlist entry (primer section 3, `hooks.md:2071-2100`). A foreground `hermes chat` asks first.

A Hermes port that keys the spool by stdin `session_id` and emits `{"context": …}` would reuse the hook's best parts unchanged: the byte cursor, the head-sha256 truncate detection and the 500-id dedupe list (`extensions/codex/inbox-hook.py:91-153`, VERIFIED). Delivery would then be **turn-start only**. Hermes runs `pre_llm_call` once per turn, before the tool loop, so mail that arrives mid-turn waits for the next user turn (primer section 2.2). The `transform_tool_result` hook is the native mid-turn channel. A shell hook may register for it (only `transform_api_error_classification` is refused, `hermes:hermes_cli/plugins.py:207`), but its parsed output is a `{"context": …}` dict while the dispatcher keeps only a `str` return (`hermes:agent/shell_hooks.py:682`, `hermes:model_tools.py:845`), so in practice only a Python plugin can use it (VERIFIED). No agent-talk code resembles it.

### Spool registration on Hermes

Fan-out goes only to session ids registered under `~/.agent-talk/by-session/<sid>` (`bin/spool-writer.py:107-124,187-193`, VERIFIED). On Hermes the natural `<sid>` is `$HERMES_SESSION_ID`, which the gateway injects into every terminal command (primer section 6, `hermes:tools/environments/base_session_env.py:12-31`). agent-talk never mentions it, so the model would have to improvise the registration as it does for pi and opencode (overview, Flaws). Without a registration, records go only to the legacy `<user>/inbox.ndjson`, which `--legacy` writes by default (`bin/spool-writer.py:195-196,264`, VERIFIED). INFERRED: logical session ids are stable across compression (primer section 6). A resumed session therefore keeps its spool, which is better than Codex's thread id.

## Wake mechanism

**agent-talk provides no wake for Hermes.** An idle Hermes session sees nothing until a human types. That is the stated behaviour for every host without a consumer: "A message that has already arrived appears the next time you interact with the session" (`docs/copilot-auto-receive.md:115-116`, VERIFIED).

What the skill text would push the model toward on Hermes:
- **"Proactive auto-wake via Monitor (recommended)"** needs a harness `Monitor` tool, which Hermes lacks (`skills/receive/SKILL.md:222-246`, VERIFIED). The closest Hermes equivalent is a background terminal process with a notification:
  - `terminal(background=true, watch_patterns=…)` on a persistent `tail -F <spool>` does not suit message traffic. Each session gets at most one match per 15 s, three strike windows disable watching, and the **lifetime cap is 8 hits**, after which it falls back to notify-on-complete. The design intent is "ONLY for rare one-shot signals" (`hermes:tools/process_registry.py:65-81`, VERIFIED). The ninth message of a session would no longer wake anything.
  - `terminal(background=true, notify_on_complete=true)` on a command that **exits on the first new spool line** (for example `tail -n0 -F <spool> | head -n1`) is the workable shape. When the process exits, Hermes injects an `[IMPORTANT: …]` notice carrying up to `COMPLETION_OUTPUT_CHARS = 2000` chars of output tail, and an idle session starts a turn (`hermes:tools/process_registry.py:61`, primer section 7, VERIFIED). The model has to re-arm the wait after every wake. agent-talk does not describe this. INFERRED that a model following the Monitor recipe would land on it.
  - **Viewer gating.** A completion for a CLI or TUI session "while no viewer is attached does not start a turn. It is written into the session as a note" (`hermes:website/docs/user-guide/features/delegation.md:633`, VERIFIED). A detached Hermes session, such as one whose terminal was closed, therefore stays asleep.
- **"Fallback: interval polling (no Monitor tool)"**: "use a scheduled wake-up/loop that polls the spool on an interval. Note the cost: each idle tick re-reads the conversation" (`skills/receive/SKILL.md:248-252`, VERIFIED). On Hermes this is `/loop <interval> <prompt>` or cron (`hermes:website/docs/reference/slash-commands.md:57`, VERIFIED), or `/heartbeat every <interval> <prompt>`, which fires only while the session is idle (min 60 s, missed ticks coalesce; `slash-commands.md:56`, VERIFIED). Every fire is a full model turn, even when no mail arrived.
- **Keystroke injection** is explicitly rejected by agent-talk as "not a supported interface … can collide with whatever the user is doing" (`docs/antigravity-auto-receive.md:77-82`, VERIFIED). agent-talk will therefore never type into Hermes's composer. On Hermes this avoids a real hazard: the default `display.busy_input_mode: interrupt` turns a mistimed Enter into a redirect or interrupt of a running turn (primer section 9).
- **The Hermes-native wake agent-talk would want**, by analogy with its pi/opencode extensions and its Codex app-server nudge, is `ctx.inject_message(..., session_key=<ses_id>)` from a Python plugin with `plugins.entries.<id>.allow_gateway_injection: true`. Alternatively an external process could call the gateway's `prompt.submit` JSON-RPC (primer sections 4 and 5.1). Either one leaves busy and idle handling to the host ("a busy session keeps the message for the next turn, an idle session starts one", `hermes:website/docs/user-guide/features/plugins.md:1084`, VERIFIED). Neither can clobber a draft, because the text goes to a queue rather than the prompt buffer (primer section 4, INFERRED). agent-talk implements neither.

Idle/busy detection: none on Hermes. agent-talk detects busy only on Codex, through app-server `thread/read` (`bin/codex_wake.py:206-220`, VERIFIED). Draft safety: not applicable, since nothing types. Latency, if a self-wake recipe were used: up to one relay poll interval (default 60 s, `bin/follow.sh:15-16`, VERIFIED), plus the spool write, plus the background-process reaper tick (unknown cadence). Failure modes: the follower dies (restarts after 2 s, `bin/follow.sh:135-140`), the model forgets to re-arm the wait, no viewer is attached, the watch lifetime cap is hit, or the session is unregistered in `by-session`.

## Setup/installation footprint on the harness

agent-talk ships no Hermes installer, so the footprint below is what a user would have to create by hand (INFERRED):
- **Skills.** Hermes loads agentskills.io-format `SKILL.md` files from `~/.hermes/skills/` or from `skills.external_dirs` in `~/.hermes/config.yaml` (`hermes:website/docs/user-guide/features/skills.md:9-11,408-426`, VERIFIED). A user would symlink `skills/` into `~/.hermes/skills/agent-talk` or add the checkout to `external_dirs`. Caveat: "agent-managed skill updates can change files in that directory" if it is writable (`skills.md:425`, VERIFIED), so the agent could rewrite agent-talk's skills in place.
- **CLI.** `retalk` on the gateway's `PATH`, not just the pane's. The terminal backend runs in the gateway and gets `PATH` through `client_env` (primer section 1).
- **State outside Hermes.** `~/.agent-talk/users/<name>/` (identity, contacts, `check-mode`, `receive-from`, pid files), `~/.agent-talk/by-session/<sid>` and the plaintext spools (`docs/README.md:9-16,44`, `skills/receive/SKILL.md:25-31`, `bin/follow.sh:28-30`, VERIFIED).
- **Background follower.** `follow.sh start` detaches with `setsid nohup` (`bin/follow.sh:93-102`, VERIFIED). Under the gateway it is a grandchild of the gateway's terminal backend. INFERRED: it survives the pane closing and lives until stopped.
- **If ported to a shell hook:** a `hooks: pre_llm_call:` entry in `~/.hermes/config.yaml` (or the profile's), plus an auto-accept or allowlist entry in `shell-hooks-allowlist.json`. **If ported to a plugin:** `~/.hermes/plugins/agent-talk/`, `hermes plugins enable agent-talk`, and `allow_gateway_injection: true`.

## Token cost per message and per quiet turn

- **Per message (pull):** one or more model tool calls (`retalk receive`, more than one in contact-list mode, `skills/receive/SKILL.md:111-115`, VERIFIED), plus the raw NDJSON in the tool result, plus model **output** tokens for the re-rendered transcript with 1-3 prior turns of context and emoji headers. INFERRED: output roughly doubles the body bytes, plus several hundred bytes of framing. The full `receive` skill (272 lines) must also be loaded on demand, although Hermes's progressive disclosure keeps only the index line in the system prompt (`skills.md:9`, VERIFIED).
- **Per message (ported hook):** the Codex framing is `N new agent-talk message(s) waiting:` plus `From <name>:\n<text>`, plus a fixed 93-byte instruction ("Surface these to the user verbatim as a chat transcript before continuing with their request.", `inbox-hook.py:205-211`, VERIFIED). It has no size bound, and Hermes spills hook output above 10,000 chars to a file (primer section 2.2).
- **Per quiet turn:** zero with pure pull. With a ported hook it is also zero, because the hook prints nothing when the spool has no news (`inbox-hook.py:183-185`, VERIFIED). With the `/loop` fallback every tick is a full turn that re-reads the conversation (the skill warns about this itself). That is the most expensive option.
- **Per self-wake (background-process recipe):** a full turn for the `[IMPORTANT: …]` notice (up to 2,000 chars of tail), plus the transcript rendering, plus a tool call to re-arm.

## Limitations and bugs you can see

1. **Unsupported and unacknowledged.** Hermes is absent from the "Adapt to your host agent" rule. A Hermes model would meet Claude-only instructions (`AskUserQuestion`, `Monitor`, `${CLAUDE_PLUGIN_ROOT}`, `CLAUDE_CODE_SESSION_ID`) with only the rule's generic fallbacks (ask in plain text, skip the monitor and session map) and no Hermes install path or session-id mapping (`skills/init/SKILL.md:52-72`, `skills/receive/SKILL.md:190`, VERIFIED). The rest would be improvised.
2. **Shell-hook incompatibility** if someone reused the Codex hook: wrong JSON shape for `pre_llm_call`, env-gated opt-in that the gateway does not forward, and stdin `session_id` ignored (see Injection). The likely result is a hook that runs and injects nothing, with no error.
3. **The watch-pattern trap.** The receive skill's "persistent monitor" idea maps on Hermes to `watch_patterns`, which disables itself after 8 hits per session (`hermes:tools/process_registry.py:74-82`, VERIFIED). A model that follows the recipe literally gets a wake that stops working silently partway through a conversation.
4. **Ack-before-model gap.** The relay acks at `retalk receive`. If Hermes truncates the tool output or the follower writes to an unregistered spool, the model never sees the body, and recovery depends on the model running `history` (overview, "Delivery guarantees"; `hermes:tools/terminal_tool.py:177`).
5. **Peer text with user authority** only on a plugin port that copied pi/opencode and injected bodies with `inject_message` (role `user`). The Hermes docs say gateway-injected text "cannot invoke slash commands, approve tools, or resolve pending confirmation" (primer section 4), which limits the damage. The text is still a user-role transcript row. Pull through the terminal tool keeps peer text inside a tool result, which is the safer channel.
6. **No priority, threshold or deadline.** If self-wake were used, every message would cost a turn (overview, VERIFIED by absence).
7. **Plaintext spool and gateway visibility.** The decrypted bodies sit in `<user>/sessions/*.ndjson` (mode 0600, `bin/spool-writer.py:147`). Every Hermes session in the one gateway runs under the same user and backend and could read any user dir it knows the path of. Isolation between "users" depends on the model choosing the right `--dir` (overview, "Identity and session model", INFERRED).

## Clever ideas worth stealing

1. **Identity by explicit path on every command** (`--dir "<user>/identity"`, `docs/README.md:16`). Under Hermes's gateway, where pane env and process ancestry are gone (primer section 1), this design keeps working without changes. For herdr-threads, the counterpart would be letting the Hermes bridge pass an explicit seat or session key (for example `HERMES_SESSION_ID` mapped at enrollment) instead of relying on the inherited `HERDR_PANE_ID`. INFERRED, but it is the most direct answer to primer flag 12.1.
2. **Refusing keystroke injection on principle** (`docs/antigravity-auto-receive.md`). On Hermes, whose default busy mode is `interrupt`, the herdr-threads `IdleWake::Native` keystroke is riskier than on Claude. `ctx.inject_message` with a session key is the queue-on-busy, draft-safe alternative that agent-talk's design philosophy points to (primer section 12.2).
3. **The cursor discipline in `inbox-hook.py`**: advance before output, a head-sha256 truncate guard, a bounded persisted id list (`extensions/codex/inbox-hook.py:26-31,91-153`). This is directly reusable for any file-backed hook on Hermes `pre_llm_call`.
4. **A body-free wake plus a single body path** (`bin/codex_wake.py:6-11,35-44`). On Hermes, a content-free `inject_message` wake followed by herdr-threads' existing `pre_llm_call` check-in would match AGENTS.md R18 and keep peer bodies out of user-role rows. Today herdr-threads' Hermes wake text is the longer `MARKER` (primer section 11).
5. **The one-shot background wait as a self-wake** (derived from agent-talk's Monitor recipe applied to Hermes, not in agent-talk itself): `terminal(background=true, notify_on_complete=true)` on `herdr-threads wait`-style long-polling gives a viewer-gated, host-queued wake with no plugin injection permission. It costs one re-arm call per wake, and the watch-pattern variant must be avoided because of its 8-hit lifetime cap.
