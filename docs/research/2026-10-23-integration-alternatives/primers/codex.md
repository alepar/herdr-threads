Source paths below are relative to the clone root and look like `codex-rs/...:LINE`.

## 0. Summary: which surfaces inject and which wake

| Surface | Injects into context | Wakes an idle session | Mid-turn delivery | Notes |
|---|---|---|---|---|
| **Hooks** (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `SubagentStart` `additionalContext`; `Stop`/`SubagentStop` `decision:"block"`) | yes, as developer context | **no** (hooks only run inside a turn or session lifecycle) | yes, at tool boundaries (Pre/PostToolUse) | Must be trusted by hash. Output above about 2,500 tokens is saved to disk and the model gets a head-and-tail preview |
| **Async command hooks** (`async: true`) | yes; the result is held until a safe boundary | no | yes: drained after each sampling step, or before the next user prompt | Up to 8 at once per session |
| **Stop hook `decision:"block"` + `reason`** | yes; `reason` becomes "a new continuation prompt, treated as a new user prompt" | n/a (it runs while the turn ends, so the turn continues) | end of turn | `stop_hook_active` guards against loops |
| **Durable queue** (`codex queue --thread ID --message TEXT`, app-server `thread/queue/add`) | yes, as a **user turn** (`turn_trigger: "queue"`) | **yes**: dispatched when the thread is idle (`start_turn_if_idle`), and re-checked every 10 s across processes through SQLite | no; it waits for idle | Persistent. Ephemeral threads (such as `/side`) are refused. Not dispatched after an *interrupted* turn |
| **App-server `turn/start`** | yes, user turn | yes (the client starts the turn) | n/a | Only through the server that holds the thread loaded (shared daemon, or `--remote`) |
| **App-server `turn/steer`** | yes, appended to the **active** turn | no; it fails when no turn is active | **yes** | Needs `expectedTurnId` |
| **App-server `thread/inject_items`** | yes: raw Responses items appended to history "without starting a user turn" | no | it changes history only; the model sees the items at its next request | Silent delivery |
| **Keystroke injection** into the TUI (Herdr `agent.prompt`, tmux) | yes, as user prompt | yes when idle | while busy, Enter steers or Tab queues (local TUI queue) | Paste-burst heuristic: an Enter within 120 ms of a fast typed burst becomes a newline |
| **`codex exec resume ID PROMPT` / `codex resume ID PROMPT`** | new prompt into an existing rollout | relaunches the session (headless or TUI) | n/a | A second process on the same thread. Not for a pane that is still live |
| **MCP tools/resources** | only when the model calls a tool (`list_mcp_resources`, `read_mcp_resource`) | no | tool result only | Server notifications (`list_changed`, `resources/updated`, logging) are **only logged** |
| **`sleep` tool** (stable, on) | n/a | n/a | the model's own sleep ends early "when new input arrives for the active turn" | A model-side wait primitive that pairs with `turn/steer` |
| **`notify` program / `tui.notifications`** | no | no | n/a | Fires on `agent-turn-complete`. Useful as an idle signal |
| **Static instructions** (`AGENTS.md`, `developer_instructions`, `model_instructions_file`, skills, MCP server `instructions`) | session start only | no | no | Static text |

## 1. Hooks

Source: the hooks page (VERIFIED unless marked) and `codex-rs/hooks/src/**`.

### 1.1 Configuration and trust (VERIFIED)

- Hooks are defined in `hooks.json` or as inline `[hooks]` tables in `config.toml`. The layers are `~/.codex/hooks.json`, `~/.codex/config.toml`, `<repo>/.codex/hooks.json` and `<repo>/.codex/config.toml`, plus plugin `hooks/hooks.json` (or a manifest `hooks` entry) and managed `requirements.toml`. "Hooks from all sources run. Higher-precedence layers don't replace lower ones." Project-local hooks load only when the project `.codex/` layer is trusted. `allow_managed_hooks_only = true` ignores every non-managed source.
- `[features] hooks = false` disables hooks. `codex_hooks` is a deprecated alias. `codex features list` on 0.163.0 shows `hooks stable true` and `plugin_hooks removed false` (VERIFIED, local).
- The structure is event, then matcher group, then handlers. Handler types are `command` and `mcp_tool`; `prompt` and `agent` "are parsed but skipped". A hook can therefore call an MCP tool directly (VERIFIED in the docs, and the handler kinds appear in `codex-rs/hooks/src/engine/mod.rs:144-158`).
- **Trust**: "Non-managed hooks must be reviewed and trusted before they run." Trust is keyed to a hash of the hook definition, so a changed hook is skipped until it is trusted again. `/hooks` in the TUI lets the user inspect, trust or disable hooks. `--dangerously-bypass-hook-trust` skips the requirement for one invocation (CLI help, VERIFIED). The app-server has `hooks/list` (schema, VERIFIED), whose `HooksListEntry` carries a trust status (`HookTrustStatus` definition).
- Timeouts are in seconds, 600 by default. `SessionEnd` and `Interrupt` default to 1 s, with a maximum of 3 s. `async: true` hooks keep the same timeouts, and "up to eight can run concurrently per session."

### 1.2 Events (VERIFIED: docs, plus `HookEventName` in the generated schema)

The schema enum is `preToolUse, permissionRequest, postToolUse, preCompact, postCompact, sessionStart, sessionEnd, userPromptSubmit, subagentStart, subagentStop, stop, interrupt`.

Matchers are regex strings. `PreToolUse`, `PermissionRequest` and `PostToolUse` match the tool name. `Pre/PostCompact` match `manual|auto`. `SessionStart` matches `startup|resume|clear|compact|fork`. `SessionEnd` matches `other`. `SubagentStart` and `SubagentStop` match the agent type. `UserPromptSubmit`, `Stop` and `Interrupt` ignore the matcher.

### 1.3 Input payloads (VERIFIED, docs)

- Common fields: `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`. Turn-scoped events add `turn_id`, and several add `permission_mode`.
- `SessionStart`: `source`. `SessionEnd`: `reason`. `SubagentStart`: `agent_id`, `agent_type`, `permission_mode`.
- `PreToolUse`: `tool_name`, `tool_use_id`, `tool_input`. `PostToolUse`: those plus `tool_response`. `PermissionRequest`: `tool_name`, `tool_input` (`tool_input.description` may be null).
- `UserPromptSubmit`: `prompt`. `Stop`: `stop_hook_active`, `last_assistant_message`. `SubagentStop`: `agent_id`, `agent_type`, `agent_transcript_path`, `stop_hook_active`, `last_assistant_message`. `Interrupt`: `turn_id`, `permission_mode`.
- herdr-threads captured live 0.158.0 payloads: `tests/fixtures/codex-0.158.0-live/` (in this repo). Every captured payload has `permission_mode: "bypassPermissions"` under `codex exec`, even with `-s read-only`. It is not a sandbox signal (VERIFIED in `integrations/codex/README.md`).

### 1.4 Outputs, and whether they reach the model (VERIFIED, docs)

| Event | Fields | Effect on the model |
|---|---|---|
| SessionStart | `hookSpecificOutput.additionalContext`; **plain stdout is also added** | developer context |
| UserPromptSubmit | `additionalContext`; `decision:"block"` + `reason`; plain stdout is added | context added before the prompt, or the prompt is blocked |
| PreToolUse | `hookSpecificOutput.{permissionDecision (allow/deny), permissionDecisionReason, updatedInput, additionalContext}`; legacy `decision:"block"` | context inserted after the call and before its output (the herdr-threads live capture, `docs/evidence/codex-158-live-hook-capture/report.md`). **Plain stdout is ignored.** `ask`, `continue`, `stopReason` and `suppressOutput` are unsupported and make the hook run fail |
| PostToolUse | `additionalContext`; `decision:"block"` + `reason` (this replaces the tool result with feedback); `continue:false` | context, or the result is replaced. Plain stdout is ignored |
| SubagentStart | `systemMessage`, `additionalContext` | context goes to the subagent |
| Stop | `decision:"block"` + `reason` | the turn continues, and `reason` becomes a new prompt (see 1.5) |
| SubagentStop | `decision:"block"` + `reason` | the subagent continues |
| Interrupt | `systemMessage` | UI only. It cannot prevent the interrupt |
| SessionEnd, Pre/PostCompact | `continue:false` (compact only) | advisory, or stops compaction |

- `systemMessage` "is surfaced as a warning in the UI or event stream" and is **not** model context. `suppressOutput` "is not implemented".
- **Size limit**: "Output over about 2,500 tokens per message is saved to disk, and the model gets a head-and-tail preview." `additionalContextLimit` changes it per handler, and the docs warn that `0` lets one hook take the whole context window. Source: `codex-rs/hooks/src/output_spill.rs:11-12` (`HOOK_OUTPUTS_DIR = "hook_outputs"`, `DEFAULT_HOOK_OUTPUT_TOKEN_LIMIT = 2_500`).
- Exit codes: 0 means success (JSON is parsed where the event expects it; empty output means continue). 2 blocks, with the reason read from stderr, for PreToolUse, PostToolUse, UserPromptSubmit, SubagentStop and Stop. Other codes are not defined by the docs.

### 1.5 Stop-hook "block and continue" (VERIFIED, docs plus `codex-rs/hooks/src/events/stop.rs:100-112,258-261`)

"`decision: "block"` does not reject the turn. Codex continues, and your `reason` becomes a new continuation prompt, treated as a new user prompt." `stop_hook_active` tells the hook whether the turn was already continued once. "If any matching Stop hook returns `continue: false`, it overrides continuation decisions from other Stop hooks." The aggregate result carries `continuation_fragments: Vec<HookPromptFragment>`.

INFERRED: this is the in-harness way to deliver mail that arrived during a turn before the session goes idle, so no nudge is needed afterwards. It costs one more sampling round per block.

### 1.6 Async hooks: deferred mid-turn injection (VERIFIED, source)

- `codex-rs/hooks/src/engine/dispatcher.rs:134-141`: an `Async` handler is scheduled (`schedule_async_hook`) instead of awaited.
- `codex-rs/hooks/src/engine/command_runner.rs:116-156`: when it finishes, its `Context` entries pass through the spiller and are sent on `result_sender`.
- `codex-rs/core/src/hook_runtime.rs:775-818` (`drain_async_hook_results`): "Before the user prompt, records additional context directly into conversation history so results from a previous turn appear before the new prompt. After sampling, injects context into the active turn's pending-input queue so it reaches the next sampling request." The call sites are `codex-rs/core/src/session/turn.rs:185` (turn start) and `:591` ("only after sampling and its tools have finished").
- `codex-rs/core/src/session/inject.rs:45-65` (`inject_hook_context_if_running`) only injects when a turn and task are active, so **an async hook never wakes an idle session**. Its result waits for the next turn.
- The docs say `hook/started` and `hook/completed` app-server notifications are "emitted only for synchronous lifecycle hooks, not asynchronous ones".

INFERRED: an async `PostToolUse` or `PreToolUse` hook that long-polls a mailbox would add mail at the next sampling boundary without delaying the tool. That differs from the current synchronous Bash `PreToolUse` digest.

### 1.7 Legacy `notify` (VERIFIED, `codex-rs/hooks/src/legacy_notify.rs:13-73`; config reference)

`notify = [argv...]` (user-level config only) runs a program with a JSON argument `{"type":"agent-turn-complete","thread-id","turn-id","cwd","client"?,"input-messages":[...],"last-assistant-message"}`. Its stdio is null, so it is fire-and-forget. It is an observability hook only: it gives a turn-complete (idle) edge per thread. The source marks it "TODO: Remove ... when legacy `notify` support is removed."

## 2. App-server (JSON-RPC): the native programmatic surface

Sources: the app-server docs page, the generated schema, `codex app-server --help`, and `codex-rs/app-server/src/**`.

### 2.1 Transports and the shared daemon (VERIFIED)

- `codex app-server --listen stdio://|unix://|unix://PATH|ws://IP:PORT|off` (default stdio). Unix sockets carry WebSocket over HTTP Upgrade. WebSocket is "experimental and unsupported". `--ws-auth capability-token|signed-bearer-token` (help).
- **Since about 0.157 the interactive TUI attaches to a shared, machine-wide app-server daemon by default.** `--no-daemon` means "Run without the shared background server, even if it is already running" (help). In `codex-rs/tui/src/lib.rs:560-600` (`start_app_server`) a `LocalDaemon` target connects first and falls back to an embedded in-process server (`allow_embedded_fallback`). `codex app-server daemon {start,stop,restart,version,bootstrap,enable-remote-control,...}` and `codex app-server proxy --sock PATH` ("Proxy stdio bytes to the running app-server control socket") exist (help).
- Socket path: `codex-rs/tui/src/lib.rs:523-548` probes `codex_app_server_client::app_server_control_socket_path(codex_home)`. A daemon test fixture uses `<home>/app-server-control/server.sock` (`codex-rs/app-server-daemon/src/update_loop_tests.rs:445`). INFERRED: the default is `$CODEX_HOME/app-server-control/server.sock`.
- `codex --remote ws://...|unix://PATH` connects the TUI to a running app-server. `codex agents` means "Browse all agent sessions on the shared local app-server daemon". `codex remote-control {start,stop,pair}` is experimental (help).
- Known problem (external reports, not verified here): daemon-run hooks and tools inherit the environment of the process that started the daemon, so `HERDR_PANE_ID` and similar variables leak across panes. Herdr's closed PR `https://github.com/herdrdev/herdr/pull/4667` ("Codex 0.157 can run `SessionStart` hooks in a shared app-server daemon"). Similar launches with `--no-daemon` appear in openrig issue #69, agentchute PR #210 and holler issue #20 (WebSearch result titles only).

### 2.2 Methods relevant to injection and wake (VERIFIED, schema `ClientRequest.json`)

- `thread/start`, `thread/resume` (by id; `excludeTurns`; "If thread_id identifies a running thread, app-server rejoins that thread"), `thread/fork`, `thread/loaded/list`, `thread/read`, `thread/list`, `thread/unsubscribe`.
- `turn/start` (`input: UserInput[]`, `additionalContext: {key: {kind, value}}`, per-turn overrides). It returns `status:"inProgress"`. `turn/interrupt`.
- **`turn/steer`** (`threadId`, `expectedTurnId` required, `input`, `additionalContext`). The docs say it "Appends input to the active turn", "fails if no turn is active", "doesn't emit a new `turn/started`".
- **`thread/inject_items`** (`threadId`, `items`: "Raw Responses API items to append to the thread's model-visible history"). The docs say "without starting a user turn. Items are persisted to the rollout and included in later model requests." In the source, `codex-rs/core/src/codex_thread.rs:829-834` (`inject_response_items`: "Record raw Responses API items without starting a new turn").
- **`thread/queue/add|list|update|delete|reorder|start`** and the notification `thread/queue/changed`. The docs page does not cover them, so see §3.
- `thread/shellCommand`, `thread/goal/set`, `thread/settings/update`, `thread/realtime/*`.
- `mcpServer/tool/call`, `mcpServer/resource/read`, `mcpServer/event/stream/start` (the client can read MCP server events through the app-server), `config/mcpServer/reload`.
- Server requests to the client: `item/tool/call` (dynamic, client-implemented tools; experimental), `item/tool/requestUserInput`, `mcpServer/elicitation/request`, approvals.

### 2.3 Idle and busy observability (VERIFIED, schema)

- `thread/status/changed {threadId, status}`, where `ThreadStatus` is one of `notLoaded`, `idle`, `systemError` or `active {activeFlags: [waitingOnApproval|waitingOnUserInput]}`. `turn/started` and `turn/completed` (`completed|interrupted|failed`), `item/*` deltas, `hook/started` and `hook/completed`, `thread/tokenUsage/updated`.
- Subscriptions are per connection. After the last subscriber leaves, a thread stays loaded for a 30-minute grace period, then emits `notLoaded` and `thread/closed` (docs).
- INFERRED: this is the precise busy/idle signal, more reliable than screen scraping. It is only observable by a client connected to the server that holds the thread, which in practice is the shared daemon. An embedded `--no-daemon` TUI exposes no socket.

## 3. The durable queue: `codex queue` and `thread/queue/*` (VERIFIED, source)

`codex queue --thread <UUID|exact name> --message <TEXT> [--remote ADDR]` means "Queue a message for an existing session" (help). Text only: `codex queue` does not support image attachments (`codex-rs/cli/src/queue_cmd.rs:45-47`).

Client side, `codex-rs/tui/src/session_queue_commands.rs`:
- `:32-36` refuses `--no-daemon` without `--remote`: "Queuing must discover the shared server to avoid writing through a separate server."
- `:41-49` refuses to queue through an embedded server while a local daemon is running.
- `:84-127` resolves a name to a thread id, then sends `thread/queue/add {threadId, input:[{type:text}], clientUserMessageId: uuid v7}`.

Server side, `codex-rs/app-server/src/request_processors/thread_queue_processor.rs`:
- `:77-95` `add` validates, enqueues and returns `queuedSubmission {id, clientUserMessageId, input}`.
- `:253-293` `require_thread` accepts **loaded or stored** threads. It refuses **ephemeral** threads ("ephemeral thread does not support queued submissions", `:265`) and archived ones.
- `:296-313` refuses direct input to multi-agent-v2 subagents.
- `:186-245` `start` returns "thread already has an active or pending turn" when the thread is busy.

Queue engine, `codex-rs/ext/queue/src/service.rs`:
- `:265-280` `enqueue` persists the item, emits `thread/queue/changed`, then calls `wake_if_loaded`.
- `:472-483` `wake_if_loaded` runs `emit_thread_idle_lifecycle_if_idle(Completed)` unless the agent status is `Interrupted`.
- `:549-566` `on_thread_idle` returns early when `cause == Interrupted` and otherwise calls `dispatch_if_idle`.
- `:405-470` `dispatch_if_idle` takes the head item and calls `thread.start_turn_if_idle(... turn_trigger: Some("queue"))`. It deletes the item only once the turn has `Started`; on `NotSubmitted` it leaves it in place.
- `:89-245` `watch_external_messages` checks SQLite's `change_version` **every 10 s** (`:96`). It discovers threads whose queue changed, including writes from other processes, and threads newly loaded or resumed (`:538-547` `on_thread_resume`). For each one it spawns a dispatcher that re-checks every 10 s (`:239`) while the thread is not `Running|Interrupted|Shutdown|NotFound` (`:218-225`).
- Persistence requires a SQLite state DB. `codex-rs/app-server/src/message_processor.rs:306-313` sets `queue_store = None` for in-memory thread stores. The TUI's embedded server is the same `MessageProcessor` (`InProcessAppServerClient`, `codex-rs/tui/src/lib.rs:36,309-323`).
- Input is limited to `MAX_USER_INPUT_TEXT_CHARS` characters (`service.rs:493-510`).

Properties for herdr-threads:
- VERIFIED: the queue checks idle on the server side. It never types into the composer, so it cannot clobber a human's draft. The draft lives in the TUI and the turn starts beside it (INFERRED).
- VERIFIED: an interrupted thread is not auto-dispatched. A human Ctrl-C stops queue wakes until the next completed turn or an explicit `thread/queue/start`.
- VERIFIED: queued items survive the session's exit and are dispatched when the thread is next resumed and loaded.
- INFERRED, untested: with no daemon running, `codex queue` uses an embedded server that writes to the same `$CODEX_HOME` state DB. The SQLite watcher in a separate `--no-daemon` TUI's embedded server should then pick the item up within about 10 s. A third-party report claims instead that `--no-daemon` isolates the TUI from `codex queue` (WebSearch summary of holler issue #20, which returned 404 on direct fetch). This is the first experiment to run, because herdr-threads advises `--no-daemon` or `CODEX_EXEC_SERVER_URL=`.
- Latency: immediate when the same server holds the thread; up to about 10 to 20 s across processes (10 s version poll plus the 10 s dispatcher loop, INFERRED).
- `/side` threads are ephemeral, so they cannot be queue targets (INFERRED from `:265` together with "The measured `/side` is ephemeral", `integrations/codex/README.md`).
- Priority, dedup and ACK: none native. The queue offers ordering (`reorder`), `clientUserMessageId` and deletion after start. Framing is whatever text is queued.

## 4. MCP (client side)

- Transports: stdio and streamable HTTP. Config is `[mcp_servers.<name>]` with `command/args/env/env_vars/cwd`, or `url/bearer_token_env_var/http_headers`, plus `startup_timeout_sec` (default 10), `tool_timeout_sec` (default 60), `enabled`, `required`, `enabled_tools/disabled_tools`, `default_tools_approval_mode`, `tools.<t>.approval_mode` and `tools.<t>.output_token_limit` (MCP docs and config reference, VERIFIED). The CLI has `codex mcp add|list|get|remove|login|logout` (help).
- Server `instructions` returned at initialization are used "as server-wide guidance alongside the server's tools" (docs, VERIFIED). This is static injection at session start.
- **Resources**: model-callable tools `list_mcp_resources`, `list_mcp_resource_templates` and `read_mcp_resource` (`codex-rs/core/src/tools/handlers/mcp_resource_spec.rs:25,54,83`, VERIFIED). The model pulls them; nothing is pushed.
- **Server notifications are only logged**: `codex-rs/rmcp-client/src/logging_client_handler.rs:74-92` handles `on_resource_updated`, `on_resource_list_changed`, `on_tool_list_changed` and `on_prompt_list_changed` with `info!(...)` only. `:63-72` logs `on_progress`, and `:99-` logs logging messages through `tracing` (VERIFIED). No notification reaches the model or starts a turn. Whether `tools/list_changed` refreshes the catalog anywhere else: unknown.
- **Elicitation**: supported. `create_elicitation` is forwarded (`logging_client_handler.rs:41-50`) and surfaces as `mcpServer/elicitation/request` in app-server clients (form and url modes). The feature flag `tool_call_mcp_elicitation` is stable and on. INFERRED: this is a UI prompt to the human, not model context.
- **Sampling** (`sampling/createMessage`): no handler in `LoggingClientHandler`. INFERRED: unsupported.
- **Long-poll MCP tool**: a blocking tool call is bounded by `tool_timeout_sec`, 60 s by default and configurable. It holds the turn open, so the session is "busy" while it waits (INFERRED).
- Codex as an MCP *server*: the old `codex mcp-server` subcommand is gone from 0.163.0 help, and `codex mcp-server --help` prints the root help (VERIFIED, local). ACP: no `acp` subcommand in help. A third-party adapter (Zed's `codex-acp`) exists but was not examined (unknown).

## 5. Native tools relevant to waiting and mail

- **`sleep`** (feature `sleep_tool` stable, on): "Pause execution for a specified duration. The sleep ends early when new input arrives for the active turn." The maximum is 12 h, and on input the tool returns "Sleep interrupted by new input." (`codex-rs/core/src/tools/handlers/sleep.rs:28,51,112-150`, VERIFIED). INFERRED: a model told to `sleep` while awaiting a reply can be woken mid-turn by `turn/steer`, or by mailbox input. The turn, and its token cost, stays open.
- **In-process multi-agent mailbox** (`multi_agent` stable on; `multi_agent_v2` stable off): `codex-rs/core/src/session/input_queue.rs:94-200` (mailbox delivery into the current or next turn; `InterAgentCommunication { trigger_turn }`) and the tools `send_input`, `wait` and v2 `send_message`/`wait` (`codex-rs/core/src/tools/handlers/multi_agents*/`). Scope is one Codex process tree (root and subagents), not other panes (INFERRED). `send_message_to_user_async`, `agent_message_board` and `defer_mailbox_preemption` are "under development" (`codex features list`).
- **`request_user_input`** puts the thread into `active{waitingOnUserInput}` (schema flag).

## 6. Headless, resume and fork

- `codex exec [PROMPT|-]` (stdin is appended as a `<stdin>` block) with `--json` (a JSONL event stream), `-o/--output-last-message`, `--output-schema`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules` (help, VERIFIED). `codex exec resume [ID|--last] [PROMPT]` continues a stored session headlessly. `--no-daemon` is a top-level flag and must come before `exec` (herdr-threads `src/harness/codex.rs:1824-1832`).
- `codex resume [ID|name] [PROMPT]` and `codex fork [ID] [PROMPT]` relaunch the TUI on a stored rollout. With `PROMPT`, the first turn starts immediately (help).
- `codex debug app-server send-message-v2 <USER_MESSAGE>` is a debugging client. `codex debug prompt-input [PROMPT]` "Render[s] the model-visible prompt input list as JSON", which is useful for checking injected context without spending a turn (help, VERIFIED).
- Rollouts are stored under `$CODEX_HOME/sessions/...` (`transcript_path` in hook input). Threads are indexed in a SQLite state DB (the `sqlite` feature is shown as `removed true`, meaning always on; INFERRED). `codex migrate-rollouts` exists.

## 7. TUI behaviour relevant to keystroke injection

- Composer prompt glyph `›`. The empty composer shows the placeholder `Ask Codex to do anything` (herdr-threads `src/harness/codex/composer.rs:8-9`, captured grammar).
- While a turn runs, **Enter** submits a steer of the active turn and **Tab** queues the message locally until the turn ends (`queue_keys: [Tab]`, `codex-rs/tui/src/bottom_pane/chat_composer.rs:825`; tests `:9632`; keymap `composer.queue` can rebind it). The TUI's local queue is `InputQueueState.queued_user_messages`, separate from the durable `thread/queue/*` (`codex-rs/tui/src/chatwidget/input_queue.rs:24-41`). INFERRED: typed text plus Enter during a turn becomes a steer, not a new turn.
- **Paste-burst heuristic** for terminals without bracketed paste: three or more chars at intervals of 8 ms or less are buffered as a paste, and an Enter within `PASTE_ENTER_SUPPRESS_WINDOW = 120 ms` "is treated as a newline inside the paste, not as submit" (`codex-rs/tui/src/bottom_pane/paste_burst.rs:1-30,159-170`). The TUI also handles bracketed paste (`codex-rs/tui/src/tui_startup_tests.rs:324-347`, `InputDiscardStatus::BracketedPasteInProgress`). An injector must send text as one bracketed paste, or wait more than 120 ms before Enter.
- A startup draft is protected: input typed before the TUI is ready is kept as `startup_submission` (`input_queue.rs:25-26`; `startup_draft_tests.rs`).
- Slash commands (`codex-rs/tui/src/slash_command.rs:15-87`) include `/hooks`, `/side` and `/btw` (ephemeral side conversation), `/fork`, `/resume`, `/new`, `/clear`, `/compact`, `/goal`, `/agents`, `/multi-agents`, `/daemon` ("Manage the local background server"), `/mcp`, `/plugins`, `/skills`, `/status`, `/ps`, `/stop`. There are no user-defined slash commands in this list. Custom prompts come through skills and plugins (INFERRED).
- `tui.notifications` (bool or event list), `tui.notification_condition = unfocused|always`, `tui.notification_method = auto|osc9|bel` (config reference). OSC 9 or BEL on events gives a terminal-level idle edge (INFERRED).

## 9. Identity and session tracking

- Environment inside tool shells: `CODEX_THREAD_ID` (and `CODEX_SESSION_ID`), `CODEX_SANDBOX` and `CODEX_SANDBOX_NETWORK_DISABLED`. herdr-threads uses them as agent markers (`src/harness/codex.rs` `AdapterMetadata.agent_env_markers`, `CallerEnvShape.session_var = "CODEX_SESSION_ID"`). Codex's own source of these variables was not traced (unknown).
- Hook input carries `session_id` and `transcript_path`. `SessionStart.source = fork` marks forks. A forked thread "keep[s] the root's session id" while getting a new `thread.id` (app-server docs). INFERRED: `session_id` can differ from `thread id` after a fork. Check this before keying delivery on either.
- Shared daemon: hooks and tools may run in the daemon's process tree and environment, so pane-derived identity (`HERDR_PANE_ID`) can be wrong unless the TUI runs with `--no-daemon` or `CODEX_EXEC_SERVER_URL=` (herdr-threads `src/harness/codex.rs:1255-1291` advice text; Herdr PR #4667).

## 10. What herdr-threads does today for Codex (brief)

- **Hooks** (`src/harness/codex.rs:272-309` `DECLARATION.owned_hooks`) are installed by `setup codex` into `$CODEX_HOME/hooks.json`. Setup never writes trust (`integrations/codex/README.md`). The groups are:
  - `SessionStart` (lifecycle check-in)
  - `SubagentStart` (child context)
  - `PreToolUse` with matcher `^Bash$` (tool-boundary attention digest)
  - `UserPromptSubmit` (turn-start digest)
  - `SubagentStop` and `SessionEnd` (disconnect only)
- **Output** is only `hookSpecificOutput.{hookEventName, additionalContext}`, capped at **4,608 bytes** (`src/harness/codex.rs:1135-1145`). It is a server-side attention digest, not message bodies: one non-durable Current check-in made only when the digest token advanced (`src/cli/hook.rs:1-21`). The model then runs `herdr-threads inbox`, which displays and ACKs. No permission decision or `updatedInput` is used; invocation transport is "UNSUPPORTED".
- **Wake**: Herdr `agent.prompt` types the content-free `herdr-threads: wake up` for hook-registered (`cooperative_top_level`) bindings. Other bindings get the longer `MARKER` "...run herdr-threads inbox" (`src/harness/codex.rs:1393-1399`; `src/notification/policy.rs:14-21`). Busy and idle come from Herdr `agent_status` (`idle|done` count as ready) plus a composer read that must classify `Empty` (`src/host/native.rs:53,2003-2070`). `composer_stash` is unsupported, so a non-empty draft refuses the wake (`src/harness/codex.rs:158`, `composer.rs:59-70`).
- **Daemon**: herdr-threads advises `--no-daemon` or the pane env `CODEX_EXEC_SERVER_URL=` so that hooks run with the pane's own environment (`src/harness/codex.rs:1255-1291`).
- Not used: `Stop` block, `PostToolUse`, async hooks, MCP, `codex queue` / `thread/queue/add`, `turn/steer`, `thread/inject_items`, `thread/status/changed`, `notify`.

## 11. Gaps and leads for the comparison reports (INFERRED unless noted)

1. **Native idle wake without typing**. `thread/queue/add` (`codex queue`) starts a turn only when the thread is idle, on the server side, with no composer read, no draft clobbering and no Herdr typing. Its weaknesses: it is skipped after an interrupted turn, has up to about 20 s cross-process latency, refuses ephemeral `/side` threads, and may not reach a `--no-daemon` TUI (contested; §3). The queued text is a user message, so a content-free `wake up` keeps rule (c).
2. **Mid-turn steer**. `turn/steer` reaches a busy session at the next sampling step through a native channel. Pairs with the `sleep` tool's early return. It needs a connection to the server hosting the thread (shared daemon), which conflicts with the `--no-daemon` advice.
3. **Silent delivery**. `thread/inject_items` adds history without a turn, matching "p1 arrives on next turn" semantics. Same reachability limit.
4. **Tool-boundary coverage**. The current `PreToolUse ^Bash$` misses turns that only call `apply_patch`, MCP or other tools. A `PostToolUse` hook with matcher `*`, or an **async** hook drained after each sampling step, would cover every tool.
5. **End-of-turn delivery**. A `Stop` hook returning `decision:"block"` when p0 mail is pending delivers it before the session idles. That removes some nudges, and `stop_hook_active` bounds loops.
6. **Busy/idle observability**. `thread/status/changed` (`idle` / `active{waitingOnApproval|waitingOnUserInput}`), `turn/completed` and `notify` `agent-turn-complete` are precise native signals, compared with screen-scraped `agent_status`.
7. **Size**. Codex spills hook context above about 2,500 tokens. herdr-threads' 4,608-byte cap stays under that. Bodies arrive through an `inbox` tool call, not in the hook.
8. **MCP push is a dead end** in 0.163.0: notifications are logged and dropped. An MCP long-poll is bounded by `tool_timeout_sec`.
9. **Keystroke injection hazards**. The 120 ms paste-burst Enter suppression, Enter steering versus Tab queueing during a turn, and the startup-draft buffer.
