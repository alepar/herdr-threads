### 7. Independent due phases and pending-unwarned discovery

Both invitations and receipts gain `warning_message_id` (nullable immutable materialization reference). The shared overdue helper writes this reference in the same transaction as the unique warning event/job (or retirement warning without job). ACK/accept, ordinary due, and retirement all use the helper; an existing unique event repairs/verifies the reference idempotently, never generates another job. Rollback commits neither marker nor event. This marker describes materialized overdue history, not ACK or retirement status.

Use partial pending-unwarned indexes, e.g. invitations `(deadline_at,ordinal) WHERE state='pending' AND warning_message_id IS NULL`, receipts `(deadline_at,ordinal) WHERE state='pending' AND deadline_at IS NOT NULL AND warning_message_id IS NULL`. Settled/already-warned retained history is absent from the scan. Effective retirement is rechecked before warning creation. Physical slices read at most remaining-budget candidates from the index **before** ordinal high-water or live-state filtering; skipped newer rows consume units and advance native physical keys. The scan stops when the ordered deadline exceeds the transaction's due horizon, without deleting future work. Newly assigned deadlines behind an active cursor are picked up by the next fresh pass; the scan is finite through a captured key/high-water range, and periodic fresh passes remain mandatory after completion/restart/UTC change. No OFFSET, no LIMIT after an arbitrarily selective filter.

Replace `due_obligations(limit,budget)->u16` with `due_obligations(DueScanRequest { state: DueScanState, max_candidates: u16 }, budget)->DueScanProgress`. `DueScanState` contains independent invitation and receipt native cursor/high-water state plus `next_phase`. `DueScanProgress` contains updated state, total physical examined count, committed warnings_added, each phase's `Complete|More|Failed(BoundedError)` outcome and explicit `has_more`; counts never imply continuation. The facade retains each scanner's native physical position. Error on one phase leaves that position unchanged and retains its captured bounds; completed progress in the other is returned. The failing position is retried, not skipped.

Before fallible work, rotate phase priority durably in the driver's retained scan state. ### 8a. One effective unavailable-warning model before and after expansion

Choose the prepared-warning representation over a second deferred event queue or a live MIN-over-all-sends definition. Preparation already visits every addressed recipient in bounded units; recording immutable warning data there adds fixed work per visited recipient and needs no new publication loop. Computing earliest warning only at query time would make identity/history dependent on incomplete materializers or repeated global scans. Physically inserting every warning at publication would restore the original unbounded writer problem. The manifest representation reuses one existing publication boundary.

Canonical warning key is `(instance, thread_id, affected_seat_id, unavailability_episode)` with the existing prelaunch invitation warning suppression rule included in eligibility; do not add an unavailable-send warning where the approved pending invitation already supplies the initial warning. A deterministic domain-separated UUID `warning_id` derived from the canonical key is the one public MessageId for this system event; store the full key alongside it and fail on inconsistent key/ID collision. It is not an ACKable ordinary message. During preparation an indexed lookup into the **effective published warning view** checks that key. If already present, no new warning entry is staged. If absent, stage one immutable payload and offset. This lookup includes previous published manifests even when their jobs have never run. Hidden unpublished preparations do not count as warnings.

The per-thread timeline_revision equality check makes earliest-send selection serializable: two preparations may both stage the same absent key, but publication of the first changes that scalar revision; the second must retry and see the now-published canonical warning. A retry must reference the original earliest published warning, not update its source send or append another one. Dedup never depends on materializer completion order. Direct warning lookup is indexed by canonical key through staged rows plus manifest visibility and executes under finite read budget; uncommitted stale staging may be removed only in bounded cleanup.

Preparation assigns contiguous offsets 1..W to its genuinely new unavailable warnings and records W as part of its sealed manifest. Each bounded staging transaction uses unique `(preparation_id,warning_key)` and `(preparation_id,warning_offset)` constraints and increments the retained warning count only for an inserted new row; retries do not increment twice. Completing the final candidate slice seals status/count/digest atomically with the cursor. Only the store-owned builder can seal; final publication checks the sealed marker and scalar revisions without recounting rows. No client supplies W or a completed marker. Duplicate-key/corrupt-prefix detection fails closed and leaves staged state invisible. In the final constant-size commit, read thread.next_sequence as base N, publish the ordinary send at N and its W logical warning entries at N+1..N+W, then advance next_sequence by checked W+1. Check W+1 and N+(W+1) for the database integer range before any publication write; overflow returns a typed sequence-exhausted error with the transaction rolled back, no partial message/operation/timeline advance and no wrapping. Staging increment overflow also fails before sealing. Every position is already backed by immutable staged event data that becomes visible in that same commit; these are fully published logical events, not empty reserved slots awaiting later decisions. This is distinct from forbidden retirement backlog sequence reservation. No physical materializer later appends/backdates a timeline row or allocates a second sequence. Other event writers allocate after N+W. Retained total-count = next_sequence-1 remains valid because no holes are reserved; aborted publication advances nothing. Per-thread N+offset orders timeline entries; global decision S orders committed decisions and occupant offer frontiers. All warnings from one publication carry generation S, not their timeline sequence or staging ordinal. The cursor fields distinguish these types. Warning payload may carry source send and publication decision S/time; materialization timestamp is separate projection diagnostics, not a rewritten immutable event field.

Define `effective_messages` / `effective_warnings` as the disjoint union of ordinary directly stored events and manifest-backed entries (a physical projection is keyed to the same warning ID and excluded as a second domain row). `Message` detail, History, Search, ordinary/system/total counts, warning recipients, Inbox/CheckIn and wake candidate/reservation all consume that same effective model. For a manifest warning, its recipient set is immediately derivable from membership-at-S plus affected eligible seat using the captured interval high water, regardless of whether a warning_job/ledger row yet exists. An attribution job can be reconstructed from the manifest entry; it is an optimization/work obligation, never the existence condition for the warning. Actionability uses its frozen source episode and current effective condition. These joins run under finite query/reservation budgets and fail explicitly if they cannot establish the answer; missing projection cannot mean no warning/no wake.

History captures logical per-thread sequence high water, merges physical and manifest-backed events in that immutable sequence order, and continues after the last fully examined logical position. Before/after/recent selectors and exact same-command continuations are unchanged. Later materialization neither changes sequence/high water nor duplicates or removes an item, so a cursor opened before expansion reaches the same canonical warning once. New manifest publication above high water appears on refresh. Body/detail route resolves the canonical warning ID directly even before attribution. Global search/order needs a logical immutable event ordering key `(publication_decision_seq, event_offset)` for manifest-backed and directly stored events, captured in its typed cursor; a projection insertion ordinal must never control discovery. Allocate no unbounded list of public IDs at publication.

A check-in offer therefore counts/references these logical warnings and provides working read-only history/inbox continuations before recording its occupant frontier. A compact page may omit an individual warning, but cannot hide its existence behind an inaccessible job. If count/history query budget is exhausted, report that error and do not advance offer state as though nothing existed. A stuck earlier send materializer cannot hide a later committed warning or prevent its effective discovery/reservation; no per-thread expansion-order requirement remains for correctness. Materializers may rotate fairly in any order because identity, earliest provenance and timeline order were fixed by publication.

Acceptance: send → check-in → continued history/wake → materialization returns one stable canonical warning throughout; no duplicate count or sequence before/after projection; force prior send job permanently stuck and still discover a later committed warning; two concurrent preparations for same episode choose exactly the first committed send; rollback/restart preserves identity; invite/prelaunch suppression remains; logical search/history cursors straddling materialization neither skip nor duplicate.
