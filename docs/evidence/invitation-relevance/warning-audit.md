# Warning notification replay audit

Initial read-only audit against base `36d86ad9d69472d5c29ed4d827e858f67ea35975` on 2026-10-07. AGENTS.md, TRUST-POLICY.md and systematic-debugging were read. Follow-up authorization expanded the task to isolated regression tests and implementation (recorded below); no shared-daemon requests, native trials or helper/daemon processes were used. The reported thread has three overdue invitation events (#29/#30/#31) and three clear events (#32/#34/#36), repeatedly presented despite empty inbox. That live count is supplied evidence, not independently queried in this audit.

## Root cause and boundaries

There are two separate replay causes, with different scopes:

1. **Warning history is embedded in every CheckIn, then rendered as hook offer data.** `src/store/mod.rs` around 1719 calls `queries::warnings_in_transaction` with a fresh page. `src/store/queries.rs:4149-4299` starts each thread timeline at sequence zero and `src/store/effective.rs:1210-1235` selects every warning attributed to the seat; neither function applies a delivery frontier or requires a live condition. `src/harness/bridge.rs:770-807` and `1036-1050` encode the complete returned CheckedIn as `OriginalOffer::Inline`; `encode_hook` at 111-137 prints it under “Original cached CheckIn offer”. Compact output explicitly prints `warning_history` (`src/protocol/output_compact.rs`, function `checked_in`); the human CheckedIn renderer also carries the warning page. Consequently any later check-in triggered by an unrelated new invitation/message/warning prints old warning IDs again. Existing coverage deliberately enshrines this: `tests/store/cooperative_checkin.rs`, `programmatic_notices_settle_page_by_page_for_the_current_occupant`, asserts that all settled warnings remain in the third offer's warning-history page.

2. **Post-v18 transition notifications have no bounded delivered-page settlement.** `schema::record_overdue_inner` (`src/store/schema.rs:3398-3476`) deduplicates the canonical open condition and appends an event only once. `clear_warning_condition_at_snapshot` (`3040-3092`) appends exactly one `warning-clear:{open}` event and retains its link in `warning_conditions`. Both enqueue a warning job whose `condition_id` is `transition:{warning}` (`2914-2915`). Migration 0008's `digest_open_warning_job` projects invitation/receipt jobs, including clears, into the nominal “open” warning tables. Its invitation-close triggers delete by the invitation id, so they cannot match `transition:{warning}`. `effective::warning_condition_actionable` (`1669-1674`) returns true whenever either side of the transition appears in `warning_conditions`, including a closed open and a clear. `attention::projected_pending_warnings` (`758-822`) applies no offered frontier to these recipient/affected walks. These six immutable events therefore remain digest-pending after offers and clear, rather than becoming delivered informational history.

The bounded path already present in `attention::notice_offer_page` (`538-653`) covers only `digest_programmatic_warnings`. Migration 0008's insertion trigger fills that projection only when `service_notification_publications` identifies a programmatic service warning. Built-in invitation opens/clears do not qualify. The existing notice frontier works for its original scope; it does not settle the reported events.

## Why inbox is empty, and what wake does

Every committed Current or Lifecycle CheckIn upserts `warning_offer.offered_through_seq` to the current global decision sequence (`src/store/seats.rs:4092`) regardless of the warning history's bounded page. `queries::inbox_batch` reads that exact-occupant cutoff (`4965-4970`) and excludes every warning at or below it (`5311`). An empty inbox with digest-pending warnings is therefore expected under the current code.

Wake candidate construction retains that cutoff (`src/store/wake.rs:164-175`). `WakeCandidate::warning_offered_for_current_occupant` (`src/ports.rs:2144-2157`) compares warning seq with it, and `notification::policy::AttentionSnapshot::select` (`src/notification/policy.rs:69-76`) excludes offered warnings. Thus the source **does not prove warning-only repeated wakes** for an unchanged exact binding. Pending invitations/receipts can still cause retries, and their next check-in reprints warning history. A replacement Lifecycle binding intentionally starts a new generation and the exact-binding cutoff/frontier no longer covers its predecessor's offers. Read-only trace cannot establish which wake reason was present for each live observation.

Tool hooks have their own coalescing: `bridge::tool_boundary_check_in` (`964-1050`) skips an unchanged digest token, but compaction disables that coalescing, digest failure fails open, and any new pending publication advances the token. Each resultant offer currently carries old history again. This distinguishes canonical duplicate creation (not evidenced) from repeated notification of canonical unique events (evidenced by source).

## Smallest coherent fix proposal

Use the existing capped notice-page/ordinal mechanism for **all informational warning events**, including condition opens and clears, with per-recipient attribution and exact binding scope retained. Generalize its projection rather than adding per-hook string suppression. Canonical publication and recipient attribution remain unchanged. Project a transition for each canonical recipient as attribution becomes available, oldest-first by insertion ordinal. Advance only the exact prefix carried in the committed offer, retain all event and attribution rows, and have digest/inbox/wake consistently classify projected, already-carried informational events as delivered. An attribution backlog remains pending until eligible for the offer page, so late projection cannot be lost behind a global decision-sequence watermark. Underlying invitations/receipts remain pending until their existing accountable settlement, independently of their informational warning delivery.

Remove automatic warning-history embedding from the notification presentation. Keep explicit read-only `warnings`, message detail and thread history available with pagination; provide the history command if needed, but do not re-notify every historical ID each time another obligation appears. Decide explicitly whether the CheckIn wire result should retain its legacy history field for compatibility while hooks omit it, or whether the field becomes empty with history accessed through the explicit query. Rendering alone fixes only cause 1; it leaves cause 2's false pending state. Filtering by global `offered_through_seq` alone is also insufficient: a bounded offer might not carry all prior events, and late recipient projection could be hidden.

Existing behavior deliberately redelivers service notices to a replacement occupant (`tests/store/cooperative_checkin.rs` cited above). Keep that documented binding scope unless the user requires durable seat-global one-time delivery; the latter changes existing successor semantics and needs an explicit policy/design choice. No new ACK/receipt provenance is needed for committed informational offers (current NoticeOffer already says commit settles even if output is lost). Exact replay of an immutable cached response must remain possible for response-loss recovery; normal fresh check-ins should not regenerate historical notifications.

## Meaningful RED regression design

Use existing production-shaped store fixtures and hook-entrypoint tests, not live shared panes. First test post-v18 transition events, rather than only the existing service-event helper. Capture returned event IDs and canonical recipients, never rely on hard-coded sequence numbers.

1. Create one pending invitation with a deadline, advance the fake clock, run real overdue generation and bounded attribution workers. Assert exactly one canonical open event and capture its id. Register two eligible recipients (affected seat and a joined observer) with separate binding contexts. Each sees that unique event once; the first recipient's offer never settles it for the second.
2. For recipient A, issue two fresh Current check-ins. After its first committed carried page, assert no repeated warning id in notices or rendered fresh hook data, warning digest count zero when no other warning is unoffered, and `warnings` history still contains it. Current code is RED: transition never appears in the notice page, remains digest-pending, and is returned as history on both check-ins.
3. Exercise real tool hooks: first presentation, repeated tool, forced compact/current, then a genuinely new message/invitation that advances the attention token. Assert no old warning id in any subsequent offered data. The new obligation must still be offered. This catches a fix relying only on normal token coalescing.
4. Inspect wake selection using the real candidate/attention witness before and after delivery. No warning-only retry after the event is offered. Leave the actual invitation pending and prove its existing invitation wake reason remains eligible. Trigger that wake/check-in and assert it cannot re-notify the delivered warning.
5. Explicitly settle the invitation through its normal fixture command, then publish/drain clear attribution. Assert one unique clear event, delivered once independently to A and B. Repeated check-ins/tools/wake evaluation show neither old open nor clear as new. Explicit thread/warnings history still contains both and their condition links remain intact.
6. Create a genuinely new invitation episode (or a new receipt after the prior condition closes), expire it, and assert a distinct canonical open id is offered once. This kills an overbroad “already warned thread/seat” suppression.
7. Add >16 events and delay one recipient's attribution job until after an offer. Only the first carried prefix settles; later pages and the late projection remain deliverable exactly once. Keep a fresh new event after the first page. Verify no history deletion and retain the intended replacement-binding replay semantics separately.

Focused runs should cover the new store regression, hook-entrypoint regression and wake policy regression with `--locked --all-features`; use the mandatory per-change clippy and cargo fmt after implementation. No full suite is called for by this read-only audit.

## Authorized implementation and observed regression evidence

The root subsequently authorized code and tests. Migration 0025 adds an independent transition-attribution trigger, preserving the historical v8 service trigger and its schema audit. Both physical and manifest-backed transition events are projected, using the existing unique `(seat_id,warning_id)` delivery table and seat/ordinal indexes. Fresh CheckIn history is empty, and the prior service-notice history assertion now queries explicit `warnings` history. The exact carried page still advances one occupant-scoped frontier upsert. Legacy pre-transition condition warnings retain their original behavior.

`informational_notice_pending` centralizes exact delivery classification, and `seat_has_pending_notices` exposes the O(1) attributed-page probe for hooks. Wake candidate selection first probes that projection and, if needed, examines only the existing bounded warning-attribution backlog; it bypasses the coarse watermark only while informational events remain unoffered. This covers an older unoffered notice even when the newest warning is a covered legacy warning. Materialization kicks the wake producer for late exact-pending informational attribution even if a prior coarse watermark covers its publication sequence.

Seven real-store regressions cover unique open/clear/new episode, 16/1 pages and delayed attribution, independent recipient and successor frontiers, v24 migration and trigger tamper rejection, unprojected/projected wake selection, older informational vs newer legacy warning, and a manifest-backed unavailable open with no physical messages row. Follow-up assertions exercise the pending-page helper and late-attribution wake attention-version kick. Raw RED logs:

- `warning-red.log`: two failures; real built-in overdue events are never carried (`[]` vs expected unique event/page).
- `warning-wake-red.log`: unprojected event incorrectly treated as carried by coarse check-in cutoff.
- `warning-manifest-red.log`: unavailable transition never carried without a physical messages row.

Observed focused GREEN before the root's additional hook protocol edits: seven new regressions passed in 0.15s; the full existing cooperative-checkin module passed 47 tests in 1.55s before later additions, and 34 existing wake tests passed in 1.00s. The attention module passed 15 tests, with 12 intentionally ignored; one old invitation-action wording assertion needed updating for the root's separate invitation relevance change. Final verification belongs to the root after the hook protocol seam is complete.

The audit also identified the remaining hook boundary: an attribution backlog warning can advance the logical digest token before the notice is eligible for the carried page. Attribution then leaves the immutable publication key unchanged, so ordinary tool coalescing can stay quiet. The root owns the additive digest-delivery wrapper and hook regression for that boundary; canonical max tokens and immutable operation replay must remain unchanged.

### Review follow-up: pending projection cleanup

Independent review identified retained canonical transition rows in the legacy open-warning projections. The new 1,001-event regression reproduced an empty pending count with `has_more=true` after all events had been carried; pending-walk work also grew with that delivered history. `warning-projection-cleanup-red.log` records that failure and the separate first-recipient parent-retention failure.

Migration 0025 now removes a canonical transition's legacy projection parent only after its exact recipient delivery row exists. The old projection's delete trigger removes legacy recipient projections. Removing the parent also prevents a later-running legacy recipient insertion trigger from recreating them. Recipients not yet attributed remain in the existing bounded warning-job backlog; a partial-fanout test proves the affected recipient still sees the pending event after the observer's first attribution removes the parent. The backfill applies the same cleanup, with explicit v24 legacy projection reconstruction in the upgrade regression. Canonical events, condition links, warning recipients and delivery rows remain retained; pre-transition legacy warnings stay unchanged.

Raw verification: the two cleanup regressions passed in 2.12s (`warning-projection-cleanup-green.log`), all nine new warning regressions passed in 2.74s (`warning-projection-cleanup-all-green.log`), and all 52 cooperative-checkin tests passed in 2.52s (`warning-projection-cleanup-cooperative.log`). The scale regression requires zero pending warnings with no saturation and exactly the same pending work after 16 and 1,001 delivered events.
