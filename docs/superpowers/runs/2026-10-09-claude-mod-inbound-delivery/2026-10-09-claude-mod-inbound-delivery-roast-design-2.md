  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: D6 line 228 maps 'no live channel yet, daemon busy or unreachable' to one reaction, 'retry after the next registration'; line 230 makes every id retryable on any non-zero `watch ack` exit. D7 line 251 re-acks the set only when 'the same binding generation re-registers within the grace', and nothing re-registers while the stream stays up. All three seats grepped for retry/re-ack/unacked and found no timed retry and no retry on an Attention frame or next delivery. D5 de-dup suppresses re-delivery of the re-paged id, D7 suppresses native wake while live, and the stall predicate (lines 256-259) resets on any later ack of another item, so the stuck receipt never trips it in a busy seat. ## Rejected (with reason)
- D5 Busy state 'The open set is kept in `$.state` ...' and 'A stale open id, from a lost `turn.complete`, is cleared when a later turn of the main conversation starts or completes'; D8 'That is safe because of the D5 assumed-busy startup and `$.state` turn tracking' — Keeping open turn ids in `$.state` across reloads turns a missed `turn.complete` into a stuck busy state for an idle agent until the 10-minute stall handover. Rejected 3-0: the mechanism is real but bounded by design. D7's stall handover (Close{stalled}, kick the wake lane, native ladder resumes) is the chosen backstop, and D7 'Considered' rejects 'hard suppression with no stall bound' for exactly this reason; the outcome is a delay of up to about 10 minutes then native delivery with nothing lost, which stays within requirement 4. The trigger needs a `turn.complete` lost inside the brief reload window, and the test list covers 'reloads mid-turn'. Iteration 1 already rejected the same residual ('Skipped turn.complete leaves a stale id forever', 3-0) on the same stall-bound reasoning; the rejection stands. Residue: D8's word 'safe' is loose, and running the idle probe after every load (or reconciling `$.state` against `$.prompt.read()`) is a one-clause hardening worth a line.
- D2 notify call sites 'settlement by another path (hook or inbox ACK)'; D4 'paging until drained after every Attention frame'; D5 idle-submit gates (post-abort hold, 120 s draft wait) — The mod has no way to drop a held item settled through another path, so a held message can later start a spurious turn via $.prompt.submit. Rejected 2-1: D2 pushes Attention on settlement by another path and D4 re-drains pages after every Attention frame, so a settled receipt disappears from the drained pages; dropping a held id absent from a drained page is an implementation detail of a specified mechanism. D6 maps `already_settled` to idempotent success, the hold windows are short and bounded, and with a live channel the agent rarely learns of a held item before the mod delivers it. Ground seat's Nit (spec never writes the 'drop a held id missing from a drained page' step; a pre-submit re-check or a 'settled' frame would close it) cites the same spec text the majority addresses; a one-line clarification is worthwhile but not a confirmed gap.
