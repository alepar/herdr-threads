IMPORTANT I1 — Settled-mail passive classification also disables wake_on: all lazy wakes.

Primary location: integrations/claude/mod/hooks/register.js:292 (introduced in 575c5280).
Supporting locations: src/store/queries.rs:6486–6504; src/delivery/assemble.rs:146–149,222–225; src/cli/watch.rs:576–579; register.js:415,432,519,547; TRUST-POLICY.md:681–688.

The new passive flag treats every message with ack_required:false as mail already settled by another binding. That wire shape is also the existing deliberate promotion of lazy mail for a seat that opted into wake_on: all: the store sets wakes=true, Assembler emits DeliveryKind::Message with ack_required=false, and watch sends kind=message. The mod cannot distinguish promoted lazy from settled ordinary mail with its current predicate.

Concrete schedule: a Claude binding has a live mod channel, the model is idle, the composer is empty, and its seat has wake_on: all. A fresh lazy message arrives with no invitations/warnings/ordinary mail. The watcher emits kind=message, ack_required=false. receive marks it passive; pumpLazy appends it and completes it via append, while pump excludes it and submits no wake. There is no independent attention item for that lazy message: drain_pages raises attention only for invitations and waking warnings (src/delivery/page.rs:87–90). After completion its lazy cursor can pass it, so subsequent wake discovery need not rescue it. The model remains idle until unrelated work starts a turn.

This regresses an explicit supported preference and Delivery contract rule 2's wake_on: all exception. It is Important, not a minor settled-mail refinement. Preserve passive treatment for settled ordinary mail while carrying or retaining enough delivery-policy information to recognize promoted lazy mail (for example an explicit wake-policy/source flag). Owner should choose the wire-compatible solution. Add a regression that drives the real promoted-lazy shape through an idle mod and asserts one content-free wake plus lazy completion, alongside the existing assertion that settled ordinary mail appends without waking. The 97 mod tests currently pin the settled-ordinary case but do not distinguish it from promotion.

IMPORTANT I2 — Deferred F3 late lineage MAX-copy silently consumes an existing successor's unread mail.

Primary locations: src/store/bindings.rs:1267; src/store/read_cursors.rs:159–161.
Production call path: src/store/seats.rs:4437–4445; bindings.rs:1519–1526,1543–1551.
Contract locations: design spec:180–184,228–245; TRUST-POLICY.md:261–272,336–345,719–720,743–747.

link_lineage for an already-enrolled successor still calls copy_lineage, whose UPSERT raises existing cursors with MAX. That is more than recording lineage and preserving monotonicity: it can pass messages the successor never displayed. The deferred label and the fact that cursors move only forward do not establish safety.

Concrete supported schedule:
1. Hermes predecessor P is lifecycle-claimed and connected, with cursor k in a joined thread.
2. Successor session S first makes a plain CLI call before its parent-bearing pre_llm_call. It enrolls fresh at the seat maximum k. Plain enrollment intentionally does not supersede P; P remains eligible to display mail. Both rows retain the same process fingerprint.
3. A new lazy message M at k+1 arrives. P displays M through its own text inbox/completion, moving P to k+1. S has not displayed M and stays at k. This can also be a late parent-bound display/completion; the cooperative model intentionally supports calls attributed to their original session.
4. S's first lifecycle pre_llm_call carries parent_session_id=P. resolve_cooperative_with_lineage finds the open top-level predecessor; the lifecycle resolver connects/touches S and supersedes P without changing S's cursor. The subsequent link_lineage MAX-copy raises S to k+1. M now disappears from S's lazy unread stream without S ever seeing it. An ordinary M similarly disappears when P's display also settled the shared receipt.

This is a later silent skip in an already-existing stream, distinct from the explicitly accepted birth-time seat-maximum seed. The spec explicitly says the later pre_llm_call links lineage without moving cursors. TRUST-POLICY:339 does describe MAX, but it conflicts with that requirement and with the policy's own invariant that cursors never pass unshown receivable mail and its statement that named fast-forward is the sole exception. The accepted-limit text at :344–345 identifies the plain-first birth seed, not consumption of mail arriving/read by P after S's enrollment. Treat this as Important until the behavior and normative contract are reconciled; the current deferral does not explicitly accept this late skip.

Keep initial SeedMode::Lineage inheritance for a newly born successor. For an already-enrolled successor, record lineage without copying over its existing read position, as the spec requires. Add an end-to-end store regression using genuine plain-call S enrollment, then P's display of new M, then S's parent-bearing lifecycle check-in; assert S still sees M and retains its prior cursor. Existing tests only assert never-backwards behavior, and tests/store/bindings.rs:2256–2260 explicitly expect the problematic forward move. The production-level test named cli_first (tests/store/cooperative_checkin.rs:4251) enrolls S with check_in_with and does not cover this advancing-parent plain-first schedule.

MINOR M1 — Deferred F2 bound warning reads still follow a sibling frontier; its scope is broader than non-waking rows, but obligations survive.

Locations: src/store/queries.rs:6313–6324,6719–6726; src/store/attention.rs:838,884–909. Supporting recovery/policy: attention.rs:1072–1079; delivery_pull.rs:389–392,515; TRUST-POLICY.md:623–635.

Reader::Bound captures the legacy warning cutoff using SEAT_NOTICE_BINDING_SQL, and informational_notice_pending always consults that seat-selected binding's digest_notice_offer. With older live binding B and newer connected binding A, A's check-in offers warning N and advances A's frontiers. B's own bound inbox query can then omit N, although B's frontier remains before N. In the opposite frontier arrangement it can relist a reference its reader already received.

The earlier explanation "informational warnings only" needs precision: warning_wakes_seat (attention.rs:1497–1509) permits an affected seat's still-open condition and service notices to wake. These references are nevertheless not ACK receipts or invitations, and their independently pending obligations still appear/count/wake through those sources. B's own committed check-in offer and hook-pull notice page use B's frontier and recover N. TRUST A7 explicitly authorizes the seat-level wake/receipt view to follow the newest open top-level binding, so the seat-level materialization/wake selection alone is not an unaccepted cross-binding mutation. The concrete defect is the caller-bound inbox warning view using that seat-level selection. Grade Minor for this recoverable reference/presentation mismatch, not because every warning is non-waking. A future repair should select the bound reader's frontiers on bound inbox paths and retain documented seat selection on genuinely seat-level paths.
