IMPORTANT I1 — Actual push and hook-pull drains still use the seat inbox, so they omit a binding's unread ordinary stream.

Locations: src/service/delivery_pull.rs:140–149; src/cli/watch.rs:505–528; src/store/queries.rs:6215–6217, 6334, 6673–6695.

The hook-pull StorePageSource passes InboxQuery { claim: None, seat: Some(seat) } directly to StorePort::query. The push ClientPageSource does the same over the socket. run_session_marked moves the registration claim into open_watch and retains only the seat for watch_loop/drain (src/cli/watch.rs:387–410, 422–473). DomainService dispatches InboxBatchV2 to store.query without inserting a claim (src/service/dispatch.rs:1124–1143); SqliteStore::query fills only a missing seat (src/store/mod.rs:1512–1550). ReadContext contains no caller binding (src/ports.rs:307).

With claim None, inbox_v2::reader selects Reader::Seat. capture creates the ordinary unread source only for Reader::Bound. Thus these production drains show ordinary messages solely from the receipt source, which filters EffectiveReceiptState::Pending; already-settled messages never enter the page. Lazy rows also use the seat-level union of connected top-level readers rather than the requesting binding's cursor (src/store/lazy_delivery.rs:62–70, queries.rs:6610–6626).

Concrete failure: A and B are connected top-level bindings of one seat, with different live processes, both enrolled before ordinary message M. A displays and settles M (via text inbox or mod/hook receipt), advancing only A's cursor. B, whose cursor is still before M, then opens/reconnects its push watch or performs its next hook pull. B's drain returns no M because the shared receipt is now settled and the unread source was disabled. An explicit InboxBatchV2 carrying B's claim would return M as already settled. For hook pull the empty drain can record a whole read and subsequently return Unchanged even though B's binding fingerprint still reports unread ordinary mail. For push the per-binding channel exists but its drain cannot supply the body.

This breaks spec §2 ('Other bindings still see the message in their own stream, marked already settled') and the delivery contract requiring in-turn context delivery. It also makes a reader receive already-consumed lazy mail if a sibling still has it unread, especially after watch reconnect. Binding source data is preserved: B can recover ordinary mail through explicit bound inbox; a native lifecycle hook may also recover through its bound inbox path. Those paths mitigate permanent loss but do not repair the channel/pull delivery guarantee.

Existing config9 does not cover the failure: tests/integration/session_bindings_smoke.rs:2183–2213 sends a default lazy message, waits for both watch pushes before either reader displays/settles it, then verifies independent cursors by explicit text inbox. It never starts B's drain after A settles an ordinary message. Fix both PageSource paths to retain/pass the actual binding claim on every page, with focused ordinary-after-sibling-settlement and lazy-after-own-cursor/reconnect checks.

IMPORTANT I2 — The accepted per-seat hook-pull offered ledger loses valid confirms and defeats delivery bounds when live sessions share a seat.

Locations: src/delivery/ledger.rs:149–186; src/service/delivery_pull.rs:329–335, 561–562, 662–676, 732–750; src/ports.rs:3871–3882; TRUST-POLICY.md:1021–1028.

OfferedLedger is keyed only by SeatId. seat_mut discards that seat's offers whenever native_session differs, even when both sessions are open/connected and share the same mapping generation (the intended session-keyed model). Every pull and confirm calls seat_mut for its own session. The outlook/parking interface is also only seat + mapping generation.

Concrete deterministic sequence with two connected hook-pull bindings A/B of seat S and a pending message M:
1. A DeliveryPull records M in S's A entry and injects it.
2. B DeliveryPull replaces S's A entry with S's B entry and injects M.
3. A DeliveryConfirm(M), based on valid transcript evidence, calls seat_mut(A), deletes B's entry, and creates an empty A entry. The forwarded list is empty, so M returns NotOffered and no receipt/cursor settlement occurs.
4. B DeliveryConfirm(M) similarly returns NotOffered. Alternating hooks can repeat this indefinitely.

Even without confirms, alternating A/B pulls continually recreate offer.count=1 and reset last_at, allowing the same unconfirmed id to be injected repeatedly less than 60 seconds apart and more than 3 times in one binding generation. This directly contradicts the normative re-offer bound; it is not merely a performance probe/index nit. Alternating confirms can also erase a sibling's parked/capped ledger. Pending source data survives and explicit text inbox can settle it, but automatic hook confirmation can fail indefinitely in a supported multiple-live-binding configuration. Keep offers and next-pull/parking outlook per binding (with an appropriate resume fence), and test interleaved pull/confirm plus bounds. The dispositions' accepted 'per-seat hook-pull offer ledger' classification should be revised; acceptance there did not document or waive these observable semantics in TRUST-POLICY.
