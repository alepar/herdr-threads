# Registry health, doctor and canary discovery

Bead: `ht-3bi.3`. Ancestor: `2026-10-03-harness-adapters-design.md`. Producers: registry/interface `.1`, runtime/domain model `.2.3`, evidence store `.2.4.1` and negotiated evidence handler `.2.4.2`; native setup/launch `.5` and Hermes adapter `.6` supply concrete adapter observations rather than adding core branches.

## Goal

Every registered harness participates in bounded observation, negotiated health and local doctor inspection. Shared canary and manifest tooling discovers adapter-owned strategies and contracts from the same binary; exact Hermes development-source evidence cannot become a bare-release or live-model PASS.

## Problem description

The current daemon observes a fixed Claude/Codex pair in `app.rs`, renders fixed health fields and iterates a two-item `harness_states` constant. Doctor duplicates installed/setup interpretation and rendering by brand. Canary orchestration and Python report/manifest/release helpers repeat npm package names and two-brand selectors. Replacing these with another growing enum would miss the author's one-module-plus-registration criterion. At the same time, shipped strict Health and harness.states messages and semver evidence need frozen compatibility projections.

## Main challenges

Health must distinguish installation admission, selected-profile setup, actual attributed runtime and domain verification without replacing one with another. Old clients reject extra strict fields; old daemons cannot serve rich runtime identities. External canary scripts need a small explicit discovery contract but not a general installer/plugin framework. Manifest schema 2 already has semver rows, so exact build rows must live in a distinct collection and must be ignored by old readers. Native captures, model-free checks and model-backed acceptance are different evidence stages.

## Key decisions made

Use registry-keyed daemon observations, one strict negotiated `harness.health_v2` result, generic doctor iteration and a dedicated local `adapters --json` discovery document. Preserve old Health and harness.states wire shapes exactly. Keep schema 2 and add `runtime_contracts` plus `runtime_rows` as separate top-level collections; legacy `rows` and `contracts` retain their meaning. Adapter-owned canary descriptors select either existing npm-release mechanics with owned probe companions or an exact-runtime companion; missing installer/probe support is explicitly unsupported/inconclusive. Coordinator retains merge/final sweep/release ownership, and migration `.4` alone places v22 after CLI v19/v20 and invitation-rejection v21 have landed.

## Decision points

### Observation lanes and health vocabulary

Replace the pair/array in `HarnessObservations`, `ObservedBinary`, and `AdmissionReobserver` with a registry-ID keyed map in registry order. Each entry has executable identity, install observation/admission, declared receipt capability and adapter setup scope label, plus reuse policy/fingerprint supplied by the adapter. Reuse is valid only for unchanged declared observation inputs: Hermes profile/config/owned-assets inputs cannot reuse solely because the executable inode is unchanged. An unchanged reusable admission keeps its bounded observation; unknown/transient failures retry. Cancellation preserves the entire previous snapshot; never publish a partial pass. Health reads cached observations and bounded store summaries, never starts native version/setup discovery subprocesses on its request path. Existing scheduler pacing, cancellation and bounded log lines remain. Preserve main commit `021ac1ec` wake_batch_delay_ms=0 defaults in InstanceSettings/StoreSettings, explicit batching/retry overrides and the intentional legacy HealthSettings absent-field fallback; this work does not change them. Absorb main only at the root integration/freeze gate.

Vocabulary is independent typed axes, not one success bool: installation `unknown|not_found|present|unavailable`; enablement `unknown|not_applicable|disabled|enabled|unavailable`; admission `unknown|listed|schema_matched|optimistic|refused|unsupported`; callback observation `unknown|not_observed|observed`; runtime/domain verdict `working|new|broken|unavailable`. Observed means an honestly attributed callback/record for the declared scope, not PATH presence or plugin files. Schema-matched remains live-unverified; optimistic is informational with current legacy precedence. Receipt basis is an explicit string from supported provenance/adapter policy; working does not mean native receipt. Setup/native permission trust is a separate diagnostic, not inferred enabled from admission. Bounded details contain no tool/conversation content.

The daemon entry explicitly describes its own environment/default profile snapshot, e.g. scope `{ kind: "daemon_default", profile: null }`. It does not claim to inspect the invoking doctor's selected profile. Existing Claude/Codex daemon setup facts remain unknown because the elected daemon currently only probes installation; Hermes may supply bounded default-profile enablement through its adapter, otherwise unknown. A global runtime evidence summary is labeled `runtime_evidence_all_scopes`: current v2 persistence keys do not contain profile, so observed runtime evidence cannot establish selected-profile enablement or callback occurrence. Do not infer a local observed status by joining only harness ID. A future profile-specific evidence index is outside this work.

Keep the historical healthy/degraded rules for Claude/Codex and apply the same policy generically: not-installed is a note; transient/refused installation is a limitation; recipe-known-broken/below-floor is explained by its verdict rather than double counted; schema-matched limitation and optimistic note keep their semantics. Unsupported optional composer/canary facilities do not degrade health. Registry-driven cooperative wake/receipt wording replaces static recipes/name lists; Hermes no-composer/no-soft-poke remains explicit, without promising mid-turn wake. Legacy `Health.harness` stays a Claude/Codex projection, while existing overall health/notes/limitations can truthfully reflect other registered harness failures within current line caps.

### Strict negotiated wire and frozen projections

Add `HARNESS_HEALTH_V2 = "harness.health_v2"`, `Command::HarnessHealthV2` (no arguments) and `CommandResult::HarnessHealthV2(HarnessHealthV2Report)`. Both new report and all nested structs use `deny_unknown_fields`; map keys are bounded registered lower-case IDs. Report shape is `{ harnesses: BTreeMap<String, AdapterHealthV2Report> }`. Each adapter entry has exactly `scope`, `installation`, `enablement`, `admission`, `callback_observation`, `receipt_basis`, `limitations`, `notes`, `runtime_evidence`, `unattributed`, `hook_parse_failures`. State axes use the enums above with `detail: Option<String>` in a shared strict `{state, detail}` object. Scope is strict `{kind, profile}`; scope kinds are `daemon_default|runtime_evidence_all_scopes`, and the entry scope is daemon_default. Runtime rows themselves carry runtime_evidence_all_scopes so aggregate evidence cannot masquerade as a profile observation.

`runtime_evidence` is a bounded vector (20 newest records per adapter, deterministic identity/domain/contract tie-break) whose strict rows contain `identity` (the canonical runtime descriptor from `.2.3`, including identity key), `domain`, `origin`, `contract_id`, `state`, `source`, `line`, `notes`, `issue_url`, `last_seen_at`, `in_health_window`, `scope`. Required milestone source/state comes from the shared evidence/ladder model, never a health-specific second verification algorithm. Unattributed rows identify domain/origin/reason/time and are capped by declared descriptor count and store read limits. Cap limitation/note/detail strings at existing health text limits and permit no raw native body fields. The server handler uses registered descriptors, cached installation observations and `.2.4.1` bounded reads; budget/store failures yield explicit unavailable diagnostics or the existing advisory ApiError, never fabricated empty working results.

Advertise the capability only in the commit that wires its actual command handler; add a probe arm to `every_advertised_capability_has_a_handler`. Do not bump protocol version. Serialize existing `Health`, `HarnessHealth {codex,claude}`, `HarnessStatesReport`, `HarnessStateReport`, `DetectedVersion` and `VersionStateReport` exactly as before; add no strict fields. Legacy harness.states iterates adapters but emits only facts with that adapter's explicit legacy release projection. It can include an empty Hermes block (contract_id null, detected null, versions empty and available bounded unattributed/parse facts), but it cannot stuff a build hash/derived version into `version`, assign a single rich-domain contract to old contract_id or let rich verification imply legacy verification. Rich-only facts appear in v2. New doctor fallback explicitly says rich runtime evidence is unavailable on an older daemon; it never converts build identity to semver.

Considered changing Health fields directly or overloading harness.states were discarded because shipped strict readers reject additions or give build keys release semantics. A full health v2 replacement was discarded; only the harness subtree needs negotiated expansion.

### Local doctor and selected-profile separation

Doctor queries capabilities once, then v2 if advertised. If capability absent, use existing Health plus harness.states behavior and an explicit rich-evidence unsupported reason. If advertised request fails or returns wrong result, show unavailable with that cause rather than silently presenting fallback facts as complete v2. Failure is advisory and does not prevent the rest of doctor from rendering. Use one existing bounded doctor request budget, not one fresh unbounded budget per adapter.

Registry iteration calls adapter install/status inspection against the invoking process environment and explicit selected profile. `.5` supplies generic local status/diagnostic value types; `.6` supplies Hermes profile resolution and native config-only enabled inspection. The independent source audit `/private/tmp/herdr-hermes-readonly-boundary-review.md` supersedes the earlier feasibility inference: installed37daf85 has no complete official nonmutating structured runtime/effective-config/dispatcher-timeout boundary, including warm callbacks. Hermes local inspection remains Unsupported. Do not run native config-get/import/bootstrap or infer enabled/admitted from raw config; generic selected-profile diagnostics must report the missing boundary. A genuine upstream read-only API or separately reviewed/measured equivalent is a prerequisite; no new native experiments are authorized. Local result includes resolved profile/home, owned files installed, enabled, admission and diagnostic rows. Daemon result is kept under a separate labeled scope; no PATH/config-root/profile conflation. Text lists registry entries in stable order and distinguishes local setup/enablement from daemon installation and aggregate runtime evidence. Doctor JSON retains existing Claude/Codex hook keys and their meanings through adapter-owned compatible projections; other adapters add their ID entries. Brand-specific trust, allow-rule, prompt-suggestion and sandbox diagnostics are adapter-provided rows/projections, not core ID switches. Existing public JSON compatibility snapshots determine unchanged fields; normalized shared fields may be additive only in this non-strict CLI report. This leaf consumes `.5`'s status contract rather than redesigning setup transactions.

Automatic doctor repairs dispatch only actions declared safe by adapter policy through existing ownership/setup rules; native enable/trust/consent are manual instructions. Hermes enablement stays manual. Existing Claude consent and Codex sandbox-review behavior are retained in their concrete adapter policies. Doctor has no seat/binding/receipt mutation. An injected third adapter must render without a doctor edit.

### Same-binary tooling discovery and strategy ownership

Introduce local `adapters --json` with versioned strict schema `{schema_version:1, adapters:[...]}`; it never contacts the daemon or observes native installs. This avoids changing the shipped `contract-id --json` output or turning a scalar legacy contract ID into a multi-domain structure. Each entry has `id`, `display_name`, `host_kinds`, `setup_scopes`, `legacy_contract_id` (nullable), `contracts` (domain/origin/id/events/required_milestones using `.2.3` descriptors), `canary_strategy` (nullable). Registry metadata produces IDs/order; descriptor contract hashes preserve legacy bytes. Existing contract-id/version helpers retain syntax/legacy output; new tooling requires adapters discovery and may explicitly fall back to frozen legacy contract-id only when interrogating an old release binary.

Canary strategy is data returned by adapter's optional provider, not executable shell source: discriminant `npm_release|exact_runtime`, candidate kind `stable_release|exact_build`, optional npm package, optional model-key environment variable, and explicit repo-relative probe companion path plus artifact schema version. Npm-release uses existing stable candidate/bisect machinery; package and companion come from the descriptor. Exact-runtime does not enter semver bisection or call npm. This task may provide Hermes's native captured-runtime companion through `.6`; it must require an explicit isolated runtime/install input and record exact source identity. Generic routine canary must report unsupported/inconclusive if no install/probe inputs exist; it does not clone/install a new runtime automatically. Companion names/paths are validated bounded relative paths under declared `scripts/canary/adapters/`, and processes use argv with no shell interpolation. External companions are an explicit future harness exception to the Rust-module criterion; ordinary binary functionality still requires only module/registration.

Move genuine Claude/Codex probe details and model-specific handling to strategy-owned companions. Shared orchestrator selects descriptors, creates isolated env/work dirs, schedules bounded attempts and combines outputs without ID switches. All registry IDs accepted. `--harness all` selects all registered adapters; legacy `both` retains its explicit Claude/Codex compatibility selection; `all` is the registry-driven default and expands automatically. This historical selector projection is the only shared two-brand exception in canary selection. Unsupported strategy is a distinct inconclusive block with no candidates/verified_max, never `all_pass`/`no_candidates` success. Existing legacy npm probe outcomes remain compatible. Report model stage explicitly (`source_captured|no_model|live`) and permit exact identity alongside nullable release version; build reports never generate semver range/known-broken snippets. Shared version functions remain stable-semver utilities called only for stable_release strategies. Unknown model-key/no companion never triggers a guessed default. Routine leaf tests and final-SHA native callback probe use model tier off; root's separately authorized native acceptance owns model-backed work.

Companion schema 1 is one UTF-8 JSON object on stdout (maximum 65536 bytes, trailing whitespace only; stderr separately capped at 8192 sanitized bytes). Strict fields are `schema_version:1`, `harness` (registered ID), `attempt` (caller-issued ASCII token, maximum 64), `identity` (canonical runtime descriptor or null), `evidence_stage` (`source_captured|no_model|live`), `outcome` (`complete|inconclusive|unsupported|infra_failure`), `reason` (nullable sanitized text, maximum 512), and `domains` (maximum registry descriptor count). Each strict domain object contains `domain`, `origin`, `contract_id`, `successful_milestones` (unique subset of at most eight declared names), `violations` (maximum eight strict `{event,field}` pairs with declared event and field identifier bounded 64), and `outcome` (`compatible|contract_violation|inconclusive`). No raw callback/user/tool values are fields. Unknown fields or duplicate domains/milestones, wrong harness/attempt, invalid identity hash, undeclared descriptors and outcome/milestone inconsistencies make the attempt inconclusive, never PASS. compatible alone does not mean verified; the consumer requires all exact-domain milestones. Unknown identity cannot produce a runtime verified row.

The orchestrator invokes a validated companion with separate argv `--harness ID --attempt TOKEN --stage STAGE --work-dir ABS --binary ABS`, and optionally `--runtime-command-file ABS` for explicit exact-runtime input; all paths are isolated or explicit read-only source inputs. Model-key material is inherited only through the descriptor-named environment variable and never passed in argv/artifacts. The runner supplies one bounded subprocess deadline and kills/reaps its own child on timeout; the companion owns and reaps its descendants. Artifact index schema 1 has strict `{schema_version:1, attempts:[...]}` (at most 256 entries), each `{harness,attempt,identity_key,evidence_stage,result_path,capture_paths}` with at most eight relative paths under that attempt directory, no traversal/symlink escape, and maximum 256 characters per path. Identity_key must match result identity, and captures retain domain/origin/stage metadata; no filename reconstruction. Index maximum 262144 bytes. Existing legacy captures may be normalized into this interface by owned npm companions while retaining their old reports. Native/model-free stage is chosen from the requested probe tier and measured operation, never inferred from milestone completion. `.6` implements this fixed contract for Hermes.

Workflow dispatch harness input becomes free string default all rather than a fixed choice list; schedule selects all. Existing key environment assignments are credential provisioning for existing strategies, not the registry discovery authority. No publishing/push/release actions are run by this task. Existing publication ruleset controls stay intact.

### Schema-2 runtime rows and release interrogation

The audited Rust manifest reader parses a JSON Value, inspects schema and `rows`, and ignores unknown top-level fields; Python schema-2 validation likewise does not reject unknown top-level keys. Add `runtime_contracts` (adapter ID to domain descriptor list) and `runtime_rows` (distinct list), preserving old `rows` objects and `contracts` scalar map unchanged. Add old-reader fixture tests that include new collections and prove they are ignored. Never place build identities in old `rows` even with an extra discriminator: old parsers would read the version field.

A strict runtime row contains `harness`, canonical `identity`, `domain`, `origin`, `contract_id`, `status` (`verified|known_broken`), `evidence_stage` (`source_captured|no_model|live`), `source` (`canary|manual`), `required_milestones`, `successful_milestones`, `broken_event`, `broken_field`, `supported_since`, `issue_url`, `last_seen_at`. Key is harness/identity_key/domain/origin/contract. Identity hash must match its descriptor. Descriptors come from binary discovery; row milestone names must match the exact declared domain. A capture-only or incomplete milestone result is retained in probe artifacts, not a verified manifest row. A complete captured model-free domain may be verified with evidence_stage no_model; it never implies live receipt/model consumption. Never credit envelope success to native-shape domain. Contract violations alone produce known_broken, with existing unrelated setup/infra/flaky safeguards; unsupported/inconclusive/unclassified does not. Explicit manual rows retain source, stage and exact scope, and are not rewritten by the canary. Preserve baseline collections when the current probe cannot establish compatible descriptors; never drop exact rows on a semver-normalization failure.

Extend manifest reader with a separate validated domain-aware collection/index; legacy row lookup remains isolated. Runtime source/state derivation is shared with `.2.3`/`.2.4`, so build rows require exact descriptor/domain/origin/id match and never semver ordering. Keep total reader cap 262144 bytes and writer cap 80%; bounded runtime retention newest 50 identities per harness plus explicit manual/current recipe/known-broken protected rows, failing output cleanly if protected rows exceed cap. Failed parse leaves existing cache usable under current rules. Candidate maximum/ranges only read legacy semver collection.

Release-contract helper interrogates each built release's own adapters discovery. Old releases fallback to legacy contract-id and replay only representable Claude/Codex legacy captures; absent rich support means per-domain unsupported, not whole-release lack of legacy support. Replace filename regex identity reconstruction with indexed probe metadata (harness, exact identity, attempt, artifact path). Reject mismatched source identity/ambiguous attempt joins. Source capture files and test outputs retain stage/origin; release replay can establish schema compatibility only and cannot upgrade no_model to live. Infrastructure failure preserves baseline rows of every relevant collection; unsupported release domain never manufactures PASS and never erases unrelated domain rows. Release/main different contract descriptors produce separate exact-key rows. Report/helper readers select explicit collection/strategy kinds, never infer a build from the appearance of a version string.

## Numbered implementation leaves

1. **Registry observation and negotiated daemon health** owns `src/app.rs` observation/reobserver seams, `src/daemon/health.rs`, `src/daemon/harness_states.rs`, new focused daemon harness-health module if needed, `src/protocol/{commands,results,capabilities}.rs` health additions and the daemon command dispatch/builder wiring. Consumes `.1`, `.2.3`, `.2.4.1`, `.2.4.2`; exports strict HarnessHealthV2Report and registry cached observations. Owns no migration, native profile probing implementation or doctor/canary. Checks: fixed legacy wire snapshots; every advertised capability handler; cancel/reuse/atomic snapshot; third-adapter iteration; build-only Hermes excluded from old semver fields; bounded multi-domain rollup and unavailable store. Serialize protocol file edits with `.2.4.2`.
2. **Generic doctor with profile-aware local diagnostics** owns `src/cli/doctor.rs` and focused doctor tests only, consuming leaf 1 v2 wire and `.5` generic status/repair policy; `.6` supplies Hermes values. Checks: injected adapter rendering, local selected versus daemon-default/aggregate evidence separation, absent/wrong/failed v2 fallback, old Claude/Codex JSON/text/repair consent snapshots, no automatic Hermes enable/trust. CLI selector/profile parsing belongs `.5`; do not duplicate it here.
3. **Same-binary adapter discovery** owns the local adapters CLI command and strict schema-1 serializer, narrow command parsing/dispatch, and strategy descriptors in concrete adapter modules. Consumes `.1` and `.2.3`; exports IDs/contracts/strategy metadata and the bounded companion artifact schema. No install probes or daemon calls. Checks deterministic discovery, duplicate IDs, legacy contract-id unchanged and injected adapter. Hermes later supplies its concrete companion through `.6`.
4. **Rust runtime manifest reader and recorder lookup** owns `src/harness/manifest.rs` runtime collection validation/index, corresponding Rust fixtures, and narrow wiring of its lookup into the completed `.2.4.2` recorder/fetch path. Consumes `.2.3` and `.2.4.2`; exports the validated exact-domain lookup to leaf 1. No external canary or release generation. Checks old-reader ignored extras, exact descriptor/domain/milestone isolation, cache byte cap, no semver collapse or stage promotion. Recording initially uses an empty rich manifest source; this leaf replaces that source. No reverse producer dependency.
5. **Strategy-driven canary execution** owns shared canary orchestration, versions/report helpers, Claude/Codex companion mechanics, offline fixtures and workflow. Consumes leaf 3 discovery/artifact contract; publishes indexed probe artifacts to leaf 6. Missing Hermes companion/installer remains inconclusive until `.6` provides it. Checks dynamic all, frozen both compatibility, unchanged npm candidates/bisect, no-model labels, no semver range snippets for builds, bounded argv/path and process cleanup. This is one external runner operation; no Rust CLI or manifest reader ownership.
6. **External runtime manifest and release compatibility** owns scripts/canary/manifest.py and release_contract.sh with their fixtures/docs. Consumes leaf 3 discovery, leaf 5 indexed artifacts, and leaf 4 validated runtime row schema. Produces compatible runtime collections for the Rust reader. Checks legacy byte-stable rows, exact identity/stage/origin matching, old-release legacy fallback, infrastructure baseline preservation, protected retention and deterministic writer cap. Release interrogation is validation/serialization, with no publication.

Leaf 3 can follow foundation/model independently. Leaf 4 follows the model and recorder; leaf 1 follows leaf 4 and leaf 2 follows leaf 1 plus the future `.5` native status producer. Leaf 5 follows discovery; leaf 6 follows the runner and runtime row schema. Shared-file edits execute serially. Every leaf uses fmt, required per-change clippy and targeted filters; before integration default-feature check. No branch full-suite runs; coordinator owns final sweep/cleanup. Independent design/code review and exact final-SHA native measurement remain root gates.
