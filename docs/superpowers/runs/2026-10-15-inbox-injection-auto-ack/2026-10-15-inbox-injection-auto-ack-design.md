## Goal

Eligible hooks and channels deliver pending inbox content directly, and automatically settle existing receipt obligations for messages they deliver completely. Agents call `inbox` only when delivery leaves inbox content undisplayed or fails; normal successful delivery requires no explicit `ack` command, locally or across linked nodes.

## Problem description

The standard hook currently injects complete inbox rows but leaves receipt-required messages pending and prints an exact ACK command. Shared lifecycle text and ready commands also tell the agent to call inbox unconditionally, including after a complete injection or an empty read. This creates unnecessary tool calls and differs from default text inbox, push-channel delivery and hook-pull delivery, which already settle eligible complete displays automatically. The user's ruling extends automatic receipt settlement to all eligible complete native hook displays and makes inbox retrieval conditional on an incomplete delivery.

## Main challenges

A bounded hook read can be empty, complete, incomplete, unavailable, or deferred to a live channel; those states must remain distinguishable through rendering and output completion. Receipt claims must describe actual output rather than a read, settle only existing obligations, preserve binding-specific display progress and retain safe behavior on truncation, output failure and uncertain bookkeeping. Concurrent cross-node work replaces local settlement writes with journaled `receipt.settled` facts, so this change must use the common canonical settlement seam and be verified on a combined candidate.

## Key decisions made

Use an explicit neutral delivery-coverage result to drive fallback instructions, rather than infer completeness from whether a page or body was rendered. Standard native hooks claim full display only after output is written and flushed and the adapter confirms context was carried. Extend the existing `cooperative_hook_context` claim to receipt-action observation, using the same canonical settlement path as existing automatic display sources. Default sends keep their delivery rows and create no receipt. Preserve existing push-channel and transcript-confirmed hook-pull predicates. No blanket read ACK, no automatic invitation acceptance, no new wake policy and no increase to context limits.

## Decision points

### 1. Delivery coverage and fallback

Recommended: model the outcome of the eligible delivery attempt explicitly. Alternatives were retaining unconditional ready commands (violates the goal) and simply removing every inbox command (strands overflow and failures). The result distinguishes a complete known snapshot, incomplete content, failed/unavailable read, and delegated channel delivery. An empty successfully read page is complete. A nonempty page is complete only if every item in the selected pending stream is injected whole and there is no continuation, truncation or withheld item. Preserve page order and a complete prefix under existing row, raw-byte and escaped-byte limits. A first item that cannot fit produces a compact fallback, not silence. Pending invitations and warnings count as inbox content for coverage; injecting an invitation is informational and does not accept it.

An incomplete result emits one exact routed `inbox` command and instructions to follow its `next:` commands. A failed read that cannot establish complete coverage also permits this recovery command, even when the pending count is unknown; do not label unknown content empty. Missing negotiated capability is an unavailable delivery path. Quiet hooks with no changed attention remain empty. A lifecycle context may still carry required identity/routing/child restrictions, but full or empty coverage carries no pending-mail ready command, fallback command, unconditional `Use inbox` direction or redundant `No other inbox content` sentence. Read failures must not trigger polling instructions.

Completeness is relative to the bounded canonical snapshot/page used for this opportunity, not a global race-free assertion that no message can arrive later. A later arrival is delivered by the next eligible hook/channel opportunity. A live channel owns its delivery and suppresses duplicate standard-hook fallback; the standard hook must not call a skipped read complete. If a channel is unavailable or has fallen back to native delivery, the normal coverage rules apply. Channel pages that retain undisplayed content must either continue delivering within their existing bounded turn mechanism or provide one inbox continuation; an ordinary full page must not prompt a redundant read. Channel truncation must direct `inbox`, not `body` or history, so the complete-display automatic-ACK path remains available without a separate manual ACK. The bundled mod currently drains its whole tool-call queue; bound each injected tool-call batch by the existing delivery envelope (32 items / 64 KiB), retain the unselected queue tail, and emit the conditional inbox continuation when that batch leaves content undisplayed. Apply the bound to rendered content including framing and continuation, and keep an oversized first item from blocking all recovery. Successful completion/ACK claims cover only the fully injected selected prefix, never the retained tail. The retained queue can continue through existing later delivery opportunities; a fallback read racing that delivery is at least once and canonically idempotent.

### 2. Successful display and automatic receipt ACK

Recommended: reuse canonical automatic settlement with a source that honestly describes each delivery predicate. Alternatives were using `AckMessages` as if the agent explicitly acted (false provenance), or changing cursor advancement to settle receipts (conflates presentation with receipt authority). Standard hooks collect exact IDs for canonical eligible pending receipts alongside complete message IDs while rendering. Once stdout is fully written and flushed, and the adapter's encoder reports that context was actually carried, submit only those complete candidates under the original connected top-level binding claim. A hook that outputs no context, a subagent callback, an encoding/write/flush failure or a truncated body produces no receipt claim. A lifecycle hook qualifies if it successfully emits complete context; being inside an active turn is a separate wake-bookkeeping property.

The daemon revalidates the claim and exact IDs against its canonical transaction view, including A2, role, liveness, addressed receipt, and allowed delivery source. The operation is idempotent and settles only pending agent receipt obligations. Already settled or ineligible rows do not become new obligations. Non-ACK messages advance ordinary presentation bookkeeping only. Invitations still require explicit acceptance or rejection. There is no implicit agreement, adoption or task completion. Preserve `in_turn` and invitation bookkeeping where applicable; automatic receipt settlement must not turn cursor advancement into authority or alter invitation wake eligibility.

Extend CompleteInboxDelivery with an optional default-empty exact receipt-candidate list, permitted only with via=hook_context and negotiated through an additive capability; omit the extension for older daemons. Its existing messages list remains lazy completion and the new list remains receipt completion. The request accepts a receipt-only hook completion without synthetic lazy IDs. It must not accept the hook claim through a source intended for transcript-confirmed hook-pull delivery. Payload digests must freeze the source and original full caller claim. Old daemons never receive unsupported claims. They may leave receipts pending for a later supported delivery or text inbox and issue conditional retrieval recovery, rather than falsely report automatic settlement. Do not add harness names to neutral core branches.

### 3. Failure, retries and oversized content

Recommended: at-least-once delivery and idempotent post-output settlement, matching the existing bounded hook completion model. Alternatives were marking displayed before output (can lose unseen mail) or retaining a permanent manual ACK requirement after every uncertain response (defeats normal automatic delivery). Post-output bookkeeping failures leave unsettled messages eligible for later automatic delivery. A response lost after canonical commit may cause a duplicate offer but not a second receipt transition. Retain existing cursor safety so a cursor cannot hide an unacknowledged obligation. Do not introduce an unbounded retry or disk journal in the hook hot path.

Default own-seat text inbox keeps its current write-and-flush predicate and fully displayed candidate filtering. JSON/machine inbox, explicit foreign/selector reads, history/read/body/search, check-in metadata and all subagent reads remain receipt-read-only. A long message displayed only as a partial body/chunk is not ACKed by injection. Its fallback uses the existing bounded text-inbox continuation behavior; only when that path has established complete display according to its existing safe continuation rules may it settle. Retain explicit `ack` for deliberate exceptional workflows that read an exact ID through a read-only command, but do not instruct it after normal successful hook/channel/text-inbox delivery.

### 4. Provenance and trust policy

Recommended: extend `cooperative_hook_context` from lazy completion claim to receipt action observation as well, because the evidence is the same complete output emission. Alternatives were reusing `cooperative_inbox_display` (a different action) and using the transcript-backed `cooperative_hook_delivery` value (stronger and different evidence). Update TRUST-POLICY.md A3, A5, A8 and accepted-limit prose that currently says standard hooks never ACK, plus the old mod-only exception wording, in the same implementation commit that adds the source. The claim states that a top-level standard hook wrote and flushed context containing the complete body, not that the harness ingested it or that the model consumed it. Preserve the binding's observation provenance separately. Keep the hook-pull source restriction: its own transcript confirmation still uses `cooperative_hook_delivery`.

### 5. Sibling bindings and wake behavior

Recommended: a receipt remains seat-level and is settled once by the first eligible top-level display; read cursors, delivery offers and display marks remain binding-specific. Alternatives were settling only the displaying binding's synthetic receipt (would invent a different receipt model) and advancing all siblings when one displays (loses their context). A sibling must still receive messages in its own unread stream after another binding settles the seat receipt, subject to existing stream rules. Do not merge/end/move bindings or use a sibling's display as evidence that the main session consumed a message. Preserve the one-process composer policy and the existing wake contract: idle threshold only, no busy nudge, invitations unchanged. Verify that receipt settlement clears receipt-based attention without incorrectly suppressing a sibling's independent delivery-row wake.

### 6. Cross-node integration

Recommended: every automatic receipt source calls the common canonical receipt settlement authoring path. Alternatives were direct receipt SQL (bypasses replication), or a new hook-specific sync fact (duplicates the existing model). The concurrent `super-auto/cross-node-sync` branch has `src/store/receipts.rs::settle_pending` authoring `receipt.settled` and `src/sync/facts/receipt.rs` applying it through `materialize_settlement` under recipient-seat-home authority. Hook auto-ACK must join that path, preserving source/provenance in its `SettleHow` representation and remote materialization. Inspect and adapt its source validation/serialization if required. Text inbox, mod and hook-pull settlement must continue sharing it. A delivery with no receipt produces no settlement fact.

Implementation on this branch must not edit the peer's worktree or merge its entire unfinished epic merely to obtain a test seam. Coordinate changed source representations and paths with the p2p tab. Local focused tests establish that the new source enters the canonical writer. Before claiming cross-node readiness, materialize a disposable combined candidate containing the relevant peer work, review its merge integration, then run two-node tests: node A sends an ACK-required message to a top-level recipient on B; complete delivery by native hook, text inbox, push channel and hook-pull respectively makes A observe one terminal ACK with honest source, B's receipt settles, and overdue conditions clear. Repeat settlement and replay/duplicate fact delivery without duplicate terminal effects; partition/reconnect and reordered prerequisite application converge. Partial/failed output and read-only views author no settlement. If combined code is unavailable, report that cross-node verification remains pending rather than claim it passed. This dependency does not authorize altering the peer's branch or deploying either branch.

### 7. Files and compatibility

Recommended: contain the change in existing delivery seams. Likely touched areas are `src/cli/hook_inbox.rs`, `src/cli/hook.rs`, shared context/ready-command assembly in `src/harness/mod.rs`, neutral protocol/authority/capabilities and service/store settlement code, existing harness hook-pull/channel renderers where they emit continuations, bundled mod JavaScript, embedded skill and relevant README/help/handoff startup wording. Enumerate all model-visible manual ACK/inbox recipes before editing; preserve a fallback in startup/handoff when there is no trusted successful injection and preserve exact routed command selection. Do not remove a fallback merely because a hook might eventually run. Registration/setup may need fixture expectation updates; do not write real user configs.

Shared guidance should state once per session that complete hook/channel/text-inbox displays automatically ACK existing requested receipts, fallback is conditional on incomplete delivery, read-only commands stay read-only, and invitations are separate. Per-message framing stays a header plus body. Target new overflow/failure retrieval text at one line no longer than 160 fixed bytes plus the routed command (routing length already variable); no per-message ACK boilerplate. Any additional model-visible diagnostics must state their actual fixed size in the commit and be checked against the token-efficiency rules. Preserve existing context limits and old wire compatibility; introduce no schema change unless source storage requires one.

### 8. Verification and acceptance

Recommended: focused unit, service/store and real hook-process tests; alternatives were asserting only rewritten strings (misses settlement) or a live paid harness run as the first test (unnecessary and insufficiently isolated). Cover full ACK-required injection with no inbox/ACK directive and terminal receipt, empty injection with no retrieval directive, mixed ordinary/ACK/invitation/warning page, exact size boundaries and escaped text, row overflow, oversized first item, later partial item, missing capability, failed/timed-out read, write/flush/encoder failure, and lost completion response followed by idempotent re-offer. Cover default no-receipt sends, read-only selectors/machine/subagent paths, disconnected/stale binding refusal, lifecycle versus in-turn display, same-seat siblings, and live-channel suppression/fallback. Existing mod and hook-pull complete/truncated predicates must remain green.

Run focused tests with `nice cargo test --locked --all-features <filter>`, `cargo fmt`, `nice cargo clippy --locked --all-targets --all-features -- -D warnings` and `scripts/check-harness-neutral`. Before merge run `nice scripts/check-default-features`. Respect the temporary restriction on routine full-suite runs, warm worktree build, one-minute incremental/lint budgets and five-minute full-suite budget. All process tests use owned isolated helpers and scratch paths; stop helpers before reporting, and run scoped leak checks after any full/integration sweep. Cross-node verification is a separately stamped combined-candidate result as described above. No release or live wake-e2e is part of this change unless a release is separately requested.

## Scope and non-goals

Scope includes native hook coverage state, automatic receipt settlement for complete native context, channel fallback consistency, documentation/trust policy and cross-node settlement integration verification. Preserve sender receipt selection, priorities/deadlines, invitation consent, native harness limits and read-only command semantics. No new polling, blanket historical read ACK, receipt creation for ordinary sends, receipt proof of cognition, wake-policy redesign, deployment or release.

## Key abstractions

**DeliveryCoverage** — new neutral enum, records whether a delivery opportunity leaves content requiring retrieval.
- Owns: complete snapshot, incomplete delivery, unavailable/failed delivery, and delegation to a live channel as distinct outcomes. Empty successful reads are complete; continuation, truncation, withheld items and exhausted rendering budgets are incomplete.
- Hides: whether the limitation came from page bounds, context encoding, channel batch selection or read failure.
- Must not: infer coverage from an empty optional offer, ACK anything, or describe delegation as a completed read.
- Relationships: native hook readers/renderers and channel batch selection produce coverage; shared ready-command/context assembly consumes it to emit one routed inbox continuation only when needed. Existing adapter selection remains in the harness registry.
- Lifecycle: request-local value, owned by the delivery attempt and retained until final context assembly; no persistent or global state.
- Errors: failed/unavailable reads preserve unknown coverage; delegated delivery suppresses duplicate native fallback without claiming success.

**CompleteInboxDelivery / LazyCommit** — extended: use the existing post-output completion request for native-hook receipt candidates as well as lazy completion. Add an optional, default-empty exact receipt-candidate list, negotiated through a new additive capability. Receipt candidates are permitted only with via=hook_context; an absent source retains existing default-text-inbox semantics. The request digest includes candidate list, source and original full caller claim. LazyCommit submits candidates only after successful write, flush and adapter confirmation that context was carried; old daemons never receive the new field. Retain separate displayed-message and invitation lists for binding-local cursor and in-turn bookkeeping.

**Canonical receipt settlement** — extended: the CompleteInboxDelivery handler revalidates native-hook candidates against the canonical transaction view and delegates eligible pending receipt transitions to the same settlement writer used by text inbox, mod and hook-pull delivery. It records cooperative_hook_context, preserving binding observation provenance. It must not route through transcript-confirmed DeliveryConfirm, mislabel the action as explicit Ack, duplicate receipt SQL, or advance siblings' cursors. The cross-node writer authors the existing receipt.settled fact; settlement-source serialization and remote materialization preserve this provenance. Complete lazy display and receipt settlement remain distinct operations even when carried in one request.

Variation: delivery mechanisms and context encoders vary by harness through existing adapter registry and policies; coverage is a fixed result set represented by the neutral enum. Receipt evidence varies by supported source through existing canonical settlement entry points, with native hook completion distinguished from transcript-confirmed hook-pull delivery.

Walk-through: a hook reads a page, selects a complete prefix and records coverage plus exact completion candidates; shared rendering adds an inbox continuation only for incomplete/unavailable coverage; successful output submits negotiated completion; the daemon settles eligible receipts once and advances only the displaying binding's stream. A future harness adapter reuses coverage and native-hook completion through its registration; it adds no receipt-writing path.

Digest:
- DeliveryCoverage: owns retrieval necessity for one bounded delivery opportunity; new outcomes belong in the neutral enum and shared fallback rendering; callers never infer completeness from missing rendered content.
