## Confirmed findings
- [Should-fix] §1 Row shape, Constraints (`length(raw) <= 524288 + header bound`); §3 'Steps (row copy)' and 'Failure'; §4 known-layout ingest (`raw = canonical_bytes()`) — The CHECK's upper bound is written as `524288 + header bound` and the bound is defined nowhere; a valid HTJRNL01 entry can exceed PAYLOAD_MAX by about 155 KiB of deps and needs, so a bound read as a small fixed header makes the delta 0005 row copy fail and roll back on every open, and refuses valid known-layout ingest after migration. [lanes: premortem, completeness, domain:database-schema-migrations]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Spec line 32 is the only mention of the bound; seat searches of the spec for "header bound", PAYLOAD_MAX, DEPS_MAX, NEEDS_MAX and 524288 found nothing else. OPAQUE_MAX_BYTES (line 86) applies only to unknown-layout raw. The CHECK text is replayed verbatim into `expected_objects` and audited by `verify_at`, so it must be a fixed number fixed at design time, and changing it later needs another table rebuild. src/sync/envelope.rs: PAYLOAD_MAX = 524288 (line 35), DEPS_MAX = 4096 (line 34) at DEP_LEN 28 (about 114,690 bytes), NEEDS_MAX = 256 (line 33) at up to about 162 bytes each (about 41,474 bytes), KIND_MAX 64, validation at lines 320-334 admits those counts. A maximal canonical entry is about 680 KB, about 156 KB over 524288. `Body::canonical_bytes` sizes its buffer as `Vec::with_capacity(160 + deps.len() + payload.len())`, which invites a ~160-byte reading of "header". Consequence as specified: §3 copy inserts every schema-4 row into journal_new; one large-deps row violates the CHECK; §3 Failure rolls the delta back ("leaving the store at schema 4"); this binary has no other path past delta 5, so it fails the same way on every open. §4 ingest would also reject envelopes that pass Envelope validation. §7 has no maximal-entry fixture ("representative rows", "every builtin fact kind"), so tests would not catch a wrong value.
  severity note: all three seats rated Should-fix. Floor considered and not applied: the failure is a rollback, the store stays at schema 4 and the previous binary still opens it, so there is no data loss and no irreversible migration; and the spec is underspecified rather than wrong, since the constants exist in code for a careful implementer to derive.
  fix-shape hint: Name the bound as a constant derived from the envelope limits (68-byte prefix + hlc + kind + kind_version + DEPS_MAX×DEP_LEN + creates + NEEDS_MAX×needs-key + PAYLOAD_MAX, or max(that, OPAQUE_MAX_BYTES)), write the number into §1, and add a maximal-size row (largest payload plus DEPS_MAX deps plus NEEDS_MAX needs) to the §7 migration fixture and a known-layout ingest test.
