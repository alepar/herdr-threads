## Confirmed findings
- [Blocking] §3 Migration steps 1-4 ('With PRAGMA defer_foreign_keys=ON … Drop the old tables, rename the new ones … Run PRAGMA foreign_key_check, which must be empty') — The §3 rebuild (defer_foreign_keys=ON, copy into journal_new, DROP journal, RENAME) fails at COMMIT with 'FOREIGN KEY constraint failed' on any store with thread_registers or sync_reissues rows, because the connection runs with foreign_keys=ON inside BEGIN IMMEDIATE and the DROP's implicit DELETE increments the deferred-violation counter that the rename never clears, even though foreign_key_check returns empty.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: All three seats reproduced it with sqlite3 3.51.0 using the spec's exact sequence: foreign_key_check returned no rows, then COMMIT gave 'FOREIGN KEY constraint failed (19)'. src/store/connection.rs:918 sets foreign_keys=ON before schema::initialize; src/store/schema.rs:369 runs each delta inside BEGIN IMMEDIATE, where PRAGMA foreign_keys=OFF is a no-op. https://www.sqlite.org/foreignkeys.html §5: 'the DROP TABLE command performs an implicit DELETE … an error is reported when the user attempts to commit the transaction'. The real user store is at schema 4 with 59 thread_registers rows. Fresh stores and the empty in-memory expected_objects replay do not show it.
  severity note: floor — violation of the artifact's stated core purpose (the migration cannot commit on any populated store).
  fix-shape hint: Give the delta runner a way to turn foreign_keys OFF outside the transaction for this delta (and run foreign_key_check from Rust before turning it back on), or restructure the rebuild so no referenced parent table is dropped.

- [Blocking] §1 Constraints ('CHECK(length(raw) >= 68)') vs §3 step 2 ('INSERT … SELECT all rows with raw set to an empty placeholder, rejected later') — Step 2's INSERT…SELECT with raw set to an empty placeholder contradicts §1's CHECK(length(raw) >= 68) on the new table, so the copy fails on the first row of any non-empty store.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Spec §1 line 33 requires CHECK(length(raw) >= 68) on journal and 'the same CHECK' on journal_forked; §3 step 2 inserts raw = empty placeholder; line 62 says the post step 'asserts that no row has an empty raw'. SQLite evaluates CHECK per row at INSERT. Ground seat reproduced with sqlite3 3.51.0: `insert into n select id,v,x'' from p` → 'CHECK constraint failed: length(raw)>=68 (19)'. defer_foreign_keys defers only FKs, not CHECKs.
  severity note: seats rated Should-fix/Nit/Should-fix; lifted under the core-purpose floor because the migration as specified aborts on the first row of every non-empty store. The fix is small, but the spec text as written cannot be implemented.
  fix-shape hint: Use a placeholder that satisfies the CHECK (for example zeroblob(68)) and have the final assertion test for that placeholder, or compute raw before the INSERT; state which.

- [Should-fix] §2 ('an unknown-layout row is inserted with apply_state='parked_unknown' and a NULL projection … The distinction is made in one place: the apply head scan reads the projection-NULL flag'; Discarded: 'a new apply_state value') — Reusing apply_state='parked_unknown' for projection-NULL rows breaks existing consumers outside the apply head scan (startup replay and operator replay read kind as non-null String, the unapplied status page, parked_unknown counters), so the 'one place' claim is false and the status surface changes.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/store/apply.rs replay_candidates (~1096-1133) selects p.kind, p.kind_version FROM journal WHERE apply_state IN ('parked_unknown','parked_dep') and reads them with r.get::<_, String>(2) and r.get::<_, i64>(3); a NULL projection gives InvalidColumnType → store_error, failing the ReplayScope::Startup pass at daemon start and every ReplayScope::Unapplied operator replay. src/store/sync_status.rs:197-210 (unapplied page) reads j.kind as String over the same states. parked_unknown counters (sync_status.rs:165, :251; journal.rs:266) now include stalled opaque rows that 2.3.0 kept in journal_opaque, contradicting 'keeping the 2.3.0 status surface'.
  fix-shape hint: Enumerate every apply_state='parked_unknown' reader; add a projection-NULL exclusion or Option reads in replay_candidates and the status page, and decide explicitly whether counters include opaque positions.

- [Should-fix] §5 Promotion ('It is then served as Known to every peer, because a known projection exists and its canonical bytes equal raw by hash. If the projection's re-encoding were not equal to raw for a future layout, that layout's own serving rules apply'); §4 ('WireItem::Known from the projection') — Serving a promoted entry as WireItem::Known built from the projection re-encodes it as HTJRNL01, which never matches raw/hash for any promotable (non-HTJRNL01) layout including the §7 HTJRNL99 test, so every peer (including 2.1.1) gets a hash-mismatching entry; 'that layout's own serving rules apply' names no mechanism.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/sync/envelope.rs:874 asserts a promotable layout's magic != MAGIC (HTJRNL01), and Body::canonical_bytes always writes the HTJRNL01 magic; the LayoutParser doc (~840) says Envelope::verify 'does not apply' to a parsed foreign layout and that 'How a promoted entry is stored and served is ht-j87z.13's decision'. Promotion only ever touches non-HTJRNL01 rows, so the §5 premise is false by construction and the hedge covers the only case that exists. The §7 promotion test checks local apply only. The refute seat's REJECT (production promotes nothing this release) is answered by the majority: the §7 HTJRNL99 test row itself would serve a hash-mismatching frame, and no serving rule is defined.
  fix-shape hint: Serve Known only when canonical_bytes(projection) == raw, otherwise serve Opaque from raw; add a peer-receives-promoted-entry assertion to the §7 promotion test.

- [Should-fix] §3 ('It sets raw through a migration-only exemption marker') vs §1 ('journal_immutable forbids changing … raw … always') — The 'migration-only exemption marker' that lets the post step UPDATE raw despite the 'always' immutability trigger is undefined (form, visibility, removal), and any realisation inside the audited trigger text becomes a permanent bypass of raw immutability.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)

  fix-shape hint: Define the mechanism — simplest is to create journal_immutable after the post step runs, or insert raw directly into journal_new from Rust so no exemption is needed; otherwise specify a one-shot marker and a post-commit assertion that it is gone.

## Rejected (with reason)
- §3 ('Any mismatch aborts the migration with StoreCorrupt and the store stays at schema 4') — No diagnostics/quarantine/recovery after a StoreCorrupt abort. Rejected 3/3: fail-closed abort is the stated design (Key decision 2, §7 test); the transaction rolls back and 2.2.1 still opens the schema-4 store; the hlc-clamp and check_payload-drift examples are unverified. Residual nit: the error should name the failing log and counter.
- Key decision 1 ('Delta 0005 is rewritten in place (unreleased; no store has applied it outside test fixtures)') — Dev/dogfood stores at schema 5 become IncompatibleSchema. Rejected 3/3: `git show v2.2.1:src/store/schema.rs` has no 0005; the only affected stores are throwaway dev builds of an unreleased branch, an accepted tradeoff the spec states. Residual nit: one-line note that schema-5 dev stores must be recreated.
- Main challenges (d); §1 trigger ('the projection columns unless every old value is NULL (promotion)'); §5 — Promotion exemption only enforces write-once, promote() does not re-verify. Rejected 2/3: promote parses raw itself, raw/hash stay immutable, SQL cannot hash a new layout, trust model is cooperative; ground seat's Nit (add a canonical_bytes == raw assertion in promote) is a cheap hardening already implied by the confirmed §5 serving finding.
- §1 Constraints ('length(raw) <= 524288 + header bound'); §4 ('OPAQUE_MAX_BYTES applies to unknown-layout raw') — Header bound undefined; DB-level opaque cap dropped. Rejected 2/3: the constant is derivable from envelope.rs limits (max ≈ 680 KB) and a wrong value is caught by the migration's own hash gate and tests; the opaque cap is enforced at ingest by check_opaque_size, and the spec never promised a DB-level cap. Ground seat's Should-fix (pin the number, decide on a projection-NULL-conditional CHECK) is addressed by the majority; carry as a documentation nit for the implementer.
- §3 ('NodeDelta { version, sql, post: Option<fn(&Transaction) …> }') — post hook does not fit the raw BEGIN IMMEDIATE runner; expected_objects replays only delta.sql. Rejected 3/3: adapting apply_deltas is the named implementation work; the spec never says the post step creates a persistent schema object.
- §3 (one transaction; post step over 'every row'); §1 Row shape — No time/space/progress/busy-timeout analysis. Rejected 3/3: atomicity is a stated requirement; the local store is 1576 rows / ~2.3 MB; a SQLITE_BUSY or SQLITE_FULL rolls back to schema 4 as every delta already does.
- Goal / §1 Row shape / §4 ('Known-layout ingest stores raw = canonical_bytes()') — raw doubles storage per known row; NULL raw for known rows not weighed. Rejected 3/3: 'raw BLOB NOT NULL on every row' is the stated goal and the user's explicit choice (mQ0V2b8xmSWQ); NULL raw would contradict bytes-first and lose the SHA-256(raw)==hash exactness proof.
- §1 ('the CHECK ties them to raw through an ingest-time verification (EntryPrefix)') — 'CHECK' wording is loose. Rejected 3/3: the sentence names its own mechanism (ingest-time EntryPrefix verification); no schema-level guarantee is claimed; core SQLite has no SHA-256. Wording nit only.
- §3 ('migration-only exemption marker') — Same-database rule rules out a TEMP marker. Rejected 3/3 on materiality: the external fact is true (seats ran sqlite3: 'trigger tr cannot reference objects in database temp'; https://www.sqlite.org/lang_createtrigger.html), but the spec never says the marker is TEMP. The fact is folded into the confirmed exemption-marker finding's evidence.
- §5 ('The promoted entry's raw and hash are untouched'); §4 ('their bytes are equal by hash') — J3 (src/store/sync_status.rs:408) would flag a promoted non-HTJRNL01 row. Rejected 3/3: production promotes only HTJRNL01, whose re-encoding equals raw; the future-layout case is explicitly deferred by §5; salvage reads only schema-4 HTJRNL01 rows. Overlaps the confirmed §5 serving finding.
- Goal vs §4 Discarded ('the projection is authoritative for known layouts') — Two sources of truth; no read/serve-time consistency check. Rejected 3/3: §4 discards serving from raw on purpose; equality is enforced at ingest and migration; journal_immutable forbids any later projection change; local-corruption detection is out of scope under the cooperative trust model.
- §1 ('Their projection columns become nullable, all-or-none per row') — needs DEFAULT '' not removed. Rejected 3/3: the rebuilt tables are fresh DDL with `needs?` NULL for unknown layouts; a leftover default would fail the all-or-none CHECK loudly on the first opaque insert.
- §5 Promotion step list — Promotion skips the HLC fold and skew accounting. Rejected 2/3: production promotion happens only at store open, where journal::open's Hlc::resume (MAX(hlc)) covers the newly readable hlc; runtime promotion is the test hook; skew is diagnostic. Ground seat's Should-fix (src/store/journal.rs:1713-1751 fold vs :1730 'No HLC fold') is addressed by that ordering argument; residual nit: state that promotion at open runs before Hlc::resume.
- §3 ('verify passes against the log's genesis public key where the genesis is known') — Today's verify may be stricter than historical ingest rules. Rejected 3/3: duplicate-key rejection has been in src/sync/envelope.rs since v2.0.0 (commit 359ebe618), the same release as the journal write path; no tightened rule is named.
- §4 resync salvage bullet ('salvage detects schema 4') — Schemas 1-3, new schema 5 and superseded schema 5 not covered. Rejected 3/3: existing salvage (src/sync/resync.rs ~445-476) keys on a missing table/column, not a version number; the new layout reads through the same StoredEntry decoder; the journal_opaque layout was never released. Wording nit.
