## Confirmed findings
- [Should-fix] §Delivery model, Wake; §Key abstractions lazy_delivery (`wake_frontier` becomes "newest pending row admitted by T") — The T-filtered wake frontier is unspecified within a bound. Today's frontier and discovery probe scan only the newest 1000 pending rows, so a p0 row behind a large p1 backlog never wakes the seat.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/store/lazy_delivery.rs:928-941 `wake_frontier` runs `ORDER BY r.ordinal DESC LIMIT ?2` with PENDING_SUMMARY_CAP = 1000; `has_wake_rows` uses `LIMIT 1000`. Under wake_on=all every row was eligible so the window was harmless. The spec makes every non-ACK message (default p1) a delivery row and defaults T to 0, so a >1000 p1 backlog on an idle seat is the normal state. The inbox-merge subspec adds the v47 `(seat, priority, decision_seq, ordinal)` index for inbox seeks only and names the "p0 behind a large p1 backlog" hazard for the inbox; nothing says the wake frontier uses it. Root Testing covers "wake frontier at T = -1, 0, 3" but no backlog larger than the window.
  fix-shape hint: State that `wake_frontier` and `has_wake_rows` find the frontier by an index seek on the v47 index (one seek per admitted priority, or equivalent), never inside a newest-N window; add a store test with one p0 row behind more than 1000 pending p1 rows at T=0, asserting the candidate and the query plan.

- [Should-fix] §Key abstractions, NudgeThreshold "the three sites that branch on `WakeOn` today" — Raw-SQL `wake_on='all'` readers (`note_published`, `has_wake_rows`, and the `oldest_pending_at` batching) also decide wake work. They are not in the inventory; left unchanged, a p0 delivery row for a T=0 seat schedules no wake.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (refute seat REJECT, outvoted) / ground ✓)
  evidence: src/store/lazy_delivery.rs:978-985 `note_published` inserts wake_work only `WHERE ... s.wake_on='all'`; :962-973 `has_wake_rows` gates on `EXISTS(SELECT 1 FROM seats WHERE id=?1 AND wake_on='all')`, called as the discovery probe from src/store/attention.rs:1577. The migration freezes `wake_on` ('nudge' for default seats). The spec's Wake section names only `wake_seat_attention` and `wake_frontier`. These are set-based SQL statements that need the per-row `p <= T` comparison inline, which the NudgeThreshold "callers never compare priority against T inline" rule forbids; the spec does not resolve that. Refute seat dissent: the "no longer read for decisions" rule implicitly covers these sites. Majority: the enumeration and the Wake section omit them, and the inline-SQL conflict is unaddressed.
  fix-shape hint: List `note_published`, `has_wake_rows` (and `oldest_pending_at`) as sites to convert; say how set-based SQL obtains T (for example a SQL fragment owned by NudgeThreshold joined on `seats.nudge_threshold`); decide whether batching uses the oldest admitted row.

- [Should-fix] §Compatibility and migration, Schema: "new rows write `delivery_mode` = `ordinary` iff the message has explicit ACK recipients"; §Delivery model "every audience member gets a row ... except explicit --require-ack recipients" — A mixed ACK message (delivery_mode='ordinary' with lazy_recipients rows for non-ACK members) is aborted by existing triggers, and the many `delivery_mode='lazy'`-gated queries are not inventoried.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: migrations/0026_lazy_message_delivery.sql trigger `lazy_recipient_source` (BEFORE INSERT ON lazy_recipients) raises 'lazy recipient source mismatch' unless `p.delivery_mode='lazy'`; `lazy_recipient_display_published` raises 'unpublished lazy delivery cannot complete' unless `m.delivery_mode='lazy'`. No later migration replaces them. First `send --require-ack X` into a group after v47 would abort its transaction. Seventeen `delivery_mode='lazy'|'ordinary'` SQL predicates exist (wake_frontier, oldest_pending_at, pending_lazy, invitation_content SQL, handoff checks requiring Ordinary); the spec's v47 list names only new columns and the priority immutability trigger.
  fix-shape hint: Have v47 drop and recreate both triggers on a priority or row-presence basis (or write `delivery_mode='lazy'` for the delivery-row side of a mixed send); list the `delivery_mode` SQL readers to replace; add a mixed-ACK test (receipt for the explicit recipient, rows for the rest, display and wake work).

- [Should-fix] §Delivery model, Ordering: "Out-of-order display within a thread is safe because each delivery row records its own displayed state; the binding read cursor only advances over the contiguous displayed prefix" — Pending and unread predicates are driven by the binding read cursor, not per-row displayed state, so a displayed higher-priority row behind an undisplayed older row stays pending and is re-offered. [lanes: domain:message-queue-delivery]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/store/lazy_delivery.rs `binding_lazy_unread_sql!` defines unread as `m.sequence > COALESCE(binding_cursors.seq,0)` plus scope; its doc comment says post-V34 delivery predicates never read `lazy_recipients.state`. src/store/read_cursors.rs:337-387 `advance_through_displayed_with_change` stops at the first receivable row not in `displayed` and not display-ACKed. With priority-first order and 32-item/64 KiB pages, p0 seq 10 displayed before p1 seq 5 leaves the cursor below 5 and seq 10 still unread, so it is re-offered (bounded only by the re-offer ledger). The spec asserts safety without analysis; the tree snapshot only says "verify advance_through_displayed".
  fix-shape hint: Either make the pending/unread predicates (seat and binding level, hook and accept paths) also exclude rows with their own displayed state, or constrain priority paging so the displayed prefix stays contiguous; add an out-of-order paging test in one thread.

  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)

## Rejected (with reason)

At most widen the stderr note to mention receipts.
- §Delivery model, Wake "raising T schedules at most one wake for the newest already-pending eligible row (D2)" — high-water memory gives zero wakes when a newer row already woke the seat — rejected 3/3: D2 says "can wake once" and the Wake section "at most one"; zero is within contract. Rule 3 delivers every pending item on the woken turn, so the older row is normally already consumed.
- §Delivery model Wake / §Surfaces Watch stream — Channel (Claude mod) seats have no mechanism for D2's raise-T wake — rejected 2/3: src/service/mod_channels.rs:1001 `wake_suppressed` is real, but rule 6 makes who wakes per-harness, D2 is permissive, and held items arrive next turn. - §Delivery model Wake — no trigger re-evaluates wake work when T changes — rejected 3/3: `nudge-threshold` is "a cooperative accountable mutation as `wake-on` is today", and `set_wake_on` (src/store/seats.rs ~5328) already calls `wake::note_new_attention` on change.
- §Delivery model, Ordering — strict priority with bounded pages starves p5-p9 — rejected 3/3: strict order is the approved D11 key; displayed rows leave the pending set, so starvation needs sustained >32 p0/p1 items per turn, which the cooperative same-user model does not target; rule 3 states no latency bound.
