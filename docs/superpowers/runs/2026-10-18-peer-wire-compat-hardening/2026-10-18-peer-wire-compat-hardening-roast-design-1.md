- [Should-fix] §2 The opaque entry: "causal apply of that log stops at it and later entries of the log park as `parked_unknown` does today ... this is the same outcome one level lower" — The parked_unknown precedent is false: parked_unknown advances applied_through, so stopping the log is new, stricter behaviour whose cross-log blast radius through deps/needs is not analysed.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (voted REJECT, outvoted) / ground ✓)

  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)

  verdict: confirmed (reproduce ✓ / refute ✗-survived (voted REJECT, outvoted) / ground ✓)

## Rejected (with reason)        ← so re-roasts don't re-litigate
- §3 "withholds the entry otherwise: the peer's `have` head simply stays behind that counter (no error ...)"; §2 "counts toward `have` heads" — Advertising `have` heads that include withheld opaque entries makes a 2.1.1 peer run a 30 s stall/penalty/re-want cycle. Rejected 2–1 (ground seat CONFIRM Should-fix). Reason: the mechanism is real (coordinator.rs:1844-1875 failover re-wants a sole stalled source every RX_STALL_MS) but it is one idempotent Want per 30 s per log, which is not an error, close or hot loop; refute seat shows update_rounds uses advertises_wantable, which ignores penalised logs (coordinator.rs:2178-2185), so rounds complete during the penalty window; the permanently lagging 2.1.1 peer is the documented limit in §5. Residual suggestion: one sentence acknowledging the 30 s re-want cadence, or a per-link capped `have` head.
- §2 fork proofs "work on prefix fields"; Key abstractions Opaque capability gate — Fork handling toward fork.v1 peers without the opaque capability is unspecified (ForkRefs naming opaque tips, cut branch_entries). Rejected 3–0. Reason: the gate is "the one outbound function" running before `encode_halved`, which has both the entries and branch call sites; §3's no-error/no-protocol_error invariant already binds the branch reply; an empty batch maps to branch_none in existing code; the scenario needs a fork with an opaque branch to a 2.1.1 peer, which this release cannot author, and the finding itself labels the re-ask loop speculative.
- §4 "joined to the chain by `(log_ix, counter)`" — Nothing enforces cross-table uniqueness of a chain position between `journal` and `journal_opaque`. Rejected 2–1 (ground seat CONFIRM Should-fix, citing hash_at at journal.rs:899 reading journal only). Reason: a known and an opaque entry at the same counter is by definition the fork case §2 handles; ingest runs in one SQLite transaction so the race is not real; the hash_at point is already covered by the confirmed single-reader-seam finding above, where the union reader must include it. Residual suggestion: a cross-table guard trigger.
- §5 Mixed-version behaviour; §3 — The spec never states a future-generation sender's duties. Rejected 3–0. Reason: §9 bounds authoring a new generation out of scope; the receive/relay contract this release controls (prefix invariant, `envelope.opaque.v1` gate, opaque item form, HTJRNL01 genesis via NotGenesis) is stated and tested; a per-generation capability is the future release's design work.
- §2 "a received entry whose magic is not `HTJRNL01` and whose prefix, hash and signature verify is an opaque entry" — Accepting any non-HTJRNL01 magic removes the magic's domain-separation role. Rejected 3–0 (external claim; no seat returned UNVERIFIED). Reason: an opaque entry must put the log's node uuid at bytes 8..24 and verify under the genesis key, which the handshake preimage ("HTPEER1-AUTH\0"‖len‖hello…) cannot satisfy; the finding itself concedes exploitability is speculative; TRUST-POLICY's cooperative same-user model does not ask for adversarial hardening. Optional hardening: reserve an `HTJRNL` magic prefix.
- §4 "an older binary opening a schema-4 store is already handled by the repo's downgrade policy (it refuses, unchanged)" — The schema bump removes rollback to 2.1.1 for an empty table. Rejected 3–0. Reason: §4 states the tradeoff explicitly and follows the repo's standing refuse-newer policy (schema.rs:322); the spec's mixed-version goal is the peer wire, not local binary rollback; lazy table creation would put DDL in the ingest path and break the exact-version baseline check.
- §6 "the script and its test-support hooks are added there as a patch outside the tag's source by being a pure observer"; Key abstractions Peer-wire recorder — The two capture descriptions contradict each other and the fallback yields synthesized bytes. Rejected 2–1 (ground seat CONFIRM Nit). Reason: both passages describe an additive test-only `PeerIo` decorator in a scratch worktree, with no production change; the tag's own coordinators emit the bytes; the fallback is an explicitly documented contingency. The wording tension is folded into the confirmed fixture-determinism Nit above.
- §6 "Fixtures are append-only: a test fails if an existing directory file changes (hash list in `MANIFEST.md`)" — Append-only enforcement is self-referential. Rejected 3–0. Reason: the check guards accidental drift; a deliberate regeneration of fixture and manifest is a review-visible diff under the cooperative same-user model; any in-repo anchor is equally editable in the same commit, so only a merge-base CI check would differ, which is a hardening extra not a stated requirement.
- §7 Forward-compat half: "a frozen copy of the 2.1.1 peer wire structs and their `decode` behaviour" — The shadow decoder omits 2.1.1's post-decode validation and is never checked against fixtures. Rejected 2–1 (ground seat CONFIRM Nit). Reason: "decode behaviour" covers PeerFrame::decode post-checks; the cited limits (MAX_HELLO_CAPS=32, MAX_CAP_BYTES=64, 8 KiB hello) cannot be approached by one 18-byte cap; known-layout frames stay byte-identical; §6 fixtures exercise the current validators. Residual suggestion: also decode the 2.1.1 fixtures with the shadow.
- §8 The lints, R2 and "Stale baseline lines fail the check" — Lint rules miss field removal/rename, type changes, skip_serializing_if on required fields and new closed-enum variants (Role). Rejected 2–1 (reproduce seat CONFIRM Nit; external claim, no UNVERIFIED vote). Reason: the spec deliberately scopes the awk lint narrowly (challenge (e), `syn` discarded) and assigns send-side compatibility to the §7(a) shadow test, which fails on every listed case whenever the frame is emitted; R4's delta printout is a stated tradeoff. - §8 R4 "enforced in review by the check printing the delta" — Adding an existing type's new required field to the baseline bypasses R2 mechanically. Rejected 3–0. Reason: the spec states the review tradeoff and mitigation, the baseline is a committed file whose edit is visible, the design itself needs baseline growth for OpaqueWire, and the §7(a) shadow test catches a new required field on an emitted frame regardless.

Reason: WireItem and its decode are placed in src/sync/frame.rs, which is listed, and OpaqueWire's fields are added to the baseline; the lint is one of three layers, and the §6 fixtures and §7 shadow test are behavioural checks that cover tightened parsing, new decode rejections and new Role variants independent of file lists.

Rejected 2–1 (ground seat CONFIRM Nit). Reason: opaque items only reach peers that advertised `envelope.opaque.v1`, so an unknown alternative only reaches a node that advertised support; OpaqueWire is a lint-covered serde struct so inner extra fields are tolerated; malformed items map to EnvelopeError via OpaqueEntry. Residual plan-level note: key on presence of `opaque`, ignore sibling keys, and state per-item vs per-frame failure.
- §5 / §9 / Key abstractions "Extended, not new" — The whole opaque-entry subsystem is built for a generation that does not exist (YAGNI). Rejected 3–0. Reason: the Goal is relay of an unknown layout; relay code must be deployed before the first new generation or every pre-existing node becomes the partition point the spec exists to prevent; pinning the prefix alone does not meet the goal.
- §5 "recorded in TRUST-POLICY if the trust text mentions relay" — TRUST-POLICY update left conditional. Rejected 2–1 (reproduce seat CONFIRM Nit). Reason: ground seat shows the premise is false: TRUST-POLICY.md N2 (~line 1318-1321) already covers peer-entry relaying ("A relayed entry is trusted exactly as far as its origin signature, never because of the node that relayed it"), so the spec's own condition resolves to "update", and the opaque path keeps signature and chain verification consistent with N2.
