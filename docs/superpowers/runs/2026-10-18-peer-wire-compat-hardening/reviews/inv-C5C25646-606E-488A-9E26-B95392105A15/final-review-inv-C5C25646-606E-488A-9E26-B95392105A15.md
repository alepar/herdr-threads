## Step 1: own view against the design

Inspected: migration 0004, the Chain-row reader and ingest/serve/branch paths in src/store/journal.rs, the apply stall (src/store/apply.rs), sync status/verify (src/store/sync_status.rs), EntryPrefix/OpaqueEntry/StoredEntry (src/sync/envelope.rs), WireItem decode and conversion (src/sync/frame.rs), the capability gate and branch cut (src/sync/coordinator/serve.rs), oversize authentication (src/sync/coordinator/ingest.rs), coordinator wiring (hello caps, LinkEntry, oversize_logs), chain rules, fork classification, the incarnations sink and worker, re-issue and repair counting (src/store/incarnations.rs), salvage (src/sync/resync.rs), the status protocol rows, docs, TRUST-POLICY, CHANGELOG, AGENTS.md and CI.

What composes correctly across tasks:
- Prefix invariant: Body::canonical_bytes writes its first 68 bytes through EntryPrefix; OpaqueEntry::new checks length (68..=384 KiB), magic != HTJRNL01, counter >= 2 (counter 1 is NotGenesis) and prefix == header before any crypto; verify is SHA-256(raw) then verify_strict. check_next takes StoredEntry, so opaque appends, duplicates, gaps, conflicts and forged signatures follow the known rules (unit tests in src/sync/chain.rs).
- Storage: journal_opaque has a STRICT schema, a unique main-chain position index, cross-table position guards in both directions, and unconditional UPDATE/DELETE guards (the promotion exemption was removed by ht-j87z.31, consistent with the Post-Implementation Notes). CHAIN_ROWS/BRANCH_ROWS are the union sources; verify_invariants, hash_at, held_at, branch_prev, the apply head scan, sync verify J2, check_invariants I2 and the serve/branch readers use them.
- Apply: mark_opaque_heads sets blocked_on = opaque_layout only on change and next_ready_head skips opaque heads (applied_through unchanged). Dependents block on the existing unmet-dependency text. The blocked_on field reaches LogRow (serde default, skip if None) and the compact text.
- Gate: every served batch and branch reply passes gate_batch with LinkEntry::opaque_cap(). An empty cut parks the log on that link (withheld_logs), and a want from before the cut lifts the park. A branch cut sends more:false at its last counter, or branch_none when empty. Known items serialize as bare WireEnvelope, and the golden-bytes test pins that against pre-change output.
- Oversize: the actor takes the first oversize opaque item as an unverified claim. The worker stores the prefix, then authenticates log, next position, prev == head, prefix, SHA-256(raw) and signature before returning Oversize. Anything else refuses only the source (OversizeRefused, time-limited penalty). This closes ledger Task 8's (None, Some) gap.
- Incarnations/resync: classify_pair and classify_ahead_of_self work on prefix fields and the signature. Restore of an opaque own entry is reported and not rotated. The re-issue CANDIDATES opaque arm is counted (cannot_reissue), never copied, and surfaced in RepairRow plus a deduplicated log line. Salvage carries opaque rows byte-exact, names an opaque stop, and shadows a missing journal_opaque in a pre-delta backup with a TEMP table.

Findings:
- [Important, integration] Node schema number collision. The branch registers `NodeDelta { version: 4, sql: 0004_journal_opaque.sql }` in src/store/schema.rs, but main (9f1ca770d, which contains base f78f076a) already registers version 4 = migrations/node/0004_sibling_delivery.sql, and v2.2.0 is tagged. Landing as-is either conflicts textually or, if resolved by keeping both, gives two deltas numbered 4. A 2.2.0 store at user_version 4 would then never create journal_opaque, and every CHAIN_ROWS reader would fail with "no such table". docs/release.md 8b plans the renumber "at merge time", but it is now concrete and blocking. Dependent edits: the migration header, release.md 8b, CHANGELOG ("next node schema"), the src/sync/resync.rs comments and doc that say "before node schema 4", and tests/store/schema.rs journal_opaque_delta_upgrades_highest_main_store (hard-coded NODE_DELTAS[..2] and user_version 3; ledger Task 13 minor `hard-coded-slice` escalates here). The prior bounded review inv-500DAF36 raised the same issue, and the head still carries it.
- [Important, correctness/diagnostics] `sync verify` J3 rehash stops at the first opaque position of every log. In src/store/sync_status.rs, rehash_entries loops over `crate::store::journal::serve` (Rows::KnownPrefix). That read closes the batch at the first opaque row, so `from` stops there and the loop ends. Known HTJRNL01 entries past an opaque position (a shape the branch's own salvage_carries_opaque_entries test builds) are never rehashed. Opaque rows are never checked as SHA-256(raw) == hash. J3 then reports clean over rows it did not verify. Design section 4 lists sync_status among the union-required readers. The J2 tests (verify_j2_accepts_opaque_predecessor, verify_j2_flags_broken_link_after_opaque) filter J3 out with `without_j3`, so nothing covers this. Fix: iterate serve_entries, check Known by compute_hash and Opaque by SHA-256 of raw, and add a J3 test with an opaque mid-chain position and a known entry after it.
- [Minor, cross-task seam] Fork references are advertised to every fork.v1 link (coordinator.rs, full `have`: `if entry.fork_cap() { self.fork_refs() }`), whatever the opaque capability. A capless fork.v1 peer (a 2.1.1 node) can be offered a ForkRef whose side is opaque. The gate then answers branch_none or a known prefix with more:false that does not reach the tip, and that peer's worker penalizes this node for the log on each probe. No opaque item leaks and the penalty is bounded. Options: filter fork refs with an opaque side on capless links, or document it next to the "do not cross a 2.1.1 node" limit. Unreachable in practice until a non-HTJRNL01 author exists.
- [Minor, hardening] insert_opaque uses `INSERT OR IGNORE`, and ingest_batch's opaque append ignores the returned bool. A row skipped by a CHECK or unique conflict would still move the in-memory head and then sync_logs. It is unreachable today because OpaqueEntry::new and check_next enforce the same bounds and positions, but an explicit duplicate check, or a plain INSERT with the duplicate case handled before it, would turn a future mismatch into an error rather than a head without a row.
