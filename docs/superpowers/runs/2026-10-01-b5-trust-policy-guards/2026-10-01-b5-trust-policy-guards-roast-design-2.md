- [Should-fix] Implementation decisions §3 "Seatless check-in (client and wire)": "it is journaled under an instance-scoped intent; the daemon's response returns the chosen seat and binding generation, which the hook writes into the pane's client context exactly as an ordinary lifecycle check-in does. A refusal leaves today's diagnostics unchanged." — The paragraph defines only success and refusal; if the daemon commits the rebind but the hook loses the reply before writing the client context, no per-seat pending record exists to replay it, the instance-scoped intent has no named replay point, and later hooks in the pane go Quiet until an unrelated SessionStart. (new)
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Ordinary check-in crash safety comes from `contexts.get_or_prepare` recording a PendingCheckIn before dispatch (src/harness/bridge.rs:350-389) and the next hook replaying it (src/cli/hook.rs:1063-1077). That journal is opened per seat (`super::seat_contexts(&paths, instance, &seat)`, hook.rs ~929) and PendingCheckIn.context requires a seat and binding_generation (src/harness/context.rs:47-57). A seatless request has no seat before the daemon answers. On the next non-lifecycle event, `find_seat` resolves the now-rebound seat and the empty context yields `Failure::Quiet("no registered execution for this session; a lifecycle check-in (SessionStart) registers one")` (hook.rs ~950). A repeat resume SessionStart no longer passes the C1 gate because the seat is no longer unresolved. Grep of the spec for replay/pending/lost/idempot/recover finds nothing relevant. Refute seat (REJECT) argued "journaled under an instance-scoped intent" implies replay and the outcome is low-impact; it did not read the cited code, and the majority answers that the spec never says who replays the intent or when. Not demoted under the profile: the lost reply occurs on the restore path that C1 exists for, and the silent outcome is the feature's purpose failing, which this profile does not down-weight.
  fix-shape hint: add one sentence that the hook checks the instance-scoped intent journal before `find_seat` on every event and replays it under the same operation key, with the daemon's idempotent reply returning the recorded seat and generation; add a lost-reply-then-next-event test to ht-rzi.2's acceptance.

## Rejected (with reason)
- Implementation decisions §3 "On a match the deciding transaction rebinds the seat, records `cooperative_continuity` in seat history ... and calls `lift_baseline_hold_if_clear`." — C1 rebind never releases the reattached target's own per-target hold state (recovery_holds row, baseline release, disposition), so the seat stays held while other seats are unresolved. Rejected 2-1: "rebinds the seat" names the existing rebind operation, and in src/store/seats.rs:3305-3330 that operation itself releases the target's `recovery_holds` row, inserts `recovery_baseline_releases` and sets disposition 'already_owned'; TRUST-POLICY C2 already makes per-target release on cooperative continuity normative and the spec states "where they differ, the policy wins". The ground seat's dissent (CONFIRM, Should-fix) cited the hold checks at seats.rs:2789, seats.rs:3455, wake.rs:50 and effective.rs:144 and conceded "the spec might intend 'rebinds the seat' to reuse the operator-rebind routine, but it never says so"; the majority's evidence answers that point, so the default stands. Residual nit worth one sentence: say explicitly that the C1 deciding transaction performs the same per-target release as operator rebind. Related to the iteration-1 Blocking finding, which is resolved.
- Implementation decisions §3 "Seatless check-in (client and wire)": "carries pane target, harness, session id and source but no seat ... returns the chosen seat and binding generation" — Neither field list names the execution id that A2 and `occupant_bindings.execution_id NOT NULL` require. Rejected 2-1: the execution is client-minted today (src/cli/hook.rs ~1123 `uuid::Uuid::new_v4()`) and carried through `caller_claim`/`occupant_context` (src/harness/bridge.rs), and the spec says the seatless variant behaves "exactly as an ordinary lifecycle check-in does", so the enumerated fields are the delta from the ordinary request, not a full wire schema. The ground seat confirmed only at Nit and said it "could not show that an implementer would fail from it". Residual nit: add "execution" to the request field list.
