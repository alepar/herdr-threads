## Confirmed findings
- [Blocking] Implementation decisions §1 "Hold lift (C2)" — Decision 1 clears only the instance-wide `baseline_hold_unclaimed` flag, but restored targets are also held by per-target `recovery_holds` rows that the effective-disposition check reads first and that only an allocation on that same target releases, so the C2 lift leaves held panes refused.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/store/seats.rs:2599-2602 inserts a `recovery_holds` row (reason 'unresolved saved seat continuity') for every held_for_repair baseline target. src/store/effective.rs:144-149 returns `ExplicitHold` for an unreleased row before it reads `baseline_hold_unclaimed`. seats.rs:2788-2797, seats.rs:3455, wake.rs:50 and queries.rs:689 also check `recovery_holds` directly. The only release is `UPDATE recovery_holds SET released_at` at seats.rs:3305, scoped to the single target of an operator rebind or fresh seat. Failure story (reproduce seat): panes A and B held; operator rebinds S1 to A (releases A only), retires S2 (zero unresolved, flag clears); B stays `ExplicitHold` and `seat resolve`/`launch`/`me init` on B are still refused. TRUST-POLICY C2 marks the instance-wide lift **required**. All three seats confirm; severity set at Blocking because the spec's stated Goal is that every required guard works, and as written the C2 lift does not lift the main case (held targets). The "me init on a new pane succeeds" sweep would not catch it, since panes created after the baseline are never held.
  fix-shape hint: add to Decision 1 that the lift transaction also releases every open `recovery_holds` row for the instance (same transaction, same predicate), and add a test where a held pane resolves after the last unresolved seat is retired rather than rebound.

- [Should-fix] Implementation decisions §3 (Herdr `agent_session` / `session_start_source` hint rule) — The hint is written by Herdr's own SessionStart hook, which runs in parallel with the herdr-threads check-in and is known to lag, so a mandatory present-must-match rule produces timing-dependent false refusals of legitimate resumes.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: https://code.claude.com/docs/en/hooks: "All matching hooks run in parallel." and SessionStart hooks "run in the background" on --resume; no ordering between Herdr's integration hook and the plugin's hook. docs/compatibility/herdr-host.md line 9 records a measured Codex `/new` case where "`agent get` retained the old `agent_session` ... before the first new turn". The spec rule is asymmetric: absent accepts, present-but-stale refuses, with no freshness, re-read or retry rule, and the SessionStart check-in fires once. Refute seat (REJECT, outvoted) argued the failure is fail-closed to the operator path; the confirming seats accept that it is fail-safe, which is why this is Should-fix and not Blocking. Actual race frequency for Claude resume is unmeasured.
  fix-shape hint: either demote the Herdr hint to diagnostic-only, or add a re-read/retry of `agent get` before refusing, and have the ht-rzi.2 capture log `agent get` from inside the hook for resume, /new and /clear.

- [Should-fix] Implementation decisions §3 "The harness session id from the hook payload is persisted on `occupant_bindings` ... Schema change via the next migration number" — `occupant_bindings` already has a NOT NULL `native_session` column filled from the hook `session_id` (with synthetic `plugin_context:<uuid>` sentinels), so the new column and migration may be redundant and the matching rule does not say which stored values count.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: migrations/0001_initial.sql:204 and migrations/0009_human_occupant.sql:17 declare `native_session TEXT NOT NULL`. src/store/seats.rs:2329-2332 and :3693-3695 insert it on registration and lifecycle check-in. src/harness/bridge.rs:247-255 fills it with the Native hook session id, or `format!("plugin_context:{id}")` when only a plugin context exists; src/cli/mod.rs:1355-1359 handles the same prefix. The spec never mentions the column, premises a migration (and the B4 numbering coordination) on its absence, and its rule "session id equals the last binding session" does not exclude sentinel values from the "exactly one seat" uniqueness test. All three seats confirm.
  fix-shape hint: state that the existing `native_session` column is reused, that `plugin_context:` and human-occupant values never match, and drop the migration unless a different column is genuinely needed (which also removes the B4 numbering coordination).

- [Should-fix] Implementation decisions §3 "A Herdr `session_start_source` of `startup`/`new`/`clear` (a fresh session) also refuses reattachment." — Herdr 0.9.1 does not expose `session_start_source` on any read route, so the fresh-session refusal cannot be fed from Herdr as written; the hook payload's own `source` is the usable signal.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Verified against the installed binary, not the web. `herdr --version` = 0.9.1. `strings ~/.local/bin/herdr` shows `session_start_source` once, under `PaneReportAgentSessionParams` (the request Herdr's hooks send); both `AgentSessionInfo` schema definitions have only agent, kind, source, value. Live `herdr agent list` returns `agent_session:{agent,kind,source:"herdr:claude",value}` with no start-source field, and `source` there is the reporter id. src/host/observation.rs:127-138 reads only those four fields. The plugin's own hook payload already carries Claude's `source` (src/harness/claude.rs:154-161). Refute seat (REJECT, outvoted) argued the clause is redundant with session-id equality; the confirming seats agree it is mostly redundant but note the spec names a signal that does not exist and the seam bead ht-rzi.9 would carry a dead field.
  fix-shape hint: reword the clause to gate on the hook payload's `source`/EventKind, or drop it and say the session-id equality check covers fresh sessions.

- [Should-fix] Implementation decisions §1 "cleared in the same transaction that leaves zero unresolved nonretired seats" — The lift predicate can fire between the snapshot publish that sets the hold and the page-by-page reconciliation that unresolves saved seats, and has no fence against host boot/epoch or reconciliation progress.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/store/seats.rs:684 sets the hold at publish as `unresolved || changed_or_unknown_incarnation && nonretired`, before any seat is unresolved. Saved seats are unresolved later, per page, at seats.rs:1565-1589, and that path re-sets the flag. A seat still `state='resolved'` is not counted by the spec predicate, and effective.rs:129 treats its target as Owned. Failure story: incarnation changes, hold set, seats A/B still 'resolved' pending reconciliation; operator retires an unrelated seat (a §1 trigger) leaving zero unresolved, flag clears; a newcomer claims A's restored pane before the next page unresolves A. Contradicts C2 "every unowned target in that baseline is held". All three seats confirm; the window is narrow and self-healing except for a claim made inside it, so Should-fix rather than Blocking.
  fix-shape hint: require the lift to see no saved seats still pending reconciliation for the current recovery boot/epoch (or that reconciliation of the current baseline has completed), and say so in Decision 1.

- [Should-fix] Implementation decisions §3 "A top-level *lifecycle* check-in in a pane whose target is held or unowned ... rebinds that seat to the target in the deciding transaction" — Cooperative continuity needs a lifecycle check-in that does not know its seat, and the spec does not define its wire or client shape; the existing hook client requires a seat plus binding generation and stops before contacting the daemon when the pane has no resolved seat.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/cli/hook.rs:708-768 `find_seat` returns Err for a held pane ("pane seat is held or its mapping changed") and for an unresolved pane ("pane seat mapping is ..."), and Ok(None) for an unowned pane; hook.rs:891 turns Ok(None) into `Failure::Quiet("no resolved seat for pane")`. So every C1 target class stops in the client before any daemon contact. src/harness/bridge.rs:255-268 builds `CallerClaim` with required `seat` and `binding_generation`; prepare_event (bridge.rs:357-361) needs a seed via `initial.or(current)` or fails with LifecycleRequired; the journal scope is `IntentScope::Cooperative { seat }`. The spec gives only the daemon-side rule. Refute seat (REJECT, outvoted) called this plan-level work but could not read bridge.rs ("path not found") and did not address the client-side early exit.
  fix-shape hint: add a paragraph defining the seatless lifecycle claim (what the request carries, how it is journaled before a seat is known, and how the daemon's chosen seat and generation flow back into the client context), or explicitly delegate it to a named bead.

- [Nit] Implementation decisions §1 trigger list "(rebind, fresh seat, retire, replace, cooperative continuity, reconciliation retirement)" — The enumerated lift triggers omit structural reconfirm, which also moves unresolved seats back to resolved, and say nothing about stores that are already in the sticky state at upgrade.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/store/seats.rs ~2090 (Reconfirm/ReconfirmStructure) runs `UPDATE seats SET state='resolved' ... WHERE state='unresolved' AND unresolved_reason='host_invalidation'`; it is not a retirement or rebind and is not in the list. The flag is set at seats.rs:1589 and carried forward at seats.rs:684-685 (`!new_recovery && old_hold != 0`), so only an explicit write clears it. Both confirming seats rate it Nit because the governing sentence ("zero unresolved nonretired seats") is general and the parenthetical reads as examples. The read-time-predicate alternative is a design preference, not a defect.
  fix-shape hint: add structural reconfirm to the list, state that the rule applies to any transaction that reduces the unresolved count, and say whether a startup/migration repair covers stores already stuck with the flag set.

## Rejected (with reason)
- Implementation decisions §3 / Non-goals "except the evidence capture `ht-rzi.2` needs (see below)" — C1 rests on an unverified premise that resume keeps the harness session id; no fallback if a harness fails. Rejected 2-1: a negative capture only makes C1 inert for that harness and falls to the operator path, which TRUST-POLICY C1 and "Restore costs operator time" already accept; the spec's bar is stand-in-agent tests. Residual nit all seats agree on: the "(see below)" reference is dangling — nothing after Non-goals describes the capture or its failure outcome. Worth one sentence.
- Implementation decisions §2 "reuses the bounded retirement cutover (`begin_retirement`)" — begin_retirement opens its own IMMEDIATE transaction and requires ClosureEvidence. Rejected 2-1: the code premises hold (src/store/control.rs:26-100), but "the bounded retirement cutover" plus "one deciding transaction" clearly points at `begin_retirement_fence` (control.rs:111), which runs in the caller's transaction; a literal implementation would fail loudly. Residual nit: name the fence, and say what closure_* values an operator retire records.
- Implementation decisions §3 / Coordination — picking "the next migration number" on both B4 and B5 can leave branch-migrated dev stores skipping or re-applying a migration after renumbering. Rejected 3-0: the Coordination section explicitly delegates this to whichever branch lands second; the spec's bar is deterministic tests on fresh stores; branch-migrated demo stores are throwaway. Also moot if the native_session finding above removes the B5 migration.
- Implementation decisions §5 "Optional envelope field" — WireRequest is deny_unknown_fields, so a new CLI sending expected_boot to an old running daemon fails every request. Rejected 3-0: src/protocol/wire.rs:23-34 confirms the mechanism, but version skew after a binary upgrade is the repo's existing lifecycle case (src/daemon/lifecycle.rs:190-213 returns DaemonVersionMismatch with "run `daemon stop` then `daemon ensure`"), the failure is loud and pre-dispatch, and upgrade policy is outside the spec's scope. Task note from the reproduce seat: the ensure handshake's Health probe goes through LocalSocketClient and its `Err(_) => return Ok(None)` arm would hide the version-mismatch message against an old daemon.
- Implementation decisions §3 "in a pane whose target is held or unowned" — a resume matching an unresolved seat but landing in a pane owned by another seat is handled as same-seat replacement. Rejected 3-0: TRUST-POLICY A4 line 124 explicitly allows "Agent to agent, same seat ... replaces the binding"; nothing is attributed to S, S stays unresolved and recoverable; preventing it would need the adversarial verification the spec excludes.
- Implementation decisions §5 "The daemon refuses a mismatch before dispatch with a definite error." — no client re-read/retry policy. Rejected 3-0: policy A2 requires only pre-dispatch refusal; the field is optional and the spec never requires hooks to send it; a refused check-in degrades to the accepted operator path; retry is a task-tree item.
- Implementation decisions §6 carry-forward on structural reconfirm — removes the recipient_unavailable signal and can carry a stale session id. Rejected 3-0: TRUST-POLICY C4 (lines 84-87) and row O1 make carry-forward required and deliberately remove the lapse; C5 and "Unseen exits" accept it; a stale id fails closed because decision 3 needs exact equality.
- Implementation decisions §1 (re-arm after lift) — existing code sets baseline_hold_unclaimed=1 on any later unresolve while the baseline generation persists. Rejected 2-1; pre-existing on base (src/store/seats.rs:1588-1592, unchanged by this spec). C2's "nothing left to protect" rationale implies re-arming when something is unresolved again is consistent; over-holding is the policy's accepted failure direction. Final severity FYI.
- Implementation decisions §3 "exactly one unresolved nonretired seat" — same session resumed in several panes (e.g. `claude --continue` in each), first check-in wins. Rejected 3-0: once the first check-in rebinds the seat it is no longer unresolved, so later duplicates fall to the held/operator path deterministically; provenance `cooperative_continuity` is recorded and the operator can rebind; cooperative model, no adversarial verification.
- Implementation decisions §3 — a check-in landing before the new baseline snapshot sees disposition Unknown and misses reattachment. Rejected 2-1: effective.rs:151-160 confirms Unknown in that window, but the outcome is the accepted operator-path fallback, and the spec does not promise first-check-in success. Residual nit from the ground seat: say whether Unknown counts as "unowned".
- Implementation decisions §3 "when absent the claim alone suffices" — a Herdr read error/timeout is neither present nor absent. Rejected 2-1: observation.rs:120-136 already separates absent (None) from error (Err); policy principle 3 ("holds and asks") plus "the policy wins" resolves error to hold; the hint is never proof. Residual nit: one sentence stating that an error is not "absent".

Rejected 3-0: policy A2 already fixes decision inputs to the effective host observation at the current boot/epoch; the hint is a veto, never proof, so a stale read can only refuse conservatively; I/O placement is plan-level.

Rejected 3-0: TRUST-POLICY principle 1, "Same-user spoofing" accepted limit, and A4's own "unless --operator" make this the designed cooperative model; `operator_human` is labelled best-effort; the finding calls its dilution point speculative.
