- [Should-fix] src/main.rs:125 — The new `peer --stdio` fallback runs on any `resolve_context` error, so an explicit `--state-dir` or `HERDR_PLUGIN_STATE_DIR` that fails validation (for example a relative path) is silently replaced: the default state dir is created and a daemon with a fresh node identity starts there, instead of the pump failing with the configured path's error. (new this iteration) [lanes: correctness, simplicity-design, regression, api-contract] [fix-regression]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/main.rs:125-137 `resolve_context(&inputs).or_else(|first| { let dir = default_state_dir_to_create(&inputs).ok().flatten().ok_or(first)?; std::fs::create_dir_all(&dir)?; resolve_context(&InstanceInputs::from_process(Some(dir), ...)) })`. The closure never checks `inputs.state_flag` or `inputs.env_state`, and never checks which error `first` was. `resolve_state_dir` (src/cli/instance.rs:285-296) returns a flag or env value unchanged; `RuntimeContext::explicit` (src/daemon/paths.rs:32-36) then rejects a relative path with InvalidInput "state and host endpoint must be absolute", and that error enters the fallback. `default_state_dir_to_create` (instance.rs:193) reads only HOME/XDG_STATE_HOME, so the retry passes the default dir as the flag and overrides the explicit choice. A scout reproduced it on a fresh build of 7f0269782: `env -i PATH=/usr/bin:/bin HOME=$S/home herdr-threads --state-dir rel/state peer --stdio </dev/null` exited 0, created `$S/home/.local/state/herdr/plugins/herdr-threads/node/{herdr-threads.db,node.key,...}` and left a daemon running there; before the diff the same call exited 3. `remote_command` is per-target and user-set (src/sync/dialer.rs:152-161), so `--state-dir` in it is the way to pick a non-default store on the far side, and a mis-spelled path now links to a different store with a new node identity and reports success. The flag-first precedence in instance.rs:4-8 and docs/install.md no longer holds for this entry point. Also `create_dir_all(&dir)?` returns its own io error in place of `first`. The user ruling ("if no daemon is running, start one creating initial state as usual") covers only the no-state-dir case. The only new test (tests/cli/peer_stdio.rs `pump_on_a_fresh_node_creates_the_default_state_dir`) covers only the no-flag, no-env path. All three seats confirmed at Should-fix; none re-ran the repro, the code paths match it. Not Blocking: it needs a misconfigured explicit path, and no data is lost.
  fix-shape hint: fall back only when `inputs.state_flag.is_none() && inputs.env_state.is_none()` (and the first error is the state-dir-unknown case); otherwise return `first` unchanged; put the policy in instance.rs next to `resolve_state_dir` so it is unit-testable, and add a test that `--state-dir rel/x peer --stdio` still exits with the resolution error.

- [Should-fix] src/main.rs:131 — The fresh-node fallback creates the default state dir with `std::fs::create_dir_all`, so the leaf directory gets the process umask's mode instead of the 0700 the daemon uses. Under umask 002 the leaf is 0775, the daemon's `ensure_owned_state_root` rejects it, the pump fails, and the group-writable directory stays behind and becomes the resolved default for later local commands. (new this iteration) [lanes: regression] [fix-regression]
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/main.rs:131 `std::fs::create_dir_all(&dir)?` creates every component, leaf included, at 0777 & ~umask; grep for "umask" in src finds no private umask set first. `NodePaths::prepare_node_dir` (src/daemon/paths.rs:229-232) calls `ensure_owned_state_root`, which creates a missing root with `DirBuilder::new().mode(0o700)` but on AlreadyExists runs `check_owned_state_root`, which fails when `mode & 0o022 != 0` ("unsafe state directory (must be an owned directory without group/other write)"). Under umask 002 the pre-created leaf is 0775, so the daemon start fails and the pump exits "daemon unavailable". The directory now exists, so `default_state_dir` (instance.rs:172-187, `exists.then(...)`) selects it for every later command, and doctor/setup (doctor.rs:862, harness/setup.rs:3764) hit the same unsafe-root error until the user chmods it. Before this diff nothing was created and the pump failed with no residue. The new test runs under the test process's umask (typically 022, which gives 0755 and passes), so it does not cover this. External premise, partly grounded by the ground seat: https://manpages.ubuntu.com/manpages/noble/man8/pam_umask.8.html says with `usergroups` "the umask group bits are set to be the same as owner bits" with the example "022 -> 002" when the username equals the primary group name; whether stock Ubuntu/Debian sshd sessions enable this by default was not fetched. The bug does not depend on the premise: it fires for any user or distro with umask 002 or 007. No seat ran it under umask 002. All three seats Should-fix: a first inbound link to a fresh node fails on affected hosts and leaves a bad directory that breaks later local commands. Not Blocking: conditional on a non-default umask, no data loss.
  fix-shape hint: `create_dir_all(dir.parent())` only and let the daemon create the leaf at 0700, or `set_permissions(0o700)` on the leaf right after creating it; add a test that runs the fresh-node pump under `umask 002` (own `[[test]]` target, since umask is process-wide).

If the interactive shell exports XDG_STATE_HOME to an existing store, `choose_state_dir` finds `xdg_store && home_store` and returns Err "both ... hold a store; pass --state-dir" for every default-resolving command. Final severity Nit, following the reproduce seat: it needs XDG_STATE_HOME set only in interactive or login-only files plus herdr off the ssh PATH or not running; the outcome is a loud, documented refusal that names its remedy, and it is recoverable by deleting the phantom store or passing `--state-dir`; the hazard existed before the diff on the herdr-on-PATH path.
