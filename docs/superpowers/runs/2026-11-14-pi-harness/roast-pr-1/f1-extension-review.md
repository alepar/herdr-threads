## Important I1 — Re-admission bypasses the confirmation join

`integrations/pi/extension/herdr-threads.js:191` handles watch exit code 3 by clearing the child/live state, discarding the page, setting `bound = false`, and returning. A confirmation already emitted for that page may still be running. On the next genuine `before_agent_start`, `admit()` (`:108`) completes SessionStart and directly calls `startWatch()` (`:116`). Its guard (`:179`) does not check `confirming` or `replacing`, so it starts a successor watch while the previous confirmation still owns its receipt/page references.

The ordinary exit/backoff path now correctly calls `replaceWatch()` and joins the captured confirmation (`:163`), but re-admission does not use that gate. This breaks the explicit requirement that successor page parsing follow the prior confirmation/stop join, and invalidates the reserved-memory phase assumptions. It can also occur if re-admission runs while a replacement is already waiting.

Route re-admission through the same owned startup/join gate without making confirmation completion await itself. Add a regression that holds presentation-confirm, calls the current watch's `exit(3)`, starts a genuine native run, and asserts there is still only one watch until confirmation resolves. Include shutdown while that re-admission is waiting. Existing `extension.test.mjs:758` covers exit(1) and conflicting-page retry, so it does not exercise this bypass.
