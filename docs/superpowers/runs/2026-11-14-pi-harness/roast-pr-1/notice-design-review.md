# Canonical notice seam: independent design review

**Verdict: Approved narrowly for neutral implementation of the frozen contract in `notice-canonical-design.md`.** No unresolved design blocker remains after the empty-token progress correction and the approved applied-clear exception. This is not source approval, Pi-adoption approval, or qualification evidence. Independent review of the implemented neutral seam and its compatibility tests must precede Pi adoption.

## Compatibility and authority

The Notice-only `context_key = dn1:<sequence>:<event_seq>:<ordinal>` encoding is suitable. Together with the Notice descriptor's warning/thread it preserves the complete canonical `WarningRef` and projection ordinal; it does not infer missing fields from client IDs. Its maximum is 65 ASCII bytes. Keeping the existing optional string avoids changing the `FrozenPresentation` wrapper that currently rejects unknown fields (`src/store/invitation_content.rs:1587`). Old Notice replay/confirmation ignores this field, whereas Invitation matching uses its existing meaning (`:1756`). A retired outbox on an old reader still leaves the deferred frontier unadvanced, allowing a fresh offer. This supports the proposed at-least-once downgrade behavior without authorizing fallback by the manual integration.

Checked parsing, item-kind separation, version rejection and validation of all tags before effects are required. `None` must retain legacy behavior. The default-false, false-omitted local pull flag and capability refusal before registration preserve default clients and old-daemon compatibility. Refusing a default pull only while an unretired tagged Notice remains prevents accidental automatic confirmation without permanently fencing a token whose tagged slots were already retired.

Canonical prefix settlement is the correct authority boundary. Allocation must validate the exact oldest prefix but defer its frontier write. Confirmation must validate current ownership even when every captured ordinal is already covered, compare the remaining canonical WarningRef **and ordinal** prefix, and perform frontier advancement and descriptor retirement in one transaction. The existing store confirmation wrapper already provides a transaction (`src/store/mod.rs:1665`); a mismatch must leave all effects uncommitted and return the specified non-success result. No client high-water mark, display ID, receipt count or digest becomes frontier authority. Existing `settle_pulled_notices` is a useful bounded predicate, but its current false result does not itself distinguish already-covered success from an uncovered gap (`src/store/attention.rs:1203`). The implementation must make that distinction explicitly.

## Coverage, lifecycle and wake

Whole emitted-page coverage is required because existing confirmation retires every non-control descriptor, rather than a submitted subset (`src/store/invitation_content.rs:965`). Stable token-plus-item digest keys avoid index changes after pruning and prevent a prior notice episode's evidence from covering a new token. Notice, Invitation and Attention require exact current-branch plus final-context evidence. Main's separately approved AttentionCleared exception is coherent: its exact current-owner clear must be applied locally; it contributes no fabricated model-content evidence and cannot cover another item's body.

An emitted page and the complete retained token are deliberately different. Replay may hide Attention under Unknown while retaining its slot (`src/store/invitation_content.rs:1749`). Its stamp must stay out of the receipt. Confirming emitted Notices can leave that hidden control pending, so the CLI must report only `emitted_page_confirmed`, never token retirement. Revision, reload and owner replacement invalidate local evidence and require current lease admission; opaque receipts preserve Rust u64 values without JavaScript round-tripping.

The corrected no-output rule is essential. `presentation_relevance::advance` makes bounded persisted-scan progress on each pull (`src/store/presentation_relevance.rs:1220`); Unknown does not imply that another external event will arrive. Empty hidden-token pages must continue the existing cancellable pull quantum, without a receipt, confirmation, parking or restart. Actual emitted nonordinary pages park once. This avoids both the original repeated-`more` loop and an external-event-only deadlock. Ordinary-only output must retain an explicitly tested no-receipt path so the extension cannot mistake an empty required set for confirmation permission.

Deferring the canonical notice frontier also preserves recovery when `load` resets the outbox on execution/generation/instance changes (`src/store/invitation_content.rs:417`). It does not undo another binding's legitimate presentation or existing frontier seeding rules. Pending warning wake evidence is read above the frontier (`src/store/attention.rs:1243`, `src/store/wake.rs:230`); retaining an outbox alone would not preserve it. Native threshold/idle/busy gates remain unchanged. The stated head-of-line backpressure is an explicit limit, not a promise that new urgent mail can bypass an indefinitely rejected native page; no ordinary-only lane is approved here.

## Bounds and required implementation proof

I independently recalculated the frozen maximum using compact JSON strings with 32 distinct 20-digit epochs and maximum u64 versions: stamp 82 bytes; receipt 2,802; escaped receipt 3,136; key array 2,145; empty-items envelope 5,350. Raw existing WatchLine objects replace already-counted JSON lines without double-escaping bodies, yielding a 70,886-byte maximum including framing. This fits the 73,728-byte transport cap, 8,192-byte metadata cap and 4,096-byte confirmation-input cap. The calculation is a design check only: tests must use the actual production serializers, including escaping and LF, and prove that every valid existing 64 KiB Watch page remains representable. Retained parser, receipt, key, protected-page and proposal bytes must all count inside the existing extension budget.

Implementation acceptance requires focused causal tests for:

- Exact `dn1` reconstruction, boundary integers, malformed/unknown versions and no effects on rejection; old wrapper decode and actual old-confirm/fresh-reoffer behavior.
- Deferred allocation, atomic confirmation, partial/already-covered prefix races, uncovered-gap refusal and malformed retired tags; default output/frontier compatibility and mixed-mode fencing/release.
- Same-scope restart and execution/generation reset before confirmation; stale leases, owner replacement, lost response and replay, without cross-binding frontier changes.
- Mixed Notice/Invitation/Attention pages, applied-clear-only pages, hidden Attention omission, partial native coverage and new-token/same-ID identities. Ordinary ACK/receipt/invitation acceptance must remain untouched.
- Empty hidden-token Unknown advancing to known without an external event, without confirm/restart, and with Close/cancellation observed between quanta; parked emitted pages must not busy-loop and confirmed pages must resume.
- Actual serializer maximum sizes, opaque u64 round-trip above 2^53 through u64::MAX, bounded stdin and aggregate extension memory accounting.
- Warning-only p0 arriving after `agent_settled`, with unconfirmed/confirmed frontier behavior and unchanged Native wake gates; lifecycle output must not settle omitted notices.
- Adapter saturation/reload/transformed-context cases against the real canonical path after the neutral seam has passed review.

## Review scope and evidence

Read the frozen design and adapter boundary assessment, and focused existing code for descriptor decoding/replay, confirmation, notice prefix/frontier seeding, lifecycle reset, exact Watch serialization, watch continuation, lease admission, wake selection and TRUST rules. During review, the original external-event-only handling of empty hidden-token pages was rejected; root and implementer incorporated bounded continuation into the frozen contract. The transport maximum was independently calculated without building or executing project tests. No production changes, builds, test reruns, credentials, shared services, threads writes or subagents. Only this report was written.
