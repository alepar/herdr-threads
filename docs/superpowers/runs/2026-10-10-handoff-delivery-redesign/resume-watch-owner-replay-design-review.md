## WRD-1 — make the accepted recorded-count domain explicit

**Priority P1; specification ambiguity with an already demonstrated failure mode.** Design line45 requires validation of “nonzero bounded Offer counts,” but never names the bound. Lines87/135 and WR2/WR12 emphasize three, without carrying forward the accepted distinction between the three-offer eligibility threshold and the full recorded-count domain. An implementation using `count <= MAX_OFFERS_PER_GENERATION` would reintroduce the exact CIR-1 regression already found and repaired in this task.

This is not hypothetical malformed state. `SeatOffers::record` saturating-increments the `u8` (`src/delivery/ledger.rs:196`); two independently selected due count-two offers can finish as three and four. V1 does not take the V2 owner permit. Current `validate_due_snapshot` deliberately rejects only zero (`src/store/invitation_content.rs:1773`). `presentation_capacity_retained_concurrent_offer_count_does_not_refuse_passive_work` (`tests/service/delivery_pull.rs:8747`) realizes the V1 before-record interleaving, verifies actual count four, and preserves independent passive progress. `capacity-implementation-rereview.md` explicitly accepted all nonzero `u8` recorded stamps, without clamping or adding serialization.

If new replay validation narrows that domain, the first pull for a replacement Watch fails before replaying the pending message or independent outbox/passive content. Reconnecting again leaves the same offending stamp. Exact stamp equality does not cure this: the rejected stamp is the genuine current stamp.

**Minimal fix:** replace the ambiguous validation requirement with “accept every nonzero recorded `u8` count (1..=255), including counts above three produced by supported concurrent recording; zero is invalid; exact full stamps are retained unchanged; `is_due` alone parks logical retries at count >=3.” State that the sequential 60-second/three-offer policy does not newly strengthen cross-route serialization. Add an owner-replay variant of the existing count-four interleaving: a newly admitted Watch replays that pending ID immediately, leaves all four fields unchanged, permits independent nonordinary output and does not create another logical offer. Preserve the zero-count rejection test. Put these requirements in the JSON as well.

The design does not explicitly demand the incorrect <=3 check today. The finding is that it leaves this load-bearing choice ambiguous despite an accepted, source-supported contrary disposition; resolve it before handing the design to an author.

## WRD-2 — specify mode-aware continuation and wake bookkeeping

**Priority P2; quality/dataflow gap.** Lines85–89 correctly require physical offered/truncated metadata and bypass of `record`, and line116 requires independent owner/ordinary/nonordinary continuation. However, the proposed output contract gives only completed/emitted replay subsets. It does not explicitly separate the existing two uses of page metadata that assume every ordinary output is a logical offer:

1. The allocator forms `consumed` from every `offered`/`truncated` ID and passes it to `ordinary_runnable` (`src/store/invitation_content.rs:2467–2479`). At zero capacity the helper excludes those IDs because ordinary recording is expected to make them non-due. That exclusion is false for physical replay. With 255 parked count-three offers and one due count-two offer sorted into the final owner-replay page, the last physical page can exclude the only logical due key, empty the owner worklist and return `more=false`, even though no logical stamp changed. No subsequent attention is guaranteed. Physical delivery did occur, so this is not a claim of lost pending body; it is a violation of the proposed independent logical-runnable continuation rule.
2. Service bookkeeping currently assigns `entry.more_pending = page.more && any_physical_message` (`src/service/delivery_presentation.rs:235–236`). Filtering the replay IDs in that expression would avoid asserting new wake work but would assign false on every replay-only page, clearing preexisting native outlook. The requirement that replay cannot affect native outlook needs to mean preservation in both directions, not just preventing a new true value. Outbox/control-only calls during an active replay pass also need a stated rule. `read_attention`/`whole_read` preservation alone is insufficient because `SeatOffers::next_pull` reads `more_pending` independently.

**Minimal fix:** explicitly distinguish ordinary source mode and logical-offer IDs from physical replay IDs throughout finalization. Pass only successfully allocated logical IDs as the consumed set for logical `ordinary_runnable`; physical replay never consumes a logical due episode. On owner-replay calls, preserve the current `more_pending` value in the post-store ledger critical section (including a concurrent V1 update), and never derive it from combined owner `Page.more`. State the equivalent rule for outbox/control-only calls while replay work remains. A small internal mode/disposition field is sufficient if the existing emitted subset cannot distinguish an empty replay quantum from ordinary allocation. No wire field is needed.

Add focused tests with (a) the final-full-page single-due-key arrangement and (b) initial `more_pending` both true and false, empty/missing replay quanta, mixed nonordinary output, and a concurrent V1 change. Assert logical continuation according to the selected rule and unchanged native outlook fields/`next_pull` apart from real canonical settlement or independent legitimate logical work. Do not use a native wake assertion alone while the channel is Live: registry suppression would mask a corrupted outlook until handover.

If the parent instead intends physical replay to suppress one otherwise runnable logical continuation, document that policy explicitly; it is not the independent OR formula currently specified. Preserving existing ordinary scheduling is the smaller correction.

## Sound portions and implementation gates

- The registry Entry is an appropriate owner for the once-initialized state: its 64-entry admission bound and lease replacement lifetime solve the same-lease ledger-eviction tombstone problem without historical lease retention. The 256 full-stamp key bound is adequate; no body needs retention. Exact incumbent lease checks plus the existing per-seat permit can serialize initialization/application with register/unregister/close. Grace entries have no replay authority.
- Canonical admission precedes replay. Reusing the exact hydrator preserves instance/publication, sparse manifest-first effective receipt, recipient and lazy eligibility. A missing key can finish a physical attempt without providing terminal proof or releasing a logical slot. Current exact-key SQL already has the declared charged envelope; implementation still needs executable evidence that it selects this path once and never also runs normal/due work.
- Outbox-first behavior is compatible: original token/descriptors/slots and codec can replay/confirm before the owner continuation. Including owner debt in the outbox reply avoids ordinary-only loss behind a successfully confirmed mixed old page. No ordinary Message descriptor or ACK authority belongs in that outbox.
- Stable owner replay is finite under the stated successful-call/eventual-quiescence conditions: bounded attempts, <=32 hydrations, rotation, no refills and terminal standalone-render failure. Original ordinary cursor/carry/partial/scan progress can remain byte-identical. Source-mode selection must happen before the existing positive-capacity normal query/reset branch, not merely inside output class0.
- Full-stamp/incarnation pruning at snapshot and successful application is necessary. It may abandon obsolete candidates but must not rewrite newer offers or initialize a replacement lease. Failed/refused store work must produce no initialization or attempt progress. Successful allocation followed by lost response may consume the current lease's physical attempt; a replacement recaptures pending logical IDs. Those are stated accepted local-lifetime limits, not receipt settlement.
- Current Watch renders typed items and independently records truncation after successful output; keeping offered/truncated metadata physical is compatible. Existing `AckModDelivered` remains the only cooperative ordinary/lazy settlement in this path. The proposed exact-key body assembler preserves promoted-lazy marker reconstruction. No new model-visible framing is required.
- Clarify that normal due-cache scope maintenance may still run as existing independent maintenance; owner attempt results themselves must not populate or clear ordinary due deferrals. The design's “cannot change ordinary due deferrals” should not accidentally disable preexisting render/publication invalidation.

Required tests remain substantive: actual immediate reconnect, initial Watch after Hook offers, 256-capacity replacement with unknown257/partial preservation, mixed old outbox replay, sparse and physical fallback, lazy/promotion/truncation, stale/grace owners, deterministic store overlap and ledger recreation, rollback/lost-output, exact budget counters plus real encoded bytes, and finite same-lease quiet. Add the two findings' boundary cases rather than weakening those gates. No separate architectural blocker was found in fencing, sparse receipt semantics, lazy settlement, or the declared fixed work/memory bounds.

**Disposition:** revise the two artifact requirements, then perform a scoped independent rereview before source authorization. This review does not clear implementation, current whole-D activation or merge readiness.
