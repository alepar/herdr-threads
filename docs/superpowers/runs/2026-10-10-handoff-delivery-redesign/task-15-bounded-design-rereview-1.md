## 1. Exact Watch lease and deciding fence

Actual interfaces confirm there is no exposed owner fence. `LocalService::watch_register` (`ports.rs:3734`, `service/dispatch.rs:915`) returns internal `(ModChannelId,u64)`. `daemon/transport/watch_connection.rs:157` discards the channel identity from `WatchAccepted`; `protocol/watch.rs:281` carries only attention version. `ModChannelRegistry::register` (`service/mod_channels.rs:496`) replaces the per-seat `Entry.channel`, while `ModChannels::is_live` explicitly accepts generation plus reconnect/rebind grace and authorizes existing receipt ACKs. Reusing `is_live` for new presentation would be incorrect.

Concrete minimal wire selection:

- Add optional `presentation_v2: true` to `WatchRequest`, serde default/skip-absent. A capable new watch client probes `delivery.presentation_v2` before sending it. Historical watch requests and historical Accepted replies remain unchanged when absent; old daemon deny-unknown parsing is never exercised with the new field.
- Add optional `presentation_lease` to nested `WatchAccepted`, exact32 lowercase hex characters, emitted only for the explicit capable request. The existing nested Accepted type accepts unknown fields, but preserving absent-case bytes avoids relying on that for compatibility. Lease is freshly random per accepted registration, retained only in the process-local current live channel entry, scoped to instance/daemon boot/seat/generation/native session/internal channel. A daemon restart has no live lease; reconnect/replacement gets a new one.
- V2 `consumer: watch` pull/confirm requires this exact lease. `consumer: hook` forbids it and retains unchanged `hook_pull_view` admission, including NoHookPull. A claim or generation alone never authorizes Watch presentation. No arbitrary consumer namespace is introduced.
- Expose a neutral `ModChannels` current-owner admission operation with an inert default that refuses. Its implementation requires exact **Live** lease/channel/generation/native-session, never grace. It returns or executes under a bounded per-seat owner permit through canonical allocation/confirmation. Replacement, unregister and close must serialize their ownership transition against that permit. Do not hold the registry's global state mutex across a database operation: this would violate the registry's documented lock contract. A dedicated per-seat owner gate with call-budget-aware acquisition is suitable; the same gate must survive entry replacement so an old permit cannot protect a detached Entry. Read-only lease checking followed by an unprotected deciding transaction is not a fence.
- Confirmations still check exact outstanding/last-confirmed page token in the store. Replacement revokes the old lease, **not** fixed Watch progress or outbox. The replacement owner replays that outbox under its fresh lease. An old confirmation cannot retire a successor page. Refused owner admission performs no content progress, allocation or confirmation mutation.

This is a bounded neutral interface extension, not new caller verification: the existing accepted cooperative watch channel remains the authority. The chosen per-seat gate/lease implementation needs explicit mapped ownership; it cannot remain the checkpoint's conditional "if not exposed" prerequisite. Required tests: absent watch request/reply exact bytes, old-peer no new field, wrong/missing lease, grace refusal, replacement racing allocation/confirmation, disconnect/restart and replacement replay of the same outbox. Existing message `AckModDelivered` grace semantics stay unchanged.

## 2. Preserve ordinary bounds; keep five-way output fairness

Parent scope clarification permits independently declared invitation/message/notice work bounds. The checkpoint's stronger single100 total with20 ordinary candidates is not required and currently has no owned API. The actual ordinary V2 query in `store/queries.rs::inbox_v2::query` already has `CANDIDATE_LIMIT=100`; `scan` returns `(item,work)` and accounts lazy candidates, `scan_effective_receipts(...,1)`, and warning physical/published merge probes via `scan_global_logical_candidates(...,2)`. Its source `State` stores finite highwaters/cursors. `service/delivery_pull.rs::StorePageSource` currently calls that public query through the generic `PageSource` abstraction and can drain4096 pages; that abstraction does not expose work counts or an invitation exclusion mode.

Recommended narrow selection, replacing only the arbitrary all-source algebra:

1. Keep invitation fresh-allocation work at100: initial40, context inspection/expansion40, revisit/cleanup20; lend unused invitation quota within those classes. Replay performs no fresh allocation and revalidates at most32 invitation descriptors. Topic inspection and expansion share their40; cleanup consumes up to10 of revisit20. Keep the already selected exact ordered indexes and finite highwaters.
2. Add one **internal** ordinary-only page operation by factoring the existing `inbox_v2` implementation. It runs at most one current100-candidate query page per V2 quantum, marks Invitations done/excluded **before capture/scan**, and does not execute the legacy invitation seek. It returns the existing bounded item page, continuation and actual examined count (including both warning merge probes). Keep public `InboxBatchV2` behavior and cursor wire unchanged. An ordinary-only cursor is scoped/tagged internally so a public/default cursor cannot silently re-enable invitations.
3. Retain ordinary-only continuation plus any partial assembler state between successful quanta in the existing generation-scoped delivery/Watch state. Do not restart it at cursor=None on every quantum. Losing process-local ordinary state on restart retains existing at-least-once message semantics; durable invitation state remains separate. Source cursor advances only after an item is either carried/recorded under existing message semantics or retained as bounded pending assembly/output, so a fetched-but-byte-withheld ordinary item is not discarded. One ordinary page provides <=32 bounded source items/64KiB encoded page, in addition to existing assembly/offer ledger bounds.
4. Existing hook notice read remains one indexed page of `MAX_NOTICE_PAGE_ITEMS+1 = 17` (`results.rs:1208`, `attention.rs:841`), with its existing bounded carried-prefix settlement re-read of <=16. This is17 inspected notice candidates plus up to16 settlement validation rows, not an invented20 budget. Fixed per-item indexed canonical/topic/author checks are separately stated. Watch notices/warnings keep their actual ordinary source behavior; do not create a second notice settlement route solely to match hook presentation classes.

Thus a fresh Hook quantum has at most100 invitation candidates +100 ordinary source candidates +17 notice candidates, plus <=16 existing carried-prefix validation rows and fixed binding/highwater/context/key probes. No claim that this sums to100. Warning merge losers count toward the ordinary100 even if no matching output survives. A replay quantum has <=32 invitation descriptor validations and no fresh ordinary/notice work; it cannot perpetually block fresh progress under the successful-confirmation premise. One call is not a4096-page drain. H/D/I accounting stays untouched.

Five-way rotation remains **output** arbitration: ordinary message, notice, initial invitation, context invitation, revisit. Source discovery order must not consume page bytes before the selected first-output class receives its full standalone allowance. When an invitation class has priority, its producer must run first or its allowance must be held before ordinary page admission; reordering only an already-filled assembler is insufficient. Borrow unused quotas/slots, rotate after successful fresh quantum, and leave failure rotation unchanged. Class active means it has an eligible output candidate; an insufficient-size incomplete obligation must not cause repeated empty pages or consume first priority forever. The remaining descriptor/frame memory bound must include the one bounded ordinary page and existing message assembler, rather than claiming only invitation descriptors exist in memory.

This operation is a narrow factoring of existing code, not new message policy. If the implementer instead chooses an actual20-candidate internal adapter, it can reuse the same scan work counter, but that stronger cap is unnecessary. Persist which alternative is selected and map the private ordinary-only helper/continuation owner before authorization.

## 3. Continuation and quiet-state decisions must precede suppression

The selected proposal says continuation drives yielded calls, but the actual gate order matters. `service/delivery_pull.rs:281` can return Unchanged before constructing a source, using process-local whole-read/offer state. `cli/watch.rs:465` blocks waiting for a new Attention after its drain. `ModChannelRegistry::observe_fingerprint` emits no new signal when recipient content version is unchanged. Without explicit integration, a first bounded quantum can leave initial/context/revisit/outbox work silently parked after a stable-version reply.

Required concrete V2 sequence:

1. Validate binding and consumer/lease. In a bounded canonical probe determine outstanding page and each unfinished initial/context/revisit/dirty-sizing frontier, plus an eligible incomplete item and producer source continuation.
2. Resolve a supplied exact confirmed token; replay a remaining outbox **before** any Unchanged/whole_read decision. Already-confirmed tokens are idempotent. A replay from another prefix uses its frozen prefix/render key and residual budget. No fresh message/notice allocation accompanies replay. Revalidated empty outbox becomes obsolete and reports continuation for a subsequent fresh quantum.
3. Return V2 Unchanged only when no replay, unfinished captured walk, eligible revisit/sizing work, ordinary continuation or existing due/message/notice output remains. A stable attention/content version does not veto these. A permanently insufficient item with unchanged render key does not count as immediately runnable continuation after its sizing debt is exhausted.
4. Watch, after complete successful output+flush and confirmation, issues one next bounded call when `more`, yielding/checking parent/channel liveness between calls. It does not block for Attention while continuation exists and does not run a new idle turn merely for Lazy work. Hook exposes truthful continuation and serves the next successful in-turn hook opportunity; there is no unbounded hook loop or Lazy wake. Empty maintenance progress can return an empty page with `more`, but should not inject the static frame header alone.
5. ModRefresh owns separate notification-only maintenance cursors. If a40-context/20-lifecycle quantum has unfinished maintenance, the existing worker schedules another bounded pass/yield until that finite capture completes; no recipient Attention is emitted merely for unrelated-row advancement. Only a relevant recipient content-key change produces a passive drain signal. It does not advance Hook/Watch presentation progress or mark a warning offered. No wake/stall changes follow from maintenance alone.

`NextPull`/whole_read's ordinary-message bookkeeping must not be taught that an invitation outbox confirms a message or clears an origin warning. Native eligibility of still-open sender/inviter warnings remains canonical and independent of FULL OFFER, replay, stable content version and informational frontier settlement. Keep D's independently demonstrated scheduler warning exception; no H/D/I driver work is added.

## Contracts now resolved in principle

Current-state PKs with generation/execution in values remove per-episode multiplication. The remaining retained-invitation cleanup debt is honest and bounded by retained canonical items times two fixed consumers, with eventual cleanup under continued calls. Latest-context plus a monotonic invitation command epoch handles requirement attach/release and None->required->None. Coherent topic/context writes and checked actual UPDATE count prevent old-key/new-text or overflow publication. Fixed Hook/Watch rows with one partial and one complete logical allocation each give <=2 complete allocations per unchanged key/binding; physical replay is separately at-least-once. Prefix changes invalidate sizing without resetting counters; unfinished finite dirty-sizing walks must not restart. The final64KiB invitation frame cap, not ordinary8KiB truncation, governs full eligibility. Hook/Watch post-emit+flush evidence matches the parent-selected cooperative OUTPUT contract and explicit TRUST A7 limit.

Frame checks must run on actual `delivery::frame` output (`frame.rs` header, label JSON quoting, body indentation/line splitting), and Watch must check the equivalent eventual frame as well as bounded JSON serialization. A frame of65536 bytes does not imply a JSON object of65536 bytes, but existing1MiB generic transport is ample for the bounded escaped payload; no transport cap increase is necessary. Page token is optional when a fresh result carries only ordinary frames/no invitation allocation; a token is required for an invitation allocation. Empty obsolete replay cannot fabricate an ACK or acceptance. These exact result cases should be recorded in the wire schema, with complete counters committed only alongside a nonempty valid invitation outbox allocation.

The above three dispositions make the design concretely implementable without redesigning ordinary delivery.
