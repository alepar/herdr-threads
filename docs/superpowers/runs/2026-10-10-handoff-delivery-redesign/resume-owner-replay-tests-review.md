## Required revisions

1. **WR8/WR17: distinguish deterministic ledger simulation from actual V1 completion.** `presentation_owner_replay_preserves_post_snapshot_native_outlook_and_newer_stamp` (`tests/service/delivery_pull.rs:9912`) uses `Failpoint::connection("store.writer.acquired", ...)` to call `entry.record` and assign `more_pending`, `read_attention`, and `whole_read` directly. The seam is after the service's snapshot and before its post-store merge, so this is a useful, nonvacuous deterministic oracle for preserving the *current* ledger value and full stamp. It does not run a competing V1 producer or show that the specified outlook transitions arise through V1's real bookkeeping (`src/service/delivery_pull.rs:669–685`). WR17 and the parent plan explicitly require genuine V1 completion; WR8 also calls for genuine record/remove races. Keep this service oracle and add a supported V1-producer/scoped-ledger proof at the allocator/registry boundary. Current Hook and Watch adapter entrypoints are mutually exclusive; do not rewrite the claimant's binding/capability to force dual admission. State the lower boundary honestly. The registry lifetime test uses real recorder/registry operations but no actual overlapping V1 call or removal race.

2. **WR7: replacement is launched, but contention is not deterministically established.** `presentation_owner_replay_owner_permit_fences_replacement_during_store` (`:10119`) correctly waits for the pull's store pause and proves the registry's owner mutex is held with `try_lock().is_err()`. It then spawns `watch_register` and immediately releases the pause. The scheduler may start the replacement only after release; a passing test therefore does not establish replacement actually waited during the critical interval. The current permit assertion is meaningful and catches omission of the pull lock, but the stated replacement-race proof needs a barrier proving registration has entered its owner-acquisition path while the pull remains paused, plus an assertion that it cannot acquire/proceed until release. This is a test-proof gap, not an observed production race.

3. **Notice N2/N3: make negative and lost-outbox witnesses exact.** `presentation_watch_notice_continuation_preserves_remaining_confirming_condition` delegates to `presentation_notice_settles_current_execution` (`:5767–6035`). It creates a real, distinct RequireAck invitation before the second Warn and correctly follows only returned `more`, but discards the invitation result and never asserts its exact identity/RequireAck/pending state after informational notice settlement and at terminal quiet. Add those canonical assertions so “no Clear” cannot pass after accidentally losing the intended witness. The Watch positive helper deliberately loses output and replays before Confirm, asserting the token, `more`, zero ordinary visits, no later Notice, matching Clear and finite quiet; it does **not** compare the notice outbox's descriptors, retired/confirmed/slot masks or codec before/after replay. Reuse the exact retained outbox snapshot strategy from `owner_outbox_state`, and assert replayed Notice/control identity. The owner-outbox test covers a different mixed ordinary/invitation fixture and cannot alone prove the notice variant's exact retained state.

4. **WR9: owner-specific final-sizing failure and mid-work exhausted-budget progress remain unproved.** `presentation_owner_replay_refusal_and_store_error_do_not_consume_first_capture` (`:9802`) covers a writer error, a save trigger abort, pre-cancelled budget and foreign execution, then successful same-lease recovery. This is valuable rollback coverage, but cancellation before the request is not exhaustion after capture/attempt work, and there is no owner-replay final RPC sizing refusal/retry oracle. Existing generic sizing tests are not a replay-initialization/progress assertion. Add these seams if supported; if a final-sizing refusal is unreachable for valid bounded Watch input, document that with the actual bound proof rather than claim this test covers it.

5. **WR17 all-pruned active recovery needs a causal service oracle.** Parent's separate implementation review reports this as a confirmed gap and has authorized an author successor after the reviewed immutable checkpoints. The static mechanism is visible here too: registry snapshot keeps `active=true` from saved debt while pruning `remaining` to empty; store begins with RecoveryControlOnly but, absent `control_only`, overwrites it with Normal/LogicalDue based on capacity even when no ordinary logical item allocates. A resulting nonordinary Page can then assign native outlook in service. Neither the missing-key test (keys remain captured and are attempted) nor the new deferred-control test (`control_only=true`) exercises this seam. Add a same-lease, all-stamps-pruned, nonordinary-only Page test for both current outlook values and full read/NextPull state before counting the matrix complete. This report does not assess the forthcoming fix or its runtime evidence.

## Notice continuation quality

The prior unconditional 32-pull helper has been repaired: the loop stops at `more=false` or Unchanged, and its iteration ceiling is a failing guard. It requires initial more, confirms only actual output and checks matching epoch/version Clear. No third stimulus is supplied during the causal chain. The later CheckIn is after the Clear/quiet assertions and only checks frontier persistence. The Watch raw replay before confirmation is a deliberate lost-output scenario, not a retry mechanism that repairs a missing continuation after confirmation. These tests are **not vacuous**. Strengthen the exact negative/open witness and immutable notice outbox comparisons described above; do not replace the loop with unconditional pulls.

## Production correspondence and remaining limits

The reviewed production source uses owner mode at either capacity, routes through the existing exact-key hydrator, excludes emitted physical IDs from `consumed`, skips `SeatOffers::record` for them and guards native outlook assignment using explicit OwnerReplay/RecoveryControlOnly disposition. Snapshot/apply compare full scope/incarnation/stamps and installation follows successful store return. Those source facts agree with the main tested invariants. The disposition guard's all-pruned boundary remains the concrete exception described in revision 5; no claim about the forthcoming fix is made.

Coverage still does not establish every WR clause: first successful empty capture followed by new offers/signals/time as a distinct service oracle; all-pruned-on-this-call active recovery; actual concurrent V1 removal/outlook; explicit max+1/foreign-seat input rejection; owner final-sizing/mid-work budget failure; actual daemon restart; Hook/default-inert and unchanged fallback/probe effects across the selected compatibility union. Some are appropriately covered by unchanged existing tests/source bounds, but parent should map exact selected leaves rather than count new comments as proof. Aggregate bounds alone do not prove source exclusivity; retained-tuple, exact source selection, due-on-final-page and post-ACK normal counters are the stronger existing assertions.

There is no pure implementation-mirroring tautology in the main positive or retained-tuple assertions. Limits to avoid overstating: allocator-only `window.offers()==stamps` is inherently weaker than service record exclusion because that call never performs service bookkeeping; repeated pure getter equality is not evidence that store refusal cannot initialize; and scheduler thread spawn is not a barrier proving contention. The separately authored service/rollback tests address the first two boundaries, but the actual V1/contended replacement claims still need revision.
