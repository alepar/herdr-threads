## Concrete serialized-state risk requiring actual regression

Migration40 limits `ordinary_partial` to **16384 serialized UTF-8 bytes**. `invitation_content::pull` restores `Assembler.partial`, pushes ordinary source chunks, then `encode(&assembler.partial)` stores that map unchanged. `delivery/assemble.rs::emit_chunk` retains an incomplete message whenever its assembled raw body is **less than8192 bytes**. These are different bounds:8191 NUL/control bytes JSON-encode to about49KiB, plus message-ID/map structure. A legal64KiB OrdinaryOnly source page can contain an earlier complete message and a later partial highly escaped body smaller than8192 raw bytes, whose retained JSON exceeds16KiB. Saving then fails the CHECK and rolls back the source cursor, allowing the same valid chunk to fail repeatedly.

This is a source-derived serializer/schema mismatch, not an observed test failure. It was promptly relayed to coordinator/author. Required proof is a **real canonical OrdinaryOnly chunk-page RED**, not a fabricated oversized database row, followed by a measured supported-record bound or bounded alternative encoding. Preserve message semantics and the page/source caps. Do not increase the constraint by intuition. Include the map/message-ID overhead and the fact that source-page fitting can leave a small partial after previous items. An isolated all-NUL message on an otherwise empty page may produce a chunk larger than8192 and immediately truncate, so it is not necessarily the reproducer.

The distinct `ordinary_pending <=65536`, outbox payload<=65536 and descriptor JSON<=262144 constraints also need exact serializer witnesses, but I have not established a corresponding defect in those shapes. Ordinary pending content is transformed from canonical V2 items into WatchMessage/PresentationMessage wrappers and includes generated truncation commands; compare its worst supported serialization to its SQL cap, including prefix quoting and up to32 entries. For outbox descriptors, context keys are individually checked<=4096 and there are<=32 descriptors, so the262144 cap appears plausible; derive all field/label/range overhead and prove it rather than conflating descriptor size with body size. Frozen bodies are stored once in outbox_text, which is the right separation.

Two CHECK-limited consumers, one outbox per consumer and explicit bounded body/descriptor state match the selected shape. Removed-item rows remain explicit retained-canonical-item cleanup debt; no DELETE CASCADE performs an unbounded lifecycle walk. Consumer/item FK existence does not alone enforce invitation recipient/instance equality: current canonical scope, pending-projection hydration and typed writers are the enforcement path, which final integrity/corruption tests must cover.

Static query/index alignment is promising:

- Context seeks use `(instance_id,last_change_seq,thread_id)` with matching lexicographic order. Topic candidates increment visited before expansion/filtering; expansion rows share the context quota. Empty recipient expansion can perform one extra indexed empty seek **per visited topic row**, not merely two empty probes per whole class. ## Transaction, restart and schema validation proof obligations

`SqliteStore::presentation_pull/confirm` take the canonical writer and run under `execute_decision`; `connection.rs:388` starts BEGIN IMMEDIATE, commits only after success, and RAII rollback covers errors. Content state, counters, ordinary cursor and invitation outbox are therefore in one transaction at the inspected call site. Failure after item updates but before state serialization/save should roll everything back; the serialized partial issue above particularly needs that assertion. No database transaction spans socket/stdout I/O here. Replay revalidates canonical context and preserves token for survivors; empty obsolete replay clears token and reports continuation. Final tests must prove restart/lost reply/corrupt descriptor/retired generation and failed-confirmation cutpoints, not infer them solely from transaction structure.
