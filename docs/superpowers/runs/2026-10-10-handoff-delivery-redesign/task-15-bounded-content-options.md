## Alternative M: coalesced latest row per retained thread

Add canonical latest-topic-change row/index `(instance,last_change_seq,thread)` and topic_revision. Per-binding durable initial-invitation frontier/highwater and topic frontier/highwater are independent, with bounded partial-item revisit state. Read fixed-size candidate pages ordered by seq/thread, count EVERY examined row before recipient filtering, then fixed indexed seat/thread pending probes and canonical state checks. Unrelated topic changes advance only maintenance cursor, never recipient content version/output/nativewake or initial-walk reset. Sparseholes complete by indexed empty-range probe, not ordinal arithmetic. Snapshot completion advances to capturedhighwater; new changes enter a successor phase.

Storage O(retainedthreads +active binding progress +explicit bounded/reclaimed revisit state). No topic event log, recipient fanout worker or due-driver work. However mutable rows can move beyond a captured highwater: eventual latest-topic offer requires that thread's updates become quiescent plus successful fair pulls. Strict delivery of each captured change during continuous updates cannot be promised. Live initial/update reads can offer the same current revision a finite extra time during races unless persistent per-invitation revision state is added. Quiet unchanged canonical state must not rescan/reprint indefinitely. These are proposed accepted limits, not silently approved semantics.

## Alternative J: immutable indexed topic journal

### Proposed API and transaction boundary

Store API proposal: `advance_invitation_content(binding, mode, limits, render_context) -> ContentStep { blocks, continuation, relevant_version, inspected_by_class }`, where mode separates Pull from ModRefresh. This is a NEW store-port operation, not a claimed existing signature. Store owns canonical validation, progress, item completeness and bounded decisions; service owns final delivery frame composition. Canonical selected seq/revision/text and requirement metadata come from the same transaction, not an old candidate followed by newer live text.

A pull serializes allocation against the binding row in a canonical transaction, validates generation/execution, reads candidates, produces bounded content decisions and commits durable cursor/item changes together. Budget/DB/validation failure rolls everything back. Concurrent callers cannot allocate duplicate complete offers; stale callers cannot advance successor state. Source candidates advance only once either their presentation is allocated or their persistent incomplete/revisit obligation is recorded. Output-byte exhaustion without that recording leaves the candidate unadvanced.

Response-loss policy needs explicit review: committing presentation allocation before transport write can lose a reply. Recoverable delivery requires a persisted bounded pending-page/outbox plus page-token confirmation on a later pull (presentation confirmation only, never receipt ACK). Recovery replays the same logical allocation. Existing seen_attention_version alone must not be assumed to uniquely identify successive pages. Either add a scoped presentation token or explicitly accept lost-reply delivery; the latter conflicts with unconditional eventual display and is NOT the preferred proposal. Outbox payload is bounded32 blocks/64KiB and at most one outstanding page per binding; do not hold SQLite transaction across I/O. Review whether existing request/result wire can carry token compatibly before code.

### Exact work/output shares and revisit rules

Pull candidate budget100: initial discovery40; topic inspection/relevant expansion40; revisit/stale cleanup20. All physically examined source rows, including unrelated/stale/removed/superseded rows, count BEFORE filtering. Topic candidates and their invitation expansion both spend the same40 share; preserve current expansion across calls. Lend unused candidate quotas to active classes without exceeding100. Maximum two end probes per class per call, tracked separately as fixed indexed probes; no loop of zero-row probes. One candidate performs at most one source seek and a fixed set of canonical/context/item-key reads; requirement resolution must be reviewed for bounded indexed behavior.

Output32 blocks/64KiB: reserve8 slots for each active class before lending the spare8 and unused slots. Byte allowance is fair through rotating first-output class, persisted across successful calls; an item that fits a standalone supported page cannot starve behind earlier large blocks. Existing ordinary message/notice delivery also needs a declared output reservation/rotation so invitation progress does not starve or get starved; this is a REQUIRED interface-review question, not permission to consume all32 slots silently.

Mod refresh budget60: topic inspection/expansion40, lifecycle/cleanup20, no pull allocation; same count-before-filter and fixed-probe rules. Passive notification changes only on relevant canonical recipient changes. No nativewake/stall work absent existing wake_on policy; unrelated globaltopic processing advances maintenance only.

Incomplete item rules: allocate at most ONE partial notice per context revision, persist its missing/full obligation, then advance initial/topic traversal so1025 partial invitations cannot pin discovery. Full-context retry uses canonical goal hydration and item-key dedup, not V2 goal omission. Item is FULL only when complete context actually fits the allocated page; partial attempt never consumes its complete allowance. Initial and update routes share the row, so the proposed bound is at most ONE new COMPLETE logical offer per unchanged context revision (stronger than required <=2), plus at most ONE partial logical notice. Transport replay is the same allocation and is not bounded physical exactly-once display.

Persist required rendered byte length where determinable. Revisit only when a supported standalone budget can fit it, or when render shape/budget increases beyond the recorded failed class; do not retry unchanged insufficient capacity on every quiet pull. The index must select eligible revisits by budget, then spend20 on visited rows; initial discovery continues independently. Permanently oversized items remain incomplete with a usable inspector continuation, but that continuation does NOT satisfy full-display obligation. A later adequate supported budget activates automatic full retry without a new topic revision. No retry-count terminal state can suppress that later full attempt. There is one partial output maximum; failed sizing probes have a strictly increasing recorded byte-budget watermark (at most65537 distinct integer classes within current64KiB supported page range), and fresh canonical context revision resets that watermark. Re-render on changed command-prefix shape must have an explicit scoped invalidation/budget key; never pretend the old byte estimate proves fit for a different shape. Complete canonical read must distinguish omitted goal from truly full context.

### Persistence, retention, proofs and accepted limits

Live completeness storage is O(retained invitation items x retained binding episodes), not a1024 cache. Working memory is <=100 candidate descriptors plus32 blocks/64KiB. Current active binding has one row per touched retained invitation; stale binding/item rows require indexed bounded cleanup. Proposed minimum cleanup: spend up to10 of the20 revisit quota on ended-binding/removed-item rows whenever such rows exist, lending unused cleanup share. Discovery/revisit candidates canonically removed are deleted immediately within their visit. No unbounded multi-binding DELETE trigger on removal/retirement. Retained closed-item rows awaiting cleanup are explicit cleanup debt; total disk cardinality is bounded by touched retained canonical invitation/binding history, NOT strictly by currently pending count during arbitrary removal bursts. If a strict current-pending cardinality is required, additional producer-side bounded cleanup/retention policy is necessary; do not claim it already follows. Restart resumes debt/cursors and never LRU-evicts incomplete obligations. Binding generation/execution rotation begins a new presentation episode; retired episodes cannot allocate or resurrect output.

Finite initial snapshot of N pending candidates needs <=ceil(N/40) allocated inspection quanta plus fixed tail probes, excluding output backpressure; surviving fitting items receive fair standalone page space. Topic rows use captured highwater and seek-after keys; sparse holes close by indexed empty-range probe. A row moving beyond highwater enters a successor phase. Latest offer requires that thread to quiesce, continued successful passive calls and bounded competition; transient updates are not guaranteed. Independent initial traversal cannot be restarted by updates. Revisit uses finite per-class highwaters and rotates fairly; new obligations cannot restart the captured revisit walk. Partial saturation has no silent parking: every fitting surviving obligation eventually becomes a complete allocation. Relevant-version changes arise from canonical recipient changes only, never globaldecision_seq or unrelated topic events. Converged unchanged state uses constant indexed highwater/lifecycle/eligible-revisit probes, not a pending rescan.

Due H/D/I/global100 accounting and fairdriver remain EXACTLY unchanged. No topic-maintenance task is inserted into that driver. Bounded passive transactions must meet existing call budgets and not introduce unbounded writer holds; fresh review must inspect this scheduling seam. Original receipt/inviter warnings remain eligible after full/partial presentation, outbox replay, whole_read and Unchanged; final canonical settlement clears passively.
