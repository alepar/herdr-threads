## Strengths and settled parts

- Checkpoint lines 13-25 specify bounded, exact captured control tuples and an acknowledged subset rather than upgrading token equality into proof of every later-visible control. Whole-request tuple validation before proof maintenance or allocation is the right boundary; exact epoch/kind/version and original frozen-set membership prevent successor aliasing. Explicit malformed/duplicate/foreign-result validation avoids applying an uncaptured returned stamp.
- Lines 29-42 retain original descriptor positions and bounded retirement/confirmation masks. Preserving original identities as replay shrinks closes reindex aliasing; one current token plus one last-token record is constant-state storage. Old subsets cannot mutate a successor outbox. Recomputed acknowledgement applicability avoids resurrecting a retired episode in local seen hints.
- The selected input/output limits are finite: at most 32 tuples/descriptors, u32 masks, canonical 20-byte decimal u64 epochs, exact versions, unchanged 64 KiB output and 1 MiB RPC bounds. Additional result metadata must be included in existing actual serializer tests, as line 59 requires. This creates no receipt, invitation acceptance or model-uptake authority.

## Important findings

1. **Pending and mandatory durable Hook completion storage are not source-backed or concretely settled.** Checkpoint lines 31, 33, 39 and 46 introduce descriptor-specific Unknown/Pending, then mandate adding a persistent cache if existing completion cannot retain it. No actual submitted-stamp operation requiring such uncertainty is identified. Active D `src/store/invitation_content.rs:334-387` already keeps the last exact Open/Closed state, active epoch, allocated Attention and pending retired-episode clear. Unknown relevance preserves those facts. Once the client actually emitted an original frozen Attention stamp, its recorded episode is still applicable or has retired; a clear is judged from its exact retired-episode fact. An unrelated unfinished warning sweep is expressly insufficient to block confirmation. These fixed episode facts appear sufficient for a definitive confirm/obsolete decision without Pending.

   The helper does not have an existing durable completion cache: `src/harness/agy/delivery.rs:690-701` defines a bounded serialized payload, `:1242-1270` returns it in memory, and `:794-850` returns without hint/probation writes on an unsuccessful confirmation. `src/cli/hook.rs:273-282,2970-2993,3723-3727` carries and consumes that in-memory handle after actual emit/flush. Mandating a new cache therefore adds a real mechanism. Its exact path/schema/publication timing, retry trigger, original-route and digest guards, concurrency policy, expiration/reclamation and failure cutpoints are not specified by “existing isolated state ownership”; line 46 delegates that choice to the implementer despite line 61 claiming no unresolved choice.

   Recommended bounded disposition: remove Pending unless a concrete submitted frozen stamp cannot be decided from persistent episode facts; keep exact-subset same-invocation retries and canonical last-token idempotence. On lost/unknown confirmation response, perform no hint/probation success write. A later invocation may receive canonical replay and independently emit before confirming; physical re-emission is already allowed by A7. A response lost after canonical retirement may simply leave local hints unsaved; hints are not authority. No mandatory durable Hook completion cache or stronger physical exactly-once guarantee is needed for that contract. If parent retains Pending/cache instead, the full bounded lifecycle above must be selected in this checkpoint before implementation, with an actual reachable uncertainty case.

2. **Piggyback confirmation has no defined acknowledgement reply channel.** Lines 17 and 48 require piggyback to perform the same exact-subset confirmation, while lines 23-25 require the client to validate the returned status/acknowledged subset before applying hints. The document defines only the direct confirmation result. Active D `src/protocol/delivery.rs:232-254` still returns DeliveryPullReplyV2::Unchanged/Page/Refused, none containing a confirmation reply. `src/store/invitation_content.rs:469` currently discards the return value of confirm before continuing pull. A new Page's emitted_controls is not the acknowledgement of the submitted previous subset; it may represent later-visible controls or a successor token.

   Select an exact bounded piggyback reply field/wrapper available on every relevant pull outcome (including Unchanged, replay and refusal), carrying the requested token identity plus the same confirmation status/acknowledged subset, with omission semantics when no confirmation was submitted. Specify whether StaleBinding/NotCurrentPage stops pull before fresh work; the current checkpoint says these return without effects, so silently allocating a successor after that outcome would violate it. Alternatively explicitly remove piggyback confirmation from this refinement and use the separate confirm command. Do not let the author invent this interface or infer acknowledgement from Page metadata.
