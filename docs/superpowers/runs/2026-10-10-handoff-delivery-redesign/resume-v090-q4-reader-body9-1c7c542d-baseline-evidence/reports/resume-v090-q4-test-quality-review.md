## Canonical fixtures and reader causality

The six reader controls use the original control fixture only for host/seat/structural observations. They deliberately use `fixture`, not `bound_fixture`, and enroll through public DomainService CheckIn, retaining the returned canonical claims. Siblings have different native sessions, execution IDs and liveness fingerprints; exact BindingKey resolution and connected-binding checks prevent accidentally testing the same or superseded binding. The fixture does not launch those PIDs: they are local unit-test claim evidence, not real process integration evidence.

Pair Ensure, Lazy Send, Accept, Reject and later Invite all go through real service/store decisions. No positive setup writes a cursor, consumer, recipient, manifest, legacy flag or invitation episode. Send diagnostics verify modern `legacy_pending=0`, Lazy mode and recipient/message/manifest/instance/thread correspondence. Own InboxBatchV2 is claim-bound and requires a complete small public page, rather than looping until an expected answer appears. Its assertion extracts exact complete Lazy IDs/bodies with wakes=false. Public Message assertions inspect the canonical complete body before explicit display/completion mutations where relevant.

The six decisive oracles are not mirrors of a proposed predicate. They require initial body visibility with a missing cursor and unchanged authority; independent siblings despite shared Lazy display bookkeeping; an unshown early body blocking a later display; acceptance preserving unread content and established own progress; post-join enrollment keeping the seat maximum; and rejected cursorless readers failing to bootstrap by AdvanceCursors. The episode-2 control uses real rejection/reinvitation and verifies canonical decision ordering, then requires a fresh reader to exclude old history while an established reader retains it. Both CompleteInboxDelivery and AdvanceCursors must pass the excluded historical gap for eligible fresh readers, without changing the established sibling. Old recipient rows remain physically retained, ruling out deleting history to satisfy the oracle.

The store controls exercise the cooperative declaration boundary: invoking CompleteInboxDelivery/AdvanceCursors with IDs asserts complete display to the service. They are not evidence of terminal flush or model uptake. The real CLI controls below own flush attribution. Counts of receipts/intervals/wake state are adequate in these all-Lazy, initially empty authority fixtures; they are not broad exact preservation tests for preexisting mixed authority. The separate acceptance-private test is still needed for that richer state.

## Real CLI output and failure path

BodyFixture uses a UUID instance and real lifecycle enrollment with session-derived execution IDs so the actual ContextJournal/CLI path can reconstruct the exact caller. It creates the direct pair and messages through public operations. The LocalClient spy does not fabricate results: it forwards typed commands and OutputSpec to DomainService.handle_with_output, records the actual MessageDetails, and checks a successful writer flush before forwarding AdvanceCursors. The CLI still runs its real parser, journal, body-reader claim logic, mode query, selected encoder and canonical store.

The positive test publishes the actual 65536-byte multi-byte body, follows server-produced continuation argv and assembles exact body_data at successive UTF-8 offsets. It also checks the bytes emitted by the real text writer contain each returned chunk. The explicit 128-call ceiling is finite; every partial iteration requires no cursor and byte-for-byte unchanged consumer rows. The final result requires exact assembled body, one exact-claim/ID AdvanceCursors, the displaying binding's cursor at the body and the sibling cursor absent. Full row snapshots allow only the two Q3 private counter increments on A; B remains identical. This would detect missing canonical display progression even if the CLI sent an apparently correct mutation that the store ignored.

The negative test exercises actual JSON, machine, incomplete text, explicit nonzero offset, short-write-then-BrokenPipe and flush-error cases. Production `cli/output.rs:305–306` writes and flushes before returning; the test writer drives both error branches. Successful full nontext output remains read-only, and failures must return errors with no mutation in the captured command list, cursor or consumer state. These are synchronous in-memory writers; no stdout redirection, broken child pipe or spawned helper is needed. The flush flag is reset for each CLI invocation, so an earlier successful read cannot satisfy the later mutation's flush witness.

## Captured continuation and internal presentation scope

The continuation control requires the first real private pull to produce a truncated Lazy Message and an actual persisted Source::Lazy cursor pinned to the exact ID at a positive UTF-8 boundary. It never constructs or edits that cursor. After optional physical token confirmation, A completes the long body through real CLI continuation; B's entire captured consumer row and missing cursor must remain unchanged. Subsequent real store pulls, bounded to four calls, must consume the captured tail without another physical long-body item and reach the following targeted body. This catches leaving the separate continued-Lazy membership check unchanged after fixing fresh eligibility, and catches cross-binding destructive invalidation.

`private_pull` intentionally calls StorePort with fixed Watch render/lease input, empty logical offer sets and no due snapshot. This is an internal reader/continuation test. It does not prove registry lease election, public Watch admission, logical replay pacing or actual AGY native encoding. The proposal states that limit honestly; the unchanged registered actual AGY test and separate channel controls supply those boundaries. The `ordinary <= 100` assertion checks reported work only and is not a physical SQL-plan/VM proof. No review result should promote it to one.

## Resource and boundedness assessment

These modules create no child process, daemon, worker thread or shared Herdr resource. Therefore no process-tagging omission or live-run leak-check false positive is introduced. Test instance/database/journal paths are unique; completed fixture construction installs Drop cleanup for owned files/directories, including assertion-unwind paths. Construction failures before the fixture object exists can leave temporary files, as in the inherited fixture style; this is not a process leak and should not be reported as one. Cleanup does not access real user configuration.

All presentation/body loops have explicit finite iteration limits; small inbox reads require actual exhaustion. There is no polling sleep, background accept loop or unjoined worker. Inherited fixed-clock call budgets do not furnish a wall-time timeout if an unrelated internal deadlock is introduced, but these controls add no contention/wait mechanism and do not claim such a timeout. SQL accesses in the tests are local canonical diagnostics/snapshots, not mutations used to unlock the missing behavior.

## Remaining scope and evidence

Classify setup/admission/output-budget failures separately from the intended cursor/eligibility RED, and require the negative rejection/output cases to remain GREEN. Parent's runtime trace, not this static review, establishes whether each test reaches its decisive assertion. The explicit acceptance-only Hook/Watch invalidation control is separate and mandatory as already planned. Native/operator/service event-floor writer tests, virtual-floor rollback/overflow, stale historical completion, production SQL constants/plan controls and the full exact-bound accounting are not supplied by these nine controls.
