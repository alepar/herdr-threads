## Problem and selected repair

At zero ordinary offer slots, an unknown carried ID blocks the normal finite inbox walk. Its retained carry, unfinished cursor and unmatched scan signal all currently assert `more`; Watch immediately pulls again. Suppressing those reasons alone leaves due known IDs behind that carry forever.

Select **exact-key due traversal, with a bounded negative-attempt cache whose lifetime is the process-local offer ledger**. The durable ordinary cursor/carry/partial remain the only normal inbox traversal. When post-reconciliation slots are zero, park that traversal intact and spend its ordinary source allowance on due known keys instead. A missing key consumes a visit and is remembered for this canonical signal/render epoch; it cannot keep continuation alive. Output uses the existing message hydrator, assembler and final presentation sizer.

No public wire change, SQL change, extra durable body buffer, second pending-table scan, new wake source, or larger existing cap is needed. The cache is an optimization/progress hint, never canonical evidence or settlement. A restart already discards ordinary offers under DP5; discarding their negative-attempt cache with them adds no new restart limit.

## Exact private cache and internal port additions

Add to each `SeatOffers`:

```
presentation_incarnation: [u8;16] // fresh at entry creation; not caller chosen
ordinary_due: [OrdinaryDueCache;2] // fixed Hook, Watch indexing
```

`OrdinaryDueCache` has `scope: Option<DueScope>` and `deferred: BTreeMap<MessageId, OfferStamp>`. `DueScope` is `{execution: ExecutionId, ordinary_version:u64, passive_generation:u64, render_key:[u8;32]}`. Render key is the existing profile+prefix key, decoded to fixed bytes. `OfferStamp` is the existing `Offer` value (all four fields); reuse `Offer`'s existing Copy/Eq instead of a lossy timestamp-only comparison. There are at most256 keys, each a validated <=128-byte ID. No body, topic, prefix vector or rendered text is stored here. The cache's payload bound per consumer is256*(128 ID bytes + two i64 timestamps + u8 count + bool truncated), plus a <=128-byte execution and fixed scope. Rust allocator/tree overhead is additional but bounded by256 nodes; do not call this a serialized-byte cap. Two fixed consumers per at most4096 ledger entries is the global cardinality bound. Prune cache entries whose ID/stamp no longer equals the ledger's current offer on every snapshot/application; clear ID on `record`/`remove` as a fast path, and prune after `retain_pending` too.

Internal `PresentationInput` additions:

* `ordinary_due_snapshot`: optional typed snapshot containing the ledger incarnation, up to256 `(MessageId,Offer)` stamps, and the selected consumer cache. Service snapshots these under the same ledger lock as known/blocked/slots. The stamps may cover all known IDs, simplifying validation; they never exceed256.
* Existing known/blocked semantics remain. Validate known uniqueness, blocked subset, stamps unique and exactly matching known, cache <=256 and only matching stamp entries, valid scope bounds. Store rejects malformed internal snapshots before mutation. Legacy internal test constructors use `None`; `None` means no due traversal/cache, preserving their previous no-retry fixtures. Production V2 always supplies `Some`, even with an empty ledger. Do not silently allow a production full ledger to omit it.

Internal `PresentationOutput` addition: `ordinary_due_update: Option<OrdinaryDueUpdate>` with incarnation, selected consumer scope/cache, and the input stamps necessary to merge safely. `None` on refusal; an admitted Unchanged may carry an update. No cache survives a store error/rollback. `finish` propagates this along with the existing reclaimed delta.

After successful store return, service applies reclamation and page offer recording as today, then installs the returned consumer cache **only if incarnation and canonical ledger generation still match the snapshot**. Retain only entries whose exact current `Offer` equals the snapshot stamp. This prevents an old miss from suppressing an ID reoffered via another route while store work was running. Do not replace the entire seat entry or its offer map. The current per-seat V2 owner permit serializes Hook/Watch V2 and owner replacement; it remains held through this update. V1 may change offer values, so stamp comparison is still necessary. A evicted/recreated same-generation seat has a new incarnation and rejects the stale update. Native session/execution mismatch invalidates cache scope. No ledger mutex crosses DB work.

An admitted store call after publication advancement computes scope from current canonical `ordinary_passive_generation`, input `ordinary_version`, claim execution, and requested render key. Scope mismatch empties the cache; that includes an ordinary canonical signal or a changed usable render shape. Scope changes do **not** reset the durable normal cursor/carry/partial. New valid canonical material can retry a previously missing key after a signal. Time alone does not clear misses; a successful offer changes its stamp, so the next due episode cannot inherit suppression. Daemon/ledger eviction discards both offers and cache together, exactly DP5's lifetime.

## Exact allocation algorithm

1. Preserve admission, render/owner fences and transaction. Reconcile the <=256 offered IDs first. Compute effective slots from retained known IDs using the existing allocator, including same-call terminal reclamation. Remove reclaimed IDs from cache/snapshot eligibility.
2. Advance publication and relevance exactly as now. Build current due candidates in sorted ID order: known, not blocked, `retry_messages`, and not deferred at the current scope/stamp. This is a bounded in-memory set difference, not discovery. Merely testing this set consumes no SQL visits. The ordered set minus deferred keys is the finite traversal position; no second cursor is necessary.
3. Replays allocate no new message and perform no due hydration. Their `more` is independent replay/maintenance work OR current ordinary runnable work (below). Return applicable descriptors using the existing frozen profile/token. Obsolete replay retirement continues through the current path. Cache scope pruning may be returned; it records no presentation attempt.
4. On a fresh allocation, pick exactly one ordinary source mode based on **post-reconciliation input slots**, before normal query work:
   * slots >0: existing normal carry/query/partial algorithm. Do not additionally invoke due hydration, even if this allocation uses its last slot. The following call can switch modes. All already-known non-due skipping stays as now.
   * slots ==0: do not reset, fetch, consume or reserialize the normal carry/cursor/partial/skip/scan tuple. No `ordinary_presentation_page` call. At rotating output class0, traverse the current due-key set using the helper below. Other four classes keep current discovery and output opportunities.
   * control-only fresh call: perform neither ordinary source. Preserve its due candidates as continuation, independently of control continuation.
5. Due class0 loop has TWO limits: at most100 attempted keys (including misses) and at most32 hydrated presentation candidates, and always the global32 output blocks. Before each key, check `CallBudget`; error rolls back all private state and applies no cache update. Charge one `work.ordinary` visit before inspecting even an absent key. Query only that exact key.
6. A missing/nonpending/nonaddressed/wrong-mode/unpublished result adds that `(id,stamp)` to the current negative cache and continues to the next key. It does not reclaim that ID or alter count/timestamps. This distinguishes traversal progress from canonical settlement.
7. A canonical candidate is hydrated whole, passed through a fresh `Assembler` with the request prefix and no filesystem truncation hint; then converted through the same PendingMessage/output construction as normal allocation. Extract the existing assembly/conversion block into a small shared helper if needed. For due input there is one complete body chunk with offset0, so no durable partial is necessary. Reuse marker removal/reconstruction exactly once; preserve source `marker_lazy` separately from `DeliveryKind::Lazy` (wake-on-all promoted lazy matters).
8. Test `outputs + candidate` with the existing `Sizer::measure` once. On success append and add ID to offered/truncated exactly as normal; put it in a local consumed set so it cannot assert continuation before service records it. On failure when `outputs` is nonempty, stop class0 without consuming/defer-caching that key: it deserves a later standalone class0 turn. On failure with empty outputs, cache the ID/stamp for this render scope as unrenderable at the current supported limit and continue (up to32 hydrated candidates). Do not count a logical offer or truncate further. A changed render key retries it. This is a bounded eligibility deferral, not successful delivery evidence; see decision point below.
9. Never materialize due bodies in `ordinary_pending`. Hydrate one key at a time. The existing hydrator/assembler can transiently hold two <=65536 raw-body copies while slicing or assembling, then the <=8192 raw prefix plus marker; do not claim that these helpers are zero-copy. They never retain32 full bodies in a second buffer. Once selected or deferred the temporary body/assembler is dropped. Normal carry/partial are byte-identical throughout the zero-slot call.
10. Keep rotating classes and the current rotation advance on fresh nonempty output. At most32 due sizing attempts replace, rather than add to, the old at-most32 normal-message sizing attempts. One refused candidate after earlier-class output is retried when class0 gets first opportunity, within the existing five successful fresh-output rotations. Passive/control/outbox work continues independently.

## Continuation and finite-progress proof

Replace ordinary-only continuation reasons with one helper used by fresh allocation and replay:

```
normal_pending = carry_nonempty || ordinary_done == 0 || scan_signal_unconsumed
if effective_slots > 0:
    ordinary_runnable = normal_pending
else:
    ordinary_runnable = current_due_minus_deferred_minus_this_page_offers_nonempty
```

Here `effective_slots` in the continuation helper means **remaining capacity after this page's new-ID allocations**, not the mode-selection input capacity. Replay has no new-ID allocations and uses its post-reconciliation capacity. For the fresh normal branch, recompute remaining slots after its outputs; if it became full, compute the second formula for the reply. It is valid to leave due known IDs in carry while this formula requests one successor exact-key call. Carry, unfinished cursor, `retry_messages=true`, and signal mismatch alone never make a full ledger runnable. Never advance the scan's version/passive-generation just to quiet it: those remain unconsumed and restart/resume correctly when real capacity returns.

At positive capacity, finishing the finite normal pass with empty carry and a consumed scan signal ends ordinary continuation even if a conservative due offer has no canonical pending row. Neither `current_due_exists` nor `retry_messages` is a continuation reason in this branch. A later independently admitted fresh pull may start another normal pass under the existing retry rule; completion of the previous pass must not itself request that pull. This is equally the replay helper's rule: an outstanding nonordinary outbox cannot turn an exhausted positive-capacity normal pass back into ordinary continuation just because the ledger still contains a missing due ID. A new canonical signal remains a normal continuation reason, and when it is stable its successor finite pass can finish.

Compute nonordinary continuation with the existing independent publication/relevance/control/invitation/notice conditions. Store only this part in `outbox_more`; fresh page returns `nonordinary_more || ordinary_runnable`. Replay uses `state.outbox_more || publication/relevance current work || ordinary_runnable || relevance_unknown`, retaining current descriptor/token behavior. Crucially do not keep OR-ing the old composite `outbox_more` or raw `ordinary_signal_pending`. After actual confirmation/retirement, the finite fresh nonordinary pass recomputes its reasons. There is no global `slots==0 => !more` rule.

At a fixed scope and zero capacity, every examined due key either (a) is output and becomes non-due after ordinary ledger recording, (b) is deferred and leaves the current set, or (c) is withheld because earlier output used the budget. Case(c) produces fresh output and advances output rotation; it receives the full standalone allowance within the existing rotation guarantee, then becomes(a) or(b). No other zero-progress key loop is allowed. There are at most256 current IDs; missing canonical rows therefore drain in at mostthree all-missing fresh ordinary quanta (100+100+56), after which no due key asks for continuation. At positive capacity the captured normal traversal is finite; absent ledger IDs add no source rows and cannot sustain continuation after it finishes. A canonical ID made due after its source position was passed can be retried by a later independently admitted pull, as under the existing normal retry rule. All renderable due IDs get their second/third offers under continued admitted successful calls and eventual stable scope; no fourth is selected. New admitted time after60s changes due eligibility via offer stamps without a cache reset loop. Finite canonical/render changes produce finite restarts; infinite changes are not a claim of quiescence.

With zero due IDs and zero slots, ordinary contributes false on the first such call regardless of backlog size or partial/cursor position. Independent sources may require their finite existing quanta, then return Unchanged or a final Page with `more=false`. Actual Watch reaches its stream wait without a client drain cap. This adds no autonomous timer requirement and no idle wake: due work is checked when an admitted pull occurs.

Reclamation in the next call can make slots positive before source-mode selection. The exact normal tuple then resumes immediately in that call, with its frozen prefix and body position. A due reoffer may also still be present in normal carry; the ordinary blocked-ID predicate skips it on later resumption, preserving offer limits without destroying unknown siblings. No membership, receipt, lazy completion or invitation state is fabricated.

## Bounds, compatibility and failure details

* Ordinary physical work100; whole fresh433; reconciliation256/1280 unchanged; new due keyed allowance explicitly1303+100 seeks, mutually exclusive with normal query. At most32 due hydrated candidates/call and one raw body at a time.
* Final32 blocks/65536 actual encoded native or Watch bytes use existing Sizer/page. At most32 ordinary measurements in either mode; total352 candidate passes plus existing final RPC pass unchanged. Canonical max65536 body, ordinary8192 truncation, prefix8/4096, carry155731, partial49415, cursor8192 unchanged. Existing outbox and RPC envelope remain unchanged.
* No schema column, index, migration or wire field. Existing State readers/validators remain strict; cache input/output are internal typed state with explicit cardinality/identity/stamp checks. Hook and Watch cache slots are fixed, not caller namespaces. A newly created/empty cache defaults to no deferrals, so old/new fixed consumer rows retain normal durable continuation intact.
* Refusal or budget/render/store error never installs cache progress. Store success followed by lost socket still records the ordinary offer as existing policy does. Missing cache update after process crash cannot permanently suppress anything; ledger also vanished. Outbox replay cannot count due offers because it emits none.
* Full unrenderable due candidate remains known and pending, with unchanged offer count; current shape does not demand an endless continuation. Changed shape or one of the declared canonical scope signals allows another attempt. **Topic-only shortening is not guaranteed to retry a deferred candidate until a declared scope change occurs**: current topic affects the hydrated label, but its revision is not part of this cache scope. Parent accepts this narrow limit; document it in TRUST-POLICY.md in the same implementation commit. Do not extend invalidation scope or add a query solely to remove this accepted limit. No partial fallback beyond the ordinary inherited8KiB behavior.
* Check ledger `record`, `remove`, `retain_pending`, generation rotation and LRU recreation together. Returned cache merge filters by incarnation and exact stamp; V1 concurrency cannot apply an obsolete negative result to a newer offer. This does not add stronger cross-route offer-allocation serialization than the existing system promises.

## Alternatives considered

1. A second finite inbox cursor reuses query_mode most directly, but it traverses every retained receipt/lazy candidate to find at most256 due keys, needs another cursor/partial/body-skip state, and must distinguish multiple exhausted/missing-key passes. That introduces more durable state and much worse backlog-dependent latency; not selected.
2. Durable due snapshot/cursor or a second due carry can work, but needs new bounded columns/JSON schemas, serialization proofs, and ledger-incarnation coordination anyway because offers are process-local. Piggybacking metadata into the current155731 carry would invalidate its tight existing byte proof. Not selected.
3. Only suppress `more`, or advance past/drop unknown carry, or OR `any_due` into `more`: respectively starves known due IDs, loses mandated cursor/carry continuity, or spins forever on conservative missing known keys. Not acceptable.

## Revision round1 — CDR-1

Independent `capacity-design-review.md` found that positive slots plus a conservative missing due ID could keep `current_due_exists` true after every finite normal pass. Exact-key/cache progress runs only atzero slots, so that positive-slot formula would request repeated normal restarts forever. The report's counterexample is valid.

This revision removes due existence from the **positive-capacity** continuation predicate; it is exactly `normal_pending`. It explicitly uses capacity remaining after allocation for the fresh final predicate, retains exact-key finite continuation atzero capacity, and applies the same helper to replay. It changes no source-mode selection, query, cache invalidation scope, physical/keyed/byte bound, offer policy, or durable carry/cursor/partial rule. Added regressions cover reclamation plus missing due IDs with no replacements, initially nonfull missing-ID state, replay, a final page withremaining capacity, and last-slot consumption with and without remaining due work. The three parent dispositions are recorded above, including the topic-only shortening limit and same-commit TRUST amendment requirement.

No source or runtime validation was performed for this revision; only this artifact was changed. Production remains unauthorized pending independent scoped rereview. COMPLETE + QUIESCENT.
