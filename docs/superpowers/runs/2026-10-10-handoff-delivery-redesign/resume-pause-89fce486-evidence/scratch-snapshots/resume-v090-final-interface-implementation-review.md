## Findings

### IF-1A — Blocking: modern ordinary DirectSend omits independent send-time capability negotiation

The new client can create an ordinary ACK obligation on a daemon that has not advertised `messages.send_time_receipts_v1`. This contradicts TRUST-POLICY.md:648–650, which requires explicit discovery before a new ACK-required send and forbids a legacy fallback. This finding applies to a newly created modern `Some(creation_policy)` + Ordinary DirectSend independently of any historical compatibility argument. A selective capability responder advertising direct + Ensure-policy while omitting send-time is not malformed: capabilities establish independent semantics, not an inferred all-features version gate. The composition plan explicitly identifies this direct-send requirement at `upstream-478ec4a9-composition-plan.md:27`.

**Direct send:** `src/cli/direct_send.rs:174–195` checks `thread.direct_v1`, optionally `direct_threads.ensure_creation_policy_v1`, and optionally `send.lazy_v1`. It never checks the send-time capability when `lazy == false`. New start invokes that check before recording at lines 266–286. Retry invokes it at lines 378–383, then calls Ensure at 384 and `SendMessage` at 427. `src/cli/mod.rs:3550` handles DirectSend in its own branch, bypassing the generic ordinary-send gate at 3581–3584. The retained DirectSend branch returns directly to this executor at 3630, before the generic retry gate at 3695–3698. The earlier recipient-resolution check at 2795 applies only to `MutationSpec::Send`, not DirectSend.

New modern direct sends accept a responder advertising direct creation policy but omitting send-time semantics; capability conjunction must be explicit rather than inferred from another capability. The root design's Ensure-capability refinement at lines 119–121 explicitly exempts modern **Lazy** direct send from send-time while requiring its separate Ensure-policy capability. That exemption does not extend to Ordinary. Lazy direct sends must remain exempt from send-time.

### IF-1B — Blocking: pending historical ordinary retries bypass the receipt gate

**Contract and compatibility disposition:** `2026-10-10-handoff-delivery-redesign--receipts-design.md:52` and root design:90 explicitly say: “A pending historical retry on an unsupported daemon refuses before additional effects.” This followed original design roast round 1 R1-4 (`2026-10-10-handoff-delivery-redesign-roast-design-1.md:18–21`) and the settled capability contract in `roast-fix-ledger.md:7`. TRUST-POLICY.md:655–658 also conservatively gates ordinary commit-unknown retries/pending replay while preserving immutable bytes. The later root refinement at 107–112 preserves historical **invitation** timed behavior when Ensure policy is absent and still requires applicable receipt capabilities before effects; 119–121 preserves historical fields/bytes and completed inspection while defining the separate Ensure-policy gate. It does not expressly withdraw the pending ordinary receipt rule. These requirements can all hold together: preserve `None` exactly, require no new Ensure-policy capability for that frozen request, allow completed inspection unchanged, and refuse an unfinished ordinary send against a daemon lacking receipt semantics. The finding is about the last operation, never about rewriting None or gating completed inspection.

**Historical direct send:** a retained original has `creation_policy: None`; its exact serialized Ensure remains understood by Main565. Main's `src/protocol/capabilities.rs` advertises `thread.direct_v1` and has no send-time capability. A pending retained ordinary direct send whose child Send has not committed passes the same discovery described in IF-1A and can submit a fresh old-timing obligation. This is a concrete published-peer route, separate from IF-1A's selective-capability modern route.

**Automatic delivery/existing-pane handoff retry:** `src/cli/handoff_delivery.rs:1807–1818` puts the entire completion-status and `require_policy_capabilities` block inside `policy.is_some()`. An original with historical `None` skips it, calls Begin at 1833, Ensure at 1837, and Send at 1874 when not completed. Public dispatch in `src/cli/topology_runtime.rs:709–721` requires only the old automatic capability before calling this executor. The early completed-result dispatcher at 172–212 only returns early when canonical status is already Completed; an unfinished operation continues to the affected executor.

**Automatic new-tab bootstrap retry:** `src/cli/topology_handoff/automatic.rs:338–348` makes the same `Some(policy)` mistake before Begin/creation/attachment processing. `resume_to_writer` later sends the child at 728–732 if `progress.message` is absent. The public runtime's automatic-bootstrap retry dispatch at `src/cli/topology_runtime.rs:676` has no send-time gate that repairs this omission. Historical automatic requests retain the released shape and are understood by Main565. Native work may also occur before this unsupported timing is discovered, because it is never discovered on this path.

**Source verification/refutation:** compared Main's capability list, followed the public specialized dispatches, inspected the generic gate and all occurrences of `require_send_time_receipts_capability`/`require_policy_capabilities`, and checked that historical option omission is intentional in the protocol serializers. Generic ordinary sends, persistent service sends, legacy explicit delivery retry (`handoff_delivery.rs:768`) and legacy launch retry (`handoff.rs:968`) do have a send-time gate; they do not cover these branches. Existing direct-send tests remove the creation-policy capability, not the send-time capability, so that negative control does not exercise this gap. No runtime reproduction is claimed.

**Fix shape:** require send-time semantics independently of invitation-policy presence before any specialized unfinished path can create an ordinary obligation, preferably before earlier durable effects. Continue requiring invitation/Ensure policy capabilities only for explicit modern policy. Preserve exact original claims, historical omitted fields, child keys and digests. Preserve canonical Completed/retained-result inspection without demanding a new-send capability; do not blanket-gate every status/read or turn a completed record into a new mutation.

**Required focused controls:** new ordinary direct send against a capability list missing only send-time must refuse before journal publication/Ensure/Send; Lazy direct positive remains supported. Historical absent-policy direct and automatic delivery/bootstrap retries with an uncommitted child Send must refuse against an old-capability responder without changing original bytes, progress or canonical rows/native effects. Supported retries and completed retained results must still work. Both absent capability and refused discovery should be covered. These controls are proposed, not executed by this reviewer.

### IF-2 — Nit: historical automatic identity overflow reports the modern ceiling

`src/protocol/handoff/automatic_bootstrap.rs:157–167` enforces 131072 bytes when the frozen policy is absent, but always returns `automatic bootstrap original exceeds 512 KiB`. A historical original between 128 KiB and 512 KiB therefore receives a false threshold. The actual refusal is correct and the historical capacity remains intact. Use the selected limit or neutral retained-capacity wording, as the attachment validator already does. This is diagnostic only; no request/migration bound should change.

## Accepted limits and rejected candidates

- Post-flush physical confirmation is cooperative output evidence, not model uptake. A crash between flush and confirmation can replay; ordinary logical offers and durable nonordinary outboxes have intentionally different lifetimes. No exactly-once guarantee inferred.
- Failed or AlreadyConfirmed Watch confirmations do not create fresh channel health. Fresh applicable Attention confirmation is a publication cutoff, not a restarted stall timer; registry health and durable confirmation are not atomically persisted.
- Passive publication scans, work hints and reader invalidation do not grant a native wake. Process-local replay/hints can be discarded on replacement/restart; no durable recovery promise added.
- Q4 acceptance/read fanout and inherited public reads are not globally constant work. The private presentation counters are source-accounting bounds, not measured SQLite VM or elapsed-time claims. Physical controls are still required.
- Q5 normalizes known generated typed argv, not arbitrary shell text. Its shadow parse does not repair inherited option-looking literal spellings that independently need CLI escaping; the implementation comment states that scope. Final decoration may refuse an insufficient original budget before output/display effects. Neither is a reason to loosen cursor/row guards.
- A capability flag is a semantic contract, not version attestation. IF-1 requests the existing explicit capability check, not adversarial caller verification, a version gate, new provenance, or a historical-blob rewrite.
- No other concrete interface/transport defect was established in this pass. This statement is source review only and is not a runtime, formal-roast, merge-readiness or whole-store clearance.
