## Requirements

- R1: Absent/false Watch opt-in serializes exactly as the historical claim-only request. Historical Accepted omits the presentation lease. Legacy registry behavior includes the existing `1/1 -> 2/2 -> 3/2` sibling fingerprint oracle.
- R2: A channel is capable only after explicit negotiated opt-in; capability advertisement, a generated lease, a V2 RPC or another binding's election cannot silently promote a legacy channel.
- R3: Capable registration, worker passes and Pull/Confirm never invoke `mod_binding_view`, `seat_digest`, `binding_unread_stats` or another legacy aggregate. Dinv and ordinary passive content use their bounded private sources.
- R4: Actual publication and the current canonical binding's reader state determine eligible ordinary content, including a sibling-settled message that this binding has not read. Initial Accepted drain, continuation, wake signals and idle wake permission are distinct.
- R5: The new passive invalidation, recheck hint and drain frame create no `wake_work` authority, native wake, receipt obligation, receipt evidence, invitation acceptance or additional channel health timestamp. Actual passive display may still call its existing completion/ACK route; preserve that route's canonical settlement and health policy, including `AckModDelivered::AlreadySettled -> record_ack`. The existing `wake_on: all` exception remains canonical. A generating/tool-running session receives in-turn content, without an idle nudge.
- R6: Existing exact Live owner, seat/binding/generation/session/execution and replacement fences remain. Grace never gains V2 authority. New private progress commits only with its canonical operation; rollback/refusal installs none.
- R7: No migration, global output version, recipient fanout at publication, new wake timer or unbounded binding-history update. Existing numeric work/output/storage envelopes remain unless a measured explicit adjustment is reviewed.

## Selected negotiation

Add **`mod.watch_presentation_v2`** beside the existing capabilities. Its precise meaning is support for the explicit Watch registration opt-in and mode-bound Accepted lease, not a redefinition of `delivery.presentation_v2`. Advertise it only with the complete handler.

The CLI elects the new channel mode only when discovery includes all of `mod.watch_v1`, `delivery.presentation_v2`, `mod.watch_presentation_v2` and `inbox.binding_cursors_v1`. Discovery error retains the current retry/refusal behavior. Missing only presentation prerequisites keeps the historical Watch path and its existing conditional binding-reader selection. Do not infer support from a harness version, daemon version or a lease unexpectedly returned by an old peer.

Extend `protocol::watch::WatchRequest` with `presentation_v2: bool`, `#[serde(default, skip_serializing_if = "is_false")]`. False/absent has identical encoded old bytes; true adds the JSON member `,"presentation_v2":true` (23 bytes). Strict type/unknown-field rejection remains. There is no new model-visible framing string.

`cli::watch::probe_mod_watch` records the conjunction above; `run_session_marked` passes it to `open_watch`; that function sends true only for the negotiated conjunction. V2 execution still additionally requires a valid Accepted lease. A capability-absent peer receives exactly the old request even if it advertises the older `delivery.presentation_v2` alone. This explicitly supports old unlanded D strict request decoders without pretending they accept the new field. The parent's supplied released Main565 lacks V2; that fact is evidence, not an operational version gate.

`WatchAccepted` needs no new field: its existing optional lease acknowledges the requested mode. Only explicitly capable registration yields a lease. Legacy Accepted contains the original attention version and omits the lease. The client ignores any unsolicited lease when it did not negotiate the conjunction. Missing/malformed lease retains the existing client fallback behavior; a conforming new daemon must never register capable mode and deliberately return an absent/malformed lease. The transport test makes that pairing an invariant.

## Service and registry split

Add a neutral internal `ModChannelMode { Legacy, PresentationV2 }` (or equivalent typed boolean) to `ModChannelRegistration` and registry `Entry`. The field is immutable for that channel id. Re-registration replaces the entry under the existing owner permit and chooses its own mode; it does not mutate a sibling or upgrade an existing lease.

`DomainService::watch_register` selects `mod_binding_view` for Legacy and `presentation_seat_view` for PresentationV2. Both retain the same A2 and push-channel binding admission checks. The new capability is a delivery-mode agreement, never caller authority. Direct service tests must choose the mode explicitly.

`ModChannelRegistry::pass` includes the snapshotted mode with channel/binding/session. Legacy uses the historical view and its `pending_invitation_version`, with no V2 passive refresh. PresentationV2 uses the bounded view followed by bounded `presentation_refresh`. The legacy first-pending and changed-fingerprint behavior stays intact.

**Strengthen the final notification fence, not just the store-result check.** Current `observe_fingerprint` checks the channel, releases its lock, then calls `notify_binding(binding, ...)`, which has no expected channel and can push into a replacement entry. Pass the expected channel id **and mode** to the final active helper. Under the same registry lock, compare the exact entry, require Live, perform the nonblocking `sink.push`, and apply any existing active-path `last_attention_push` update only on successful enqueue for that exact entry. The passive helper uses the same final identity fence but adds no health timestamp. Do not hold this lock across store work. A result for C1 must neither push into C2 nor update C2's fingerprint, passive bit or health. The earlier fingerprint check alone is not sufficient.

Make the entry lease optional or otherwise inaccessible in Legacy. `presentation_lease`, `presentation_owner_live`, replay snapshot/application and presentation attention bookkeeping require PresentationV2 as well as their existing exact-owner checks. `daemon::transport::watch_connection` returns a lease only for the opt-in, advertised new capability, existing V2 support and the matching registry entry. Prefer trusting the registered entry's mode over separately reconstructing it after registration. The existing seat owner permit remains a serialization lock; it does not confer mode or identity.

Keep the fake-store legacy test. For the capable tests, wrap a real SqliteStore with a `ModStoreReads` guard that delegates bounded methods and fails/counts any legacy view call. The inherited trait default currently hides the real-store distinction; a fake relying on that default cannot prove R3.

## Why capable ordinary delivery needs more than a legacy fix

Both CLI loops drain immediately after Accepted. Absence of an initial daemon Attention frame therefore does not prove lost initial body delivery. V2 subsequently drains `Page.more` with Close/cancellation checks and then waits for a channel frame. The ordinary logical ledger bounds offers/retries; it does not wake a parked CLI by itself.

Currently a new ordinary receipt can move `wake_work.attention_version` through materialization. That scalar is retained in the bounded presentation fingerprint. The ordinary allocator uses its signal plus private passive generation, then queries the addressed claim's stream (`queries::ordinary_presentation_page`, `claim: Some(...)`). Exact-key due/carry/replay paths independently recheck current canonical receipt and binding unread state. `queries::ordinary_presentation_message_by_id` explicitly allows terminal seat receipts through the binding's unread predicate, yielding `ack_required:false`; a sibling's ACK never moves this binding's cursor.

That shared version is not sufficient publication coverage. `materialization::project_receipt` bumps only for effective Pending with no prior sparse receipt state. A sibling can ACK after ordinary publication but before first recipient materialization. The other binding's unread body remains eligible, but the materializer then has no pending receipt to announce. Current `advance_ordinary_publications` inspects only Lazy rows, so an already-quiet capable channel can receive neither signal. The real-store control below must demonstrate this scheduling hypothesis without manually setting a private version.

**Selected correction after that control is RED:** extend the existing private 100-manifest scan to both ordinary and Lazy addressed publications. For each already-fetched manifest, first point-read its exact canonical message/mode and validate instance/thread/decision identity, then point-read the mode's exact recipient relation: `(preparation_id, seat_id)` in `prepared_recipients`, or the existing Lazy key with message/thread validation. Unrelated, unpublished or mismatched rows cannot increment content generation. Do not ask effective receipt state here: the event is recipient publication, not wake or output eligibility. Increment existing private `ordinary_passive_generation` and `mod_version` once per changed quantum; the actual pull rechecks the current binding cursor and receipt.

This reorders/reuses the existing two probes rather than adding an ordinary probe after the Lazy probes. Require actual EXPLAIN/VM evidence that both recipient paths are unique/indexed and no hidden source walk appears. Keep 100 physical manifests, at most 200 point probes and three head/range seeks per quantum; rejected candidates still spend visits. Do not claim the bound from a SQL LIMIT or counter increment alone. A publication already consumed before this change is not repaired by replaying old scanner history; the affected supported rollout starts on the current unlanded schema lineage, and tests must not claim arbitrary historical-data reseeding.

The resulting channel frame is only a drain request. The JS mod decides model behavior from actual emitted items: Lazy, Notice and nonwaking invitation items are appended passively; a settled-but-unread ordinary message with `ack_required:false` and no `wakes` is also passive (`register.js` `passive`/`pumpLazy`). Pending ACK-required ordinary items remain nudge-class but are supplied as context while busy; the idle path checks its existing gates before submitting the content-free wake. Never promote a transport Attention frame itself into model-visible Attention or idle wake authority. Private publication changes use the passive registry branch and add no health evidence. Preserve both the existing applicable explicit presentation-confirmation policy and the separate existing mod ACK health policy; successful passive display can issue its ordinary completion command and `AlreadySettled` can legitimately record mod ACK health. Q3 does not suppress those commands or their established accounting.

## Current reader progress, including a parked ledger

The historical cursor-only frame oracle is not itself a required capable output. Advancing a reader cursor removes unread eligibility; the next capable pull must honor that exact cursor rather than reemit already-read settled mail. However capacity and retained continuation can need a new pull even without new publication: a parked 256-offer channel may have unoffered carried/backlogged mail after a canonical own read and ACK release capacity. The publication scan alone does not solve that case.

**Selected no-schema correction if the parked control is RED:** add an internal checked `note_binding_reader_change` helper in `store::invitation_content` that invalidates only the exact canonical binding's existing current-scope Hook/Watch consumer rows. It increments their existing `ordinary_passive_generation` and `mod_version`; it never changes their captured scan generation, cursor, carry, partial body, outbox, offer ledger or canonical read cursor. No row means no work: the next initial pull already scans fresh. Check both generation/execution scope and instance against the canonical binding; never use a client-supplied sibling id. Checked exhaustion or malformed private state fails the surrounding transaction atomically.

**Coalesce once per owning canonical operation and affected binding; do not add this helper inside `read_cursors::advance`.** Retain the low-level cursor operation's changed result and propagate a changed flag through the full-display helper where needed. `control::advance_cursors` ORs those flags across its thread loop and invalidates its one resolved binding once. `lazy_delivery::complete_displayed_for_binding` ORs across each existing target's thread loop and invalidates that target once. `first_contact::fast_forward` ORs across **all** joined-thread gaps and invalidates its one binding once after the loop. `MAX_THREADS` limits its returned descriptions, not its cursor writes; the old source traversal is not bounded by the display input limit. The added private work is constant per operation/binding even when fast-forward moves arbitrarily many existing gaps.

The helper performs one canonical binding point read plus at most two consumer point reads and two checked row updates per affected binding, once at the owning operation boundary. Reuse the already-selected target set; do not enumerate new bindings. A historical unbound completion may already select N open targets: its additional work is at most N times this per-binding allowance, not a claimed constant for the whole historical operation. There is no scan/update of retained consumer history by seat and no new recipient fanout. Successful cursor advancement remains allowed with zero presentation rows, including legitimate subagent fast-forward; V2 admission is not a new prerequisite for that established operation. A no-change operation performs no private invalidation.

The canonical binding lookup includes native session as well as binding id, instance, generation and execution. Consumer rows carry binding id rather than a second native-session field; resolve that id canonically and do not substitute a sibling selected by seat or generation. A row is current only when its instance matches and **either** its primary `(generation, execution)` header matches the canonical binding **or** its passive-refresh `(mod_generation, mod_execution)` header matches. This is the existing signal-initialization rule: it includes a current refresh-only Watch row without reviving a row for which both headers are stale. Scope-mismatched rows are left unchanged; no headers are repaired or promoted. Read/check the applicable current counters, then perform checked updates under the same transaction. Malformed applicable state, either counter's overflow or later transaction failure rolls canonical cursor changes and private counters back together. No physical presentation token, captured scan tuple, carry/partial bytes or full logical offer stamp is rewritten.

**Receipt settlement additionally needs a bounded live-channel recheck.** Own-binding invalidation alone is insufficient: B may already have fully read a body (its cursor passed it) while its receipt remained Pending, so Q1 correctly retained B's captured body/offer. A's later shared ACK makes B's captured body terminal and now permits retirement. That ACK may leave the existing shared attention version unchanged; a generic commit kick only runs `pass`, whose scalar comparison cannot discover the change. Preserve Q1's Pending guard and cause a fresh bounded canonical recheck instead of weakening it.

Add `ModChannels::presentation_delivery_may_have_changed(&SeatId)` with a no-op default and a registry implementation that visits only that seat's **current registered entries**, bounded by the existing global 64-channel cap. Set one `pending_delivery_recheck` boolean on each Live PresentationV2 entry, mark the worker dirty and kick its existing pacer. The name intentionally describes a hint, not an observed receipt delta. No historical consumer row is visited or updated, and Legacy entries retain their own fingerprint behavior. Do not use this mechanism for arbitrary commits or unrelated seats.

**Choose conservative ordinary-or-Lazy success hints, not a new durable delta API.** `ModAckOutcome::Settled` represents both ordinary settlement and Lazy completion, and `DeliveryConfirmOutcome::Settled` carries the same ambiguity. `AlreadySettled` can accompany this binding's first successful display/cursor advancement. Do not infer an ordinary receipt change from those values and do not add post-commit per-item classification queries.

After a successful canonical operation returns through `DomainService::cooperative_mutation`, conservatively hint for ordinary Ack/AckDisplayed with a nonempty acknowledged/already-acknowledged result, and for AckModDelivered/DeliveryConfirm with at least one Settled or AlreadySettled item. This includes ordinary-only, Lazy-only and mixed successful/refused batches; exclude errors, all-refused/retryable/stale batches and presentation confirmation. Capture the admitted seat and mutation class before consuming the mutation, obtain the typed result in an inner writer scope, then release the foreground/store writer turn before registry bookkeeping. A retained successful reply may issue the same coalesced hint; it is not proof of fresh durable mutation. The hint records no receipt provenance, private counter or logical offer stamp. No durable ordinary-delta API is added merely to narrow its label.

**Preserve existing mod ACK health semantics.** `AckModDelivered` continues its established `counts_as_mod_ack` handling, including `AlreadySettled -> record_ack`; Q3 adds no timestamp to that path. Health tests snapshot after that ACK handler finishes and require subsequent hint consumption/passive passes to add no health update. Ordinary Ack and isolated hint controls can assert an entirely unchanged health timestamp because they have no independent mod ACK action. Do not make a blanket no-health assertion across an operation that intentionally records existing health evidence.

**Quietness is conditional on unchanged canonical/render scope and unchanged retry eligibility.** Drain existing continuation and freeze the clock below the current 60-second DP5 due threshold when asserting that duplicate/retained hints produce no output, ledger delta or additional health timestamp. Separately cross the threshold with a distinct eligible pending offer and compare the hinted pull with an otherwise identical explicit ordinary pull: legitimate retries, spacing and the existing three-offer limit remain. The hint itself never resets or increments a stamp, refills owner replay, manufactures model Attention or writes health; the canonical bounded pull may legitimately allocate a now-due offer. Absolute silence across advancing retry eligibility would require a different pull mode and is not this design.

In `pass`, atomically take each exact entry's pending boolean into its work snapshot **before** store work. A new event during that pass then remains pending for the next pass; successful processing never clears that newer bit. On store failure, OR the captured bit back only if the same channel id and mode still own the entry, then use the existing dirty/backoff path. Replacement starts fresh and initial Accepted already drains. On success combine the bit with private-version changes into at most one passive drain frame for that pass; this reason never calls the health-arming branch. Final active and passive pushes and any local bookkeeping require the exact-channel/mode lock fence specified above. ReconnectGrace has no usable presentation authority; the next newly registered Live channel drains initially.

**Use the existing sink contract accurately.** `ModChannelSink::push` already returns bool. The concrete sink uses unbounded Tokio mpsc: false means the receiver is gone, not a queue-full/retryable-overflow result. True proves enqueue only, not socket delivery or flush. A false return may follow enqueue followed immediately by receiver closure, so recovery is inherently at-least-once. On false for a capable drain, OR a pending recheck back only into the same channel/mode, do not add health evidence, and do **not** mark dirty or immediately kick solely for that dead sink. Imminent transport unregister handles the drop; if delayed, the existing safety pass may retry. This avoids an immediate busy loop and never transfers the bit to a replacement. A later socket-write failure is not a synchronous failed push: transport unregister and reconnect/Accepted drain supply recovery. Keep existing transport timeouts and registry lifecycle handling.

The 64-entry bound covers registry iteration and one coalesced bit per current entry. It does not bound queued transport frames or retained durable history. No queue-overflow test, bounded-queue API or new transport-memory cap is claimed. Queue redesign is outside Q3.

The resulting V2 pull first performs its existing exact-key reclamation and continuation checks against **B's current** cursor and the shared terminal receipt. It can now release capacity or retire the captured body and continue to existing backlog. If B remains unread, the same ACK must retain B's offer/body and deliver it passively. No private or global version is needed for the receipt event itself: the process-local recheck is lost safely on daemon restart because every new channel drains on Accepted. The publication scanner remains necessary for a message never offered before A's early ACK.

Reader invalidation requests maintenance, not settlement: an own body read with a still-pending receipt cannot reclaim that receipt; a sibling's ACK cannot reclaim this binding's unread offer. Reconciliation and the existing mutually exclusive ordinary source modes decide whether any capacity is truly free. Test read-before-ACK and ACK-before-read to ensure the second canonical event is sufficient. Test both sibling cases: already-read B must retire its now-terminal retained body, while unread B must remain eligible. The new code does not change either Q1 predicate.

`binding_cursors` is WITHOUT ROWID and SQLite's update hook does not report it; this is already documented by `lazy_delivery::complete_displayed_for_binding`. Do not solve it by adding `invitation_presentation_consumers` to `MOD_NOTIFY_TABLES`: every refresh saves that table and would kick itself forever. Existing receipt/Lazy writes provide immediate worker kicks when applicable; the existing ten-tick safety pass (one-second worker tick) observes a remaining private version change without adding a timer. This is finite progress under successful worker/store calls, not a new hard latency guarantee. The private update itself must not reset stall history or touch native wake state.
