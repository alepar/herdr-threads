## Finding ORI-1 — fully pruned recovery can clear current native outlook

**Should-fix.** Primary location: `src/store/invitation_content.rs:2168`. Effect: `src/service/delivery_presentation.rs:264`. Producing seam: `src/service/mod_channels.rs:580`.

The registry deliberately computes `active` from the saved worklist before exact-stamp pruning (`mod_channels.rs:580–592`). It can therefore correctly return an active recovery snapshot with an empty remaining set. The store initially preserves that context as `RecoveryControlOnly` (`invitation_content.rs:1988–1990`), but replaces it with `Normal` or `LogicalDue` whenever `control_only` is false and `owner_pending` is false (`2166–2175`). That decision is made before knowing whether any ordinary logical ID was actually allocated. A subsequent page containing only unrelated nonordinary output reaches the service's normal assignment and writes `more_pending = false` because its offered/truncated lists are empty (`delivery_presentation.rs:264–266`).

A concrete supported-state trace:

1. A replacement owner's successful old-outbox replay captures a pending ordinary ID/full stamp, leaving that physical attempt outstanding.
2. Confirm the old token normally. Before the next pull, a concurrent logical recorder changes that ID's full stamp; its new offer is recent/blocked. Current native outlook is `more_pending=true`, with current `read_attention`/`whole_read` values.
3. Make a fresh passive invitation eligible. The next getter returns `active=true`, `remaining={}` after stamp pruning.
4. At positive capacity, Normal traversal filters the blocked ordinary ID, while the invitation yields a Page. No ordinary logical allocation occurred, but the selected Normal disposition clears current `more_pending`. The same source/disposition problem exists at zero capacity when no due logical ID is allocated.

This is a source-selection versus successful-allocation conflation. The reviewed design's section 4 (`resume-watch-owner-replay-design.md:89–100`) requires recovery bookkeeping to survive exhaustion/pruning and preserve the post-store current outlook when no independent ordinary logical allocation occurred. WR17 expressly requires this distinction; a live registry suppressing wakes does not make the altered outlook harmless after handover.

**Fix shape:** retain active-recovery context independently of the selected ordinary query mode. Finalize the bookkeeping disposition using the actual logical offered/truncated subset. Preserve the current post-store outlook for the active/pruned call when that subset is empty; permit existing Normal/LogicalDue bookkeeping when a legitimate logical allocation occurs. Keep current-value preservation under the ledger lock, not snapshot restoration. Do not re-enable captured replay, alter logical stamps, or forbid legitimate later ordinary discovery.

**Required regression:** initialize outstanding owner debt, change all captured stamps before the next snapshot, and assert that pruning emptied the snapshot while `active` remained true. Exercise a passive-only fresh Page with both positive and zero capacity, initial false/true outlook, and direct comparisons of `more_pending`, `read_attention`, `whole_read`, and `next_pull`. Include a current-value change at the existing store barrier and a companion case where real logical allocation legitimately updates outlook. The new tests must fail the existing mode-only disposition branch. Existing tests at `tests/service/delivery_pull.rs:9399`, `:9476`, `:9912`, and `:10440` exercise missing attempts, outbox replay, mutation after snapshot, and mixed emitted replay respectively; none enters this fully pruned fresh-page path.

## Other quality observations

The change keeps one bounded owner worklist per registry Entry, an exact lease/incarnation/full-stamp scope, no durable schema or public protocol expansion, and no new receipt provenance. Registry and ledger mutexes are not nested or held across store work; the existing per-seat owner permit deliberately spans the allocation/application boundary. Physical attempt outcomes do not become logical due deferrals. The outbox token, original descriptor slots and codec remain authoritative.

TRUST-POLICY documents the logical/physical distinction, nonzero count domain, memory/work bounds, success/loss semantics and lifecycle limits. Its A7 update and the bridge comment align existing shared notice-frontier behavior without adding notice authority. No adversarial caller checks or harness rewrites were introduced. No additional source defect was established in this static review.
