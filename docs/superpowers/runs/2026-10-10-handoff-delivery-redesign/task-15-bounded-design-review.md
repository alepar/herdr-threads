## 1. Presentation allocation is not presentation confirmation

**Important.** There is no compatible existing page-token field. `src/protocol/delivery.rs:18` has a `deny_unknown_fields` request with only claim, attention version and prefix; `DeliveryPage` has no token. An attention version is recipient content state, not a unique page identity: successive 32-item pages can have the same version. `src/harness/agy/delivery.rs:848` persists that version before returning the rendered hook output; invitation-only pages are explicitly not transcript-confirmable through the message-ID mechanism. A crash after saving state and before emitting output can therefore lose a page even if the socket reply succeeded. Simply adding a token to the next request and saving it at that same point moves the loss window rather than closing it.

Suggested bounded disposition: introduce a capability-gated invitation presentation protocol with an opaque binding-scoped page token, separate from message ACK and invitation acceptance. Retain at most one invitation outbox page per current seat binding: token, render key, <=32 invitation descriptors, and <=64KiB final framed invitation text including overhead. Allocate completeness/cursors and outbox atomically; a retry lacking confirmation replays that logical allocation, not a new offer. Confirmation must be based on the harness's actual context insertion evidence. AGY can extend its existing injected-frame/transcript tracking to carry the invitation token; a local receipt of the reply is insufficient. The Claude mod can confirm after its successful context append, using its existing cooperative insertion boundary. Do not charge this as message ACK, acceptance, or a registration claim. Token strings have a fixed documented size and carry no repeated explanatory prose.

Before authorization, name the exact request/reply types, capability/preflight and old-client behavior. Preserve the old `delivery.pull_v1` request bytes; new token fields must not be sent to an old daemon. An alternative new command family is simpler to gate than silently extending a deny-unknown request. No token must acknowledge a different binding, render key, or page; duplicate confirmation is idempotent. A completed presentation may be physically replayed on a lost confirmation, so the bound is on logical allocations only.

Pending-page invalidation must also be explicit. Recommended: before replay, revalidate at most32 stored invitation descriptors in one transaction. Drop canonically removed/settled descriptors; suppress superseded revision text and leave its current revision eligible for a later allocation. Keep the token for surviving descriptors and retire it automatically if none remain. A confirmation of the original token retires only that original allocation, never a replacement page. No rollback of unrelated message offers or informational notices is needed: keep this outbox invitation-specific, then combine its frames with the existing message/notice delivery behavior.

## 2. Lifecycle revision detection alone cannot discover existing-item changes

**Important.** The binding schema proposes only `lifecycle_revision_seen`; the independent initial walk advances by invitation ordinal. `src/store/service_controls.rs:365` can attach a required membership to an existing timed voluntary invitation. Its ordinal and topic revision do not change, but the acceptance command changes from `accept` to `accept-required ... --revision N`. Release at `service_controls.rs:466` changes it back. Both bump inbox revision, but neither writes a topic row. Once initial discovery is complete, neither the initial frontier nor the proposed topic frontier revisits this invitation. Resetting the initial walk on every inbox revision would discard the promised independent finite progress and cheap quiet behavior.

Bounded disposition: give acceptance-context mutations a concrete discovery source. One small alternative is to broaden the coalesced per-thread row to **invitation-context latest**, recording a new sequence for actual topic changes AND requirement creation/release/other command-affecting changes. A change for another recipient can cause bounded maintenance inspection/expansion, but must not increment this recipient's version or print/wake unless its canonical item key changes. This preserves O(retained threads), no recipient fanout and the same latest-after-quiescence limit. If that alternative is not selected, add a separately specified indexed per-invitation lifecycle-change frontier; the scalar alone is insufficient.

Define the item context key concretely. At minimum it includes invitation ID/episode, canonical topic revision, and effective pending requirement ID/revision/issuer (or explicit None), plus frozen confirmation/deadline. To make the ONE-complete-per-revision proof robust across `None -> required -> None`, use a monotonic per-invitation command-context epoch when command metadata changes, rather than resetting counters on an equality tuple that can recur. Topic changes must not reuse an old key with newer text. Existing requirement lookup is bounded: `current_requirement` at `src/store/service_substrate.rs:62` uses the unique partial `requirement_episodes_effective(thread_id,seat_id)` index in migration0002. Its existing retained identity/revision constraints are suitable inputs; no provenance change is needed.

Modern Ensure is a composed B producer. Required integration proof is actual B Ensure-created Lazy invitation -> D canonical context -> full AGY hook and channel display, plus existing pending reuse. Do not substitute a fabricated metadata fixture.

## 3. Watch is a separate consumer, not ModRefresh plus DeliveryPull

**Important.** `src/service/mod_channels.rs:431` emits an Attention signal for passive content changes. The actual watch client at `src/cli/watch.rs:503` then drains `InboxBatchV2` using `delivery::drain_pages` (up to4096 pages), not `DeliveryPull`. Its assembler at `src/delivery/assemble.rs:110` suppresses duplicates by invitation ID/topic revision, which also suppresses requirement-only changes. The mod at `integrations/claude/mod/hooks/register.js:276` uses the same topic-only key. A new store operation invoked only from hook pull will leave those consumers on the old unbounded traversal and wrong content identity. Conversely, letting ModRefresh allocate presentations could consume the invitation before either consumer inserts context.

Required disposition: name a bounded **watch presentation** route using the same canonical item key/completeness state and token allocation semantics, distinct from the read/maintenance-only ModRefresh frontier. The watch client must stop emitting invitations from its old V2 drain when using the new route; ordinary message/warning behavior can remain. The mod's dedupe key must include the new context key and preserve partial-to-full upgrades. Specify whether hook and watch share one serialized per-binding outbox or have separate bounded consumer episodes. Shared state requires one confirmed insertion boundary; independent consumer episodes multiply the logical offer bound and must be accounted explicitly. A passive watch signal with outstanding bounded traversal must schedule further in-turn drain quanta even if content version stays unchanged; otherwise1025 items can stop after the first quantum. It must not manufacture idle wakes, ACKs or stall eligibility.

## 4. Exact indexes and output arbitration still need a fixed contract

**Important.** Current `digest_pending_invitations_seat/thread` indexes sort `created_decision_seq` before ordinal (`migrations/0008_digest_pending_paths.sql:43`); they do not prove the proposed ordinal seek. Add `(seat_id,ordinal)` and `(seat_id,thread_id,ordinal)` indexes to that projection for exact fixed candidate visits. The existing invitations seat/thread partial index does not remove cancellation/rejection filtering from a scan of historical invitation rows. Use the already maintained pending projection, count each retrieved candidate before canonical checks, and do not count only surviving rows.

Revisit must choose one indexed ordering, not combine a budget inequality with an unrelated ordinal ORDER BY and assume LIMIT bounds examined work. Suggested exact known-size index: `(binding_key, required_render_bytes, revisit_ordinal)` and a finite lexicographic walk in that same ordering, restricted to `required_render_bytes <= standalone_capacity`. Store highwater/cursor in that ordering; do not claim an ordinal-only cursor supports it. Unknown-size candidates need their own explicitly bounded bucket; with complete canonical hydration and a deterministic render key their rendered size should normally be determinable on first visit. Each prefix/render-key change must invalidate the cached estimate in a scoped manner. Query-plan controls should reject a temp sort or a scan through all ineligible rows before the LIMIT.

The output plan currently reserves slots for three invitation classes but has no ordinary-message/notice arbitration. Existing pull reserves notice bytes before invitation rendering (`src/service/delivery_pull.rs:338`); an invitation fitting a standalone64KiB page can then fail forever behind a constant notice stream. A concrete resolution is persisted rotation among ordinary messages, notices and the three invitation classes: each active class eventually receives first-output priority with a full standalone byte allowance (minus header), followed by slot lending to others. Slot reservations cannot permanently reserve bytes away from that first candidate. Count actual final `frame` bytes, including header, indented body lines and continuation/prefix escaping, not source body length. Include attention framing in the same bound. State the rotation bound (e.g. five successful calls for an active class) and how failed calls leave rotation unchanged.

Canonical topic and goal are each <=1024 bytes (`migrations/0001_initial.sql:220`, `protocol/commands.rs:1159`, `protocol/service.rs:410`); the observed omission comes from intermediate V2 page fitting at `store/queries.rs:5492`, not intrinsically enormous canonical goals. A dedicated canonical read removes that accidental omission. Rendered command prefixes can still expand: allowed prefix input is4096 bytes and8 arguments (`protocol/delivery.rs:13`), and BODY_LIMIT is8KiB. Specify whether invitation full eligibility uses that8KiB body cap or the64KiB page cap. A budget of64KiB cannot activate full retry if the renderer still unconditionally truncates at8KiB. Adequate-later-budget tests must exercise the declared supported cap and a shorter/changed render prefix where necessary, not claim a larger page alone fixes body truncation.

## 5. Episode retention and cleanup are not yet bounded as required

**Important.** One item row per retained invitation **per retained binding episode**, with only cleanup during current pulls, can grow with unlimited resumes. The proposal explicitly downgrades to O(retained invitation x retained binding history), while the requested bound is tied to pending items/current bindings plus explicit reclaimable debt. An idle ended binding cannot run its own cleanup, and a new binding that creates32 rows but cleans10 per call can accumulate obsolete generations indefinitely. A foreign-key CASCADE deleting all an episode's items would violate the bounded hot-transaction requirement.

Suggested small resolution: retain one current binding row per seat and one presentation item row per `(seat, invitation)`; store generation/execution in the value. Rotation replaces constant binding/outbox state and never scans item rows. An old-generation row is reset on its next item-key visit; no historical episode rows accumulate. Keep an indexed bounded stale/removed-item cleanup cursor, visiting/deleting at most10 rows per allocated cleanup quantum. Canonically removed items may remain as explicit debt until that cursor reaches them, but there is no detached per-generation history. State the disk bound as retained canonical invitation items plus bounded outboxes/current seat rows, with eventual cleanup after finite removals and continued maintenance; do not claim instantaneous pending-only cardinality. If cleanup must progress without any seat pulls, select an existing independent bounded maintenance lane explicitly, without adding H/D/I work or fanout.

Schema must declare real composite PRIMARY KEY/UNIQUE and FKs, instance-scoped consistency, boolean/counter/range checks, fixed token/payload caps and overflow behavior, rather than the ambiguous `execution_id PRIMARY KEY` notation. Add prospective migration40 only after verifying the composed schema tip; preserve1..39 bytes/manifest guarantees. Sequence allocation via existing `schema::next_decision_seq` is legitimate canonical ordering, not receipt provenance. Both writer paths must check actual UPDATE count (including topic-revision exhaustion) before writing the coherent latest row; ordinary replay/noop and service replay/noop must create no content work. TRUST must explicitly distinguish new durable invitation presentation state from the still process-local message offer ledger, latest-after-quiescence, logical allocations versus physical replays, and bounded cleanup debt.

## Assessment of planner's concrete follow-up dispositions

The coordinator supplied these after the checkpoint review. They narrow the alternatives but have not yet been persisted as a final checkpoint.

- **Capability-gated V2 with fixed Hook/Watch consumers:** suitable. One outbox and one complete allocation per unchanged context key **per each of those two fixed consumers** gives the required <=2 total complete allocations per binding. The item state/outbox key must include the consumer enum; no caller-generated consumer identities. Independent per-consumer initial/topic/revisit frontiers are needed. Physical retries remain unbounded by the logical counter until confirmation. Do not retain the stronger ONE-total claim in the current proposal. This does not require changing `NoHookPull` admission for the hook consumer; watch uses its existing authorized watch binding/channel checks.
- **Neutral HookOutcome completion after emit+flush:** an actual reusable seam exists at `cli/hook.rs:263`, `:3421` and `:3617`. Extending it with a neutral bounded invitation completion handle can defer both AGY token confirmation and its local seen-token/version persistence until after complete stdout write+flush. Failure or crash before that boundary leaves the outbox pending; crash after flush but before confirmation replays physically. This closes the observed pre-emission state-save loss window without adding harness branches to core. However flush establishes hook-output presentation, not proof the harness/model retained it. That limitation must be explicit, matching the cooperative delivery model. The stricter transcript-token confirmation suggestion above is optional if the parent explicitly selects this existing output boundary and its accepted limit.
- **Watch flush -> confirmation:** insufficient for an unconditional claim that context entered the model. `cli/watch.rs:549` writes a JSON line into a downstream mod; the mod may enqueue it and die before successful context append. Confirming durable completeness at the CLI flush would then suppress retransmission. Prefer token propagation through WatchInvitation and a cooperative mod confirmation after the existing successful insertion boundary. Reconnect retries the outstanding token and the mod dedupes an already-inserted token while re-confirming it. If the parent selects watch-flush presentation instead, name this loss window explicitly and narrow the guarantee to transport presentation; do not claim it satisfies unconditional eventual model-context delivery. This choice remains a blocker until selected.
- **Generalized invitation-context latest row:** suitable for the same-invitation service requirement attach/release hole, provided every actual command-affecting writer participates and no-op/replay does not. The per-item `topic revision + effective requirement ID/revision/state` tuple distinguishes adjacent changes, but `None -> required -> None` can revisit an earlier tuple. Specify a monotonic per-invitation command-context epoch or explicitly define logical revision as a transition epoch, so counter reset cannot silently break the unchanged-revision bound. The output/watch/mod dedupe must use the same identity.
- **Bounded watch continuation/yields:** required and suitable, but name the resumption trigger. One passive Attention cannot be the only trigger for a many-page backlog once its content version is stable. An in-turn consumer must continue bounded quanta while `more`, yielding normally between them and persisting progress; it must not create repeated idle turns merely to drain Lazy invitations. ModRefresh remains notification-only and cannot advance these presentation cursors.

Remaining approval choices are therefore precise: watch confirmation boundary, transition identity across requirement release, exact revisit index/cursor order, five-class output arbitration, and removal of per-ended-episode storage multiplication. Resolve these in the proposal before production implementation. The neutral HookOutcome completion seam itself is not a blocker.
