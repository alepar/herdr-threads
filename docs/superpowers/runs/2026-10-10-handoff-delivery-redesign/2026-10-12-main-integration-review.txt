Important issues

I1. Obsolete invitation contexts accumulate without bound while append is stalled; recovery appends the entire history.
File: integrations/claude/mod/hooks/register.js:292–299,543–553 (candidate).
Trigger: A pending invitation receives topic/command-context revisions while one io.append is unresolved, or successive append attempts are refused. The duplicate predicate only matches the same contextVersion. Every new version gets another queue object/body; there is no same-ID replacement of non-inflight obsolete contexts, nor a bounded pump batch.
Impact: Memory grows with revisions to one invitation, defeating the bounded-state and latest-context contract. Once append resumes, pumpLazy frames all retained obsolete versions in one request, producing an unbounded model-visible burst and potentially repeated oversized/refused appends. This requires cooperative ordinary writers and a stalled consumer, not adversarial input.
Evidence: Ran exact frozen createCore under Node with mock IO, no native harness/daemon. One stalled append, 2,000 revisions of invitation:one, a 1,000-byte goal and small topic/accept command: queue=2,000, unique IDs=1, body bytes >=2,000,000. Resolving the first append left 1,999 queued revisions and produced a second append of 2,247,800 bytes (first append 1,151 bytes). Every individual context fits canonical topic/goal limits. This independently reconfirms the old punch-listed queue concern; its prior scope filter is not a production waiver.
Fix: Preserve the exact object already in flight, coalesce pending contexts for the same invitation to the latest whole/current context (including the partial-to-whole rule), and bound the consumer's framed append batch. Keep run fencing so late failures cannot delete a replacement-run object. Add a focused stalled/refused append regression asserting bounded retained revisions and eventual latest context.

I2. Main's person-producer wake driver still expects a wake for a new Lazy direct invitation under wake_on=nudge.
File: scripts/wake-e2e.py:772,788 (Main 7ac8c4bf; these Main-only changes survive the ordinary three-way integration).
Trigger: invite/1:1 for an idle nudge-only recipient. Main now runs human send --seat RECIPIENT --lazy (Main driver:645–650,788). The feature direct-send producer freezes EnsureCreationPolicy::Lazy unconditionally, including a Human claim (src/cli/direct_send.rs:253–257). Its invitation has no wake obligation; publication of the Lazy body only enqueues wake work for wake_on=all (src/store/lazy_delivery.rs:904–909). InvitationContext::wakes returns false for that Lazy invitation (src/delivery/invitation.rs:108).
Impact: The authenticated release matrix reports correct passive behavior as FAIL. The expected-wake formula exempts only send-lazy/nudge, not invite/1:1/nudge. This invalidates that release oracle; it is not evidence that the core should wake Lazy invitations.
Evidence: Traced current Main driver through current feature CLI/canonical producers and wake projection. Human Invite parsing clears policy on the group route (src/cli/commands.rs:1873), so the earlier cooperative/group reproduction is obsolete after integration and is deliberately NOT repeated here. Human priority bypasses catch-up hold, but does not change the Lazy body wake mode or the explicit direct invitation policy. No authenticated matrix was run by this review.
Fix: Correct the direct-invitation oracle to passive under nudge, or separately create an explicitly confirming invitation if that is the case the driver intends to exercise. Preserve Main's guarded person coordinators. Add a driver control covering the merged producer semantics. This is a release-qualification defect; a live authenticated gate is required before tagging, not automatically before an ordinary merge.

I3. Public usage guidance contradicts the independent active-direct-invitation reader contract.
File: docs/agent-usage.md:159 (candidate).
Trigger: Two bindings of one seat read a direct opening message before/after acceptance of the active invitation. The guide says accept/join starts every session at the thread head and the first top-level reader settles the pending opening mail for every session.
Impact: Agents/operators are told acceptance skips their own backlog and a sibling's display settles their stream. Actual direct acceptance preserves existing cursors, inserts missing open-binding cursors at the invitation event floor, and leaves independent sibling delivery intact. These are functional instructions about what work remains, not cosmetic prose.
Evidence: TRUST-POLICY.md:851–904 explicitly states the direct exception. src/store/control.rs:1095–1142 chooses init_for_direct_accept rather than generic init_for_join; the former inserts missing cursors without raising existing ones. The candidate report already records this unresolved contradiction. A review cap cannot clear it.
Fix: Limit head-seeding/seat-pending wording to generic join/nonpair acceptance, and document active direct acceptance's own-cursor/event-floor/sibling exception, while retaining the normal fresh-binding-after-acceptance seeding rule.
