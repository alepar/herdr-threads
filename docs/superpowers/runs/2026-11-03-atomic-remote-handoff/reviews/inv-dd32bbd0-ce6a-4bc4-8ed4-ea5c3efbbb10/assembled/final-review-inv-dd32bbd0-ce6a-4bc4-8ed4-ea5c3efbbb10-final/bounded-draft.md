## Step 1: own view (diff against spec and earlier findings)

- The prior Must-fix "Requester::poll overruns its budget after a slot wait" (inv-b56f0808 #1) is fixed by 09d27f3ef. send_window() is cut from the budget's remaining time minus REPLICA_WAIT_MS and SETTLE_MARGIN_MS and capped at SEND_WAIT_MS. It is computed once before the slot wait and again after it. A window the slot wait used up settles as Timeout without sending. If wait_slot gets the slot, the ledger row is re-read, so a re-send that settled the row while the poll waited is answered from the ledger. I found no new overrun. The leftover nit is that a sub-second window reports `secs: 0`, already deferred by inv-583f17bf.
- The prior Must-fix "handoff_warning_of reuses a cleared pre-link warning" (inv-b56f0808 #2, ht-8lem.14) is fixed by 9987863fd. The lookup now joins warning_conditions on open_warning_id with clear_warning_id IS NULL, so a cleared pre-link overdue:handoff warning no longer stands in for the linked message's receipt, and a fresh overdue:receipt is appended. The commit adds a store test. One small difference remains: the `active` query also excludes conditions covered by warning_close_sweeps, and handoff_warning_of does not. The swept-condition clearing just above (clear_warning_condition_at_snapshot) closes such a condition before this lookup, so I judge the difference harmless. It is deferred as inv-583f17bf already noted.
- ht-8lem.44 moves wait_slot and the re-send task period onto a Pacer. The Pacer latches kicks (`kick_latched`), and the waiter registers before its first try_slot, so a slot freed between a failed try_slot and wait_blocking still wakes it. There is no lost wakeup. wait_slot still uses a fresh SystemClock Pacer instead of the injected clock (ht-8lem.44 minor, deferred).
- ht-8lem.45/.46 are a golden bless and an allowlist line. The help text matches the coordinator answers Q2, Q3 and Q6 (required --summary, absolute --profile-dir on the target, pair only, thread options refused).
- ht-8lem.47 adds wait_seats on nodes 0 and 1 before the node-0 send in older_third_node_fails_then_replays_after_upgrade. That is correct. The sibling test at tests/multinode/handoff_atomic.rs ~l.975-990 (cluster mn-handoff-tamper, links (0,1),(2,1)) still waits only on node 2 before `support::send` from node 0's seat. This is the same race the sweep caught on its sibling (Must fix below; the ledger graded it minor [sibling-test-same-race] in ht-8lem.47).
- New finding, carried from inv-583f17bf and still unfixed at head: the re-send pass replays the request of a retired author. ledger::resend_set selects every sent|launched row with no author-state filter. resend_pass checks nothing about the author. No seat-retirement path touches handoff_obligations: git grep finds no reference to it under src/store/seats*. The only author-retirement handling in the ledger is ALERT_PENDING_SQL, which only suppresses alerts. When the target is offline while the author retires and the link then comes up, the re-send fires on link-up. It can reach the target before the retirement fact replicates there. handoff_refusal's SENDER_SEAT_RETIRED check then passes, and the target stages the handoff and starts an agent for a retired author. Otherwise, rows keep re-sending every 30 s until the 6-day expiry. Spec §3.1 step 3 and the roast Should-fix (peer_launcher.rs:601) intend that a retired author's request writes nothing. The sender is the only place that can enforce this without a race. No bead or disposition for this finding appears in the ledger or run.md.
- src/cli/peer_handoff_launch.rs (first claimed review): the order is capability check, PeerRequestView (state running, frozen prompt present), launch_request (the same handoff_directory projection decide validated), prepare_peer_startup (template, envelope, preflight_startup, validate_whole_input), one PeerHandoffStage, then launch. Everything that can refuse runs before the first fact is written. There is no two-step fallback without PEER_HANDOFF_STAGE_V1. A launch failure after staging returns an error and does not undo the facts, which is the Failed{staged} contract the recorded-answer builder relies on. Unit tests pin the order, the frozen-prompt argv, the missing-capability path and the post-stage failure. The test-support RecordingLauncher polls `.hold` with a 100 ms std::thread::sleep. src/cli is outside the loop-inventory scan, and the code is test-support only, so it is acceptable.
- src/cli/handoff.rs (first claimed review): StagingAuthor::PeerRequest replaces the per-phase caller mutations with one PeerHandoffStage and returns before any create, invite or send phase runs. Prompt v2 (`<summary> — from: <name> (<id>)`, FROM 11 bytes, `Handoff` 7 bytes) is frozen into new local plans (sender_prompt) only when the daemon advertises HANDOFF_SENDER_PROMPT_V2. Retained pre-upgrade plans without sender_prompt keep the v1/summary text through launch_prompt, retained_prompts and pane_prompt, so resume and retained-argv matching stay compatible. sender_line degrades to the bare id on any SeatInspect error, so a handoff never fails for a name. Local pane handoffs now lose the thread id and inbox hint in their startup prompt (spec §6, coordinator Q1). That is intended. It relies on turn delivery for the body, and a recipient with no turn delivery still gets the pending-hint line.
