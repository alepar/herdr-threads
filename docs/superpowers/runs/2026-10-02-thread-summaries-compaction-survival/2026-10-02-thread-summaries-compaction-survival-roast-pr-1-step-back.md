decision: patch
summary: Round 1 has 19 findings that are mostly independent, plus a few clusters where one rule was applied unevenly. None of them traces back to a flawed design decision. The worst coupling (poke admission tied to the wake retry backoff) differs from what spec §10 says, so fixing the implementation is enough and the spec does not need to change.
pattern: There is no cross-round recurrence because this is round 1. Several findings cluster by cause. (a) Poke admission and candidate selection: r1 [Nit] src/scheduler/mod.rs:259 and the open bead ht-2i4 have the same root. can_reserve_poke (src/notification/dispatch.rs:413) requires `state.guard.eligible(now)`, which includes the wake retry backoff (30/60/120/300 s), and candidates are cut to 16 before that check runs. Spec §10 only says "Pokes share the wake dispatcher's limits: one in-flight attempt per seat, at most four active prompts, and the per-seat elapsed spacing". It never mentions the retry backoff, so the code is stricter than the spec, and the spec itself holds up. ht-jf3 makes this worse, because a misread composer leads to Unsafe, which pushes the backoff to 300 s for both wakes and pokes. (b) The composer reader classifies rows from raw text rather than from what is rendered on screen: r1 [Should-fix] src/harness/composer.rs:122 (counts chars instead of display columns, fails open) and ht-jf3 (Claude's dim suggestion text is read as a draft, fails closed). (c) Agent-facing contract changes never reached the authoritative docs: agent-usage.md, output_compact grammar, operations.md, and the hook text that ht-dtq covers. (d) Fold and bundle size accounting does not measure or cap every serialized byte. (e) Diagnostics are dropped on new skip and failure paths. (f) Integration tests use wall-clock deadlines with thin margins. Each cluster has a single local fix.
