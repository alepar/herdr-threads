## Rejected (with reason)
- Evidence store and recording, Attribution bullet ("maps it to a version through B6's admission observer cache keyed by path/inode"); Testing ("keeps attributing to A after the PATH binary is upgraded to B") — B6 has no path/inode cache for Claude and the Codex cache holds only the PATH-resolved binary, so after an upgrade the old session's path maps to no observed version and the attribution test cannot pass as specified. Rejected 2-1 (ground CONFIRM Should-fix citing main: `src/harness/claude.rs:181` `observe_installed_version` runs `<binary> --version` on the PATH binary and keeps no per-path state; callers `src/cli/hook.rs:268`, `src/app.rs:295`; `BinaryIdentity` exists only in `src/harness/codex_schema.rs:261` for the Codex schema fingerprint). Majority: B6 is unmerged here and B6 code is outside the spec; a cache "keyed by path/inode" is by definition one entry per observed path, so the version-A entry survives once PATH moves to B; the explicit fallback ("maps to no observed version → nothing recorded") is stated and safe; extending the observer cache to retain per-path entries is implementation work under a stated design, and the spec already mentions both fixes (multi-entry cache, `versions/<v>` path layouts). Dissent noted for the author: the spec should say when per-path entries are populated (for example at SessionStart, before an upgrade) or that the version is parsed from the `versions/<v>` path; the confirmed fixed-path finding's fix covers this.
- Evidence store and recording ("a successful lifecycle check-in already reaches the daemon and records `lifecycle_ok_at`") vs the Attribution bullet — Lifecycle evidence keeps the PATH-observed version from B6's check-in unless the spec says to replace it. Rejected 3-0: the Attribution bullet governs the whole `harness_version_evidence` table ("the version is that of the running harness process, not the binary currently first on PATH") with no carve-out for lifecycle events, and "nothing is recorded" on an unrecognized parent covers `lifecycle_ok_at` too; "already reaches the daemon" describes transport, not the version source; the Testing case "a session started on A keeps attributing to A" would catch the misattribution. Residue: one clause saying the check-in's version is the parent-derived one.
- Evidence store and recording > Attribution (lines 78-83) vs Deriving the state (line 136) and Fetch trigger (a) (line 108) — The round-1 fix splits "the harness version" into running-process and PATH versions, and the state function, Health/doctor and trigger (a) never say which they mean. Rejected 2-1 (ground CONFIRM Nit citing lines 136, 108 and 89 "clears when the harness version changes"). Previously rejected in iteration 1 ("Undefined which version Health shows with several installs/PATHs", 3-0); re-surfaced by the regression lane against the round-1 fix. Majority: the state function is a pure function per (harness, version, contract_id) and every input is looked up by that key; line 88 "A violation sticks to (harness, version, contract_id)" means A's violation never carries to B; a Health line naming A's real violation while B is silently "new" contradicts no stated requirement. Residue: one sentence that state is derived per running version and which versions Health enumerates.

## Unverified nits (spot-checked)
- Manifest > Fetch policy ("At most once per day per harness, 5 s timeout ... result cached in the state dir with its fetch time"; `curl -fsS --max-time 5` subprocess) — No single-flight guard and no off-request-path rule, so N sessions starting on a new version within the 5 s window each trigger a fetch, and an inline fetch can stall the triggering hook call by up to 5 s. Spot refute REJECT: the spec says "the daemon fetches it" and never puts the fetch on the hook request path; duplicate conditional GETs of a 256 KB file write the same cached result and change no state; the stall is bounded, once per daily window, and the "new" state is admitted regardless. Possible guard: say the fetch is detached and single-flight per harness.
