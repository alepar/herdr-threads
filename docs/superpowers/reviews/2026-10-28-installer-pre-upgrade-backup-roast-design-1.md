## Confirmed findings
- [Should-fix] The backup (helper), step 3 ("`VACUUM INTO` from a read-only connection ... in one read transaction that also reads `user_version`") and step 4 (copy's user_version must "equal the source's") — Step 3 cannot be built as written: SQLite refuses VACUUM INTO inside an open transaction, so user_version cannot be read in the same read transaction as the copy, and the step 4 equality check compares two separate snapshots.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: https://www.sqlite.org/lang_vacuum.html: "A VACUUM will fail if there is an open transaction on the database connection that is attempting to run the VACUUM." Reproduced by all three seats on SQLite 3.51.2, WAL db opened mode=ro: `BEGIN; PRAGMA user_version; VACUUM INTO 'out.db'` fails with "cannot VACUUM from within a transaction". The same VACUUM INTO outside a transaction works and the copy carries the source's user_version (7 -> 7). Built literally, the helper fails on every store and the fail-closed installer aborts every upgrade.
  severity note: no floor hit. The failure is fail-closed and caught on the first test; nothing is lost. Should-fix because the spec's single-snapshot claim is false and the step 4 guarantee is misstated.
  fix-shape hint: drop the "one read transaction" claim; read user_version in its own statement (or take it from the copy, which VACUUM INTO preserves) and state what the step 4 comparison guarantees, noting it is safe because the old daemon never migrates the store.

- [Should-fix] Docs: docs/install.md bullet ("restore by hand: stop the daemon, copy the three files back into `node/`") — The documented manual restore omits removing the live herdr-threads.db-wal/-shm sidecars (and reinstalling the older binary / stopping re-ensure first), so a leftover WAL can be replayed onto the restored older db and corrupt the rollback.
  verdict: confirmed (reproduce ✓ / refute ✗ (seat rejected; outvoted) / ground ✓)
  evidence: spec line 117 is the only restore text and names no sidecars; a grep of the spec for wal, shm, sidecar, restore, checkpoint finds nothing else about the live sidecars. The store runs in WAL mode (src/store/connection.rs sets journal_mode=WAL); the live node/ on this host holds a 4.3 MB herdr-threads.db-wal and -shm. https://www.sqlite.org/howtocorrupt.html section 1.4 "Mispairing database files and hot journals": "Overwriting a database file with another without also deleting any hot journal associated with the original database" is listed as likely to lead to corruption. A rollback is most needed after a crash or kill, which is when a -wal survives. install.sh itself notes clients re-ensure the daemon after a stop (ht-xe3v).
  refute-seat dissent: the line is a one-clause summary of a docs paragraph, not a defined procedure, and the ACs have no restore item. The confirming seats answer this: that line is the only restore guidance the spec gives, and restore is the backup's sole purpose. Default route stands.
  severity note: not raised to Blocking. The backup entry itself is untouched by a botched restore, so the restore can be redone after removing the sidecars; the loss is not irreversible.
  fix-shape hint: expand the docs bullet to: reinstall the older version, make sure no daemon restarts (re-ensure path), remove `herdr-threads.db-wal` and `-shm` from `node/`, then copy the three files back.

- [Nit] Where the work runs ("The installer runs it with the new package's executable ($package/bin/herdr-threads, extracted and checksum-verified, not yet installed) ... Capability is probed with `internal pre-upgrade-backup --help` ... If neither has it, the installer refuses (fail closed) and names `--no-backup`") — The installer newly executes the extracted package binary from ${TMPDIR:-/tmp}; a noexec mount or any exec failure makes the --help probe fail and is read as "build lacks the helper", so a first upgrade from <2.5.0 is refused with advice that points at --no-backup instead of the real cause.
  verdict: confirmed (reproduce ✗ (seat rejected; outvoted) / refute ✗-survived / ground ✓)
  evidence: scripts/install.sh line 603 `work=$(mktemp -d "${TMPDIR:-/tmp}/herdr-threads-install.XXXXXX")`; line 621 only tests `[ -x "$package/bin/herdr-threads" ]`; every execution today uses $installed_binary after the copy, so the spec adds a new exec-from-TMPDIR requirement it never states. mount(8) (https://man7.org/linux/man-pages/man8/mount.8.html): noexec means "Do not permit direct execution of any binaries on the mounted filesystem." The probe's exit status cannot tell exec failure (126/127, signal, loader error) from a clap usage error. Reproduce seat's point that the refusal text (spec lines 106-108) says "Fix the cause" and never claims "helper missing" is acknowledged; the misdirection is the --no-backup suggestion on the upgrade that introduces the safety net.
  severity: seats split Nit / Should-fix. demoted to Nit: profile states a two-host production tool where the failure is fail-closed with no data loss, and a noexec TMPDIR is a hardening setting neither host is known to use; the cost is a misleading hint with a one-flag workaround.
  fix-shape hint: have the probe distinguish exec failure from a usage error (exit 126/127 or signal → name the exec failure and suggest TMPDIR), or stage the helper under the install prefix before running it; say which in the spec.

- [Nit] The backup (helper), step 2 ("Built in a private staging directory `<root>/.staging-<pid>` (0700; its name does not match the grammar, so pruning never sees it), removed on any failure"); AC 8 — The staging directory is removed only on handled failures; an interrupt or kill (SIGINT under curl|bash, SIGKILL, power loss) leaves a full store and node.key copy that pruning deliberately ignores and nothing ever sweeps; collision behaviour on pid reuse is unspecified.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: all three seats searched the spec for sweep, stale, signal, SIGINT, trap, exclusive: the only staging mentions are lines 63, 72, 134 and 138. "Removed on any failure" covers only errors the helper handles; a Rust process killed by a signal runs no cleanup, and install.sh's EXIT trap removes only $work and $retained_old (line 603). AC5 requires pruning never to touch the staging directory; AC8 covers only the helper's own refusals. This contradicts Risks "Disk: ... bounded by pruning (3 + one per older schema)". The "created exclusively"/EEXIST wording quoted by some members belongs to an earlier draft; the current spec leaves collision unspecified. The VACUUM INTO target-must-not-exist claim was not fetched by any seat and the verdict does not rest on it.
  severity note: seats unanimous at Nit: same-user 0700 leftover, seconds-long window, fail-closed with a --no-backup or rm escape.
  fix-shape hint: have the helper remove any `<root>/.staging-*` entries at start (they are its own by construction), define collision as remove-and-recreate, and add an AC for it.

## Rejected (with reason)
- [FYI] Where the work runs ("If neither has it, the installer refuses (fail closed) and names --no-backup"); Installer > --no-backup justification — The unconditional "neither executable has the helper" refusal breaks every pre-2.5.0-to-pre-2.5.0 install, forcing --no-backup where a loud skip would do. Rejected 3/3: the refusal and the --no-backup escape are a stated tradeoff (spec lines 25-27, 101-108) that follows from the fail-closed purpose; a loud skip is what --no-backup already is; a pre-2.5.0 target can still migrate the store (e.g. 2.3 to 2.4); the main-served install.sh ordering is release logistics, not a spec defect.
- [FYI] Installer ("--no-backup: skip the backup (and pruning)"); Pruning ("right after a successful backup") — On the full disk the spec names as the opt-out's rationale, the installer can never reclaim its own backups and pushes the user to --no-backup. Rejected 3/3: steady-state installer-owned backups are already at the cap (3 + one per schema), so a prune-first step would reclaim almost nothing; the 1.5 GiB laptop figure is the manual directories the spec deliberately leaves to the user; the failure message names "fix the cause" first; prune-before-backup would delete a retained copy before the new one is verified, against the fail-closed intent.
- [FYI] When ("before the old daemon is stopped"); Backup step 3 ("Consistent while the daemon runs"); Risks — Writes committed between the snapshot and the daemon stop are absent from the backup and the spec does not state the window. Rejected 3/3: the ordering is mandated by AC1/AC2 (fail-closed needs backup-before-stop); a point-in-time snapshot losing later writes is inherent to any backup and identical to the manual §7.1 recipe; a rollback discards everything after the upgrade anyway. At most a one-sentence docs caveat.
- [FYI] Naming and location ("Contents: herdr-threads.db, node.key, node.json"); Docs restore — The backup omits contexts/, intents/, launches.jsonl, harness-manifest/ etc. with no justification. Rejected 3/3: the three-file set is the inherited RELEASE.md §7.1 scope the user asked to automate; the finding itself calls one-way migration of the sidecars "speculative" and "not verified"; grep of src/daemon/paths.rs and src finds no sidecar migration; the backup protects the thing that migrates (user_version).
- [FYI] Risks ("A user who keeps manual backups under the same pattern gets them pruned"); Tests ("mtimes set with File::set_times") — Stale text from an earlier revision contradicts the current design. Rejected 3/3: neither quoted sentence is in the current spec; Risks now says manual directories are "left for the user to remove" and documents the hand-copied-under-grammar case; Tests no longer mention set_times; grep for set_times/mtime hits only Pruning (mtimes NOT used) and AC6. Residual: Tests do not name stamp-parse edge cases (-N suffix, TAG with '-'), a test-detail nit the finding did not argue.
- [FYI] Naming and location ("`<TAG>` the version being installed"); helper `--target-version TAG` — The spec does not pin which installer value becomes TAG or whether it carries the v prefix (pre-vlatest, pre-vv2.5.0). Rejected 2/3 (ground seat CONFIRM Nit): the backup runs after `changed` is known, by which point install.sh has read `new_version=$(cat "$package/VERSION")` (line 622), the bare Cargo version; AC1 tests the exact name `pre-v<new>-<stamp>` so a doubled v or "latest" fails the criterion; pruning never parses the tag. Dissent cites install.sh lines 64/600/622 and the missing sentence; the majority's AC1 point answers it. A one-line clarification would not hurt.
- [FYI] Acceptance criteria 1-8; Tests — No AC or test runs a restore. Rejected 3/3: restore is a documented manual file copy outside the helper's scope; the copy is a standalone VACUUM INTO db verified by integrity_check, user_version equality and byte-equal node.key; a restore test would mostly re-test cp. (The WAL-sidecar restore gap is the separate confirmed finding above.)
- [FYI] Risks ("bounded by pruning (3 + one per older schema)") — Per-schema keep retains one copy per distinct user_version forever, so "bounded" is misleading. Rejected 3/3: the Risks line states the growth term itself; user_version is finite and rises only on migrations; the per-schema keep is the deliberate rollback point AC5 tests; the host evidence (8 schemas in 11 days, 8-41 MB stores) implies a few hundred MB against the 1.5 GiB status quo.
- [FYI] Pruning > schema = PRAGMA user_version; Keep newest per schema — Retention keys rollback safety on user_version alone and never requires that every one-way change bumps it. Rejected 3/3: the spec's stated guarantee is rollback across "a one-way schema migration", defined as user_version; the newest-3 rule and the unconditional keep of the just-taken backup retain pre-change copies for three further upgrades; requiring the daemon's migration code to bump user_version is outside this spec.

## Unverified nits (spot-checked)
Each got one refute-seat pass that REJECTed at FYI; one pass is not panel-strength verification, so they are listed, not confirmed or dismissed.
- [FYI] Pruning, schema (immutable=1 read) — a backup later written to and left with a non-empty -wal reads a stale user_version (0 observed) and is misclassified. Spot: VACUUM INTO copies are rollback-journal with an empty WAL (seat-tested); only a hand-reopened backup is affected; newest-3 and just-taken keeps bound the effect.
- [FYI] Pruning, Keep ("every entry whose schema is unknown, with one warning each") — unknown-schema entries are kept forever with a repeating warning and no operator remedy; a damaged entry with a readable user_version can displace a good one. Spot: steps 3-6 verify and fsync before the rename, so a damaged grammar-named entry needs later tampering; keep-and-warn is the deliberate fail-safe; the warning names the directory.
- [FYI] Pruning ("A deletion that fails warns ... and continues") — remove_dir_all is not atomic, so a half-deleted entry becomes a permanently kept unknown-schema warning. Spot: rare trigger, few-KB leftover, named in the warning, hand-removable; rename-to-trash is optional hardening.
- [FYI] Pruning, time ("the UTC stamp in the name") — a future-dated stamp from a wrong clock holds a newest-3 slot indefinitely. Spot: the just-taken backup is kept by path and newest-per-schema keeps the latest of the current schema; worst case is one generic slot lost until the clock passes; wrong-clock hosts are out of scope.
- [FYI] The backup (helper), step 6 (directory fsync) — Rust sync_all uses F_FULLFSYNC on Apple and may fail on some filesystems or directory fds; the spec does not say whether a directory fsync error is fatal. Spot (web search only): fail-closed is the stated contract, so a fatal error is a refused install with no data loss; APFS is listed as F_FULLFSYNC-supported; the risk is an XDG_STATE_HOME on SMB/FAT. The spike (open a temp dir, sync_all on macOS) belongs in implementation.
- [FYI] Pruning (legacy directories / keep per schema) — the spec never counts distinct legacy (layout, user_version) keys, so most of the laptop's 1.35 GiB may be kept. Spot: the quoted "Legacy directories hold most of the 1.5 GiB" text is not in the current spec; manual directories are never read, counted or removed (AC5); the finding targets a stale draft.
- [FYI] The backup (helper) steps 3-4; Tests — no time budget or progress output for VACUUM INTO and integrity_check while the user waits on curl|bash. Spot: seconds of work on a ~42 MB store, same as the manual .backup; an interrupt before the stop is safe (the leftover staging dir is the confirmed Nit above).
- [FYI] Pruning ("right after a successful backup"); When — pruning completes before the install is known to succeed, so retries of a failing upgrade push older same-schema backups out of newest-3. Spot: a failed install before the replace leaves the store unchanged, so the retried backups are identical; newest-per-schema keeps every older schema's rollback point.
- [FYI] Acceptance criterion 2 ("unwritable parent") — the trigger stops failing once the root exists. Spot: misquote; the spec's AC2 (line 126) says "unwritable backup root" and Tests line 144 says "backup root made read-only".
- [FYI] Pruning > Keep (new backup vs newest 3) — unclear whether the new backup counts toward the newest 3, so AC5 cannot pin an exact survivor set. Spot: the keep rules are a union (just-taken by path, newest 3 by name stamp, newest per schema, unknown), order is total by stamp/-N/name, mtimes are not used; the survivor set is fully determined.
- [FYI] The backup (helper) step 7; Pruning lines — success/warning/pruned lines have no output stream and install.sh's relay is unstated. Spot: AC4 is met by not running the helper; AC7 covers all channels; the lines use install.sh's say/warn/die prefixes (lines 77-79) and pass through by default.
- [FYI] Where the work runs ("--state-dir DIR ... local only") — unclear whether `--state-dir` is the subcommand flag or the global one, and whether startup paths touch the live state dir. Spot: the spec's invocation puts the flag after the subcommand; the branch's `run_parsed_in_pane` returns `pre_upgrade_backup::run(state_dir, ...)` before NodePaths::resolve or context building, and defines `--state-dir` on `InternalSub::PreUpgradeBackup`.
- [FYI] When ("the two default roots"); Risks; AC4 — a store outside the default roots gets no backup and no message. Spot: Risks explicitly accepts the custom --state-dir case as documented, matching the daemon-stop limit; AC4 deliberately requires silence on no-store; the installer cannot tell fresh from elsewhere.
- [FYI] Pruning > Keep ("the backup just taken (by path, unconditionally)") — no lock on the backup root, so two concurrent installers can prune what the other keeps. Spot: staging names are off-grammar, the rename is atomic, the newest stamp survives newest-3 from either snapshot; concurrent installs already collide on the prefix swap and daemon stop; the finding itself calls it low-likelihood speculation.
- [FYI] Pruning, Keep ("the newest 3; the newest per schema") — count-based retention rotates out every clean copy three upgrades after a silent data-corruption bug; releases came 14 hours apart. Spot: the stated goal is rollback across a schema migration; a backup taken after silent corruption already holds it; an age floor is a new feature outside the user's "clean up as it goes" request.
- [FYI] Pruning ("Delete the rest"); Risks — the first 2.5.0 upgrade deletes most of the 23 existing backup directories with no dry-run or confirmation. Spot: premise false; the manual directories sit outside `herdr-threads-backups/` and off the grammar, are "never read, counted or removed", and AC5 requires them byte-identical; the new root is empty on the first upgrade.
- [FYI] When vs Pruning (legacy layout) — per-instance schema reading for legacy-layout backups preserves rollback points the spec itself says are unneeded. Spot: the spec has no legacy-layout branch; Pruning reads only `<entry>/herdr-threads.db`; the described hex-dir walk does not exist.
- [FYI] Risks; Pruning > Candidates — pruning runs over the whole parent including manual and legacy directories. Spot: stale; candidates are only grammar-matching entries inside the installer-owned root; no legacy detection or mtime logic exists; cleanup of manual directories is explicitly the user's.
- [FYI] Where the work runs (three-way executable selection) — the fallback to the installed executable adds code and test surface for the narrow >=2.5.0 to <2.5.0 rollback. Spot: the "always use the installed binary" alternative fails the primary case (first upgrade from <2.5.0 has no helper); the fallback is one probe branch with a stated fail-closed outcome; two prune policies on one directory are harmless because matching is grammar-only.
- [FYI] Tests ("New tests/release/installer_backup_test.py ... wired into CI and scripts/release-qualify") — a new file and wiring point where the requirement said extend existing suites. Spot: tests/release/ is one file per installer topic, so a new topic file follows the pattern; release-qualify line 132 builds paths from a name list (one entry) and ci.yml needs one line; the suite covers helper-capability fallback cases install_test.sh cannot.
- [FYI] The backup (helper) step 3; Risks ("Disk: one more full copy") — VACUUM INTO may use SQLite temp storage, so the backup can fail on a small tmpfs even when the parent has room. Spot (SQLite page not fetched): any helper failure ends in the same documented fail-closed path with the partial removed and --no-backup named; a temp-space note in Risks is a docs suggestion.
- [FYI] The backup, step 1 ("-2, -3 appended") and step 2 (pid-scoped staging) — collision handling for same-second or concurrent installs the installer does not otherwise support. Spot: the -N suffix is part of the grammar and the tie-break; back-to-back installs in install_test.sh and installer_backup_test.py can share a second and a rename onto an existing entry would fail closed; a pid suffix costs less than fixed-name-plus-stale-cleanup; the "created exclusively" quote is from an earlier draft.
- [FYI] When ("An identical re-install (changed = 0) ... take[s] no backup") — a same-package re-install skips the backup even when a dev-checkout daemon migrated the store. Spot: the rule is stated; a re-install replaces nothing so the installer causes no migration; the finding calls the dev-daemon migration "not established".
- [FYI] The backup (helper), step 3 (VACUUM INTO vs backup API) — VACUUM may renumber implicit rowids while the store orders by rowid (read_cursors.rs:365, retention.rs:155). Spot: https://www.sqlite.org/lang_vacuum.html quote confirmed, but the finding's own 3.51.2 test preserved gapped rowids; VACUUM copies in rowid order so relative order holds; the rowid uses found are transient; the spec requires no page-identical copy.
- [FYI] The backup, steps 3, 5, 6 (fsync chain) — per-file plus directory plus parent fsync exceeds what a pre-upgrade backup needs. Spot: without fsync-before-rename a power loss can leave a grammar-matching hollow entry that counts toward newest-3 and newest-per-schema; the window right after install, when the new daemon migrates, is when the backup is needed; cost is a handful of calls.
- [FYI] Backup step 3 ("The copy is chmod 0600 and fsynced") — SQLite fsyncs VACUUM INTO output only when the source's synchronous is NORMAL/FULL; the spec's claim rests on the helper's own fsync and its ordering. Spot: the finding concedes the helper's explicit fsync covers it; step 4 verifies before the step 6 rename, so a truncated copy never gets a grammar name; the rollback-journal copy mode is harmless and cleaner for immutable reads.
- [FYI] The backup (helper), step 4 ("integrity ok") — integrity_check on the copy shows the copy is well-formed, not that it matches the source; the source gets no check. Spot: a well-formed, logically complete copy is the property a restore needs; damage in live pages fails the VACUUM INTO or the copy's check (AC8); checking the live store is a separate feature the spec never claims.
- [FYI] The backup (helper), step 3 ("read-only connection to the live store"); Where the work runs ("local only") — a read-only VACUUM INTO on a cleanly closed WAL store creates -wal/-shm in node/ that persist after close (seat-tested on 3.51.2). Spot: "no effects" applies only to the --help probe; sidecars beside a WAL store are normal SQLite state the daemon reuses or removes on next open; no requirement depends on the live directory staying untouched.
- [FYI] Backup step 3 ("VACUUM INTO from a read-only connection") — SQLite's docs do not say read-only connections are supported. Spot: https://www.sqlite.org/lang_vacuum.html fetched: "VACUUM (but not VACUUM INTO) is a write operation"; seat-tested mode=ro VACUUM INTO on a WAL db on 3.51.2 succeeded with the row present; step 4 would catch an inconsistent copy; the daemon holds the -shm open.
- [FYI] Naming and location ("Root: `<parent>/herdr-threads-backups/`") — the root sits in Herdr's shared plugin state directory with no cited guarantee that Herdr ignores unknown subdirectories. Spot: 16 manual `herdr-threads-pre-v*` sibling directories have coexisted there since 2026-10-17 across many Herdr releases with no observed effect; Herdr internals were not researched.
