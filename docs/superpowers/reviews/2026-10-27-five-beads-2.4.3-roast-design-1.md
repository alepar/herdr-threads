## Confirmed findings            ← consumed by super-design, one task per finding
- [Nit] ht-xe3v Fix: "A stale daemon is stopped ... and the installed executable ensured in its instance; then verification repeats, at most five checks (four replacements). A stale daemon that cannot be stopped is never ensured over: ... exit 3." — The replacement loop does not cover the race it exists for: an old client restarting the daemon between the installer's stop and its ensure makes the stop report failure or the ensure hit a version mismatch, and either ends verification with exit 3 on the first attempt, so the four-replacement budget is never used.
  verdict: confirmed (reproduce ✓ CONFIRM Nit / refute REJECT FYI — dissent not material, tally stands / ground ✓ CONFIRM Nit)
  evidence: scripts/install.sh `replace_stale` runs `ensure_instance "$instance" || return 1` after the stop; `verify_installed_daemons` runs `replace_stale "$stale" || return 1`; the no-stale branch runs `ensure_instance ... || return 1`. `stop_with_installed` returns failure when any daemon pid is live after its 5x0.2 s poll. `ensure` in src/daemon/lifecycle.rs returns `DaemonVersionMismatch` for a live owner of another version. A restart landing in the stop-to-ensure gap therefore exits 3 after one round; only a restart landing before `stale_instances` gets another round. tests/release/installer_daemon_test.py restarts the daemon inside the stub's `stop`, so the gap is not exercised. The refute seat's point (the gap is milliseconds wide against a 2 s ensure cadence, the outcome is the documented exit-3 status, and the spec's acceptance bullet 2 only requires bounded give-up) is why this is a Nit and not Should-fix; it does not disprove the premise, and both confirming seats already weighed it.
  fix-shape hint: treat a stop failure or an ensure mismatch inside a replacement round as "stale, next round" (rescan `stale_instances` and continue the bounded loop) instead of `return 1`, and add a Python case with the racer restarting between stop and ensure; or state in the spec that the stop-to-ensure gap is outside the retry budget.

## Not verified (beyond panel cap)   ← severe candidates the panel cap left unverified — listed, never dropped
- [suggested Should-fix] ht-hvyf Fix: "It runs on the first scanned pass and whenever a destination found by the previous one is gone"; "retires (deletes) every enabled herdr_remote_process row that never linked" — Retirement equates "never linked and client not currently running" with "not a real peer", so a legitimate remote whose first link has not succeeded loses its row (including on the first pass after every daemon restart, since `last_found` is in-memory), an unacknowledged behaviour change.
- [suggested Should-fix] ht-xe3v Fix: "Keep `<prefix>.old` until daemon verification ends (removed by the EXIT trap)" and "ends with ... exit 3" — On the exit-3 give-up path the EXIT trap still deletes `<prefix>.old`, removing the only executable the spec says can stop the old daemon across a wire change, with no recovery hint for the operator.
- [suggested Should-fix] ht-hvyf Fix / Acceptance: "the Dialer reloads after a retirement" — Retirement hard-deletes rows the Dialer may have an in-flight dial or fresh link on, breaking the "rows are never deleted" invariant; a link that succeeds afterwards fails its state write ("unknown dial target") and loses `learned_node_uuid`/`last_linked_at`, and the spec does not say what reload does to such a task.
- [suggested Should-fix] ht-hvyf Operator: "`herdr-threads human peer forget test-only` is the manual fallback" — `peer forget` only disables an existing row; once retirement has deleted the row, forget is a no-op and the next harness sighting re-inserts an enabled row, so there is no durable way to suppress a known test destination.
- [suggested Should-fix] ht-xe3v Fix: "argv[0], symlinks resolved, equal to the installed executable" — The executable-identity check assumes argv[0] is an absolute, resolvable path to the daemon's image; a relative or bare argv[0] (or any spawner not passing current_exe) is misclassified as stale, so a correct daemon is replaced up to four times and the installer exits 3.
- [suggested Should-fix] ht-xe3v Fix: "Keep `<prefix>.old` until daemon verification ends (removed by the EXIT trap)" — The spec ignores long-lived pre-swap clients (the mod watch, open hooks) after `.old` is removed: on Linux their current_exe names a deleted file and their ensures hit version mismatches, so they can no longer restart a daemon that later exits, and the guarantee holds only at the instant the installer exits.
- [suggested Should-fix] ht-xe3v Acceptance / Fix: "removed by the EXIT trap" — Nothing rechecks after the last clean `stale_instances` check: an old client can restart the old daemon between that check and the EXIT trap's removal of `.old`, leaving a daemon running from a deleted inode after the installer reported success.
- [suggested Should-fix] ht-xe3v Fix: "Verification checks every live instance for the installed version *and* for its executable (argv[0], symlinks resolved, ...)" — The check reads the executable with `ps -p PID -o command=` without `-ww`; on BSD-derived ps (macOS) a non-terminal output may be cut to a fixed width, so the " daemon run " suffix would not match, the path would come back truncated, and a correct daemon would be flagged stale.
- [suggested Should-fix] ht-xe3v Acceptance: "An upgrade where an old-executable client restarts the daemon after every stop ... (Python `installer_daemon_test.py`, fails on main)"; Root cause: "/proc/self/exe ... follows the rename" — The acceptance tests model the race synchronously inside the stub's `daemon stop` with a separate old-client directory, so neither the asynchronous timer-driven racer nor the /proc/self/exe rename-follow mechanism named as root cause is exercised.
- [suggested Should-fix] ht-xe3v Fix: "Verification checks every live instance for the installed version *and* for its executable" — The executable check widens the installer's stop authority: any same-version daemon on a default state root started from another build (dev checkout, another prefix) is now classed stale, stopped and replaced, where before only a version mismatch was reported.
- [suggested Should-fix] ht-xe3v Root cause: "A client process that started before the installer's directory swap ... ensures the daemon from `std::env::current_exe()`." — The root cause is asserted from current_exe semantics without any cited observation from blacky (stale daemon's argv[0]/exe under `.old`, the spawning client), and the mechanism barely fits the pre-fix timeline (the old installer deleted `.old` right after the post-swap stop).
- [suggested Should-fix] ht-xe3v Root cause / "Fix (scripts/install.sh)" — The fix mitigates in the installer only and leaves the stated root cause (clients ensuring from a current_exe that follows the rename) in place, with no client-side change or follow-up noted, against the project rule "Fix root causes, not symptoms ... note it as a follow-up".

## Rejected (with reason)        ← so re-roasts don't re-litigate
- [FYI] ht-hvyf Fix: "A discovery pass whose process scan completed retires (deletes) every enabled `herdr_remote_process` row that never linked ..." — "Scan completed" cannot tell a failed or partial process listing from an empty one (`list_pids` swallows errors into an empty Vec), so a scan failure retires every never-linked process-scan row.
  votes: reproduce REJECT FYI / refute REJECT FYI / ground CONFIRM Nit (minority cites the same code facts the majority accepts; majority answers the impact).
  reason: the mechanism is real (src/sync/discovery.rs:457-477 sets `scanned` on any Ok join; src/host/process_table.rs:185-194 `read_dir("/proc")...unwrap_or_default()`), but retirement touches only never-linked `herdr_remote_process` rows, which hold no learned identity or link history, and the spec states "a later sighting adds the row again". A bad scan costs one delete and a re-add on the next good pass; `last_found` becomes the empty set so no retire loop follows. Hardening nit (propagate a scan error so "completed" means "succeeded"), not a gap against the stated contract.
- [FYI] ht-xe3v Fix: "A stale daemon is stopped (retained old executable, else the installed one) and the installed executable ensured in its instance" — Replacing a stale daemon calls `stop_with_installed`, which stops every live instance, but re-ensures only the stale ones; a healthy daemon in another instance is left down while the installer reports success.
  votes: 3x REJECT FYI.
  reason: accurate code reading, but `stop_with_installed` is the installer's established stop-everything helper, already used for the pre-swap and post-swap stops (scripts/install.sh ~l.468, 474, 653, 690), so every upgrade already stops all instances and relies on lazy re-ensure by the next client (hooks, the mod's 2 s watch ensure). The spec states no multi-instance keep-alive requirement; its acceptance is "installed executable serving" and bounded give-up. The scenario needs a node daemon plus a legacy `instances/<digest>` daemon with exactly one stale. Documentation nit at most.
- [FYI] ht-hvyf Root cause "accepts any same-uid process ... whatever server or config it belongs to" vs Fix "a later sighting adds the row again" — The fix leaves the scan's over-broad acceptance unchanged, so each mosh harness run re-adds and dials `test-only` while the client lives and only retires it afterwards.
  votes: 3x REJECT FYI.
  reason: the finding rests on a requirement ("keep test remotes out of the shared server's discovery") the spec does not state. The ht-hvyf problem statement is a never-linked row kept forever and dialed 2000+ times; the fix scopes to retiring such rows once their client is gone, and explicitly accepts "a later sighting adds the row again". A live `herdr --remote test-only` is indistinguishable from a real remote client without heuristic attribution, which the repo's trust policy avoids. "Steady passes write no more than before" concerns passes with no change in the found set; a client appearing or vanishing is a change. Design preference, not a contradiction.

## Unverified nits (spot-checked)
- [FYI] ht-xe3v Fix: "its executable (argv[0], symlinks resolved, equal to the installed executable)" — Identifying the daemon's executable by argv[0] rather than the kernel's exe record misses an old image spawned with the installed path as argv[0], so a same-version, different-bytes upgrade can leave a pre-swap daemon undetected. (refute seat: REJECT; on Linux the spec's own mechanism yields an argv[0] under `.old`; the extra case needs a cached pre-rename path plus an identical version string.)
- [FYI] ht-hvyf Fix: "retires (deletes) ... a later sighting adds the row again"; Operator: "`peer forget` (disables it ...)" — Retiring by DELETE instead of disabling discards the row's dial history, backoff and diagnostics and introduces a second removal semantic next to forget. (refute seat: REJECT; only failed-dial counters of a never-connected peer are lost, each retirement is logged, forget stays the manual choice.)
- [FYI] ht-hvyf Fix: "whenever a destination found by the previous one is gone" — Retirement triggers on a single pass of absence with no hysteresis, so a flapping or racily unread client is deleted, reloaded and re-inserted with reset backoff each cycle. (refute seat: REJECT; a long-lived client is not plausibly missed repeatedly, worst case a few extra early dials.)
- [FYI] ht-xe3v Root cause: "On macOS `current_exe` returns the original path string ... which is why the laptop never showed it" — The macOS half of the root cause rests on platform behaviour Rust documents as unspecified, is uncited, and the new check runs on macOS with no macOS acceptance coverage. (external claim; refute seat: REJECT, the fix is platform-independent and nothing in the spec acts on the macOS aside; the seat did not run the web research.)
- [FYI] ht-xe3v Fix: "at most five checks (four replacements)"; Acceptance bullet 2 — The five-check bound has no derivation and cannot win against a persistent racer; without fencing it only changes how long the installer takes to fail. (refute seat: REJECT; the spec specifies exactly that loud bounded failure, and fencing is out of scope for a patch bead.)
- [FYI] ht-xe3v Acceptance: "give up in bounded time with the existing incomplete status" — "Bounded time" is not quantified: only the round count is limited, each round can wait on real stop/ensure timeouts, and the only tested bound is 30 s against instant stubs. (refute seat: REJECT; the spec defines bounded as a round cap and sets no wall-clock target.)
- [FYI] ht-xe3v Root cause / Fix — The spec assumes an old-version client only ensures when no daemon is running; if it also replaced on version mismatch, installer and client would displace each other after verification ends. (refute seat: REJECT; the spec's own root cause says a mismatched ensure only warns, never replaces.)
- [FYI] ht-xe3v Fix bullet 1: "so the old executable can still stop an old daemon across a wire-protocol change" — Keeping `<prefix>.old` for a wire-change stop rests on an unverified premise since the installed binary is already the fallback stopper. (refute seat: REJECT; the version-tolerant rule covers the peer wire, not the local stop request, and the fallback covers first installs.)
- [FYI] ht-xe3v Fix: "for the installed version *and* for its executable" — The executable-identity check is added on top of the version check, but the described race is already caught by the version check alone; no scenario needs the identity check. (refute seat: REJECT; the existing status is "running daemon does not match the installed executable", an identity statement; same-version rebuilds are ordinary for local-build installs.)
- [FYI] ht-hvyf Fix: "It runs on the first scanned pass and whenever a destination found by the previous one is gone" — The `last_found` trigger is an unjustified write-avoidance optimisation and misses never-linked rows whose destination was not in the previous pass's found set. (refute seat: REJECT; never-linked process rows come only from this worker's own sightings, so the trigger is complete for the spec's design.)
- [FYI] ht-xe3v Fix: "Keep `<prefix>.old` until daemon verification ends" — Keeping `.old` widens the window in which a pre-swap Linux client can start the old daemon; under the old installer later spawns would fail on a "(deleted)" path. (external claim; refute seat: REJECT, the verification loop exists to catch exactly those daemons and the spec's acceptance assumes them.)
- [FYI] ht-hvyf Operator: "`peer forget <dest>` (disables it; discovery never re-enables a forgotten row)" — Forget leaves a disabled row forever and the spec does not say whether retirement or an upgrade ever removes it. (refute seat: REJECT; forget is an existing command with documented disable-not-delete semantics, presented only as a fallback.)
- [FYI] ht-hvyf Fix (retirement within the discovery pass) — In the same transaction, upserts run before retirement, so at the target cap a newly seen destination is skipped in the pass that frees room and only added on a later pass. (refute seat: REJECT; one-pass delay at the cap, nothing lost; the cap is pre-existing behaviour the spec never mentions.)
