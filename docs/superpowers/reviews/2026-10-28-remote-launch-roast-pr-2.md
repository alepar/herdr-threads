- src/cli/peer_launch.rs:347; :306; :313; :308; :305 — After a remote launch child exits 5 (start unconfirmed), the requester keeps the request-id file and the launching node keeps a terminal `failed` row, so every rerun of the same command replays the same failure (exit 3) until the 7-day prune at a daemon start, after which it silently launches; no command or doc clears the kept id. [fix-regression] Rejected 2-1 (reproduce REJECT FYI, refute REJECT FYI; ground CONFIRM Nit). Reason: the mechanism is undisputed, but the keep is the spec's stated contract: design spec round-1 note (~line 661) "An unconfirmed start (child exit 5) keeps the id too: a rerun reports the same", the code comment at peer_launch.rs:306 "never a second agent in a pane that may already run one", and TRUST-POLICY N15 "answered with the recorded outcome, never a second launch ... never resumed or relaunched automatically". The 7-day retention is stated in N15. A way out exists without new code (change any plan field, which changes the id key; or the operator's inspection on the launching node). The confirming ground seat itself concedes "That is an accepted tradeoff, not a defect" and cites nothing the majority does not address. This is the follow-on of resolving the iteration 1 Nit at src/cli/peer_launch.rs:270. What remains is a UX wish: the exit-3 (retryable) code on a terminal answer and the absence of a hint naming the id file or an override. Carried as a note: a script that retries on exit 3 can never change the answer; a distinct exit code or a one-line hint in the detail would close it cheaply.
