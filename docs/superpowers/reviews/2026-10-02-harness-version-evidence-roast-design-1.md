## Confirmed findings
- [Should-fix] Evidence store and recording, Attribution bullet — Version attribution resolves the installed binary on PATH/inode, not the running harness process, so after an in-place/background upgrade payloads from old sessions are credited to the new version, falsely verifying it or sticking a violation on it.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Spec: "the version is the one B6's admission observer resolved for the executable that ran the hook (path/inode cache, re-observed on change)". B6 src/cli/hook.rs `observe_harness_in` calls `resolve_on_path(name, path)` then `claude::observe_installed_version(&binary, ...)`: it resolves the first `claude` on PATH, not the parent process. https://code.claude.com/docs/en/setup: "Updates download and install in the background, then take effect the next time you start Claude Code"; `~/.local/bin/claude` is a symlink into `versions/`. So old sessions keep running while PATH resolves to the new build; the "cannot attribute → record nothing" guard never fires because the observer returns one confident, wrong version. With "local violation → broken" first and violations sticky until version change, a misattributed violation degrades the new version and the "pin to ≤ last working" action points at the wrong version.
  refute seat note: rejected on scope (spec says "executable that ran the hook"; B6 code is another artifact) and on bounded impact; the two confirming seats answer this by showing the spec names no mechanism that identifies the running process, so the requirement is unimplementable as written.
  fix-shape hint: key attribution on the parent harness process's executable path (or the `versions/<v>` path it was launched from), or gate recording on a SessionStart version snapshot matching the per-event observation; otherwise record nothing.

- [Should-fix] Manifest > Format ("schema_version 2, extending B6's generated file"); Embedded copy; Canary and publishing — Two producers (B6's RECIPES-generated in-repo file and the canary-written branch file) share one filename with different schemas and no reconciliation rule, and the canary's since-verified selection rejects non-schema-1 files.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Spec lines 87-93 define schema_version 2 with canary-only fields (status, supported_since, broken_event, broken_field, last_working, issue_url, latest_release, contracts) and embed the branch file "falling back to the in-repo generated file"; local builds embed the in-repo file. On branch super-auto/remaining-herdr-threads-findings, docs/compatibility/harness-versions.json is schema 1 with rows {harness, version, recipe, evidence, known_broken: []}, regenerated from RECIPES under `versions_json_guard`/HT_BLESS; scripts/canary/versions.py line 25 raises `not a harness-versions.json (schema_version 1)` on any other schema. The spec never says whether the in-repo generator emits v2, which copy the canary reads, how `verified_max` advances, or what a daemon does on a schema_version mismatch ("Unknown fields are ignored" only). Local and release builds of one commit can classify the same unseen version differently.
  refute seat note: rejected because B6 is not merged in this worktree and "extending" implies the amendment; the confirming seats cite the B6 branch files directly.
  fix-shape hint: state one producer chain: the in-repo generator emits schema 2 (canary-only fields null), the canary reads the branch file as its baseline, versions.py accepts schema ≥ 1 with a defined upgrade, and a daemon treats an unsupported schema_version as "no manifest" (fall back to embedded).

- [Should-fix] Canary and publishing ("known_broken with the failing event/field and last working version"); Goal — The spec assumes every canary failure maps to a payload event and field, but B6 canary checks include non-payload failures (setup/unsetup, config load, Codex schema fingerprint drift, launch flags in --help, admission classification). The spec does not say whether those produce known_broken rows that degrade users, nor what broken_event/broken_field they carry.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: `bd show ht-p03.14` Tier 0: "setup/unsetup clean on a fresh isolated home; harness loads the written config via a model-free command; Codex hook-schema fingerprint match/drift; launch flags appear in --help". Spec row schema has `status (verified | known_broken)` plus `broken_event`/`broken_field` with no null convention; "Deriving the state" maps any `manifest known_broken (same contract)` to broken for a never-verified version, and the broken line must name "the failing event and field". Testing lists only "all pass, break, known broken persists, flaky". Either a config-load failure degrades users with an empty event/field (a false degrade on a routine upgrade, which the Goal forbids) or it never reaches users; the spec picks neither.
  severity note: reproduce Should-fix, ground Nit; kept at Should-fix because the undecided branch directly produces the Health noise the spec's top priority rules out, and the fix is one sentence before the writer is built.
  fix-shape hint: state which canary outcomes write `known_broken` (payload-contract failures only; Tier 0 and infra_error/inconclusive stay issue-only), and make `broken_event`/`broken_field` required on known_broken rows.

- [Should-fix] The payload contract ("`contract_id` = a short hash of the declaration"); Manifest `contracts: {harness: contract_id}` — The canary and manifest writer must compute the same `contract_id` as the Rust binary, and contract_id must be stable across builds and toolchains; the spec defines it only as 'a short hash of the declaration', without a canonical serialization or a way for the canary to obtain it.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Spec line 64 defines contract_id only as "a short hash of the declaration"; line 88 puts `contracts: {harness: contract_id}` and a per-row contract_id in the manifest; lines 115-118 match rows on "same contract". No canonical serialization, hash algorithm, or CLI/dump for the canary is named; the only source text is "supported_since come from the recipe/contract tables". Testing has a drift test and a writer selftest but no test that a canary-written contract_id equals the binary's. If the Python writer computes a different id, every canary known_broken row silently never matches and the manifest path becomes a no-op, defeating Decision 3 ("needs no herdr-threads build"). The DefaultHasher scenario is speculation; the undefined cross-language definition is the gap.
  fix-shape hint: define contract_id as a truncated SHA-256 over a canonical (sorted-key, minified) JSON of the declaration, expose it via a `herdr-threads contract-id` subcommand or build-time dump, and add a selftest pinning the value.

- [Nit] Manifest > Format ("size capped at 256 KB"); Background ("Harness versions change almost daily"); Fetch policy ("Any failure falls back silently") — The manifest has no retention/pruning policy, so near-daily rows will exceed the 256 KB cap, after which fetches silently fail forever.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: No section defines row expiry, pruning or a writer-side size check; "size cap" appears only as a reader-side test. The canary appends rows after each run and "known broken persists". Seats estimate ~11 fields per row, ~700 rows/year across two harnesses, reaching the cap in roughly 1-2.5 years (estimate, not measured). An oversized fetch is "any failure" and falls back silently to cache then embedded copy, so new verdicts stop reaching users and nothing alerts anyone; the release build would then embed the oversized file too.
  severity note: two seats Nit, reproduce Should-fix; demoted: profile is a pre-release single-maintainer tool with a graceful, slow (>1 year) failure that local evidence and the embedded copy still cover, so a missing pruning rule is a Nit here.
  fix-shape hint: keep only the newest N versions per harness plus any known_broken rows, and have the canary writer fail loudly above ~80% of the cap.

- [Nit] Manifest > Fetch policy ("Opt-out: config `harness_manifest = \"off\"` (default `\"auto\"`) and env `HERDR_THREADS_OFFLINE=1`") — The opt-out config key and HERDR_THREADS_OFFLINE env var are unspecified as to location, which process's environment counts, and reload behaviour.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: The opt-out appears once (line 97). The spec says "the daemon fetches it at runtime", and the daemon is long-running and started separately from the user's shell. A grep of `src` finds no herdr-threads config file (only Codex's `$CODEX_HOME/config.toml`), so `harness_manifest` has no stated home; HERDR_THREADS_OFFLINE appears only in this spec. Nothing says hooks/CLI forward the flag, that the daemon reloads config, or how `doctor` shows the effective policy. A user exporting the variable after the daemon started gets no specified effect, while the Testing line "opt-out and offline honored" could pass with the env set in the test process.
  severity note: demoted: profile is a pre-release single-operator tool and the opt-out guards one conditional daily GET of a public static file that sends no user data, so an undefined reload rule is a Nit here.
  fix-shape hint: name the config file, have the daemon read env and config at each fetch decision (not at start), and have `doctor` print the effective fetch policy.

## Rejected (with reason)
- Evidence store ("A violation sticks ... not when a later payload parses"); Deriving the state — Single violation permanently marks (harness, version, contract_id) broken with no threshold/recovery/clear command. Rejected 3-0: stickiness is an explicit tested decision (Decision 5, Testing "violation sticks until version/contract change"); a violation is narrowly a real contract break; misattribution is a separate finding; action line (upgrade/pin/report) is defined. Residue: no manual clear command, an ergonomic omission only.
- Manifest > Trust ("block") vs Deriving the state — Spec contradicts itself on whether manifest known_broken "blocks" a version. Rejected 3-0: "broken" is defined only as degraded Health plus a doctor line; manifest rows never feed the B6 admission ladder; lifecycle_ok_at and tool-ok notes keep accruing while unverified, and "local verified → working" outranks the manifest. "Block" is loose wording (Nit).
- Manifest Format rows; Deriving the state ("manifest verified ... → working") — Only known_broken checks "same contract"; manifest row key undefined. Rejected 2-1 (ground CONFIRM Nit): the unqualified verified branch errs optimistically, "working" and "new" produce identical Health output, local violation still wins; the row key omission is a documentation clarification.
- Deriving the state ("ladder Refused → broken" before local verified); states table — Refused applies to all B6 refusal reasons, contradicting Decision 5 and the Goal. Rejected 2-1 (ground CONFIRM Should-fix citing `bd show ht-p03.13` three Refused rows: unparsable, compiled known_broken, older than floor). Majority: the spec says "B6's ladder remains the internal classifier" and does not redefine refusal reasons; an unparsable version has no attributable version anyway; the action ladder ends in "report". Dissent noted for the author: the table's parenthetical covers one of three reasons; a one-line clarification of which Refused reasons are meant would close it.
- The payload contract (violation = missing/wrong-type required field) — Contract model cannot express value-level constraints (SessionStart source enum, agent_id/agent_type co-presence, length limits, tool_name == Bash). Rejected 2-1 (ground CONFIRM Should-fix). Reproduce seat confirmed the parser facts (src/harness/claude.rs lines 134-160 return ContextError::Invalid on those) but all rejections rest on the spec deliberately scoping the contract to fields/types and routing everything else to B6's never-degrading counter; this is a false-negative tradeoff the spec states, not an unstated gap.
- Canary and publishing; Testing ("flaky") — Nothing stops a flaky/false canary run from publishing known_broken. Rejected 3-0: Trust bullet accepts "at worst block a version never seen here"; local verification self-heals; the canary rewrites rows every run; run classification (inconclusive/infra_error) belongs to B6's canary, which stays the producer.
- Manifest `supported_since`; Canary and publishing — supported_since needs per-release contract history the canary cannot produce. Rejected 2-1 (ground CONFIRM Should-fix): each release tag carries its own in-tree contract declaration (readable via `git show <tag>:path`, no build needed); equal contract_id means equal required fields by the drift test; the action ladder falls through to pin/report when no release supports the version. Residue: the derivation rule should be stated in the plan.
- Evidence store ("payload ok" note at most once per session, "daemon's last reply") — Per-session state and non-blocking send are unspecified. Rejected 2-1 (ground CONFIRM Should-fix): "best-effort" explicitly accepts a dropped note, retried next session; a stuck "new" state is silent in Health; where the flag lives (state-dir file, check-in reply) is an implementation choice.
- The payload contract; states table row "new" — No liveness detector when a harness stops invoking hooks or renames event kinds. Rejected 3-0: the Goal deliberately limits "broken" to observed violations or canary rows; "new" has a doctor line; the canary covers hook-registration breaks via known_broken rows; absence-based degradation would reintroduce noise.
- Canary and publishing ("`contents: write` scoped to that branch") — GITHUB_TOKEN cannot be scoped per branch. Rejected 2-1 (ground CONFIRM Nit). External premise grounded (docs.github.com workflow-syntax#permissions: per-scope only, no branch option) but immaterial: the spec's cooperative trust model and "`main` stays protected" (rulesets) are the actual mechanism; wording fix only.
- Canary and publishing — Manifest write not required to run in a separate job from the one running npm-installed harnesses. Rejected 3-0: a poisoned manifest is inside the spec's accepted worst case ("advisory and unsigned"; signing is a non-goal); the data-only branch carries no code; job split is workflow-YAML hardening.
- Manifest Fetch policy (once-per-day limit shared by triggers (a) and (b)) — A same-day violation cannot look up a fix. Rejected 3-0: the daily cap is Decision 4; the broken state and fallback action (pin/report) do not depend on a fresh fetch; a same-day re-fetch would rarely return a new row.
- Canary and publishing — No merge/concurrency semantics for the manifest writer. Rejected 2-1 (ground CONFIRM Nit): single producer (B6's canary, with its existing `harness-canary` concurrency group); a dropped push is self-healing on the next daily run; per-row merge keyed by harness+version is the natural reading. Residue: one sentence on merge-per-row and rebase-and-retry.
- Evidence store ("same channel B6 uses for parse failures") — New hook↔daemon messages need protocol/capability changes and skew handling. Rejected 3-0: attribution is daemon-side per the Attribution bullet; every skew combination fails safe to the silent "new" state; B6's capability-gate pattern is an implementation convention.
- The payload contract / Evidence store — Spec does not define what the hook does at the moment of a violation. Rejected 3-0: violations ride B6's parse-failure path, whose hook-side behaviour this epic does not change; a violating payload is already unprocessable, and "broken" reports that loss.
- Manifest `evidence (live | no_model | schema)`; Deriving the state — State function ignores the row's evidence tier. Rejected 2-1 (ground CONFIRM Nit): `status` is the canary's judgment, delegated to B6 ht-p03.14; local violation still flips to broken; working and new share Health output. Residue: show the tier in doctor or restrict `verified` to tool-exercised tiers.
- Manifest Fetch policy trigger (a); Trust — Cached/embedded rows suppress trigger (a) with no TTL, so a corrected known_broken is never refreshed. Rejected 3-0: "broken" is display-only, not admission; recording continues while unverified; one lifecycle + one tool payload flips the version to working ("local verified → working, manifest known_broken shown in doctor only"); pre-first-use degraded line is the accepted Trust bound.
- Manifest → Embedded copy / Fetch policy — No freshness or precedence rule among fetched, cached and embedded manifests (no generated_at comparison). Rejected 2-1 (reproduce CONFIRM Should-fix). External premise (raw.githubusercontent.com max-age=300) not fetched by any seat and not relied on. Majority: the Trust section bounds a stale row to blocking a never-seen version; TUF-style freeze/rollback defenses are an adversarial model the spec excludes; a cache row for V exists only when V had no embedded row at fetch time, so cache-vs-embedded conflict is a narrow post-upgrade window. Residue: a one-line "prefer newer generated_at" rule would be a harmless tidy-up.
- Manifest Embedded copy; Canary and publishing — Release builds embed the moving branch tip without pinning or recording a commit. Rejected 2-1 (ground CONFIRM Nit): reproducibility and provenance are not stated requirements; different snapshots stay inside the advisory-manifest bound. Residue: read the manifest SHA once in the version job and record it.
- The payload contract; Coordination with B6 ("parse-failure counter stays") — B6's "N hook payloads not understood" Health line still surfaces on routine upgrades. Rejected 2-1 (ground CONFIRM Should-fix citing `bd show ht-p03.23` line 18). Reproduce seat cites the same bead's line 55: the count "render[s] within" the Optimistic note, which the spec turns into the "new" state's silent Health, so the count is silenced with it. Residue: say outright that the counter is doctor-only.
- Evidence store (table keyed by (harness, version, contract_id)); states table — Undefined which version Health shows with several installs/PATHs, and no pruning. Rejected 3-0: state is a pure function per observed version; the new version has a fresh row after upgrade, so the old violation does not apply; attribution refuses ambiguous cases; table growth is one small row per version.
- Canary and publishing; Manifest Format (no platform field) — Manifest rows lack a platform dimension. Rejected 3-0: the contract is JSON field names/types with no stated OS dependence; local evidence and local violations override; the finding itself hedges ("if hook payloads ever differ by platform").
- Decisions 1; Evidence store — Verification by one lifecycle + one tool event leaves other shapes untested and a version can flip working → broken. Rejected 3-0: violation detection runs on every payload after verification (only the "payload ok" note stops); working → broken on an observed violation is the specified first derivation rule; Decision 1 is the user's choice.
- Canary and publishing ("known_broken with the failing event/field") — B6's report gives only free-text detail and a bisected range. Rejected 3-0: rows are per probed version, unprobed range versions stay "new"; parsing event/field from the report is writer implementation covered by its selftests; the Goal limits known_broken to contract violations.
- The payload contract (violation vs malformed) — Parsers return one undifferentiated ContextError::Invalid, so a new error taxonomy is required. Rejected 3-0: the contract-as-data declaration drives a separate validator that yields (event, field) and separates malformed JSON and unknown kinds without changing parser errors; the drift test keeps the two aligned.
- Evidence store ("same channel B6 uses for parse failures") — Lifecycle violations cannot ride a check-in. Rejected 3-0: the spec never says they ride a check-in; it reuses B6's separate parse-failure report channel; best-effort when the daemon is down is inherited and only delays a "broken" state.
- Evidence store; Coordination with B6 ("violations are a strict subset of what it counts") — B6's parse-failure channel counts only under Optimistic, so Listed/SchemaMatched violations have no transport. Rejected 2-1 (reproduce CONFIRM Should-fix). Refute and ground both cite ht-p03.23's transport line: the hook reports each failure to the daemon over its local-client connection, gated only by the `hook.parse_failure_report` capability; Optimistic scoping applies to logging/counting/rendering, not transport. The spec stores violations in its own table and derives "local violation → broken" for any admitted version. Residue: the "strict subset" sentence is imprecise.
- Decisions 2 vs 4; Fetch policy trigger (a) — Trigger (a) fires on nearly every routine upgrade, contradicting "update check only on failure". Rejected 3-0: Decision 2 is the release lookup on violation; trigger (a) is the evidence fetch explicitly authorized by Decisions 4 and 5 and the Goal ("or the published canary has, for a version never seen locally"), bounded to once per day per harness with opt-out. Residue: Decision 2's heading is loosely worded.
