## Confirmed findings            ← consumed by super-design, one task per finding
- [Should-fix] §2 D2 raw form; §4.4 errors; §7 failure table; D7 — The raw-form dual reading leaves undefined what happens when the whole-string local reading hits but the split remote reading cannot be evaluated (M known but unreachable, lacks the cap, times out or has no live Herdr): accepting the local hit is the silent local fallback D7 forbids, refusing breaks `user@host`-style labels that resolve locally today.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (voted CONFIRM at Nit) / ground ✓)
  evidence: spec D2 lines 79-86 cover only two cases: both readings hit (Ambiguous) and a suffix naming no known node (no reading). §4.4 and §7 define `unreachable`, cap-missing and timeout only for an address already treated as remote. D7: "Never a silent local fallback." §8 tests the `@` label only with no matching node. With a local pane `user@laptop` and a known-but-offline `laptop` node, either outcome contradicts a stated rule. D2's "both are resolved" also implies a remote round trip of up to 10 s for every raw `@` address whose suffix names a known node.
  fix-shape hint: add one rule to D2 (for example: local hit plus unevaluable remote reading resolves locally and prints a one-line warning naming the unevaluated machine, or is refused with the reason) and a §8 test for the known-but-unreachable suffix case.

- [Should-fix] §5.2 request id, Pending and "a re-run with the same intent resumes"; §4.2 AddrResolve "fresh per request"; AC6 — Remote-launch idempotency is keyed only on a caller-minted request id that is neither persisted on the caller nor derived from the intent, so "a re-run with the same intent resumes" has no mechanism and a re-run after Pending, a CLI crash or a caller daemon restart opens a second tab.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (voted REJECT, outvoted) / ground ✓)
  evidence: §5.2 makes `peer_requests.id` the only idempotency key ("a repeated id returns the recorded result or Pending ... so no double tab") and promises "a re-run with the same intent resumes". The spec defines no `--request R` flag, no caller-side persistence of R and no intent-derived id. §4.3 line 244 keeps pending requests in memory. The only "journal" mention (line 35) is replication, not the CLI intent journal (`src/cli/journal.rs`). AC6 and §8 cover only a repeated id after a dropped link within one process. The refute seat's point that the existing intent journal plausibly carries the id is not stated anywhere in the spec.
  fix-shape hint: state where R lives on the caller (journal it with the intent before sending LaunchRequest, or add `--request R`), and say whether identical deliberate launches are meant to collide.

- [Should-fix] §2 D4; §5.2 last bullet ("The caller then runs today's --existing delivery against the new seat"); §7 — A seat ID returned by M (phase-1 resolve, or the seat a phase-2 launch just created) may not yet be replicated to the caller's node, yet D4 and §5.2 run the follow-on send/handoff against the caller's own view at once with no wait, retry or failure row for "seat not yet replicated".
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: §1: remote seats exist locally only via journal replication (`seats.state='remote'`). AddrResolved and LaunchReply carry the seat ID over the new request/response path, separate from the journal. D4: the local daemon decides the command against its own view (A2). §5.1 `inspect()` accepts only `ContinuityStatus::Remote`, i.e. a row already present locally. §7 lists only "seat retired between resolve and use". A seat minted by `_peer-launch` moments earlier is exactly the not-yet-replicated case, so the headline launch-then-handoff flow can fail intermittently as unknown seat. No seat ran the two-node spike; the window is probably sub-second on a direct link.
  fix-shape hint: have the caller wait, bounded, for the seat row to appear locally before the follow-on delivery (or carry a journal position in the reply), and add a §7 row for it.

- [Should-fix] §4.3 step 3 (`REMOTE_RESOLVE_TIMEOUT = 10 s`); §5.2 (`REMOTE_LAUNCH_TIMEOUT = 120 s`); §4.4 timeout row; AC5 — The spec defines daemon-side waits of 10 s and 120 s but never states or raises the CLI-to-daemon call budget (today's cooperative budget is 5 s), so the client can time out first and the §4.4 error texts and AC5 cannot be observed as specified.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (voted REJECT, outvoted) / ground ✓)
  evidence: `src/cli/mod.rs:4289` `cooperative_budget` sets the deadline to now + 5000 ms and is used by `seat_resolution.rs:495` and the handoff paths. The spec's only "budget" is M's 3 s topology budget (line 248). It never names the CLI call budget for `RemoteResolve`, and for the 120 s launch wait it does not say whether the CLI holds one call or polls. If the 5 s budget is reused, the caller sees a generic client timeout instead of "did not answer in 10s; pass an exact seat ID".
  fix-shape hint: one sentence naming the per-call budgets (resolve > 10 s plus the 3 s topology read and overhead; launch either one long call or a poll loop) and their interaction with hook-time callers.

- [Should-fix] §5.2 `peer_requests(id PK, node_uuid, kind, state, result, created_at)`; "a repeated id returns the recorded result or Pending" — `peer_requests` has no recovery for a row left Pending when M's daemon or the `_peer-launch` child dies mid-launch (no lease, restart scan or tab adoption rule) and no retention or GC, so a crashed launch answers Pending forever and the table grows without bound.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: §5.2 lines 319-321 record the row "before acting"; the launch runs in a separate hidden child (line 323). The spec has no state transition for a dead child or a daemon restart, no lease or timeout on a row in progress, and no rule for a tab created before the result was recorded. §7 lists "link drops mid-request" (caller side) but not "executing node dies mid-launch". Because a re-run reuses the same id, a stuck row makes "a re-run with the same intent resumes" impossible, and getting a new id risks the double tab the table exists to prevent. `created_at` exists but nothing prunes rows.
  fix-shape hint: a startup scan that moves in-progress rows to failed (or re-runs them), a per-row deadline, an explicit rule for adopting or refusing an already-created tab, and a retention window.
