# 2.4.3 patch: five open beads

Status: implemented on `fix/ht-five-beads`. One commit or more per bead; each
subject names its bead. Behaviour changes (design-roasted): ht-xe3v, ht-hvyf.
The others are a log wording, a test budget seam and a gate portability fix.

## ht-xe3v: installer leaves an old daemon running

**Root cause.** Clients restart the daemon the moment it stops: blacky's
daemon.log at the 2.4.2 install shows the old daemon stopped at 23:47:42.65Z,
a daemon started 0.6 s later, stopped again at 43.83 (the post-swap stop) and
another started 30 ms after that, with seven mod channels registering at
once (the Claude mod restarts its `watch`, whose 2 s ensure is ht-dtx0 D1b).
Each such client ensures from `std::env::current_exe()`. The installer
checked for a daemon only at points (one pre-swap stop, one post-swap
`live_instances` snapshot, a version check at the end), so a start in flight
or launched between them survived: a start begun before the swap runs the old
image from `<prefix>/bin` (invisible to the snapshot until its endpoint is
published), and on Linux `current_exe` is `/proc/self/exe`, which follows the
rename to `<prefix>.old`, so a pre-swap client can start the old executable
after the swap. On macOS `current_exe` keeps the original path string, which
after the swap names the new executable; this narrows the window there and
fits the laptop's clean install, though one clean run proves little. The
installer output of the failing runs was not kept, so which window each
failure used is not established; the fix closes both.

**Fix (scripts/install.sh).**
- Keep `<prefix>.old` until daemon verification ends (removed by the EXIT
  trap), so the old executable can still stop an old daemon across a
  wire-protocol change.
- Verification checks every live instance for the installed version *and*
  for its executable (argv[0], symlinks resolved, equal to the installed
  executable). A stale daemon is stopped (retained old executable, else the
  installed one) and the installed executable ensured in its instance; then
  verification repeats, at most five checks (four replacements); a stop or
  ensure that a racing restart fails is followed by the next check. A stale
  daemon that cannot be stopped is never ensured over: after the fifth check
  the installer warns with its pid and the manual remedy and ends with the
  existing `running daemon does not match the installed executable` status,
  exit 3. Success after a replacement is claimed only for a daemon found
  running, and every instance a replacement's stop took down is ensured
  again. `<prefix>.old` is removed then too; `kill` is the remedy that works
  across a wire-protocol change.
- Accepted: a same-version daemon on a default state root started from
  another build (a dev checkout) is now replaced too, since the installer's
  outcome is the installed executable serving. A client can still restart the
  old executable between the last check and the removal of `<prefix>.old`
  (milliseconds); after that removal a pre-swap Linux client's `current_exe`
  names a deleted file and its start fails, so it cannot recur. The client
  side (ensure from the installed path rather than `current_exe`) is left
  unchanged: the installer is the only place that renames the executable.
- New operator-visible lines: `daemon in DIR runs from PATH; installed
  executable is PATH` (~45 bytes plus two paths), `could not stop the stale
  daemon[: ERR]` (30 bytes plus the error), `could not replace the stale
  daemon (pid P); stop it by hand: kill P, then herdr plugin action invoke
  ensure --plugin herdr-threads` (~115 bytes plus pids), `replaced the stale
  daemon; the installed executable runs` (56 bytes).

**Acceptance.**
- An upgrade where an old-executable client restarts the daemon after every
  stop before and after the swap ends with the installed executable serving
  (Python `installer_daemon_test.py`, fails on main).
- An old client that wins the race between the installer's stop and its
  ensure (the ensure meets a version mismatch) is replaced on the next check.
- A client that keeps restarting it makes the installer give up in bounded
  time with the existing incomplete status and the manual remedy.
- Shell harness: an old-executable client ensuring just before the installer's
  own ensure (the Herdr stub's ensure action) is replaced; the old package is
  gone after verification; every existing case still passes.

## ht-khs7: sync link log wording

**Root cause** (RCA in the bead): `up_for` is measured on the monotonic clock,
which on macOS excludes sleep, so a laptop logs 5 s links that spanned a
16-minute dark wake; and the dialer logs `dial failed, backing off` for a link
that came up and later ended.

**Fix.** `sync::link::up_for_text(monotonic, wall)` renders `N s`, plus
`(wall M s, host suspended ~S s)` when wall time ran ahead by >= 5 s (≈35 bytes
extra, only then). `sync: link down` uses it (wall from the coordinator's
`since`). The dialer logs `link ended after <up_for_text>, redialing: <why>`
for an attempt whose link was established (`dial failed, backing off` stays for
dials that never came up). Log text only: no wire change, timers keep the
monotonic clock.

**Acceptance.** Unit tests for both strings; sync lib and peer_stdio suites green.

## ht-gdy4: `golden_surfaces::doctor_reports` flakes under load

**Root cause.** Doctor shares one fixed 2 s observation budget
(`HEALTH_BUDGET_MS`) across its probes. Hermes profile inspection runs two
Python processes and doctor performs it three times; under CPU load the third
misses the deadline and reports `installed: unknown`. The test-child timeout
seam (`HT_TEST_TIMEOUT_SCALE`, `protocol::time::external_bound`) was not
applied to this budget. No fixture race.

**Fix.** `observation_budget` goes through `external_bound`: production keeps
2 s, a scaled test child gets the scaled bound. In-process tests that pin the
budget run without the variable.

**Acceptance.** 10 reruns pinned to one CPU at nice 19 beside two nice-19 busy
loops: before 2/10 fail, after 0/20. Doctor lib and combined tests green.

Follow-up (not in this patch): Hermes `doctor_projection` discards a status it
just computed, causing the third inspection.

## ht-hvyf: stray dial target `test-only`

**Root cause.** Herdr's own mosh test harness (`tests/mosh_harness.rs`,
`spawn_remote_client`) runs a real `herdr --remote test-only` client as this
user. The discovery process scan accepts any same-uid process whose argv[0]
base name is `herdr` with `--remote X`, whatever server or config it belongs
to, and `upsert_discovered` keeps a sighting forever. The row (created
2026-10-24 08:02 UTC, never linked) has been dialed 2000+ times since. No
herdr-threads test uses `test-only`.

**Fix.** A discovery pass whose process scan completed retires (deletes) every
enabled `herdr_remote_process` row that never linked (`learned_node_uuid` and
`last_linked_at` NULL) and whose destination is not among what the pass found.
It runs on the first scanned pass and whenever a remote client found by the
previous one is gone (a flapping machine list does not trigger it), so steady
passes write no more than before. A row mid-dial (`dialing`) is kept, since
its link may be up before the Dialer records it. Explicit,
`herdr_machine`, forgotten and once-linked rows are untouched; a later
sighting adds the row again. The Dialer's reload cancels the retired row's
task (and kills its dial child); a task whose row id SQLite reused for another
destination restarts.
- Accepted: a real remote whose `herdr --remote` client closes before its
  first link (typically one without herdr-threads installed) loses its row,
  including at the first pass after a daemon restart (the last pass's findings
  are kept in memory only); its next client adds it again. Process discovery
  thus means "while a client runs, until the first link". A scan that fails
  silently (an unreadable process table reads as empty) retires such rows
  once; the next good pass re-adds any that are running.
- The scan's acceptance of any same-uid `herdr --remote` process is left as
  is: a test harness's client is indistinguishable from a real one without
  heuristic attribution. Follow-up for Herdr: its mosh harness could avoid a
  resolvable-looking destination. Log line: `sync discovery: retired N never-linked
dial target(s) whose herdr --remote client is gone` (~85 bytes).

**Operator.** The supported way to drop a stale target already exists:
`herdr-threads human peer forget <dest>` (disables it; discovery never
re-enables a forgotten row, and retirement never deletes one, so a forgotten
row is also the durable way to suppress a destination). After the upgrade blacky's `test-only` row is
retired by the first discovery pass; `herdr-threads human peer forget
test-only` is the manual fallback.

**Acceptance.** Store test: only the never-linked, unseen process row goes;
the worker test: retirement on the first pass and on a vanished client, not
otherwise; the Dialer reloads after a retirement.

## ht-gin2: package lifecycle gate is macOS-only

**Root cause.** `scripts/validate-package.sh` pins the macOS aarch64 Herdr
0.9.1 digest, and the manifest pin test requires `herdr` on PATH to be 0.9.1;
a Linux release host has a newer Herdr on PATH.

**Fix.** Both read the host target's 0.9.1 digest from
`tests/herdr-releases.tsv` and take `herdr` on PATH when it is that binary,
else the release-smoke cache entry (`$HT_HERDR_RELEASE_CACHE` or
`~/.cache/herdr-threads/herdr-releases/0.9.1/<os>-<arch>/herdr`). The
validator puts the pinned binary first on the private PATH and makes its root
in the platform temp dir (`/private/tmp` on macOS for the socket path limit).

**Acceptance.** `manifest::installed_herdr_semantically_accepts_only_valid_disabled_package`
passes on blacky with no PATH override; release-qualify's package step passes
on blacky.
