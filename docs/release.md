## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request with Rust 1.99.1 and Python 3.11.9. The test jobs run on `ubuntu-24.04` (Linux x86_64); macOS arm64 runs the same suite locally before a merge (`scripts/full-suite-gate`). Both jobs download the [official Herdr v0.9.1 Linux x86_64 asset](https://github.com/herdrdev/herdr/releases/tag/v0.9.1) and check its architecture, `herdr --version` and SHA-256 `2a02fed16beb651ef006e1d43f048f652ca4dc58ad053cd2d44450563d5c54b7` (GitHub's asset digest), so the real-parser package tests run in the ordinary suite.

The `tests` job runs in three parallel shards. Each shard:

1. `cargo test --locked --all-targets --all-features --no-run` and `tests/service/check_failpoints_absent.sh --prebuild` (the ordinary and `test-support` incremental release builds the package suite compares, in their persistent `target/failpoints-release` and `target/failpoints-control` directories), before the timer.
2. `cargo nextest run --locked --all-targets --all-features --profile ci --partition slice:N/3` (one process per test; test groups in `.config/nextest.toml`; the three slices split the sorted test list round-robin, about a third of the test time each). `--all-features` enables `test-support`. The package suite runs `check_failpoints_absent.sh`, whose two incremental release builds are then no-ops. Ignored tests (the package lifecycle gate and the 10^5 to 10^6 scale tests) do not run. Each shard fails at 300 s wall clock.
3. `scripts/check-no-leaked-processes`, even after a failure.

The `deterministic` job:

1. `cargo fmt --all -- --check`.
2. `./scripts/build.sh`, then checks that every command in `herdr-plugin.toml` resolves to an executable file.
   Then `tests/release/install_test.sh bin/herdr-threads` drives `scripts/install.sh` offline against fake releases (stub Herdr, scratch HOME).
3. The Python fixture tests under `tests/native/` and `scripts/` with `unittest`, then the leak check.

`clippy` runs `-D warnings` with default and all features on both `macos-15` and `ubuntu-24.04`, so each platform's gated code is linted.

The `package-lifecycle` job runs the ignored package gate (`install::clean_package_install_lifecycle`) with the same pinned Herdr. It runs **only on manual dispatch** (`workflow_dispatch`) because it takes several minutes and starts private Herdr servers. It passed on GitHub at `e86e5840` (manual run 38326670628); that historical source does not qualify a later composed candidate (see [validation/package.md](validation/package.md)).

The macOS arm64 `herdr-releases` job runs `scripts/herdr-release-smoke` (**manual dispatch only**, like the package gate). The separate `linux-e2e` job runs the listed smoke releases and driver self-test on Linux x86_64 and aarch64 on every push and pull request; it does not run authenticated harnesses or the upstream inventory policy check. The macOS `herdr-releases` job first runs `--check-upstream`, which fails when GitHub lists an official (non-prerelease) Herdr release at or above 0.9.1 that `tests/herdr-releases.tsv` lacks, or whose asset digest differs; `scripts/herdr-release-smoke --update` rewrites the list from GitHub's asset digests, and the new row is committed with the run that proves it. It then downloads each listed release's macOS arm64 binary, checks its SHA-256 against the list and its `--version`, and runs the e2e smoke against it in a private Herdr server. The matrix goes to the job summary. Locally the same script caches binaries under `~/.cache/herdr-threads/herdr-releases` (override with `--cache` or `HT_HERDR_RELEASE_CACHE`) and ends with `scripts/check-no-leaked-processes`.

**Clippy is a required gate.** The `clippy` job runs `cargo clippy --locked --all-targets -- -D warnings` and `cargo clippy --locked --all-targets --all-features -- -D warnings`; a warning in either fails the workflow. Structural lints (`too_many_arguments`, `large_enum_variant`, `result_large_err`) are allowed only on individual items, each with a one-line justification; there are no crate-wide allows.

CI runs on GitHub; the source-bound current observations are recorded above. Required jobs still need final-candidate results: a functional failure blocks release, and a result limited by the local environment is recorded as such, never counted as a pass. The current-cut timing exception is explicit and does not turn a budget miss into a passing measurement.

Native model tests are not in CI. They need an isolated, authenticated Herdr environment and retain their own evidence.

## Release workflow

`.github/workflows/release.yml` publishes **only from a `v*` tag push**; a manual dispatch builds and uploads workflow artifacts and never creates a release. It checks that the tag equals `v` plus the `Cargo.toml` version and that `herdr-plugin.toml` has the same version, then builds with Rust 1.99.1 and `--locked`:

| Archive | Runner and target | Checked |
| --- | --- | --- |
| `herdr-threads-macos-aarch64.tar.gz` | `macos-15`, `aarch64-apple-darwin` | Mach-O arm64, `--version` |
| `herdr-threads-macos-x86_64.tar.gz` | `macos-15`, cross to `x86_64-apple-darwin` | Mach-O x86_64 only (not run) |
| `herdr-threads-linux-x86_64.tar.gz` | `ubuntu-24.04`, `x86_64-unknown-linux-musl` | static, `--version` |
| `herdr-threads-linux-aarch64.tar.gz` | `ubuntu-24.04-arm`, `aarch64-unknown-linux-musl` | static, `--version` |

Linux uses musl so one static executable runs on any distribution regardless of its glibc; each architecture builds on its own native runner, so no cross C toolchain is needed for the bundled SQLite (`musl-gcc` from `musl-tools`). `scripts/package-release.sh` writes each archive (manifest, `scripts/view.sh`, `scripts/build.sh`, `scripts/install.sh` (from 2.7.0, run by `herdr-threads update`), `bin/herdr-threads`, READMEs, `LICENSE-MIT`, `LICENSE-APACHE`, `THIRD_PARTY_LICENSES.html`, `VERSION`, `TARGET`, `PREBUILT`). The release job (tag push only) writes `SHA256SUMS`, then publishes idempotently: create a **draft** release with `gh release create --draft --verify-tag` unless one exists (a tag with a `-` is a prerelease), `gh release upload --clobber` the four archives and `SHA256SUMS`, download them again and verify with `sha256sum -c` and the expected asset count (five), and only then `gh release edit --draft=false`. A failed or re-run job therefore leaves a draft or converges, never a half-published release. `ci.yml` also carries a `build-targets` job that compiles all four targets on every push and pull request, so a Linux or Intel macOS build failure shows before a tag exists. The release workflow generates `THIRD_PARTY_LICENSES.html` for the normal dependency graph of the four release targets with a pinned `cargo-about` (`about.toml` lists the accepted licenses, `about.hbs` is the template; the file is not committed, so it cannot go stale). A new dependency with another license fails the build until it is added to `accepted`; to preview locally, run `cargo about generate --locked about.hbs -o THIRD_PARTY_LICENSES.html` (needs `cargo install cargo-about --locked --features cli`). `scripts/package-release.sh` refuses to run without that file (or `--third-party FILE`). `scripts/install.sh` consumes these assets ([install](install.md#installing-a-prebuilt-release)).

Linux archives are **experimental**: `herdr-plugin.toml` declares `platforms = ["macos", "linux"]` so the plugin can be linked from a Linux archive, and in an Ubuntu 24.04 arm64 container a locally built release linked into headless Herdr 0.9.3 and ran a healthy daemon ([evidence](evidence/linux-arm64-container/README.md)); x86_64 and harness sessions stay unverified, and a published-release download, upgrade, uninstall and Herdr-down await the clean-machine rehearsal in the follow-on checklist; the host incarnation witness covers Linux through `SO_PEERCRED` and procfs, and the deterministic suite passes there. The workflows pass `actionlint` locally and in CI. Four-target CI release builds, including both Linux architectures and Intel macOS, passed at `8e8e395e`; a release workflow for the final tag and its published archives are separate qualifications.

CI's dedicated `release-proof` job runs `manifest::failpoints_are_compiled_out_of_release_builds` once, including its Rust assertions for at least ten hooks, zero ordinary-release hook names and complete positive-control coverage. All four timed shards exclude that exact test and omit its duplicated prebuild; the local integrated full suite still includes it once. This removes four identical release-proof builds without moving a cold release build into a shard timer.

Rust dependency caches now cover test shards, clippy, target builds and the separate proof target directories. They preserve compiler/lockfile boundaries and prune workspace/incremental output; hosted before/after measurements and the artifact decision are in [CI lead-time evidence](validation/ci-release-lead-time.md).

## Integrated local qualification

Use `scripts/release-qualify --evidence-dir DIR` from a Herdr pane on the candidate SHA; see [RELEASE.md](../RELEASE.md). Its `--self-test` mode substitutes only authenticated wake and is not live wake evidence. The full suite runs alone; matrix and wake branches overlap only after it, with package lifecycle and installer checks afterward. Per-step logs, branch environment records, matrix/wake reports and a failure-aggregating `summary.json` are retained.

Ordinary CI keeps all existing required job names and five test shards for documentation-only changes confined to the explicit allowlist (`RELEASE.md`, `AGENTS.md`, `CLAUDE.md`, `docs/release.md`, `docs/superpowers/**`), but skips heavy steps through a changed-path detector. All other paths run heavy checks, including README, changelog, trust policy, integration Markdown, compatibility data and evidence. `docs/release.md` is read only by `tests/release/docs_test.sh`, which the changed-path job runs on every push. PRs compare the merge base to the PR head; pushes compare the previous SHA to HEAD. Manual dispatch, tag pushes, unknown bases and empty diffs run all checks. Detector failures or invalid/missing outputs fail the existing stable jobs; the existing actionlint check also carries the dedicated release-proof result so that a proof failure cannot disappear from required checks. Manual macOS package/matrix jobs remain available for diagnostics; local qualification supplies these release gates without a required manual CI dispatch.

CI currently retains no release binaries or archives: `build-targets` compiles all four targets but uploads none. Release builds also inject a moving harness-manifest branch input that CI does not embed, so equal source SHAs alone do not prove compatible build inputs. `release.yml` therefore continues building and packaging all four archives, preserving SHA256SUMS, VERSION, TARGET and archive verification. Reuse would require a shared build pipeline that retains compatible four-target artifacts and records the resolved manifest input, toolchain and source SHA before publication.

## Versioning

Every release number follows one rule (the user's standing decision, 2026-10-16, refined 2026-10-28):

- **Major:** backwards compatibility is broken, for example a new wire protocol version, a store that older versions cannot open, or removed or changed CLI behaviour that scripts rely on.
- **Minor:** only a new user-facing feature or a significant UX change, with nothing broken.
- **Patch:** bug fixes, and small changes to existing features, such as a new parameter or flag on an existing command.

A release takes the highest level among its changes. A schema migration alone does not force a major bump when the user decides it is a fix release (v1.2.1 adds schema 48 on protocol 8 as a patch). The p2p cross-node sync work (protocol 9 and a fresh node store) is breaking and ships as 2.0.0.

## Release checklist

1. **Provenance.** Record the reviewed source SHA, `Cargo.lock`, Rust, Herdr, Codex and Claude Code versions, host OS and architecture, and the locked build result. Inspect the archive: manifest, scripts, source and lockfile, built executable path and mode. No runtime state or credentials in it.
2. **CI.** The workflow is green on the release SHA (clippy included), and `scripts/release-qualify` passes locally on that SHA (including package lifecycle, upstream inventory, matrix and live wake). Start ordinary push/PR CI alongside local qualification; manual `ci.yml` dispatch is optional. Every official Herdr release at or above the README's floor (0.9.1) is in `tests/herdr-releases.tsv` and passes the release smoke; a failing release blocks the release or lowers the stated support.
3. **Package lifecycle.** The integrated driver evidence satisfies the isolated package gate on the release SHA ([validation/package.md](validation/package.md)); never against the shared Herdr server. Add the real GitHub install once the repository is public.
4. **Scoped setup and unsetup.** The setup CLI is merged, including the separate permission component (Claude allow/ask rules, the Codex rules file) and the legacy Codex sandbox allowance for the measured 0.159.2 and 0.159.3. Still to show on the release SHA: it leaves unrelated Codex and Claude configuration, hooks and permissions unchanged. `doctor` separates installed from observed.
5. **Codex version admission.** Fingerprint admission is merged. Keep its "schema-matched, live-unverified" status documented wherever it applies (0.159.2), and decide from evidence whether a version is promoted into a recipe.
6. **Native scenarios, for each harness.** Recorded so far in the [validation report](validation/report.md) (PASS_WITH_GAPS, at the run SHAs): prelaunch handoff (manual and managed, including a lost initial prompt), idle wake, active-turn boundary delivery, clear/resume/replacement, child reads with child ACK absent, blocked UI, burst continuation and required invitations. Still owed: two concurrent children (both harnesses), Codex TUI children, the live SW2 coalesced wake, daemon crash and host-event gap with a live model, restore/move identity with a live model, and a re-run of the required scenarios on the release SHA. Keep accepted message IDs, the actual model-issued ACK and accept calls, the SQLite receipt rows, duplicates, missing messages and notification overhead separately. A prompt, a hook output, or an agent's claim without the committed ACK is not a pass.
7. **Wake e2e (prerequisite).** The releasing agent runs `scripts/wake-e2e.py` against the release candidate locally and unattended, for every release (see AGENTS.md, "Pre-release wake e2e"): every case passes on both harnesses, or each failure is accepted by the user and recorded here. Keep its evidence directory. Run it once, against the newest release in `tests/herdr-releases.tsv`: from the local Herdr when that is the newest, otherwise through `scripts/wake-e2e-herdr <version>` (the same driver in a private server of that release); the release smoke covers the older listed releases.
7a. **Real-ssh two-node check (optional evidence).** With Docker, run `scripts/linux-e2e/run real-ssh` from a checkout of the release SHA (`scripts/linux-e2e/README.md`, "real-ssh"; `python3 scripts/linux-e2e/real-ssh-e2e.py --self-test` needs no Docker). It links two nodes over the default ssh transport and default remote command; exit 0 means every row passed and cleanup was verified. Pre-release only, never CI; record its outcome and keep the evidence directory. A FAIL is filed as a defect of the sync link, not waived by the wake e2e.
8. **Reconcile claims.** Done against report base `99ea74ca` (ht-4is.10.4): the README support table and this matrix match the [validation report](validation/report.md). Re-reconcile after the release-SHA re-run. Promoting a harness to `supported` in health needs a code change to the recipe profiles (model receipt, and Codex invocation transport), which this reconciliation did not make. Record the F6 restore-allocation dispute's outcome.
9. **Review and merge**, then the [post-merge follow-on checklist](#post-merge-follow-on-checklist), then the public steps below.

## Post-merge follow-on checklist

Done by a person after this work merges; nothing here has been done. Every step uses the real GitHub repository and the real Herdr, never the shared Herdr server of a development machine.

1. **First CI run on `main`.** Watch it: `build-targets` for all four targets, the test jobs, the Python suites and `actionlint`. Any Linux failure blocks tagging.
2. **Harness canary.** Add the `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` repository secrets if the canary's model tier is wanted. Trigger `harness-canary.yml` once by `workflow_dispatch` and confirm the report artifact. Keep the schedule alive: in a public repository GitHub disables scheduled workflows after 60 days without repository activity, and a disabled canary looks exactly like a quietly passing one. Check periodically with `gh workflow view harness-canary.yml` (state `active`, a scheduled run in the last few days) and re-enable with `gh workflow enable harness-canary.yml` when it is not. The pre-merge canary smoke could not exercise the configurations below, so run one `workflow_dispatch` of `harness-canary.yml` for each and record the result:
   - the ubuntu-24.04 (Linux x86_64) install layout and tier 0, `--harness both --versions latest --model-tier off`, when the pre-merge smoke had no `linux/amd64` container (recorded NOT_EXERCISED);
   - the scheduled job's own configuration on the real registry, `--versions since-verified --bisect`, whose candidates are the stable versions above `verified_max` minus the known-broken ranges;
   - the live issue filing step (configuration 3b in the smoke record: `scripts/canary/file_issues.py` with real `gh`), which the smoke only dry-ran.
3. **Tag.** Push the tag `v0.1.0`. Confirm the release workflow creates a draft, uploads all five assets, verifies the checksums and then publishes.
4. **Clean-machine rehearsal, macOS and Linux.** `curl | bash` install, upgrade from the tag's own artifact, and uninstall, each with Herdr up and with Herdr down. Confirm the final status lines and exit codes match the [installer contract](install.md#installer-contract-final-status-and-exit-codes).
5. **Linux link.** If Herdr refuses the Linux link, flip `platforms` back to `["macos"]` or file an upstream Herdr issue, and update the README and these docs accordingly.
6. **Parallel tests on CI.** The suite runs with no thread pin (no `--test-threads=1`) on both OSes: done for macOS locally (ht-zo4: 5 consecutive green unpinned runs; it now runs under cargo-nextest) and for Linux in a local Ubuntu 24.04 container; CI runs the suite on Linux in two parallel shards (nextest `ci` profile, 7 test threads). A failure is filed as a test-isolation bug against the merged suite.
