# Release evidence and checklist

The intended public home is `github.com/alepar/herdr-threads`, listed on [herdr.dev/plugins](https://herdr.dev/plugins/). **Nothing has been published.** Publishing, making the repository public and marketplace listing are follow-on steps that happen only after the implementation is reviewed and merged.

"Native" means a real Claude Code or Codex session in an owned pane of a real Herdr server, counted only when a transcript root call joins a SQLite receipt. ## Continuous integration

`.github/workflows/ci.yml` runs on every push and pull request on `macos-15` (arm64), with Rust 1.94.0 and Python 3.11.9. The `deterministic` job:

1. Downloads the [official Herdr v0.9.1 macOS arm64 asset](https://github.com/herdrdev/herdr/releases/tag/v0.9.1) and checks its architecture, `herdr --version`, and SHA-256 `5fc7a7e7adfaca56fa80aa89dcb025693357268dab8285b9ce2d08a2313c89de` (the same hash as the locally installed 0.9.1 used for development and by the package gate), so the real-parser package tests run in the ordinary suite.
2. Points `TMPDIR` at a short private directory, because tests bind Unix sockets and macOS limits socket paths to 104 bytes.
3. `cargo build --locked --all-targets --all-features`.
4. `cargo fmt --all -- --check`.
5. `./scripts/build.sh`, then checks that every command in `herdr-plugin.toml` resolves to an executable file.
   Then `tests/release/install_test.sh bin/herdr-threads` drives `scripts/install.sh` offline against fake releases (stub Herdr, scratch HOME).
6. `cargo test --locked --all-targets --all-features -- --test-threads=1` (serial). `--all-features` enables `test-support`, which `hook_entrypoint` requires. The package suite runs `check_failpoints_absent.sh`, which makes two extra release builds. Ignored tests (the package lifecycle gate and the 10^5 to 10^6 scale tests) do not run.
7. The Python fixture tests under `tests/native/` with `unittest`.

The `package-lifecycle` job runs the ignored package gate (`install::clean_package_install_lifecycle`) with the same pinned Herdr. It runs **only on manual dispatch** (`workflow_dispatch`) because it takes several minutes and starts private Herdr servers. It has never run on GitHub. It has passed only locally (see [validation/package.md](validation/package.md)).

**Clippy is a required gate.** The `clippy` job runs `cargo clippy --locked --all-targets -- -D warnings` and `cargo clippy --locked --all-targets --all-features -- -D warnings`; a warning in either fails the workflow. Structural lints (`too_many_arguments`, `large_enum_variant`, `result_large_err`) are allowed only on individual items, each with a one-line justification; there are no crate-wide allows.

This workflow has not yet run on GitHub. Its first real run is part of the release checklist. A red required job blocks release; a result limited by the local environment is recorded as such, never counted as a pass.

Native model tests are not in CI. They need an isolated, authenticated Herdr environment and retain their own evidence.

## Release workflow

`.github/workflows/release.yml` publishes **only from a `v*` tag push**; a manual dispatch builds and uploads workflow artifacts and never creates a release. It checks that the tag equals `v` plus the `Cargo.toml` version and that `herdr-plugin.toml` has the same version, then builds with Rust 1.94.0 and `--locked`:

| Archive | Runner and target | Checked |
| --- | --- | --- |
| `herdr-threads-macos-aarch64.tar.gz` | `macos-15`, `aarch64-apple-darwin` | Mach-O arm64, `--version` |
| `herdr-threads-macos-x86_64.tar.gz` | `macos-15`, cross to `x86_64-apple-darwin` | Mach-O x86_64 only (not run) |
| `herdr-threads-linux-x86_64.tar.gz` | `ubuntu-24.04`, `x86_64-unknown-linux-musl` | static, `--version` |
| `herdr-threads-linux-aarch64.tar.gz` | `ubuntu-24.04-arm`, `aarch64-unknown-linux-musl` | static, `--version` |

Linux uses musl so one static executable runs on any distribution regardless of its glibc; each architecture builds on its own native runner, so no cross C toolchain is needed for the bundled SQLite (`musl-gcc` from `musl-tools`). `scripts/package-release.sh` writes each archive (manifest, `scripts/view.sh`, `scripts/build.sh`, `bin/herdr-threads`, READMEs, `LICENSE-MIT`, `LICENSE-APACHE`, `THIRD_PARTY_LICENSES.html`, `VERSION`, `TARGET`, `PREBUILT`). The release job (tag push only) writes `SHA256SUMS`, then publishes idempotently: create a **draft** release with `gh release create --draft --verify-tag` unless one exists (a tag with a `-` is a prerelease), `gh release upload --clobber` the four archives and `SHA256SUMS`, download them again and verify with `sha256sum -c` and the expected asset count (five), and only then `gh release edit --draft=false`. A failed or re-run job therefore leaves a draft or converges, never a half-published release. `ci.yml` also carries a `build-targets` job that compiles all four targets on every push and pull request, so a Linux or Intel macOS build failure shows before a tag exists. The release workflow generates `THIRD_PARTY_LICENSES.html` for the normal dependency graph of the four release targets with a pinned `cargo-about` (`about.toml` lists the accepted licenses, `about.hbs` is the template; the file is not committed, so it cannot go stale). A new dependency with another license fails the build until it is added to `accepted`; to preview locally, run `cargo about generate --locked about.hbs -o THIRD_PARTY_LICENSES.html` (needs `cargo install cargo-about --locked --features cli`). `scripts/package-release.sh` refuses to run without that file (or `--third-party FILE`). `scripts/install.sh` consumes these assets ([install](install.md#installing-a-prebuilt-release)).

Linux archives are **experimental and unverified**: `herdr-plugin.toml` declares `platforms = ["macos", "linux"]` so the plugin can be linked from a Linux archive, but whether the real Herdr accepts that link, and how the daemon behaves, is unverified until the clean-machine rehearsal in the follow-on checklist; the host incarnation witness is macOS-only, so expect a degraded daemon at best. The workflows pass `actionlint` locally; they have not run on GitHub, and the Linux and Intel macOS builds have not been compiled there yet.

## Release checklist

1. **Provenance.** Record the reviewed source SHA, `Cargo.lock`, Rust, Herdr, Codex and Claude Code versions, host OS and architecture, and the locked build result. Inspect the archive: manifest, scripts, source and lockfile, built executable path and mode. No runtime state or credentials in it.
2. **CI.** The workflow is green on the release SHA (clippy included), and the manually dispatched `package-lifecycle` job green on that SHA.
3. **Package lifecycle.** Re-run the isolated package gate on the release SHA ([validation/package.md](validation/package.md)); never against the shared Herdr server. Add the real GitHub install once the repository is public.
4. **Scoped setup and unsetup.** The setup CLI is merged, including the owned Claude allow rule `Bash(herdr-threads *)` and the Codex sandbox allowance for the measured 0.159.2 and 0.159.3. Still to show on the release SHA: it leaves unrelated Codex and Claude configuration, hooks and permissions unchanged. `doctor` separates installed from observed.
5. **Codex version admission.** Fingerprint admission is merged. Keep its "schema-matched, live-unverified" status documented wherever it applies (0.159.2), and decide from evidence whether a version is promoted into a recipe.
6. **Native scenarios, for each harness.** Recorded so far in the [validation report](validation/report.md) (PASS_WITH_GAPS, at the run SHAs): prelaunch handoff (manual and managed, including a lost initial prompt), idle wake, active-turn boundary delivery, clear/resume/replacement, child reads with child ACK absent, blocked UI, burst continuation and required invitations. Still owed: two concurrent children (both harnesses), Codex TUI children, the live SW2 coalesced wake, daemon crash and host-event gap with a live model, restore/move identity with a live model, and a re-run of the required scenarios on the release SHA. Keep accepted message IDs, the actual model-issued ACK and accept calls, the SQLite receipt rows, duplicates, missing messages and notification overhead separately. A prompt, a hook output, or an agent's claim without the committed ACK is not a pass.
7. **Reconcile claims.** Done against report base `99ea74ca` (ht-4is.10.4): the README support table and this matrix match the [validation report](validation/report.md). Re-reconcile after the release-SHA re-run. Promoting a harness to `supported` in health needs a code change to the recipe profiles (model receipt, and Codex invocation transport), which this reconciliation did not make. Record the F6 restore-allocation dispute's outcome.
8. **Review and merge**, then the [post-merge follow-on checklist](#post-merge-follow-on-checklist), then the public steps below.

## Post-merge follow-on checklist

Done by a person after this work merges; nothing here has been done. Every step uses the real GitHub repository and the real Herdr, never the shared Herdr server of a development machine.

1. **First CI run on `main`.** Watch it: `build-targets` for all four targets, the test jobs, the Python suites and `actionlint`. Any Linux failure blocks tagging.
2. **Harness canary.** Add the `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` repository secrets if the canary's model tier is wanted. Trigger `harness-canary.yml` once by `workflow_dispatch` and confirm the report artifact. Keep the schedule alive: in a public repository GitHub disables scheduled workflows after 60 days without repository activity, and a disabled canary looks exactly like a quietly passing one. Check periodically with `gh workflow view harness-canary.yml` (state `active`, a scheduled run in the last few days) and re-enable with `gh workflow enable harness-canary.yml` when it is not. The pre-merge canary smoke could not exercise the configurations below, so run one `workflow_dispatch` of `harness-canary.yml` for each and record the result:
   - the ubuntu-24.04 (Linux x86_64) install layout and tier 0, `--harness both --versions latest --model-tier off`, when the pre-merge smoke had no `linux/amd64` container (recorded NOT_EXERCISED);
   - the scheduled job's own configuration on the real registry, `--versions since-verified --bisect`, whose candidates are the stable versions above `verified_max` minus the known-broken ranges;
   - the live issue filing step (configuration 3b in the smoke record: `scripts/canary/file_issues.py` with real `gh`), which the smoke only dry-ran.
3. **Tag.** Push the tag `v0.1.0`. Confirm the release workflow creates a draft, uploads all five assets, verifies the checksums and then publishes.
4. **Clean-machine rehearsal, macOS and Linux.** `curl | bash` install, upgrade from the tag's own artifact, and uninstall, each with Herdr up and with Herdr down. Confirm the final status lines and exit codes match the [installer contract](install.md#installer-contract-final-status-and-exit-codes).
5. **Linux link.** If Herdr refuses the Linux link, flip `platforms` back to `["macos"]` or file an upstream Herdr issue, and update the README and these docs accordingly.
6. **Parallel tests on CI.** Confirm `cargo test --locked --all-targets --all-features` passes with no `--test-threads` pin on CI's two OSes (macOS and Linux). A failure is filed as a test-isolation bug against the merged suite.
