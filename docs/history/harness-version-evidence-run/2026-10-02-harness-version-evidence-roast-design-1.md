  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: Spec lines 111-113: "a daemon uses only rows whose contract_id equals its own and treats the rest as no data".   verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)

- [Should-fix] Evidence store and recording > Attribution steps 1-2 ("walk the hook's ancestors"; "run `<exe> --version` once per (canonical path, inode, mtime) and cache it"); "Recording is cheap and bounded" — The spec does not say whether the hook or daemon runs the ancestor walk and `--version`, where the cache persists across short-lived hook processes, or what latency/safety bound a cold `--version` exec has on the synchronous hook path.
  verdict: confirmed (reproduce ✓ / refute ✗-survived (dissent: REJECT) / ground ✓)
  evidence: Spec lines 75-97. Only the hook (or a daemon handed its pid) can walk the hook's ancestors; hooks are one process per event. The only cache the spec locates is the manifest cache (lines 106, 123). "Cheap and bounded" covers only the once-per-session "payload ok" note; violations must be attributed on every payload since one can arrive after verification, so the walk and a possible cold `--version` sit on the PreToolUse path with no timeout or fail-open rule.   fix-shape hint: Name the owner and store (hook resolves exe path + pid, daemon holds the (path, inode, mtime)→version cache in its state), bound the exec with a short timeout that fails to "record nothing", and say the hook never blocks on it.

- [Should-fix] The payload contract ("A violation is a well-formed JSON object for a known event kind ... unknown event kinds ... are not violations") — The event kind comes from the payload's own discriminator, so a harness change that renames or drops `hook_event_name` (or its values) is classified unknown/malformed, never a violation, and the most total contract break leaves the version silently "new".
  verdict: confirmed (reproduce ✓ / refute ✗-survived (dissent: REJECT) / ground ✓)
  evidence: Spec lines 69-71. src/harness/claude.rs:227 and src/harness/codex.rs:1001, :1125 read `hook_event_name` from the payload and fail when absent (claude.rs returns ContextError::Invalid). With the discriminator gone, no violation and no lifecycle/tool ok is recorded, state falls to "new" (Health silent), and the canary writes no known_broken row because only payload-contract violations may. The refute seat reads a missing discriminator as a missing required field; the confirming seats note the definition requires the kind to be known before a required field can be judged missing, and the spec never derives the kind from hook registration.
  fix-shape hint: Treat a missing/non-string discriminator on any registered hook as a violation of every event, or have the hook classify against the event it was registered for.

- [Should-fix] Manifest > Fetch policy ("Opt-out: `harness_manifest = \"off\"` ... in the instance settings file the daemon already reads ... both are read at each fetch decision (no restart needed)") — The opt-out assumes an instance settings file the daemon re-reads at each fetch decision; the existing file is JSON, loaded once (restart applies edits), rejects unknown keys, and the spec's example is TOML syntax.
  verdict: confirmed (reproduce ✓ / refute ✗-survived / ground ✓)
  evidence: src/service/config.rs:89 reads `<instance_dir>/settings.json` (JSON, 4096-byte cap, O_NOFOLLOW, mode checks). config.rs:22-23: `#[serde(default, deny_unknown_fields)] struct SettingsFile` with three fields, so an older binary fails to load a file containing `harness_manifest`. config.rs:56-57 doc comment: "A restart applies edits; the running owner keeps its validated in-memory values."   fix-shape hint: Say the key is JSON, that a new hardened per-decision re-read (or restart semantics) is added, and how an older binary treats the unknown key; or move the opt-out to the env var plus restart.

## Rejected (with reason)
- Background / User-visible states "new" / Canary Tier 0 — A hook registration or delivery break produces no payloads, so the version stays silently "new". Rejected 3-0 (previouslyRejected, re-surfaced): the Goal promises "broken" only on an observed payload-contract violation; "new" is honest ("not yet seen working") and Tier 0 outcomes are deliberately issue-only; a liveness/no-check-in detector is a new feature outside this spec.
- Trust / Fetch policy trigger (a) / Embedded copy — False manifest known_broken for a never-seen version deadlocks. Rejected 3-0: "broken" is a Health/doctor rendering, not a gate; hooks keep running and recording, and "local verified → working" overrides the row on first use. A TTL on cached negative rows is a hardening nicety.
- Evidence store ("A violation sticks ...") — No clear command/threshold for a false-positive violation. Rejected 3-0: stickiness is a stated decision and test case; the contract is derived from what parsers require with a drift test; the broken line carries upgrade/pin/report actions.

Rejected 2-1 (ground: Nit): implementation detail; an idempotent daemon-side set of tool_ok_at or a marker file satisfies the best-effort rule.
- Decision 2 vs states table — Decision 2 says degraded only if no supporting release exists; table degrades every broken. Rejected 2-1 (ground: Nit): the table, action ladder, state function and test (line 184, "degraded with the 'upgrade to X' action") agree; Decision 2 is loose shorthand. Worth a one-line reword.
- Attribution step 1 ("a `claude`/`codex` native binary") — No recognition rule for Claude native installs whose resolved exe is `versions/<v>`. Rejected 2-1 (ground: Nit): recognition is left to the mandated spike; a miss fails safe with "version evidence unavailable: <reason>" and a listed test. - Decision 6 / Fetch policy — Repo is not publicly reachable (404, no remote) so every fetch fails silently. Rejected 3-0 (previouslyRejected, re-surfaced): a 404 on an unpublished pre-release repo is a deployment precondition for the whole epic (canary, releases, issues), not a design gap; silent fallback to cache/embedded is the stated contract and doctor prints the fetch time.

- Manifest > Rows are per contract / Retention — Clients on older releases get no manifest data for new harness versions. Rejected 2-1 (ground: Nit; previouslyRejected, re-surfaced): each harness has exactly one InputSchema variant today (claude.rs:216 Hooks2_1_283, codex.rs:985 HooksV1); a second variant is by definition a contract change and the drift test forces a decision then.
