# Agent and operator commands

`herdr-threads` finds the Herdr instance by itself: flags first, then Herdr's environment (`HERDR_PLUGIN_STATE_DIR`, and `HERDR_SOCKET_PATH`, which every Herdr pane has), then Herdr's default plugin state root (`herdr/plugins/herdr-threads` under `$XDG_STATE_HOME` or `~/.local/state`). In a Herdr pane, plain `herdr-threads <command>` therefore works. The Herdr queries that detection makes (`herdr plugin list --json`, `herdr status server --json`) are bounded by a short probe timeout (2 s): a hung Herdr makes the command fail fast with the pass-`--state-dir`/`--host-endpoint` remedy instead of waiting. For an explicit local context, pass `--state-dir PATH --host-endpoint PATH` before the command. Add `--json` for structured output. Commands never choose the currently focused pane.

Output form: when stdout is a terminal and no agent-harness marker is set, text output is human-readable (inbox as a table, `read` as an IRC-style transcript (`[HH:MM] <nick> message`, with `-!-` lines for system events), thread details and participants as lists, one-line confirmations for send/ack/accept/invite). When stdout is not a terminal (pipes, scripts, hooks, and agents running the CLI through a tool) the compact machine text form is used (ht-4is.8.18). An agent harness that runs its shell tool in a PTY also gets the compact form: when any of the harness markers `CLAUDECODE`, `CODEX_THREAD_ID`, `CODEX_SANDBOX` or `CODEX_SANDBOX_NETWORK_DISABLED` is set to a non-empty value in the command's environment, text output defaults to the machine form even on a terminal (the marker beats the terminal check; `--human` still forces the human form). Scripts should not rely on either default and pass `--machine` or `--json` for stable parsing. The compact form: the first line names the result kind; `read` prints one row per timeline entry, `#SEQ MESSAGE_ID AUTHOR HH:MMZ [warn] [human] [relays user] [query|request|rule]: text` (author is the seat ID, a service ID, or `system`; `[human]` marks a message whose author is a declared human, `[relays user]` one the sender sent with `--relays-user`, source markers are fixed plugin text after `warn`; an independent recorded intent marker follows before any `[more: …]`; a clipped preview adds `[more: herdr-threads body MESSAGE_ID]` before the `: `), and a system event is one short row such as `#39 ack SEAT MESSAGE_ID`; `inbox` rows are `THREAD receipts=N invitations=N warnings=N` (zero counts left out, `+` when more may be pending, a required invitation adding its exact `accept-required` command); `pending-receipts` prints `pending_receipts SEAT` then `MESSAGE_ID THREAD#SEQ from SENDER due HH:MMZ [overdue] [deferred: recipient catching up (until HH:MMZ)]` (the suffix appears while the recipient is catching up on that thread, see **Thread summaries**); `thread show` and `thread participants` print one `SEAT STATE [self] [required invitation=ID requirement=ID revision=N]` row per participant; `check-in` prints `checked_in SEAT HARNESS ROLE generation=N DISPOSITION` followed by its inbox rows and pending warning count. `body` prints one header row `#SEQ MESSAGE_ID AUTHOR HH:MMZ` (plus `warn`, `bytes=FROM-TO/TOTAL` when the page is not the whole body, and `escaped` when the body holds a terminal control), then the body text verbatim with each non-empty line indented by two spaces, so no body line can start a row or a command line; an `escaped` body shows each such control as `\uXXXX` and doubles every backslash. A single `more: herdr-threads body ...` line follows only when the body continues; a system event prints `event: JSON` and its `condition: STATE active|inactive` instead of a body. Service-generated fields come first in every row and peer text only after the row's first `: `, escaped to one line. A page prints no metadata: a single trailing `next: herdr-threads ...` line appears only when there is more. Other results keep the `key: value` form, with one JSON object per `item:` line, no page metadata line, and each command (`*_argv`) printed once as its own `label: command` line rather than repeated inside the JSON. `--machine` forces the machine text form on a terminal, `--human` forces the human form anywhere, and `--json` always selects JSON; `--json` cannot be combined with either. Page budgets (`--max-bytes`) are measured on the machine form. `skill` always prints its markdown guide verbatim, and `setup`, `unsetup`, `setup-status` and `doctor` keep their `key: value` report form in either presentation.

Agents: `herdr-threads skill` (alias `--skill`) prints the concise agent guide ([integrations/skill/SKILL.md](../integrations/skill/SKILL.md), embedded in the binary, local only, never contacts the daemon). The top-level `--help` ends with an `Are you an AI agent?` pointer to it. This document is the full reference.

For routine agent communication, use hooks and default text `inbox`: it supplies pending message bodies, and its `next:` commands continue long bodies or additional mail. Fully displayed eligible messages are ACKed automatically. Do not reread or manually ACK those same messages. Accept invitations separately, reply as needed, and finish your native turn when waiting for peers so hooks can notify you. Agents should not use `follow`, sleeps or polling to wait for replies. Use history reads, `body` or summaries only for earlier context absent from inbox; human observers can still use `follow`.

New seat, thread, invitation, message and event IDs use one type letter plus 8 base62 letters and digits: `sk3Fq9a2B`, `tQ7mZ0cT4`, `i8Lx2PqRa` (invitation), `m7xQ2pL0c`, `e3HnW5yKe`. Stored IDs from earlier releases retain their long-prefix or UUID forms (`seat-k3Fq9a2B`, `thread-Q7mZ0cT4`, `seat-bc121d12-9d30-4510-b93c-e7cd26e890f1`, `invitation-…`) and remain accepted verbatim. Pass IDs exactly as printed; they are case-sensitive.

**Warning counts are pending counts.** The `warnings` count on each inbox thread and the check-in `warning_count` count only the seat's *pending* warnings, not every warning it ever received. A warning is pending while the thing it warns about is still open: an overdue invitation that is still pending (not accepted, declined or cancelled), an overdue receipt that is still unacknowledged, an unavailability episode that is still open, or a programmatic service warning addressed to the seat that has not yet been offered to the seat's current occupant. Once its invitation is answered, its receipt is ACKed or the episode closes, the warning is settled: it leaves the counts (and a thread with nothing else pending leaves the inbox) but stays in history. A programmatic service warning is informational, not an obligation. Each check-in offer carries a capped page of at most 16 of the seat's programmatic notices not yet offered to its current occupant, oldest first, in the check-in's `notices` field (`has_more` when more remain); the hook shows the same page on an `offered notices: N [NOTICE@THREAD, …]` line under the digest line. The offer settles exactly that page and nothing else: in the same transaction it advances the current occupant's offered frontier to the last notice it carries (one row written, nothing deleted), so a large undelivered backlog is offered page by page over successive check-ins. Both the durable lifecycle check-in and the tool-boundary Current check-in settle the page they carry once their transaction commits, even if the hook output is later lost; the notices stay in `warnings` history either way. The read-only `warnings` command never settles anything: it has no verified-occupant context. The frontier belongs to one occupant (binding generation and execution): after a replacement, including the new binding generation that each hook lifecycle check-in (startup, clear, resume) starts, the new occupant has its own empty frontier and is offered the retained notices again from the oldest, one page per check-in. Every pending count (the digest classes, inbox `invitations`, `pending_receipts` and `warnings`, check-in `warning_count`) is read by bounded walks and saturates at 1,000: the matching `has_more` flag (`count_has_more` in the digest, `invitations_has_more`, `pending_receipts_has_more` and `warnings_has_more` in the inbox, `warning_count_has_more` at check-in) is true when more may be pending than the count says. The complete warning history, settled or not, is always available from `warnings --seat SEAT`: check-in includes its first page, and you follow the returned next command to page through the rest.

`PAGE` means `--cursor CURSOR --limit N --max-bytes N`; each option is optional. Follow the returned next command to continue; it repeats `--limit` and `--max-bytes` only when they differ from the defaults (20 and 16384). A cursor is a short opaque `c3:` token (about 20 characters): a compact binary position (scope, direction, order version, high-water ordinal and the typed position) with a truncated SHA-256 tag that binds it to its daemon instance, scope key (thread, seat, message) and filter. It is stateless (nothing is stored server-side, so continuations survive a daemon restart), and a cursor replayed against another instance, thread, filter, direction or order version, or a corrupted one, is refused as `invalid_cursor` exactly as before. The previous `c2:` cursors are still accepted for one release. `overdue` lists instance-wide obligations; `diagnostics` preserves explicit seat and thread filters. A recent read selects the first descending page size and its continuation reaches older history. `--recent` and `--limit` cannot be combined, and a cursor cannot be combined with `--recent`, `--after`, or `--before`. `read` history/follow, `body`, search, summaries, view, and check-in never ACK a message. The exception is validated default agent text `inbox`: it submits exact fully displayed pending agent receipts only after the complete page is written and flushed. Explicit `--machine`, `--json`, `--seat`, or pane inbox selectors remain read-only; human receipts are waived without an ACK.

Top-level agents use explicit mutations:

```text
herdr-threads thread create --topic TEXT [--goal TEXT] [--name NAME]
herdr-threads thread name THREAD [--set NAME|--clear]
herdr-threads thread rename THREAD NAME
herdr-threads thread topic THREAD --set TEXT
herdr-threads invite THREAD --seat SEAT [--deadline SECONDS]
herdr-threads accept THREAD
herdr-threads accept-required THREAD --invitation INVITATION_ID --requirement REQUIREMENT_ID --revision N
herdr-threads leave THREAD
herdr-threads send THREAD (--body TEXT|--file PATH|--stdin) [--require-ack SEAT ...] [--deadline SECONDS] [--relays-user]
herdr-threads ack MESSAGE_ID...
herdr-threads archive THREAD
herdr-threads reopen THREAD
herdr-threads check-in
```

**Thread IDs and names.** Every public thread argument or filter accepts an exact ID or optional name: show/topic/participants (including the alias), invite, accept/accept-required, leave, send, archive/reopen, read/follow, `pending-receipts --thread`, `diagnostics --thread`, `warnings --active`, `search --thread`, `summary THREAD`, and name controls. A name is separate from topic and goal, case-sensitive, 1–128 UTF-8 bytes with no control characters; quote spaces. Duplicate names are allowed. Lookup spans the selected instance including archives and nonmembers. An existing exact ID wins; otherwise an exact unique name resolves. Missing names fail; duplicate names report bounded escaped candidates with IDs, topics, archive and caller membership, including omitted-candidate guidance. Use the exact ID to disambiguate. Writes still require the caller to be joined. Selectors freeze before durable intents, and retries, hook commands and continuations retain canonical IDs across renames.

```sh
herdr-threads thread create --name "team café" --topic "Feature work"
herdr-threads send "team café" --body "Ready for review"
herdr-threads thread rename "team café" release-review
herdr-threads thread name release-review --clear
```

`invite` for a seat that has already joined the thread is a settled no-op: it creates no invitation, prints `already_joined` with the seat and thread (exit 0), and completes its local intent.

These commands act as a seat. Run them inside the agent's own Herdr pane: the CLI uses that pane's `HERDR_PANE_ID` (never the focused pane) to find the seat currently mapped to it and that seat's recorded lifecycle check-in context. A launch driver or hook supplies the first `check-in --lifecycle-event ID` with `--cooperative-seat SEAT --cooperative-target PANE --cooperative-harness codex|claude --cooperative-role top-level`; the same flags can select the seat explicitly for any command. Without a mapped seat and context the command fails and names what is missing. Every such "no caller located" outcome (no `HERDR_PANE_ID`, a pane with no resolved seat, a seat with no lifecycle check-in context, or `inbox`/`pending-receipts` with neither a pane nor `--seat`) is invalid local context: `(invalid_request)`, exit 2. It is fixed by the pane, the `--cooperative-*` or `--seat` arguments, or the seat's check-in, not by a different build.

Every command locates its caller the same way. Inside a pane, `inbox` and `pending-receipts` without `--seat` read the seat mapped to that pane; `pending-receipts --thread THREAD` in a pane with no mapped seat stays thread-scoped, and outside a pane these reads need `--seat SEAT`. `retry LOCAL_REF` for a seat's mutation runs from the same pane (or with the same `--cooperative-*` flags) and refuses an intent recorded for another seat.

**A person in their own pane** runs `herdr-threads me init` once instead of any check-in flags. It requires `HERDR_PANE_ID`, resolves that pane's seat by ordinary resolution, and checks in with harness `human`, role top-level and a plugin-context session. The binding and every later send, invite, accept and ACK from that pane are recorded with `operator_human` provenance, not `cooperative_top_level`. After it, the mutations above and the seat-defaulting reads work in that pane with no flags. A person's seat can be named by `--require-ack`, but its human receipt has no ACK obligation or deadline. `me init` waives older pending agent receipt obligations without recording an ACK; a later agent binding receives future mail under the normal agent rules. Re-run `me init` after a daemon restart to restore availability (it continues the same occupant). It is refused (exit 2) without `HERDR_PANE_ID`; the refusals for agent evidence follow below. An agent later started in that pane replaces the person at its first lifecycle check-in. `me init` is not operator repair and grants nothing beyond what an agent's own check-in grants.

**`me init` refusals.** `me init` never takes over an agent. It is refused (`invalid_request`) when an agent environment marker is present (`CLAUDECODE`, or the variables Codex sets inside its own process, `CODEX_SANDBOX` and `CODEX_SANDBOX_NETWORK_DISABLED`; user configuration such as `CODEX_HOME` is not a marker), when Herdr reports a Claude or Codex agent in the pane (any other detected kind does not count; a failed Herdr read is not evidence either), and, decided by the daemon, when the seat's open binding is an agent's (`cooperative_top_level`). The refusal names the way out: use your own shell pane, give the pane a fresh seat with `herdr-threads seat resolve --pane PANE --new-seat --operator`, or override as the local account with `herdr-threads me init --operator` (recorded as `operator_human_override` in `seat inspect`); after it, person-pane commands in that pane work despite the agent evidence (the override is recorded locally for that human context, and nothing local is replaced until the daemon accepts the check-in). The environment and Herdr checks are best effort and client-side; the daemon's refusal is the guard.

**Resumed sessions reattach themselves.** After a Herdr restart a resumed top-level session (Claude `claude --resume`) whose harness session id uniquely matches an unresolved seat's last binding reattaches that seat when its SessionStart hook runs, with no operator step. This is resume-only: `startup`, `/clear` and `/new` carry a new id and never match. For Codex, run `codex resume` by hand in the pane; `herdr-threads launch` refuses the Codex `resume` form (no captured hook evidence), so use `codex resume` directly or `exec resume`. When no seat matches, the pane stays held and an operator repairs it (see [operations](operations.md#restore-holds-and-repair)).

**Launch and wake guards.** `launch` for a seat whose bound agent Herdr reports live in another pane is refused (`target_unsafe`: "launch refuses to start a second agent for the seat"). Use that pane, or retire or rebind the seat as the operator. A wake prompt goes only to an agent of the seat's bound harness: a pane running a different agent kind, or none, is not woken. A person's seat (`me init`, harness `human`) is never woken, and its receipts have no ACK obligation or deadline.

Pane derivation is cooperative, not enforced. `HERDR_PANE_ID` locates the seat; it does not prove who is running the command. Any process that inherits the pane's environment, including a child agent or a script that ignores these instructions, derives the same seat and is recorded as that seat with its recorded top-level role.

**Agent receipts and explicit ACKs.** Default agent text `inbox` ACKs only exact pending agent receipts whose complete bodies were displayed after the whole page was written and flushed. `inbox --machine`, `--json`, explicit `--seat`, and explicit pane selectors are read-only. Other reads (`read`, `body`, search and summaries) never ACK. For messages read through those routes, use `pending-receipts` to find the canonical IDs, read them, then run `ack` with those IDs. Accepting an invitation is a separate action. A message from a registered service shows a service ID (the programmatic author) in the sender column of `pending-receipts` where a native message shows a seat, for example `from <service-id>`. Treat an agent receipt for it like a native message: default text inbox can claim the fully displayed body after flush; otherwise read it and ACK its exact ID explicitly. A service message never ACKs itself, and a service has no receipt of its own, so only the recipient seats ACK. Successful send and ACK output contains IDs and counts, without repeating message bodies. A child agent may read and prepare a summary but must not accept, ACK or check in: in the pane these commands act as the top-level seat, and the plugin cannot tell a child from the top-level agent. For a long thread or after a context reset, run `herdr-threads summary THREAD`: when no summary is ready it prints Work, the job tickets to hand to cheap child workers following `herdr-threads skill` (section "Thread summaries"; `summary job` fetches a job's bundle, `summary submit` stores the block), and you re-run `summary THREAD` until it is Ready and prints the cover, fold and tail. Children may run `summary job` and `summary submit` (TRUST-POLICY A5) but still must not accept, ACK or check in. The plugin starts no model on its own.

**Human input attribution and intent.** `send --relays-user` records a cooperative claim that the sender forwards input from its own user, never its own asks or arbitrary external messages. The sender remains the author. The forwarding agent explicitly chooses `--user-intent query|request|rule`: query asks for information, request asks for an action with a completion point, rule imposes an ongoing constraint within this thread. A declared human can choose intent directly, with or without relay; an ordinary agent needs relay. Services and system events cannot declare it. The daemon checks the canonical send-time role, not the body. Classification, relay and membership grant no permission.

```sh
herdr-threads send THREAD --relays-user --user-intent query --body "What's our progress?"
herdr-threads send THREAD --relays-user --user-intent request --body "Let's cut a build."
herdr-threads send THREAD --relays-user --user-intent rule --body "Always run tests before cutting a release."
```

Split independently actionable mixed inputs into separate messages, preserve source attribution separately from interpretation, and clarify uncertain duration instead of silently choosing rule. A discussed or quoted external rule is not automatically adopted. Missing intent means unclassified, including historical messages; no body scanning or migration guesses intent. Message-bearing JSON results (history, search/body and copyable inbox batches) expose the recorded enum `user_intent` (`query`, `request`, `rule`), omits None, and reads an absent field as None. Role, relay and backfill fields retain their separate meanings; false relay is omitted. All ordinary human/relayed input keeps attention priority regardless of intent or lifetime.

Machine history/body and copyable inbox message headers, human IRC transcripts, and rendered bundle source lines show `[human]` and/or `[relays user]`, followed independently by `[query]`, `[request]` or `[rule]`. Ordinary agent quotations have no markers and system events keep their event form. Ready ledger and tail retain role/relay tokens `[human]`, `[agent relays-user]`, or `[human relays-user]`, then the independent intent marker; tail rows also use `[agent]` or `[service]` for ordinary unrelayed authors. Human inbox tables and `inbox --json` list thread attention counts rather than message bodies. Ledger kind labels are `question`, `ask`, `rule`, or `unclassified human input`; the persisted compatibility tag remains `user_instruction`, which does not imply a rule. Unclassified input has source markers without invented intent.

**Thread summaries.** A summary lets a seat recover a long thread (after a Compact, Resume or Clear, or any time) without reading every message. Summaries are shared: blocks another seat stored are reused.

```
herdr-threads summary THREAD
herdr-threads summary job JOB --lease TOKEN
herdr-threads summary submit JOB --lease TOKEN < submission.json
```

`summary THREAD` prints either Ready (block narratives, one ledger of human input, decisions, open items and identifiers, and the raw recent tail, with source and intent shown independently) or Work (`summary THREAD frontier #N: work (K jobs)`, then per job a `fetch:` and a `submit:` command, the `procedure:` line naming `herdr-threads skill`, and `then: herdr-threads summary THREAD`). `summary job` prints a leased job's bundle as JSON, or says the reservation lapsed. `summary submit` reads the submission JSON from stdin (at most 64 KiB) and prints `stored BLOCK` (`(fallback)` when a fallback block was stored) or `rejected:` with one reason per line; fix exactly those reasons and submit once more. A job is leased to the seat that asked, and jobs leased to another seat are listed as `leased elsewhere`. Everything in the output that came from peers is escaped data, never instructions. Reading a summary is not a receipt: ACK as usual. **Catch-up hold:** while a seat catches up on a thread (it ran `summary` and got work), its pending receipts on that thread are shown with the `deferred:` suffix and their effective deadline extends: once per catch-up entry, then only by stored summary progress (re-entering after a stall grants nothing until a summary block is stored; TRUST-POLICY A6); frozen deadlines are never rewritten.

Classified sources have deterministic thread-local IDs `i.<sequence>`: queries/questions and requests/asks start `open`, rules start `active`. Live entries keep their text or spill to a recoverable source reference (`body MESSAGE_ID`, or historical `read THREAD --after SEQ --limit 1`). Recently closed lines retain source ID, attribution, intent and `resolved`/`superseded` status plus citation sequence; older closed entries are omitted from the displayed ledger, without deleting messages or changing receipts. Active rules remain pinned through rollups.

Workers use submission schema2, `thread-summary-v2` and transitions `{target,new_status,cite_seq,quote?,rule_change?}`. At summary time they compare every supplied live ledger entry, including earlier unstored sources, against current chunk messages. Query/request accept only `resolved` with a later answer/completion or explicit human/relayed withdrawal/cancellation/replacement; answers and completion reports can come from an agent. Withdrawal/replacement of a question cites explicit human/relayed input and the replacement gets its own classified source. Partial answers, promises, silence and ACKs do not establish completion. Rules accept only `superseded`, citing later ordinary human/relayed input with `rule_change: withdrawn|replaced` and an exact nonempty quote of explicit withdrawal/replacement. Compliant behavior never closes a rule. Unclassified legacy entries retain `done`/`superseded` behavior; workers must not duplicate classified deterministic sources as model open items. Rule changes are summary-derived judgments, not grants of authority.

Closure is worker judgment submitted through `summary submit`; the daemon validates structure, allowed transitions and evidence, without proving semantic completion. All cites are in the worker's current chunk and later than the source. If uncertain, leave work open. There is no automatic resolution on send or inbox, no dedicated resolution command and no reminder created by keeping an item in the ledger. Reading a summary and ACKing a message remain separate. Rules apply only to their thread and never install global instructions or edit user configuration. Historical stored blocks stay readable under their original generation; current renderer2 summaries use classified lifetimes without rewriting old claims.

**Live view for people.** `read THREAD --follow` is for a person watching a thread, not for an agent's loop: it runs until Ctrl-C (exit 0). It prints the recent messages oldest first (default 20, `--recent N` up to 100, `--recent 0` for none, or `--after SEQUENCE`), then polls the daemon about once a second (backing off to a few seconds while idle) for the messages after the last timeline sequence it printed and prints only those, never redrawing. A daemon restart is reported as a `-!-` notice and followed through; a slow poll or slow connect is retried quietly and reported as a lost daemon only after 10 s of continuous failure (once per outage); a daemon that keeps refusing ends the follow with one notice and the matching exit status; Ctrl-C interrupts a call in flight; an archived thread is still followed; a thread that disappears ends it. The human form is IRC style: `[HH:MM] <nick> message` in local time, where an agent nick is `SPACE/PANE/SEAT_ID` (for example `project/alice/sAb12Cd34`), with the full canonical seat ID and no harness suffix. The generation-matched local context supplies the advisory occupant kind; the daemon's target chooses the host names. Missing space or pane labels use their host IDs; an unavailable host leaves only the full seat ID. Host name components keep their independent display bounds and terminal escaping. Human nicks retain the relative workspace/tab/pane display and human suffix; an unknown occupant retains the existing relative name or short seat ID fallback; system events are `-!-` lines, limited to channel joins and leaves (`project/alice/sAb12Cd34 joined`) and warnings (`warning: … is overdue on an ACK`); ACKs, invitations, topic changes and other informational events are left out of the IRC view and remain in `--json` and the machine form; bodies are shown in full, wrapped at the terminal width under the message column and folded after 20 lines with the `herdr-threads body MESSAGE` command for the rest. Per-nick colors appear only on a terminal (never with `NO_COLOR` or `TERM=dumb`). With `--json`, or when stdout is not a terminal and `--human` is not given, it prints one JSON message summary per line (the same object as a `read` page item) and its notices go to stderr. `--no-system` hides system events. It is strictly read-only: it never ACKs, accepts or sends, and peer text is escaped so it cannot drive the terminal. Plain `read` uses the same IRC transcript in its human form.

A required invitation stays pending until the top-level native agent explicitly accepts the displayed episode and revision. Check the inbox, then `thread participants THREAD` for the current invitation ID, requirement ID and revision, including when already joined voluntarily. Use `accept-required` with those exact values. If acceptance reports `stale_requirement_acceptance`, reread before deciding again. Required membership prevents voluntary leave until the owning service releases the requirement; release does not ACK messages or remove the member.

If a mutation's result is uncertain, use `pending-ops [PAGE]` and `retry LOCAL_REF`. The local recovery reference is distinct from a message ID and cannot be ACKed. Retrying uses the persisted operation key and original payload. An intentional repeat uses a new send command.

Operator repair has three explicit forms. The local service records the effective local user for these actions:

```text
herdr-threads invite THREAD --seat SEAT [--deadline SECONDS] --operator
herdr-threads seat rebind SEAT --pane ADDRESS --operator
herdr-threads seat resolve --pane ADDRESS --new-seat --operator
```

Ordinary `seat resolve` defaults to the caller's live pane. Command-local `--space SPACE --tab TAB --pane PANE` accepts exact case-sensitive IDs or labels. Names inherit the caller's live space and tab from the selected Herdr endpoint, never UI focus or stale parent hints; outside Herdr, supply parents or a pane ID. An unqualified pane ID (`w4:p1`) is used directly; explicit parents must agree with its live location. An explicit tab ID supplies its space. Changing a parent never carries the caller's child into it: an omitted child selects the sole tab/pane, otherwise fails with `conflict` (exit 1) and escaped candidates. Pane names match the union of pane labels and live agent names within the selected tab, deduplicated by pane ID; an exact pane ID wins. A single-pane tab's label remains an alias within that scope. Missing names return `not_found` (exit 1); host unavailability returns `host_unavailable`, never passes names through. `launch`, `seat rebind`, and `seat resolve --new-seat --operator` require explicit `--pane` intent.

`invite THREAD --tab tryout --pane alice` resolves the target's seat through the daemon's ordinary guarded path, so an unclaimed future agent pane can receive work; restoration holds still apply. `--seat SEAT` remains an exact durable selector and conflicts with pane selectors. `send THREAD --body TEXT --tab tryout --require-ack-pane alice` supports repeatable pane recipients alongside `--require-ack SEAT`, deduplicated by canonical seat. Recipient selectors never change the sender's identity. Names and recipient seat IDs are frozen before submission; retry uses those IDs after a rename.

`thread list`, `inbox`, `pending-receipts`, `warnings`, and `diagnostics` accept pane selectors as alternatives to seat filters. `thread list --all` conflicts with pane selectors because it is the unfiltered instance directory. These reads only look up existing resolved mappings and never allocate; a parent-only filter still selects one pane rather than silently reading the instance. `inbox --pane PANE` is read-only, including human output: it never display-ACKs. `--cooperative-target` uses the same scoped exact locator while preserving the explicitly claimed seat, harness and role for daemon validation. `me init` remains the caller's own identity declaration. `daemon ensure` and `daemon stop` are explicit lifecycle commands. Operator mode cannot be combined with ACK, accept, send, or check-in.

Inspect a programmatic service connection with `herdr-threads service inspect`. To recover a connected but unresponsive service, use `herdr-threads service disconnect --expected-boot BOOT_UUID --expected-generation N` with the exact values just observed. A stale request cannot disconnect a successor. The result reports whether the recovery audit was persisted. These same-user operator commands are cooperative; another program under the same user can register when the slot is free. Service mutations require one live registered Unix socket held by the persistent programmatic client. A one-shot CLI process cannot retain that authority for later commands. Service `info` notices remain discoverable without waking an agent; `warn` notices use native attention. Publishing a notice does not prove recipients acted, and graph must reconcile those effects. Graph should release required memberships during teardown.

## Lifecycle, diagnostics and exit status

`herdr-threads --help` and `herdr-threads --version` print to stdout and exit 0. Running `herdr-threads` with no command prints the usage text on stderr and exits 2. `daemon ensure` exits 0 once a matching daemon is reachable, even when its health is `degraded` (for example while the host is unreachable); the printed health lists the limitations. The designed cooperative mode is `healthy`. `daemon health`, `doctor` and read commands never start the daemon.

`doctor` is read-only. It reports the executable version, the resolved state directory and host endpoint, whether the state directory is safe, daemon reachability and health, and the owned user-level Claude and Codex hook installations (`hooks.claude.setup_installed`, `hooks.codex.setup_installed`; in JSON `hooks.<harness>.setup.installed`, while `hooks.<harness>.installed` is the harness binary object `{binary, version, admission, recipe}`; installed is kept separate from `observed`). `doctor` reports `result: ok` for a healthy daemon and an environment whose installed harnesses have their hooks installed, and `degraded` with `limitation:` lines otherwise. It exits 0 when the daemon is reachable (ok or degraded), 3 when it is not running or unreachable, and 2 when the context is missing or unsafe.

The state directory may be the Herdr-provided plugin state directory (mode 0755); it must be owned by the current user and not writable by group or others. An unsafe state directory is invalid local context: `daemon ensure` and `doctor` exit 2 and create nothing, because restarting the daemon cannot fix it. Everything the plugin creates below it is mode 0700; if one of those private directories (`instances/`, the instance directory, or the runtime socket directory) is changed to another mode or owner, it is the same invalid local context: `daemon ensure` and `doctor` both exit 2 (`doctor` reports `unsafe_state_dir` and does not suggest `daemon ensure`), and neither repairs the mode. The host endpoint is a filesystem path of up to 1024 bytes and may contain spaces.

Errors print one human-readable line (`herdr-threads: DETAIL (error_code)`) on stderr. When the daemon is not running or was stopped, every command that needs it (reads, `daemon health`, `daemon stop`, `view --once`, `seat resolve`, `retry` and cooperative check-in) exits 3 with `(host_unavailable)` and the `daemon ensure` hint. Exit statuses:

| Status | Meaning |
|---|---|
| 0 | Success |
| 1 | The request failed (not found, conflict, unauthorized, stale state, ...) |
| 2 | Invalid arguments or invalid local context |
| 3 | Daemon or host unavailable; run `herdr-threads daemon ensure` and retry |
| 4 | Unsupported capability in this build or environment; includes `transport_denied`: a harness sandbox refused the daemon socket (EPERM/EACCES), so restarting the daemon cannot help. For Codex, request approved outside-sandbox execution of the CLI; report permission refusal ([install](install.md#codex-command-approvals)) |
| 5 | Outcome unknown; inspect `pending-ops` and `retry` the local reference |

## Native hooks

Native harness hooks run `herdr-threads [--state-dir PATH] [--host-endpoint SOCKET] hook claude` (or `hook codex`), the exact argv from `cli::hook::installed_argv`, with `--event NAME` appended on each per-event registration that setup writes. Agent panes do not inherit the plugin state directory, so setup passes `--state-dir`, and it passes the Herdr server socket as `--host-endpoint` because the user-level hook runs in every session: outside a Herdr pane, or in a pane whose `HERDR_SOCKET_PATH` is another server, it prints nothing, runs no version probe and starts no daemon; it only reads the payload (bounded) and may send one short best-effort evidence note to a daemon that is already running, keeping per-session gate files under `<state>/harness/evidence`. The pane comes from `HERDR_PANE_ID`. Before parsing, the hook observes the installed harness by running the first absolute `claude` (or `codex`) executable on `PATH` with `--version`; the payload is parsed for every admitted version: one the adapter's recipe registry covers (Claude Code 2.1.283 to 2.1.286 inclusive, recipe `claude-hooks-2.1.283`, and exactly 2.1.287, recipe `claude-hooks-2.1.287`, reported as `X.Y.Z (Claude Code)`; Codex exactly 0.157.1 or 0.158.0, recipe `codex-hooks-v1`, reported as `codex-cli X.Y.Z`, or an unlisted Codex version whose embedded hook schemas match that recipe's fingerprint, reported as **schema-matched, live-unverified**, as Codex 0.159.2 is), or an **optimistic** version (newer than the verified range or inside the supported span: parsed under an assumed recipe and labelled, and a payload it cannot parse is counted for `doctor` (`hook payloads not understood: N`; Health shows no line for it) and logged, rate limited); see [install](install.md#harness-hooks). For a refused version (unparsable, known broken, or older than every recipe) the hook stays quiet with one stderr diagnostic. The hook always exits 0, whatever the failure; the exit statuses above apply to ordinary commands, not to `hook`. The hook reads the native payload on stdin, finds the resolved seat mapped to that pane, and prints only `hookSpecificOutput.additionalContext`. It always exits 0 within 1.5 s (tool; a stdin that never closes is cut off at the same budget) or 5 s (startup, which may ensure the daemon), never decides permissions, and never accepts or ACKs.

**Recovery after a context reset.** On a top-level Compact, Resume or Clear with hot threads (threads that need the seat's attention after the reset), the output also carries the fixed recovery instruction (`Context was reset. Run herdr-threads skill and follow its thread-summary procedure (section "Thread summaries") for each hot thread before continuing: herdr-threads summary <id>.`) followed by the hot-thread rows as peer data. The instruction names `herdr-threads skill` because setup installs no skill file. Subagent events never get it.

There are two hook classes:

- **Lifecycle** (SessionStart `startup`, `clear`, `resume`): a durable Lifecycle CheckIn that registers a fresh execution, replayed exactly if its response is lost. A pending request that the service definitively rejects (Conflict, a changed generation, CallerUnverified) is recorded as terminal and cleared, so the next SessionStart registers against the current generation. The output presents pending attention once for that execution, followed by the seat's attention digest line (per-class counts and the newest IDs), which also seeds what the next tool call treats as already shown.
- **Tool boundary** (Claude Bash `PreToolUse`, Codex Bash `PreToolUse`, and the compact lifecycle event: Codex `compact` and Claude SessionStart `source: compact`, admitted only by the Claude 2.1.287 recipe, `claude-hooks-2.1.287`): first one read-only `AttentionDigest` query for the seat. The service computes it in one read transaction from the seat's own pending items only: pending invitations, unacknowledged receipts, warnings whose condition is still open, and service warnings addressed to the seat that no check-in has offered to its current occupant yet. It reads them through indexes and store-maintained projections that hold only unsettled rows, with at most 1,001 rows per source, so its cost is bounded: it does not grow with the number of threads in the instance, with the receipts the seat has ACKed and the warnings that have settled, or with how much is pending (counts above 1,000 print as `1000+`). Its token names the newest pending invitation, addressed receipt and actionable warning, plus the seat's own unavailability episode. The hook compares only that token with the last token shown to this execution, and only the invitation, receipt and warning components count: the seat's own unavailability episode is carried but is never new attention for its own model (another recipient's unavailability reaches a sender as an actionable warning). When nothing is newer the call prints nothing and makes no CheckIn. When something is newer (a new message, warning, invitation or required membership) it makes one non-durable Current CheckIn and prints the offer plus a line such as `attention digest: invitations=1 [INV@THREAD]; receipts=2 [MSG@THREAD, …]; warnings=0` (at most 4 IDs per class, `+more` when there are others). That CheckIn's offer reads each listed thread's pending items and the seat's pending warnings with the same bounded walks as the digest, plus one bounded page of warning history, so its cost does not grow with ACKed receipts, settled warnings, pending backlog or ordinary message history. The offer settles only the programmatic service warnings on the notice page it carries (at most 16), shown on the `offered notices:` line. The token is read before the offer, so a message arriving during the call is shown on the next call rather than lost. An ACK or an accepted invitation alone prints nothing. If the digest query fails, the hook prints the offer anyway (fail open). An offer larger than the hook budget is replaced by the compact form described under **Hook budget** below. The tool boundary writes nothing to the local context or intent journals and never replays; the full inbox stays readable with `herdr-threads inbox --seat SEAT` (with `--state-dir PATH` when the prefix rule below keeps it explicit). On any other failure it prints nothing and writes one stderr line. A tool call from a session no SessionStart registered prints nothing.

**Ready commands.** For the top-level agent, both hook classes put a plugin-authored block after the fixed instructions and before escaped peer data: `Ready commands (run exactly as written, in this pane):`. Its first, pinned action is one `inbox` command covering all pending threads. The label names the main thread for overview retention without restricting inbox to it. Invitation acceptance remains separate: `- accept: herdr-threads accept THREAD_ID` for an invitation tied to pending receipts; `- accept required: herdr-threads accept-required THREAD_ID --invitation INVITATION_ID --requirement REQUIREMENT_ID --revision N` for required membership. Other ordinary invitations are optional and bounded to two lines. One reply template names the first receipt thread. Read inbox and its printed continuations once; do not replay the messages through history reads or manual ACKs. The final `- inbox fallback (only if pending-mail command was omitted): … inbox` line reaches mail when the primary action was trimmed, rather than requesting a second read. It notes additional optional invitations when present. Templates and optional accepts apply only when relevant; the block is not a script to run in full. When the startup overview is trimmed or has more threads, a `- thread overview: … thread list --seat SEAT` line follows. Only service-generated IDs made of letters, digits, `-` and `_` are interpolated. **Command prefix.** Every ready command, fallback read command and diagnose argv starts with the bare prefix `herdr-threads` when the instance resolver, run in the hook's own environment (the agent's pane) with no flags and without the slow `herdr` query, yields the same canonical state directory as the hook's and the same host endpoint as the hook's (`--host-endpoint` or the pane's `HERDR_SOCKET_PATH`); the agent's plain command then reaches the same instance. Otherwise (a non-default, private or scratch state directory, an ambiguous default with both state roots present, a different `HERDR_PLUGIN_STATE_DIR`, or a missing default) the prefix is `herdr-threads --state-dir PATH`, plus `--host-endpoint SOCKET` when the pane would not reach the hook's endpoint by itself; paths are shell-quoted when needed. Either form is covered by the Claude allow rule `Bash(herdr-threads *)`. The fixed instructions name the `herdr-threads` CLI and the D2 `accept-required` procedure but repeat no argv shapes: the block is the one place exact commands appear. Subagents get no block and are told that in this pane every `herdr-threads` write (any accept, `ack`, `check-in`, `send`, `leave`, `invite` or other mutation) acts as the top-level seat, so they run only reads. The digest's `ITEM@THREAD` form is a display reference: passing it as a thread or message argument fails with `(invalid_request)`, exit 2, naming the bare ID to pass.

**Permission for ready commands (Claude).** Every ready command, the `inbox` fallback and the `daemon health` diagnose line start with the bare program name `herdr-threads` (never an absolute path), so `herdr-threads` must be on the agent's `PATH`. `herdr-threads setup claude` installs the owned user-level allow rule `Bash(herdr-threads *)` in `$CLAUDE_CONFIG_DIR/settings.json` (default `~/.claude/settings.json`): Claude Code then runs any single `herdr-threads ...` command (any subcommand, any arguments) without asking, including in print mode, where an unallowed command is simply denied. A command chained after it (`;`, `&&`, `|`, `$(...)`) is still checked on its own. Run the lines exactly as written; do not prefix them with `cd`, `export` or anything else, or the combined command is no longer covered. Without setup (or after `unsetup`), Claude asks for each command, and print mode denies it.

**Guidance discovery.** Fixed top-level hook instructions tell agents to run `herdr-threads skill` before using threads unless the guide is already in context. The embedded guide includes communication guidance; it loads on demand, not on every tool call. This instruction survives ordinary offer trimming, while unchanged tool calls remain quiet and subagents retain their read-only restrictions. Disabled hooks and unsupported harnesses do not guarantee discovery; top-level `--help` also points to the guide. Native permission decisions remain with the harness.

**Hook budget.** The whole native `additionalContext` is at most 4,096 bytes. On the native SessionStart event only (startup, resume, clear and Codex compact; never PreToolUse or SubagentStart), one fixed line `Agent guide: run herdr-threads skill; …` follows the instructions when the result still fits; it is the first thing to give way, before any of the steps below. The full offer (for SessionStart, the cached check-in plus the startup directory overview) is sent when it fits. Otherwise a compact form keeps the fixed instructions and the ready commands, replaces the offer body with the startup directory overview as one JSON row per thread (peer topic as data, at most 120 bytes and marked `topic_truncated` when cut, plus `created_at_millis`, `age_millis_signed`, `timeline_messages` and `joined_nonretired_participants`), the digest line and the `offered notices:` line, and then one function fits it, giving way in this fixed order until it fits: (1) the digest line's exact IDs (the commands name the same items; its per-class counts stay); (2) overview rows whose thread has no kept item command, one at a time from the end, with an `overview has_more: K of N threads shown` line and the `thread overview` command (the main thread's row, the thread of the first item command, is never dropped here); (3) the digest counts line (recomputed on every call); (4) per-item commands, from the end, down to the pinned prefix, each dropped command taking its thread's row with it unless another kept command names that thread, so a kept command always keeps its row; (5) the `offered notices:` line (the notices stay in `warnings` history), then the pinned commands; (6) the continuation-only form without any row, then the recovery block's hot-thread rows (see **Recovery after a context reset**), one at a time from the end (the recovery instruction stays); (7) a final fit check: if even that exceeds the budget (a state directory of thousands of bytes), the text is cut at a line boundary and closed by a `…` line naming the read command (`herdr-threads --state-dir …/last/two inbox`). Ready commands are never abbreviated, because a model runs them verbatim: a long `--state-dir` stays exact in every command that is kept and lower-priority parts give way first; only display text (the final `…` line) shortens a path longer than 48 bytes to its last two components. The fixed instructions and the conditional `inbox` fallback are kept in every form but the final cut, so the settled notice page survives every realistic fallback, as the CLI design requires. A typical one- to three-thread SessionStart keeps the whole overview and every ready command. The D2 `accept-required` procedure line is emitted when a required invitation is pending or when no attention digest could be read (a missing digest cannot rule one out).

Output by case:

- A registered top-level Claude/Codex SessionStart uses guarded daemon resolution to reuse a seat or enroll a genuinely new Herdr pane. Resume continuity runs first; ambiguous recovery, unresolved targets and recovery holds refuse allocation. Tool calls in a pane with no seat, subagent tool calls and routine no-change tool calls print nothing.
- A pane whose seat exists but is not resolved (for example `unresolved` after reconciliation) prints nothing on tool calls; on SessionStart it prints one compact report, `herdr-threads: check-in unavailable (pane seat mapping is Unresolved) …`, followed by the diagnose argv as JSON (bare or explicit by the command-prefix rule above). The operator repairs the mapping; the hook never allocates around an unresolved seat.
- Any other unavailable service or rejected lifecycle check-in prints the same compact report on SessionStart only.

Omitted `thread list`, `warnings`, `diagnostics`, `inbox`, and `pending-receipts` selectors use `HERDR_PANE_ID` and the daemon's existing resolved seat mapping without requiring a host read or allocating a seat. Live caller lookup scopes explicit names and parent selectors; it never retargets an omitted read or rebases its saved claim. Explicit `--seat`, cooperative selection, `thread list --all`, `warnings --active`, and thread-scoped diagnostics/receipts retain their requested scope. Own text inbox remains eligible for display ACK after context validation; explicit pane inbox reads never ACK. Operator pane invitations resolve the recipient through ordinary guarded allocation before recording the operator invitation. Existing exact IDs win over labels; absent qualified pane IDs and tab IDs return `not_found` rather than matching labels or agent names. Workspace labels such as `work` remain valid. Bounded conflict messages state total matches and omitted candidates.

A live caller lookup does not rebase a saved lifecycle claim. If the saved context still names an old pane after a move, own text inbox refuses rather than ACKing through that stale claim; a matching canonical check-in context is required.

### Human recent-channel discovery

`ht read` with no thread opens the builtin picker only when stdin, stdout and stderr are terminals, TERM is usable, and no agent marker, cooperative caller, `--machine` or `--json` is present. `ht follow` (also `herdr-threads follow`) is shorthand for `read --follow`: without THREAD it uses the same picker, and with THREAD it preserves exact ID/name resolution and human, machine, or JSON streaming. Both follow forms accept `--recent N` (20 by default, 0 to skip the tail) or `--after SEQUENCE`, `--no-system`, and `--max-bytes N`; `--before`, `--cursor`, and `--limit` are refused. Agents and scripts supply THREAD explicitly.

The picker progressively loads bounded canonical pages across the selected instance, including archived and nonmember channels, and refreshes completed listings every five seconds. Rows show explicit active/archived labels, current effective joined participant counts, sampled ordinary messages/minute, and an escaped compact last-message preview. Participants are nonretired seats with effective joined membership, including accepted service requirements; pending invitations do not count. Activity samples at most the latest 512 canonical timeline positions and counts ordinary messages over the elapsed time from the oldest sampled position through the sample time, with a one-minute floor. Empty histories have rate zero. This bounded sample avoids replaying long histories; system events occupy positions but do not inflate the message rate. Active channels sort before archived, then by participants × (1 + sampled messages/minute), with deterministic ties.

Type a fuzzy subsequence of a name or topic, use arrows or Ctrl-N/P, then Enter to read or follow the selected canonical ID. Selection stays on that channel as listings refresh. Esc/Ctrl-C cancel with status 0; Enter on a completed empty filtered list also exits 0. Color highlights selection and activity and keeps archived channels quieter on supporting terminals; explicit labels and selection markers stay readable with `NO_COLOR` or without color support. The UI is on stderr and the selected transcript on stdout; terminal settings restore on exit. Bare `--cursor` is invalid for history; choose an explicit thread for continuation. A daemon lacking the optional picker capability refuses with upgrade guidance; use `read THREAD` or `follow THREAD` with an exact ID until upgrading. All picker/history/follow reads stay read-only and never ACK or accept.

Human transcripts name authors and event recipients relative to the live invoking pane: `alice` in the same tab, `tryout/alice` in another tab of the same workspace, and `project/tryout/alice` in another workspace. Scope omission compares parent IDs, even when labels collide. Missing labels use IDs, the pane component stays visible, hostile labels are escaped, and unavailable host labels do not prevent durable history reads. Cached snapshots refresh during follow; JSON, machine output and recovery references keep their canonical IDs.

### Durable handoff and recovery

```sh
herdr-threads handoff --new-thread --thread-name review --topic "Review the change" \
  --goal "Review the change and report findings" --pane bob --kind codex -- "Review the change"
herdr-threads handoff --thread review --pane alice --kind claude -- "Check the tests"
herdr-threads handoff --new-tab parser-review --space fixture-workspace --cwd /fictional/ht-pressure/parser \
  --new-thread --thread-name parser-review --topic 'Parser recovery review' \
  --goal 'Review the parser recovery patch and report findings' --kind codex -- 'Review the parser recovery patch'
herdr-threads handoff --existing --seat fixture-seat-reviewer --thread fixture-thread-review -- 'Review the latest patch'
herdr-threads handoff --existing --pane w9001:p102 --new-thread \
  --topic 'Review parser recovery' --goal 'Review recovery patch independently' -- 'Review recovery patch independently'
```

The fixture IDs and paths above are illustrative. Handoff chooses one target mode
and exactly one `--new-thread` or `--thread ID_OR_NAME`: an explicit pane launch
(`--pane PANE --kind claude|codex`), intentional new-tab creation
(`--new-tab LABEL --kind claude|codex`), or existing-seat delivery
(`--existing --seat SEAT` or `--existing --pane PANE`). The guarded new modes
require an original top-level Agent and the daemon capability. Native execution
still requires the selected harness's approval and configuration; this reference
does not establish installed permission.

`--new-tab` conflicts with `--existing`, `--tab`, `--pane` and `--seat`. Its
`--cwd` must be an absolute existing directory; omission uses the invocation cwd,
and the path is normalized before publication. `--space` resolves an exact live
workspace ID or unique label; omission uses the caller's live workspace, never
UI focus. Creation is intentional even if its label already exists, and does not
focus the new tab. No caller identity or routing environment is copied into it.

Delivery requires exactly one existing canonical seat or pane. `--space` and
`--tab` may qualify its pane but conflict with `--seat`. It never allocates,
moves, rebinds or registers a seat, and unresolved, held, retired or foreign seats
refuse. Delivery never launches or restarts the peer. It forbids `--kind`,
`--harness-binary`, `--name` and `--agent-arg`, ignores launch-option environment,
and reports `outcome: staged` with participation `joined`, `invited_pending` or
`staged_unbound`. An unbound resolved seat may receive work; the report does not
establish a working or available session, accepted assignment or completed task.

The new channel joins its sender; an existing channel requires the sender already
joined. `--thread-name`, `--topic` and `--goal` apply only to new channels. Topic
defaults to `Handoff to DISPLAY`: the relative escaped pane display for legacy
launch, tab label for new-tab, or canonical recipient seat ID for delivery. Goal
defaults to topic. `--name` names the native agent, not the channel. Thread names
resolve once to canonical IDs; ambiguous names refuse and retry keeps the saved ID.

One quoted argument after `--` becomes one durable addressed message (1–1024 UTF-8
bytes), never native argv. Repeat `--agent-arg=OPTION` for native launch options;
`launch -- ...` retains its existing argv meaning. Optional
`HERDR_THREADS_CODEX_OPTS` / `HERDR_THREADS_CLAUDE_OPTS` prepend arguments using
shell-style quotes and escapes without variable or command expansion; unset or
empty adds nothing. Launch handoff freezes the combined argv before preflight,
and retry uses those saved arguments even if the environment changes. Handoff
stages an invitation when needed and an addressed message; launch modes then
perform guarded launch. Startup gets fixed scoped inbox instructions and the
canonical thread ID, without duplicating the task body. Handoff never accepts
or ACKs for the recipient, nor declares task adoption or task completion.

Private compound intents retain the caller, exact namespace, canonical IDs,
payload and mutation keys. `pending-ops` lists the compound recovery reference;
`retry REF` preserves committed work without duplicate messages or invitations.
Confirmed pre-start refusals can retry after repair with guards rechecked. Unknown
tab creation cannot automatically create another tab: inspect the reported exact
namespace and attempt. It is distinct from downstream possible start. Once a
start may have happened, including a crash across its durable submission fence,
retry never automatically launches again. Inspect the exact downstream pane/seat
before using any reported manual launch argv, after confirming no agent started;
manual launch guidance does not prove tab noncreation. Completed retry presents
the retained historical report and cleans its own local intent without repeating
effects or proving current availability. Output failure retains recoverable state.

Administrative bootstrap recovery uses `human` immediately after the executable,
with routing/output globals following it. Root `--human` selects output only.
Each example below is an alternative disposition for the explicit inspected
attempt, not a sequence to run. Keep the exact reported reference, positive
attempt, state directory and endpoint; the fixture values are illustrative.

```sh
herdr-threads human --state-dir /fictional/ht-pressure/state-ember --host-endpoint /fictional/ht-pressure/ember.sock \
  --machine handoff recover local:41 --attempt 3 --created-pane w9001:p104
herdr-threads human --state-dir /fictional/ht-pressure/state-ember --host-endpoint /fictional/ht-pressure/ember.sock \
  --machine handoff recover local:41 --attempt 3 --not-created
herdr-threads human --state-dir /fictional/ht-pressure/state-ember --host-endpoint /fictional/ht-pressure/ember.sock \
  --machine handoff recover local:41 --attempt 3 --cancel --reason 'Inspected quiescent bootstrap abandoned'
```

Recovery requires the guarded daemon capability and records a separate
`operator:local-user:<uid>` administrative assertion, preserving the original
Agent claim and scope. A root `--operator` form cannot substitute for the Human
namespace. `--created-pane` asserts that this exact result belongs to the inspected
attempt, requiring fresh coherent structural evidence and ordinary guards;
labels do not prove ownership. Recovery never launches or delivers downstream
work. The original Agent's later live retry still requires current canonical
authority. Exact recovery replay presents its historical decision, never a new
decision about a newer attempt.

`--not-created` asserts inspected noncreation and quiescence: the original attempt
cannot still create. `--cancel --reason TEXT` asserts inspected quiescence and
administrative abandonment, not completion; reason must be nonblank and at most
4096 UTF-8 bytes. A known in-flight invocation refuses conflicting recovery;
snapshots or guessed PIDs do not prove quiescence or authorize killing an unowned
process. Bootstrap cancellation refuses while an exact legacy child fence or live
hint remains. That child may stay protected indefinitely after pane loss or seat
retirement; cancellation cannot release its fence. Product cleanup never closes
created topology or removes committed messages, invitations, receipts or membership.

### Compatibility and choosing a target

Where an older workflow copied a seat ID for `invite THREAD --seat SEAT` or `send THREAD --require-ack SEAT`, you can now use `invite review --tab tryout --pane alice` or `send review --tab tryout --require-ack-pane alice --body "Ready"`. Exact seat/ID forms remain valid. Repeat `--require-ack-pane` once per pane; repeat `--agent-arg=VALUE` once per native argument, including options and their values. Neither flag splits one quoted value into words.

Outside Herdr, discovery can use an explicit instance (`--state-dir PATH --host-endpoint SOCKET`) and `thread list --recent --all`; use a unique thread name or ID for `read`. For pane selection, provide an exact pane ID or explicit parents, for example `--space project --tab tryout --pane alice`. Accountable writes still need the original pane context or complete cooperative claim. Names and current topology do not rebase a stale lifecycle claim.

Wire protocol 6 rejects older clients/daemons before dispatch; upgrade the CLI and daemon together. Schema 19 adds names and schema 20 adds indexed recent activity. The combined upgrade applies schema 22 for recorded user intent and frozen summary bundles, then schema 23 for canonical handoff fences and quiet-channel archival. Handoff retains private intent/progress files alongside its canonical SQLite fences. Relevant directory changes invalidate recent traversal: rerun the initial query/picker to refresh, rather than treating a partial page as the complete inventory.
