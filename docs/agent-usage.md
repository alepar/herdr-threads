# Agent and operator commands

`herdr-threads` finds the Herdr instance by itself: flags first, then Herdr's environment (`HERDR_PLUGIN_STATE_DIR`, and `HERDR_SOCKET_PATH`, which every Herdr pane has), then Herdr's default plugin state root (`herdr/plugins/herdr-threads` under `$XDG_STATE_HOME` or `~/.local/state`). In a Herdr pane, plain `herdr-threads <command>` therefore works. For an explicit local context, pass `--state-dir PATH --host-endpoint PATH` before the command. Add `--json` for structured output. Commands never choose the currently focused pane.

Output form: when stdout is a terminal, text output is human-readable (inbox as a table, `read` as an IRC-style transcript (`[HH:MM] <nick> message`, with `-!-` lines for system events), thread details and participants as lists, one-line confirmations for send/ack/accept/invite). When stdout is not a terminal (pipes, scripts, hooks, and agents running the CLI through a tool) the compact machine text form is used (ht-4is.8.18): the first line names the result kind; `read` prints one row per timeline entry, `#SEQ MESSAGE_ID AUTHOR HH:MMZ: text` (author is the seat ID, a service ID, or `system`; a clipped preview adds `[more: herdr-threads body MESSAGE_ID]` before the `: `), and a system event is one short row such as `#39 ack SEAT MESSAGE_ID`; `inbox` rows are `THREAD receipts=N invitations=N warnings=N` (zero counts left out, `+` when more may be pending, a required invitation adding its exact `accept-required` command); `pending-receipts` prints `pending_receipts SEAT` then `MESSAGE_ID THREAD#SEQ from SENDER due HH:MMZ [overdue]`; `thread show` and `thread participants` print one `SEAT STATE [self] [required invitation=ID requirement=ID revision=N]` row per participant; `check-in` prints `checked_in SEAT HARNESS ROLE generation=N DISPOSITION` followed by its inbox rows and pending warning count. `body` prints one header row `#SEQ MESSAGE_ID AUTHOR HH:MMZ` (plus `warn`, `bytes=FROM-TO/TOTAL` when the page is not the whole body, and `escaped` when the body holds a terminal control), then the body text verbatim with each non-empty line indented by two spaces, so no body line can start a row or a command line; an `escaped` body shows each such control as `\uXXXX` and doubles every backslash. A single `more: herdr-threads body ...` line follows only when the body continues; a system event prints `event: JSON` and its `condition: STATE active|inactive` instead of a body. Service-generated fields come first in every row and peer text only after the row's first `: `, escaped to one line. A page prints no metadata: a single trailing `next: herdr-threads ...` line appears only when there is more. Other results keep the `key: value` form, with one JSON object per `item:` line, no page metadata line, and each command (`*_argv`) printed once as its own `label: command` line rather than repeated inside the JSON. `--machine` forces the machine text form on a terminal, `--human` forces the human form anywhere, and `--json` always selects JSON; `--json` cannot be combined with either. Page budgets (`--max-bytes`) are measured on the machine form. `skill` always prints its markdown guide verbatim, and `setup`, `unsetup`, `setup-status` and `doctor` keep their `key: value` report form in either presentation.

Agents: `herdr-threads skill` (alias `--skill`) prints the concise agent guide ([integrations/skill/SKILL.md](../integrations/skill/SKILL.md), embedded in the binary, local only, never contacts the daemon). The top-level `--help` ends with an `Are you an AI agent?` pointer to it. This document is the full reference.

IDs are a type prefix plus 8 letters and digits: `seat-k3Fq9a2B`, `thread-Q7mZ0cT4`, `inv-8Lx2PqRa` (invitation), `msg-7xQ2pL0c`, `event-3HnW5yKe`. IDs created by earlier releases keep their UUID form (`seat-bc121d12-9d30-4510-b93c-e7cd26e890f1`, `invitation-…`) and are still accepted everywhere. Pass IDs exactly as printed; they are case-sensitive.

Read-only discovery works for nonmembers and child agents:

```text
herdr-threads thread list [--seat SEAT] [--joined|--invited|--all] [--search TEXT] [PAGE]
herdr-threads thread show THREAD [PAGE]
herdr-threads thread participants THREAD [PAGE]
herdr-threads thread topic THREAD
herdr-threads inbox [--seat SEAT] [PAGE]
herdr-threads warnings --seat SEAT [PAGE]
herdr-threads pending-receipts [--seat SEAT] [--thread THREAD] [PAGE]
herdr-threads read THREAD [--recent N|--after SEQUENCE|--before SEQUENCE] [PAGE]
herdr-threads read THREAD --follow [--recent N|--after SEQUENCE] [--no-system]
herdr-threads body MESSAGE [--offset N] [--max-bytes N]
herdr-threads search TEXT [--thread THREAD] [PAGE]
herdr-threads seat list [PAGE]
herdr-threads seat inspect SEAT [PAGE]
herdr-threads seat retirements [PAGE]
herdr-threads delivery inspect MESSAGE [PAGE]
herdr-threads delivery recipients MESSAGE [PAGE]
herdr-threads overdue [PAGE]
herdr-threads diagnostics [--seat SEAT] [--thread THREAD] [PAGE]
herdr-threads daemon health
herdr-threads doctor
herdr-threads view [--once] [PAGE]
```

**Warning counts are pending counts.** The `warnings` count on each inbox thread and the check-in `warning_count` count only the seat's *pending* warnings, not every warning it ever received. A warning is pending while the thing it warns about is still open: an overdue invitation that is still pending (not accepted, declined or cancelled), an overdue receipt that is still unacknowledged, an unavailability episode that is still open, or a programmatic service warning addressed to the seat that has not yet been offered to the seat's current occupant. Once its invitation is answered, its receipt is ACKed or the episode closes, the warning is settled: it leaves the counts (and a thread with nothing else pending leaves the inbox) but stays in history. A programmatic service warning is informational, not an obligation. Each check-in offer carries a capped page of at most 16 of the seat's programmatic notices not yet offered to its current occupant, oldest first, in the check-in's `notices` field (`has_more` when more remain); the hook shows the same page on an `offered notices: N [NOTICE@THREAD, …]` line under the digest line. The offer settles exactly that page and nothing else: in the same transaction it advances the current occupant's offered frontier to the last notice it carries (one row written, nothing deleted), so a large undelivered backlog is offered page by page over successive check-ins. Both the durable lifecycle check-in and the tool-boundary Current check-in settle the page they carry once their transaction commits, even if the hook output is later lost; the notices stay in `warnings` history either way. The read-only `warnings` command never settles anything: it has no verified-occupant context. The frontier belongs to one occupant (binding generation and execution): after a replacement, including the new binding generation that each hook lifecycle check-in (startup, clear, resume) starts, the new occupant has its own empty frontier and is offered the retained notices again from the oldest, one page per check-in. Every pending count (the digest classes, inbox `invitations`, `pending_receipts` and `warnings`, check-in `warning_count`) is read by bounded walks and saturates at 1,000: the matching `has_more` flag (`count_has_more` in the digest, `invitations_has_more`, `pending_receipts_has_more` and `warnings_has_more` in the inbox, `warning_count_has_more` at check-in) is true when more may be pending than the count says. The complete warning history, settled or not, is always available from `warnings --seat SEAT`: check-in includes its first page, and you follow the returned next command to page through the rest.

`PAGE` means `--cursor CURSOR --limit N --max-bytes N`; each option is optional. Follow the returned next command to continue; it repeats `--limit` and `--max-bytes` only when they differ from the defaults (20 and 16384). A cursor is a short opaque `c3:` token (about 20 characters): a compact binary position (scope, direction, order version, high-water ordinal and the typed position) with a truncated SHA-256 tag that binds it to its daemon instance, scope key (thread, seat, message) and filter. It is stateless (nothing is stored server-side, so continuations survive a daemon restart), and a cursor replayed against another instance, thread, filter, direction or order version, or a corrupted one, is refused as `invalid_cursor` exactly as before. The previous `c2:` cursors are still accepted for one release. `overdue` lists instance-wide obligations; `diagnostics` preserves explicit seat and thread filters. A recent read selects the first descending page size and its continuation reaches older history. `--recent` and `--limit` cannot be combined, and a cursor cannot be combined with `--recent`, `--after`, or `--before`. Reading, searching, viewing, and check-in never ACK a message.

Top-level agents use explicit mutations:

```text
herdr-threads thread create --topic TEXT [--goal TEXT]
herdr-threads thread topic THREAD --set TEXT
herdr-threads invite THREAD --seat SEAT [--deadline SECONDS]
herdr-threads accept THREAD
herdr-threads accept-required THREAD --invitation INVITATION_ID --requirement REQUIREMENT_ID --revision N
herdr-threads leave THREAD
herdr-threads send THREAD (--body TEXT|--file PATH|--stdin) [--require-ack SEAT ...] [--deadline SECONDS]
herdr-threads ack MESSAGE_ID...
herdr-threads archive THREAD
herdr-threads reopen THREAD
herdr-threads check-in
```

`invite` for a seat that has already joined the thread is a settled no-op: it creates no invitation, prints `already_joined` with the seat and thread (exit 0), and completes its local intent.

These commands act as a seat. Run them inside the agent's own Herdr pane: the CLI uses that pane's `HERDR_PANE_ID` (never the focused pane) to find the seat currently mapped to it and that seat's recorded lifecycle check-in context. A launch driver or hook supplies the first `check-in --lifecycle-event ID` with `--cooperative-seat SEAT --cooperative-target PANE --cooperative-harness codex|claude --cooperative-role top-level`; the same flags can select the seat explicitly for any command. Without a mapped seat and context the command fails and names what is missing. Every such "no caller located" outcome (no `HERDR_PANE_ID`, a pane with no resolved seat, a seat with no lifecycle check-in context, or `inbox`/`pending-receipts` with neither a pane nor `--seat`) is invalid local context: `(invalid_request)`, exit 2. It is fixed by the pane, the `--cooperative-*` or `--seat` arguments, or the seat's check-in, not by a different build.

Every command locates its caller the same way. Inside a pane, `inbox` and `pending-receipts` without `--seat` read the seat mapped to that pane; `pending-receipts --thread THREAD` in a pane with no mapped seat stays thread-scoped, and outside a pane these reads need `--seat SEAT`. `retry LOCAL_REF` for a seat's mutation runs from the same pane (or with the same `--cooperative-*` flags) and refuses an intent recorded for another seat.

**A person in their own pane** runs `herdr-threads me init` once instead of any check-in flags. It requires `HERDR_PANE_ID`, resolves that pane's seat by ordinary resolution, and checks in with harness `human`, role top-level and a plugin-context session. The binding and every later send, invite, accept and ACK from that pane are recorded with `operator_human` provenance, not `cooperative_top_level`. After it, the mutations above and the seat-defaulting reads work in that pane with no flags. A person's seat can be a `--require-ack` recipient: its receipt timer starts at `me init`, nothing prompts the pane, and the person ACKs by hand. Re-run `me init` after a daemon restart to restore availability (it continues the same occupant). It is refused (exit 2) without `HERDR_PANE_ID`; the refusals for agent evidence follow below. An agent later started in that pane replaces the person at its first lifecycle check-in. `me init` is not operator repair and grants nothing beyond what an agent's own check-in grants.

**`me init` refusals.** `me init` never takes over an agent. It is refused (`invalid_request`) when an agent environment marker is present (`CLAUDECODE`, or the variables Codex sets inside its own process, `CODEX_SANDBOX` and `CODEX_SANDBOX_NETWORK_DISABLED`; user configuration such as `CODEX_HOME` is not a marker), when Herdr reports a Claude or Codex agent in the pane (any other detected kind does not count; a failed Herdr read is not evidence either), and, decided by the daemon, when the seat's open binding is an agent's (`cooperative_top_level`). The refusal names the way out: use your own shell pane, give the pane a fresh seat with `herdr-threads seat resolve --pane PANE --new-seat --operator`, or override as the local account with `herdr-threads me init --operator` (recorded as `operator_human_override` in `seat inspect`); after it, person-pane commands in that pane work despite the agent evidence (the override is recorded locally for that human context, and nothing local is replaced until the daemon accepts the check-in). The environment and Herdr checks are best effort and client-side; the daemon's refusal is the guard.

**Resumed sessions reattach themselves.** After a Herdr restart a resumed top-level session (Claude `claude --resume`) whose harness session id uniquely matches an unresolved seat's last binding reattaches that seat when its SessionStart hook runs, with no operator step. This is resume-only: `startup`, `/clear` and `/new` carry a new id and never match. For Codex, run `codex resume` by hand in the pane; `herdr-threads launch` refuses the Codex `resume` form (no captured hook evidence), so use `codex resume` directly or `exec resume`. When no seat matches, the pane stays held and an operator repairs it (see [operations](operations.md#restore-holds-and-repair)).

**Launch and wake guards.** `launch` for a seat whose bound agent Herdr reports live in another pane is refused (`target_unsafe`: "launch refuses to start a second agent for the seat"). Use that pane, or retire or rebind the seat as the operator. A wake prompt goes only to an agent of the seat's bound harness: a pane running a different agent kind, or none, is not woken. A person's seat (`me init`, harness `human`) is never woken; required receipts addressed to it wait for a manual `ack`.

Pane derivation is cooperative, not enforced. `HERDR_PANE_ID` locates the seat; it does not prove who is running the command. Any process that inherits the pane's environment, including a child agent or a script that ignores these instructions, derives the same seat and is recorded as that seat with its recorded top-level role.

**ACK exact message IDs explicitly.** Use `pending-receipts` to find the canonical IDs, read the messages, then run `ack` with those IDs. Accepting an invitation is a separate action. Successful send and ACK output contains IDs and counts, without repeating message bodies. A child agent may read and prepare a summary but must not accept, ACK or check in: in the pane these commands act as the top-level seat, and the plugin cannot tell a child from the top-level agent. For a long thread, an optional cheap subagent can read the full history or `read THREAD --recent N` and return a summary; the plugin does not start a model summary on its own.

**Live view for people.** `read THREAD --follow` is for a person watching a thread, not for an agent's loop: it runs until Ctrl-C (exit 0). It prints the recent messages oldest first (default 20, `--recent N` up to 100, `--recent 0` for none, or `--after SEQUENCE`), then polls the daemon about once a second (backing off to a few seconds while idle) for the messages after the last timeline sequence it printed and prints only those, never redrawing. A daemon restart is reported as a `-!-` notice and followed through; an archived thread is still followed; a thread that disappears ends it. The human form is IRC style: `[HH:MM] <nick> message` in local time, where the nick is the author seat's Herdr pane name (or the label of its single-pane tab), else the short seat ID, with the harness of the seat's current local binding appended (`alice·claude`) unless the name already says it; system events are `-!-` lines, limited to channel joins and leaves (`alice·claude joined`) and warnings (`warning: … is overdue on an ACK`); ACKs, invitations, topic changes and other informational events are left out of the IRC view and remain in `--json` and the machine form; bodies are shown in full, wrapped at the terminal width under the message column and folded after 20 lines with the `herdr-threads body MESSAGE` command for the rest. Per-nick colors appear only on a terminal (never with `NO_COLOR` or `TERM=dumb`). With `--json`, or when stdout is not a terminal and `--human` is not given, it prints one JSON message summary per line (the same object as a `read` page item) and its notices go to stderr. `--no-system` hides system events. It is strictly read-only: it never ACKs, accepts or sends, and peer text is escaped so it cannot drive the terminal. Plain `read` uses the same IRC transcript in its human form.

A required invitation stays pending until the top-level native agent explicitly accepts the displayed episode and revision. Check the inbox, then `thread participants THREAD` for the current invitation ID, requirement ID and revision, including when already joined voluntarily. Use `accept-required` with those exact values. If acceptance reports `stale_requirement_acceptance`, reread before deciding again. Required membership prevents voluntary leave until the owning service releases the requirement; release does not ACK messages or remove the member.

If a mutation's result is uncertain, use `pending-ops [PAGE]` and `retry LOCAL_REF`. The local recovery reference is distinct from a message ID and cannot be ACKed. Retrying uses the persisted operation key and original payload. An intentional repeat uses a new send command.

Operator repair has three explicit forms. The local service records the effective local user for these actions:

```text
herdr-threads invite THREAD --seat SEAT [--deadline SECONDS] --operator
herdr-threads seat rebind SEAT --pane ADDRESS --operator
herdr-threads seat resolve --pane ADDRESS --new-seat --operator
```

Ordinary `seat resolve --pane ADDRESS` discovers an unclaimed pane. `--pane` (here, on `seat rebind` and on `launch`) takes a Herdr pane ID (`w4:p1`, used as given) or a unique pane name: an exact pane ID in Herdr's pane list, else a unique pane label (`herdr pane rename`), else the label of a tab that holds exactly one pane. An ambiguous name is refused as `invalid_request` (exit 2) listing the matching IDs; an unknown one is `not_found` (exit 1); both say to run `herdr pane current` inside the pane for its ID. If Herdr's pane list cannot be read, the value is passed on unchanged. `daemon ensure` and `daemon stop` are explicit lifecycle commands. Operator mode cannot be combined with ACK, accept, send, or check-in.

Inspect a programmatic service connection with `herdr-threads service inspect`. To recover a connected but unresponsive service, use `herdr-threads service disconnect --expected-boot BOOT_UUID --expected-generation N` with the exact values just observed. A stale request cannot disconnect a successor. The result reports whether the recovery audit was persisted. These same-user operator commands are cooperative; another program under the same user can register when the slot is free. Service mutations require one live registered Unix socket held by the persistent programmatic client. A one-shot CLI process cannot retain that authority for later commands. Service `info` notices remain discoverable without waking an agent; `warn` notices use native attention. Publishing a notice does not prove recipients acted, and graph must reconcile those effects. Graph should release required memberships during teardown.

## Lifecycle, diagnostics and exit status

`herdr-threads --help` and `herdr-threads --version` print to stdout and exit 0. Running `herdr-threads` with no command prints the usage text on stderr and exits 2. `daemon ensure` exits 0 once a matching daemon is reachable, even when its health is `degraded` (for example while the host is unreachable); the printed health lists the limitations. The designed cooperative mode is `healthy`. `daemon health`, `doctor` and read commands never start the daemon.

`doctor` is read-only. It reports the executable version, the resolved state directory and host endpoint, whether the state directory is safe, daemon reachability and health, and the owned user-level Claude and Codex hook installations (`hooks.claude.installed`, `hooks.codex.setup_installed`; installed is kept separate from `observed`). `doctor` reports `result: ok` for a healthy daemon and an environment whose installed harnesses have their hooks installed, and `degraded` with `limitation:` lines otherwise. It exits 0 when the daemon is reachable (ok or degraded), 3 when it is not running or unreachable, and 2 when the context is missing or unsafe.

The state directory may be the Herdr-provided plugin state directory (mode 0755); it must be owned by the current user and not writable by group or others. An unsafe state directory is invalid local context: `daemon ensure` and `doctor` exit 2 and create nothing, because restarting the daemon cannot fix it. Everything the plugin creates below it is mode 0700; if one of those private directories (`instances/`, the instance directory, or the runtime socket directory) is changed to another mode or owner, it is the same invalid local context: `daemon ensure` and `doctor` both exit 2 (`doctor` reports `unsafe_state_dir` and does not suggest `daemon ensure`), and neither repairs the mode. The host endpoint is a filesystem path of up to 1024 bytes and may contain spaces.

Errors print one human-readable line (`herdr-threads: DETAIL (error_code)`) on stderr. When the daemon is not running or was stopped, every command that needs it (reads, `daemon health`, `daemon stop`, `view --once`, `seat resolve`, `retry` and cooperative check-in) exits 3 with `(host_unavailable)` and the `daemon ensure` hint. Exit statuses:

| Status | Meaning |
|---|---|
| 0 | Success |
| 1 | The request failed (not found, conflict, unauthorized, stale state, ...) |
| 2 | Invalid arguments or invalid local context |
| 3 | Daemon or host unavailable; run `herdr-threads daemon ensure` and retry |
| 4 | Unsupported capability in this build or environment; includes `transport_denied`: a harness sandbox refused the daemon socket (EPERM/EACCES), so restarting the daemon cannot help. Launch Codex with the sandbox allowance `setup codex` prints ([install](install.md#codex-sandbox-socket-allowance)) |
| 5 | Outcome unknown; inspect `pending-ops` and `retry` the local reference |

## Native hooks

Native harness hooks run `herdr-threads [--state-dir PATH] [--host-endpoint SOCKET] hook claude` (or `hook codex`), the exact argv from `cli::hook::installed_argv`. Agent panes do not inherit the plugin state directory, so setup passes `--state-dir`, and it passes the Herdr server socket as `--host-endpoint` because the user-level hook runs in every session: outside a Herdr pane, or in a pane whose `HERDR_SOCKET_PATH` is another server, it exits 0 at once with no output (no version probe, no daemon start). The pane comes from `HERDR_PANE_ID`. Before parsing, the hook observes the installed harness by running the first absolute `claude` (or `codex`) executable on `PATH` with `--version`; the payload is parsed only when that reports a version the adapter's recipe registry covers (Claude Code 2.1.283 to 2.1.286 inclusive, recipe `claude-hooks-2.1.283`, reported as `X.Y.Z (Claude Code)`; Codex exactly 0.157.1 or 0.158.0, recipe `codex-hooks-v1`, reported as `codex-cli X.Y.Z`, or an unlisted Codex version whose embedded hook schemas match that recipe's fingerprint, reported as **schema-matched, live-unverified**, as Codex 0.159.2 is; see [install](install.md#harness-hooks)), and otherwise the hook stays quiet with a stderr diagnostic. The hook always exits 0, whatever the failure; the exit statuses above apply to ordinary commands, not to `hook`. The hook reads the native payload on stdin, finds the resolved seat mapped to that pane, and prints only `hookSpecificOutput.additionalContext`. It always exits 0 within 1.5 s (tool; a stdin that never closes is cut off at the same budget) or 5 s (startup, which may ensure the daemon), never decides permissions, and never accepts or ACKs.

There are two hook classes:

- **Lifecycle** (SessionStart `startup`, `clear`, `resume`): a durable Lifecycle CheckIn that registers a fresh execution, replayed exactly if its response is lost. A pending request that the service definitively rejects (Conflict, a changed generation, CallerUnverified) is recorded as terminal and cleared, so the next SessionStart registers against the current generation. The output presents pending attention once for that execution, followed by the seat's attention digest line (per-class counts and the newest IDs), which also seeds what the next tool call treats as already shown.
- **Tool boundary** (Claude Bash `PreToolUse`, Codex Bash `PreToolUse`, Codex `compact`): first one read-only `AttentionDigest` query for the seat. The service computes it in one read transaction from the seat's own pending items only: pending invitations, unacknowledged receipts, warnings whose condition is still open, and service warnings addressed to the seat that no check-in has offered to its current occupant yet. It reads them through indexes and store-maintained projections that hold only unsettled rows, with at most 1,001 rows per source, so its cost is bounded: it does not grow with the number of threads in the instance, with the receipts the seat has ACKed and the warnings that have settled, or with how much is pending (counts above 1,000 print as `1000+`). Its token names the newest pending invitation, addressed receipt and actionable warning, plus the seat's own unavailability episode. The hook compares only that token with the last token shown to this execution, and only the invitation, receipt and warning components count: the seat's own unavailability episode is carried but is never new attention for its own model (another recipient's unavailability reaches a sender as an actionable warning). When nothing is newer the call prints nothing and makes no CheckIn. When something is newer (a new message, warning, invitation or required membership) it makes one non-durable Current CheckIn and prints the offer plus a line such as `attention digest: invitations=1 [INV@THREAD]; receipts=2 [MSG@THREAD, …]; warnings=0` (at most 4 IDs per class, `+more` when there are others). That CheckIn's offer reads each listed thread's pending items and the seat's pending warnings with the same bounded walks as the digest, plus one bounded page of warning history, so its cost does not grow with ACKed receipts, settled warnings, pending backlog or ordinary message history. The offer settles only the programmatic service warnings on the notice page it carries (at most 16), shown on the `offered notices:` line. The token is read before the offer, so a message arriving during the call is shown on the next call rather than lost. An ACK or an accepted invitation alone prints nothing. If the digest query fails, the hook prints the offer anyway (fail open). An offer larger than the hook budget is replaced by the compact form described under **Hook budget** below. The tool boundary writes nothing to the local context or intent journals and never replays; the full inbox stays readable with `herdr-threads inbox --seat SEAT` (with `--state-dir PATH` when the prefix rule below keeps it explicit). On any other failure it prints nothing and writes one stderr line. A tool call from a session no SessionStart registered prints nothing.

**Ready commands.** For the top-level agent, both hook classes put a plugin-authored block after the fixed instructions and before any escaped peer data: `Ready commands (run exactly as written, in this pane):`, then one line per listed digest item with the exact command line to run in the agent's own pane (the pane selects the seat, so there is no `--seat`): `- accept: herdr-threads accept THREAD_ID` for an ordinary invitation, `- accept required: herdr-threads accept-required THREAD_ID --invitation INVITATION_ID --requirement REQUIREMENT_ID --revision N` for one that carries a pending required membership (the digest reports that requirement's ID and current revision, so a plain `accept` the service would refuse as stale is never emitted), `- read: herdr-threads read THREAD_ID --recent 20`, `- ACK after reading: herdr-threads ack MESSAGE_ID`, and a final `- all pending: … inbox; receipts: … pending-receipts` continuation. When the startup overview is trimmed or has more threads, a `- thread overview: … thread list --seat SEAT` line follows. Only service-generated IDs made of letters, digits, `-` and `_` are placed in these lines. **Command prefix.** Every ready command, fallback read command and diagnose argv starts with the bare prefix `herdr-threads` when the instance resolver, run in the hook's own environment (the agent's pane) with no flags and without the slow `herdr` query, yields the same canonical state directory as the hook's and the same host endpoint as the hook's (`--host-endpoint` or the pane's `HERDR_SOCKET_PATH`); the agent's plain command then reaches the same instance. Otherwise (a non-default, private or scratch state directory, an ambiguous default with both state roots present, a different `HERDR_PLUGIN_STATE_DIR`, or a missing default) the prefix is `herdr-threads --state-dir PATH`, plus `--host-endpoint SOCKET` when the pane would not reach the hook's endpoint by itself; paths are shell-quoted when needed. Either form is covered by the Claude allow rule `Bash(herdr-threads *)`. The fixed instructions name the `herdr-threads` CLI and the D2 `accept-required` procedure but repeat no argv shapes: the block is the one place exact commands appear. Subagents get no block and are told that in this pane every `herdr-threads` write (any accept, `ack`, `check-in`, `send`, `leave`, `invite` or other mutation) acts as the top-level seat, so they run only reads. The digest's `ITEM@THREAD` form is a display reference: passing it as a thread or message argument fails with `(invalid_request)`, exit 2, naming the bare ID to pass.

**Permission for ready commands (Claude).** Every ready command, the `inbox` fallback and the `daemon health` diagnose line start with the bare program name `herdr-threads` (never an absolute path), so `herdr-threads` must be on the agent's `PATH`. `herdr-threads setup claude` installs the owned project allow rule `Bash(herdr-threads *)`: Claude Code then runs any single `herdr-threads ...` command (any subcommand, any arguments) without asking, including in print mode, where an unallowed command is simply denied. A command chained after it (`;`, `&&`, `|`, `$(...)`) is still checked on its own. Run the lines exactly as written; do not prefix them with `cd`, `export` or anything else, or the combined command is no longer covered. Without setup (or after `unsetup`), Claude asks for each command, and print mode denies it.

**Hook budget.** The whole native `additionalContext` is at most 4,096 bytes. On SessionStart only, one fixed line `Agent guide: run herdr-threads skill; …` follows the instructions when the result still fits; it is the first thing to give way, before any of the steps below. The full offer (for SessionStart, the cached check-in plus the startup directory overview) is sent when it fits. Otherwise a compact form keeps the fixed instructions and the ready commands, replaces the offer body with the startup directory overview as one JSON row per thread (peer topic as data, at most 120 bytes and marked `topic_truncated` when cut, plus `created_at_millis`, `age_millis_signed`, `timeline_messages` and `joined_nonretired_participants`), the digest line and the `offered notices:` line, and then gives way in this fixed order until it fits: (1) the digest line's exact IDs (the commands name the same items; its per-class counts stay); (2) overview rows, one at a time from the end, with an `overview has_more: K of N threads shown` line and the `thread overview` command; (3) the digest counts line (recomputed on every call); (4) per-item commands, from the end; (5) only as a last resort, when the fixed text and the continuation leave no room for it, the `offered notices:` line (the notices stay in `warnings` history). The fixed instructions and the `inbox`/`pending-receipts` continuation are always kept, so the settled notice page survives every realistic fallback, as the CLI design requires. A typical one- to three-thread SessionStart keeps the whole overview and every ready command.

Output by case:

- A pane with no seat, a subagent tool call, and routine no-change tool calls print nothing.
- A pane whose seat exists but is not resolved (for example `unresolved` after reconciliation) prints nothing on tool calls; on SessionStart it prints one compact report, `herdr-threads: check-in unavailable (pane seat mapping is Unresolved) …`, followed by the diagnose argv as JSON (bare or explicit by the command-prefix rule above). The operator repairs the mapping; the hook never allocates a seat.
- Any other unavailable service or rejected lifecycle check-in prints the same compact report on SessionStart only.
