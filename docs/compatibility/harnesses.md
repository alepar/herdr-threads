# Cooperative harness planner and context seams

These Rust APIs include explicit user-level hook-file setup (Claude `settings.json`, Codex `hooks.json` plus the `config.toml` sandbox allowance) and the provisional session-flag hook composition. They do not launch a native agent, invoke a public protocol command, accept an invitation, or ACK a message. (The former `harness::STATUS = "unsupported"` scaffold constant was removed by the integration sweep; daemon health below is the capability statement.)

**Native validation status.** Native observations are reconciled in the generated [validation report](../validation/report.md) (report base `99ea74ca`, verdict **PASS_WITH_GAPS**), not in this file. Every required scenario passed with cooperative model-issued accepts and ACKs joined to SQLite receipts on Claude Code 2.1.285/2.1.286 and Codex 0.159.2 (schema-matched, live-unverified) on Herdr 0.9.1, macOS arm64. Open gaps: two concurrent children (both harnesses), Codex TUI children and the live warning-only coalesced wake. No native receipt run exists for Claude 2.1.283/2.1.284 or Codex 0.157.1/0.158.0. Those runs describe the code at their own SHAs, and the recipe profiles below still declare model receipt (and Codex transport) unsupported natively. Health therefore never reports a harness `supported` (native-verified model receipt, which no recipe proves): the demonstrated receipts are cooperative (`cooperative_top_level`), they ran on versions outside the recipes' receipt evidence (no run on Claude 2.1.283/2.1.284 or Codex 0.157.1/0.158.0, and Codex 0.159.2 is only schema-matched), and Codex `invocation_transport` gates the unused `updatedInput` rewrite in `ToolInvocation::scoped_command`, which no evidence qualifies. An installed version a recipe admits reports `cooperative`, the designed mode (ht-4is.8.16; the integration sweep's `unsupported` read as a failure and made a healthy install `degraded`), with the note `daemon::health::COOPERATIVE_RECEIPT_LINE` ("receipt cooperative: harness cooperative means an admitted recipe without native-verified receipt; ..."). `unsupported` now means absent from the daemon's `PATH` or not admitted. The deterministic evidence below (fixtures, captures, source tests) and the native evidence in the report are separate kinds and are never combined into one verdict.

## Adapter recipe registry

Each native adapter selects its parse/encode behaviour from an evidence-backed recipe table (`harness::recipe`; `claude::RECIPES`, `codex::RECIPES`). A recipe is an explicit version set or a closed interval of canonical `MAJOR.MINOR.PATCH` versions, the committed evidence that admitted them, the evidence scope, and a profile: the input-schema variant (recipes with identical payloads share one; a version whose payloads differ gets a new variant and recipe) plus per-recipe transport/receipt support. An interval is used only when every member is evidenced. Non-canonical text (prefixes, suffixes, whitespace, leading zeros, pre-release tags) is unrecognized; a well-formed version outside every recipe is refused with a message naming the supported recipes. Production entries surface that message as `ContextError::UnsupportedVersion` for both harnesses (Claude parse/encode entries directly; Codex via `From<VersionError>`). A version that could not be observed at all (Codex `VersionError::Unavailable`: a missing, relative, failing or timed-out binary; Claude: an empty caller-supplied version) is refused through the same variant with a message that also names the supported recipes. Its remedy is per harness: Codex tells the operator to point the hook at a supported absolute executable; Claude hooks run herdr-threads and name no Claude executable, so the Claude remedy asks only for a supported Claude Code version and the version its `claude --version` reports. Codex still obtains its witness only by running the absolute installed binary (`InstalledVersion::observe`), and every Codex parser and setup entry takes that witness; Claude entries take the version its caller observed from the installed executable.

## Context API for the eventual bridge

`context::{OccupantContext, SessionReference, Harness, Role, EventKind, CheckInMode, PendingCheckIn, CheckInResponse, ContextJournal, CheckInDispatcher, ContextError}` are exported local types. `LifecycleEvent`, `MailSummary`, `check_in_event`, and `render_context` are exported from `harness`.

The CLI bridge owns the durable operation UUID and serialization. Before a fresh lifecycle, choose one fresh execution UUID and build the context with `OccupantContext::for_event`; serialize the actual CLI intent using that context, mode and expected generation. Pass the same external operation UUID and exact versioned payload bytes to `ContextJournal::prepare`. No operation UUID is minted by this journal. Startup/restart/resume/clear rotate execution independently of native session ID; tool/compact return the current context unchanged. An initial lifecycle can supply its complete freshly constructed context directly.

On retry, load `pending()` or `request_for_event(event_id)` first and use its exact event/context/mode/CAS/key/payload. `request_for_event` returns the frozen pending or completed request even when current context has advanced. `get_or_prepare(event_id, factory)` atomically returns that cached request or invokes one winning bounded local intent factory while holding the context lock. The factory receives current context, must follow context-to-CLI lock order, and must recover any existing CLI intent after a crash between CLI recording and context persistence. The two filesystem journals do not form one atomic transaction. Do not call the lifecycle builder again or refresh a stale context. `check_in_event` verifies event, harness, mode, session reference and role before preparation; known children return `None` without preparing or dispatching. A caller can use `ContextJournal::dispatch` directly for an explicit top-level lifecycle driver, subject to the same journal validation.

The injected `CheckInDispatcher` has only `check_in`. It must supply a finite transport deadline and a complete response, including trustworthy historical-replay metadata. Historical responses are cached for the operation and never installed over current context. The injected response metadata must describe authoritative current-versus-historical context; operation replay alone cannot identify historical context. The journal can durably cache response/context before output: the CLI intent stays pending until selected output is written and flushed, so output loss retries the exact cached response without fresh CheckIn, execution UUID or operation key. Ordinary duplicate delivery returns its cached result; reusing an event or operation with changed bytes fails. Stale dispatch/CAS errors leave current and pending untouched. A missing context permits explicit lifecycle preparation; ordinary current hooks return `LifecycleRequired`. Corrupt and wrong-instance state requires explicit diagnosis/repair; this API does not silently replace it.

Preparation is durably saved before dispatch. Completion places current context, completion marker, original request and response in one atomic replacement, with file and directory fsync. Concurrent hooks use one persistent OS file lock, with a supplied wait bound of at most ten seconds. Dispatch holds that lock through completion. Failed persistence after a successful response retains the prior pending checkpoint for an idempotent server retry; failure after rename can leave the completed state on disk despite an error return.

The caller supplies an existing private absolute directory. Symlink ancestors/files and Unix group/other permissions are refused. macOS/Linux file opens use `O_NOFOLLOW`. These checks assume a cooperative owner and a local filesystem with atomic rename, working OS locks and fsync; they do not defend against same-user directory replacement or establish remote-filesystem crash semantics. Temporary files left by a hard crash are ignored, never treated as completion. The journal is bounded to 1 MiB and 128 completion records, with 64 KiB request/output limits and completion space reserved before dispatch. Capacity exhaustion returns `TooLarge`; automatic pruning or repair is deliberately absent from this seam.

`render_context` returns plain context for a future qualified output encoder. It keeps exact message IDs, labels topics as untrusted JSON data (the `Mail data (JSON)` section is rendered only when rows are supplied; production hooks supply none and carry pending items in the digest line and the ready-command block instead), strips control characters, limits topics to 256 UTF-8 bytes, and limits total output to 4096 bytes. No-change output is empty. The instructions give the top-level agent explicit exact-ID ACK responsibility and separate invitation acceptance; children can read/summarize and return IDs. Rendering or CheckIn never performs those receipt actions.

## Setup API for the eventual installer

`setup::{plan_claude, plan_codex, uninstall_json, uninstall_codex, verify_base, verify_codex_base, shell_command, JsonSetupPlan, CodexSetupPlan, EventGroups, OwnedEntry, SetupError}` are exported.

Claude composition accepts supplied JSON bytes, preserves unrelated keys, permission rules and hooks, and adds one exact owned group for each `claude::declared_hook_groups` entry: SessionStart and Bash PreToolUse, each a command hook with timeout 10. Its proposed `--settings` argv keeps the supplied settings path as one native argument. Codex composition accepts typed existing event groups from a future TOML/config reader, preserves those groups, and proposes `--no-daemon` plus real TOML inline `-c` overrides for the three source-supported events. It does not read or rewrite a whole Codex TOML configuration. Root explicitly authorized this typed seam rather than a new TOML dependency.

Owned group fingerprints describe structural JSON bytes; base fingerprints describe exact Claude input bytes or exact serialized typed Codex groups. Verify the base immediately before publishing a proposal. The planners perform no writes; the explicit user-level installer below writes one hook file and its manifest.

Composition is idempotent. An owned command in a changed or duplicate group conflicts. Uninstall checks the saved fingerprint and removes exact groups only; a missing entry is conservatively refused because removal cannot be distinguished from an edited owned command. Changed owned entries are never overwritten. `hooks.state`, existing trust hashes and permission decisions are not generated or relaxed; the only permission change is the owned Claude allow rule described below. Codex hook trust is the user's review: Codex records a `trusted_hash` under `[hooks.state."<hooks.json>:<event>:<group>:<hook>"]` in `config.toml` when the user trusts a hook (that is how Herdr's own `hooks.json` entry is trusted; Herdr writes no hash). Setup appends its groups so existing trust keys keep their positions, and `setup-status codex` reports the owned keys and whether a hash is recorded.

Neither source tests nor these declarations qualify live installation, native hook output delivery, guarded launch, safe wake, default Codex socket transport, mapping/retirement, or either harness's model-issued accept/ACK demonstration. Native runs of those behaviours are recorded only in the [validation report](../validation/report.md).

**Codex sandbox socket transport (ht-910).** Codex 0.159.2's default `-s workspace-write` sandbox refuses the CLI's connect to the daemon socket (`EPERM`). `setup codex` therefore writes a narrow allowance for this instance's stable socket into the user's `config.toml` (`harness::codex_config`, a structural `toml_edit` edit with its own ownership manifest; only on Codex 0.159.2, where the default-deny was measured): `sandbox_workspace_write.network_access=true`, `features.network_proxy.enabled=true` and `features.network_proxy.unix_sockets={"<socket>"="allow"}`. A key holding another value refuses; a key the user already had with the same value is recorded as pre-existing and never removed. `network_access=true` only starts the proxy, and with no domain allow entries external network stays denied. [Codex demo 2](../evidence/native-codex-demo-2/report.md) is the evidence:

- The default-deny probe refused other Unix sockets, the Herdr server socket, loopback and external TCP (`EPERM`), and proxied HTTPS got 403.
- Under the allowance the model accepted and ACKed on its own (cooperative).

Since ht-4is.8.20 the allowance also adds the instance's client-side journal directories (`<instance>/intents`, `<instance>/contexts`) to `sandbox_workspace_write.writable_roots`, as owned array members. Every mutation and check-in writes there first, and without the roots workspace-write refuses those writes (`EPERM`) whenever the state directory is outside the workspace and tmp. The SQLite database and the daemon's files stay outside every root ([write probe](../evidence/codex-sandbox-writes-probe/README.md), 0.159.3). The allowance is per state directory and Herdr instance and survives daemon restarts. Without it, the CLI reports `transport_denied` (exit 4). This is sandbox reachability only: it does not change the recipes' `invocation_transport` (an `updatedInput` rewrite, still unsupported) or `harness.codex` health.

## Explicit user-level setup lifecycle

`install_user_settings(kind, ..)` accepts a `SettingsKind` (`ClaudeUser`: a `settings.json`; `CodexUser`: a `hooks.json`; any other file name is rejected), an explicit settings path, a separate ownership-manifest path, hook argv, and the exact settings bytes the caller inspected. It rejects a changed initial baseline or a preexisting matching hook without ownership. It writes only that settings file and the requested manifest; the CLI resolves the file from `CLAUDE_CONFIG_DIR` / `CODEX_HOME` (else `HOME`) and keeps the manifest under `<state>/setup/`. A Codex installation records no permission; everything below about the allow rule applies to Claude only. The manifest records version, scope, exact original bytes, the effective installation baseline, owned group fingerprints, a unique installation ID, and a prepared/installed phase. The installation ID appears as a shell comment in the exact owned command, leaving executed argv unchanged. The manifest is published atomically before settings replacement. A failed replacement leaves a prepared record: retry composes with current unrelated settings, while removal can discard an uninstalled preparation. A partial temporary manifest is never published. If settings were published before the phase update, retry recognizes the marked hook and refreshes the removal baseline from current unrelated settings. An independently added unmarked hook is never adopted. The same installation owns one permission allow rule, `Bash(herdr-threads *)` (`claude::HERDR_THREADS_ALLOW_RULE`). It lets Claude run, without a prompt, any single Bash command whose first word is `herdr-threads` (every subcommand, any arguments); a chained segment is still checked separately. It exists because print mode denied the hook's ready commands without it (native Claude demo 2, P6). The ready commands, fallback and diagnose argv use the bare argv0 `herdr-threads` (`cli::hook::CLI_ARGV0`), and a test renders every form with the hook's renderer and checks it against `claude::bash_rule_covers`, a model of Claude's documented Bash rule matching. The manifest records the rule with a fingerprint. An identical rule already in the baseline is recorded as `pre_existing`: it is never duplicated or removed. A manifest recorded before any rule existed is not reported installed, and re-running setup adds the rule through the prepared-intent path. The retired rule `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` (`claude::CALLER_CONTEXT_ALLOW_RULE`) matched only the `updatedInput` rewrite prefix, which the production hook never emits; a manifest that records it reports `allow_rule.ownership: superseded`, and re-running setup records the owned retired rule as `superseded_permission` in a prepared intent, removes it, and adds the declared rule (a user's own copy stays). A hand-removed recorded declared rule makes re-setup refuse rather than re-add it; a hand-removed retired rule does not block the upgrade. `remove_user_settings` removes only the unchanged owned group and the owned rule (plus, for an interrupted upgrade, the owned retired rule), retaining current unrelated hooks and permissions; changed or missing installed hook entries fail closed, while an owned rule that is already gone does not block removal. `inspect_user_settings` reports the rule's ownership and presence in `HookInspection::allow_rule`. When nothing else changed, removal restores the exact effective baseline bytes. Paths containing spaces remain argv values and are shell quoted only for the command hook. The file replacement retains the settings file's permissions.

The public CLI no longer uses the session-scoped Codex path (`plan_codex`, `codex_session_manifest`, `inspect_codex_session`, `uninstall_codex`); those remain library seams for a session-flag launch. Codex is installed at user level like Claude, and `launch` adds no hook arguments. The installed hook command carries `--host-endpoint`, and the hook exits 0 silently, before any version probe, in a session that is not a pane of that Herdr instance (`cli::hook::foreign_session`). Both inspectors return independent `installed` and caller-supplied `observed` values. A `ConfiguredHook` descriptor is present only when required owned declarations match, and its fingerprint describes the currently inspected Claude bytes or Codex groups. `Observed` must come from separate native evidence and is never inferred from a settings file or fixture.

These are provisional setup interfaces against the current declaration surfaces. The Codex and Claude adapter task dependencies still need final declaration and native recipe acceptance. The file operations check exact bytes before replacement, but an unrelated noncooperating writer (including the harness itself, for example Codex recording trust in `config.toml`) can still race the final rename; avoid running setup while the harness is editing its own configuration. The scoped setup tests are deterministic and do not certify a live native callback or receipt.
