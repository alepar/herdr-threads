# Cooperative harness planner and context seams

Current Codex and Claude core operation selects a registered contract independently of runtime version metadata. Setup and launch resolve the selected executable and retain its managed wrapper and PATH; they do not inspect or bypass the wrapper's target. Ordinary setup, launch, hooks, doctor and daemon observation execute no version, help or schema probes. Explicit historical diagnostic utilities remain separate.

Setup configures owned hooks. It does not prove callback delivery, model receipt or runtime verification. Available executables report `contract_declared` with installed `version: null`; daemon cooperation describes the declared core flow. Missing metadata is informational. Missing executables, invalid configuration, ownership/trust problems and actual invalid callbacks remain actionable.

## Context API for the eventual bridge

`context::{OccupantContext, SessionReference, Harness, Role, EventKind, CheckInMode, PendingCheckIn, CheckInResponse, ContextJournal, CheckInDispatcher, ContextError}` are exported local types. `LifecycleEvent`, `MailSummary`, `check_in_event`, and `render_context` are exported from `harness`.

The CLI bridge owns the durable operation UUID and serialization. Before a fresh lifecycle, choose one fresh execution UUID and build the context with `OccupantContext::for_event`; serialize the actual CLI intent using that context, mode and expected generation. Pass the same external operation UUID and exact versioned payload bytes to `ContextJournal::prepare`. No operation UUID is minted by this journal. Startup/restart/resume/clear rotate execution independently of native session ID; tool/compact return the current context unchanged. An initial lifecycle can supply its complete freshly constructed context directly.

On retry, load `pending()` or `request_for_event(event_id)` first and use its exact event/context/mode/CAS/key/payload. `request_for_event` returns the frozen pending or completed request even when current context has advanced. `get_or_prepare(event_id, factory)` atomically returns that cached request or invokes one winning bounded local intent factory while holding the context lock. The factory receives current context, must follow context-to-CLI lock order, and must recover any existing CLI intent after a crash between CLI recording and context persistence. The two filesystem journals do not form one atomic transaction. Do not call the lifecycle builder again or refresh a stale context. `check_in_event` verifies event, harness, mode, session reference and role before preparation; known children return `None` without preparing or dispatching. A caller can use `ContextJournal::dispatch` directly for an explicit top-level lifecycle driver, subject to the same journal validation.

The injected `CheckInDispatcher` has only `check_in`. It must supply a finite transport deadline and a complete response, including trustworthy historical-replay metadata. Historical responses are cached for the operation and never installed over current context. The injected response metadata must describe authoritative current-versus-historical context; operation replay alone cannot identify historical context. The journal can durably cache response/context before output: the CLI intent stays pending until selected output is written and flushed, so output loss retries the exact cached response without fresh CheckIn, execution UUID or operation key. Ordinary duplicate delivery returns its cached result; reusing an event or operation with changed bytes fails. Stale dispatch/CAS errors leave current and pending untouched. A missing context permits explicit lifecycle preparation; ordinary current hooks return `LifecycleRequired`. Corrupt and wrong-instance state requires explicit diagnosis/repair; this API does not silently replace it.

Preparation is durably saved before dispatch. Completion places current context, completion marker, original request and response in one atomic replacement, with file and directory fsync. Concurrent hooks use one persistent OS file lock, with a supplied wait bound of at most ten seconds. Dispatch holds that lock through completion. Failed persistence after a successful response retains the prior pending checkpoint for an idempotent server retry; failure after rename can leave the completed state on disk despite an error return.

The caller supplies an existing private absolute directory. Symlink ancestors/files and Unix group/other permissions are refused. macOS/Linux file opens use `O_NOFOLLOW`. These checks assume a cooperative owner and a local filesystem with atomic rename, working OS locks and fsync; they do not defend against same-user directory replacement or establish remote-filesystem crash semantics. Temporary files left by a hard crash are ignored, never treated as completion. The journal is bounded to 1 MiB and 128 completion records, with 64 KiB request/output limits and completion space reserved before dispatch. Capacity exhaustion returns `TooLarge`; automatic pruning or repair is deliberately absent from this seam.

`render_context` returns plain context for a future qualified output encoder. It keeps exact message IDs, labels topics as untrusted JSON data (the `Mail data (JSON)` section is rendered only when rows are supplied; production hooks supply none and carry pending items in the digest line and the ready-command block instead), strips control characters, limits topics to 256 UTF-8 bytes, and limits total output to 4096 bytes. No-change output is empty. The instructions give the top-level agent explicit exact-ID ACK responsibility and separate invitation acceptance; children can read/summarize and return IDs. Rendering or CheckIn never performs those receipt actions.

## Setup API for the eventual installer

`setup::{plan_claude, plan_codex, uninstall_json, uninstall_codex, verify_base, verify_codex_base, shell_command, JsonSetupPlan, CodexSetupPlan, EventGroups, OwnedEntry, SetupError}` are exported.

Claude composition accepts supplied JSON bytes, preserves unrelated keys, permission rules and hooks, and adds one exact owned group for each `claude::declared_hook_groups` entry: SessionStart and Bash PreToolUse, each a command hook with timeout 10. Its proposed `--settings` argv keeps the supplied settings path as one native argument. Codex composition accepts typed existing event groups from a future TOML/config reader, preserves those groups, and proposes real TOML inline `-c` overrides for the three source-supported events. It adds no daemon mode flag, so wrappers need only accept the caller's chosen arguments. It does not read or rewrite a whole Codex TOML configuration. Root explicitly authorized this typed seam rather than a new TOML dependency.

Owned group fingerprints describe structural JSON bytes; base fingerprints describe exact Claude input bytes or exact serialized typed Codex groups. Verify the base immediately before publishing a proposal. The planners perform no writes; the explicit user-level installer below writes one hook file and its manifest.

Composition is idempotent. An owned command in a changed or duplicate group conflicts. Uninstall checks the saved fingerprint and removes exact groups only; a missing entry is conservatively refused because removal cannot be distinguished from an edited owned command. Changed owned entries are never overwritten. `hooks.state`, existing trust hashes and permission decisions are not generated or relaxed; the only permission change is the owned Claude allow rule described below. Codex hook trust is the user's review: Codex records a `trusted_hash` under `[hooks.state."<hooks.json>:<event>:<group>:<hook>"]` in `config.toml` when the user trusts a hook (that is how Herdr's own `hooks.json` entry is trusted; Herdr writes no hash). Setup appends its groups so existing trust keys keep their positions, and `setup-status codex` reports the owned keys and whether a hash is recorded.

Neither source tests nor these declarations qualify live installation, native hook output delivery, guarded launch, safe wake, default Codex socket transport, mapping/retirement, or either harness's model-issued accept/ACK demonstration. Native runs of those behaviours are recorded only in the [validation report](../validation/report.md).

**Historical Codex sandbox allowance (ht-910).** Earlier setup installed socket/network proxy and journal-root settings based on measured captures in [Codex demo 2](../evidence/native-codex-demo-2/report.md) and the [write probe](../evidence/codex-sandbox-writes-probe/README.md). ## Explicit user-level setup lifecycle

`install_user_settings(kind, ..)` accepts a `SettingsKind` (`ClaudeUser`: a `settings.json`; `CodexUser`: a `hooks.json`; any other file name is rejected), an explicit settings path, a separate ownership-manifest path, hook argv, and the exact settings bytes the caller inspected. It rejects a changed initial baseline or a preexisting matching hook without ownership. It writes only that settings file and the requested manifest; the CLI resolves the file from `CLAUDE_CONFIG_DIR` / `CODEX_HOME` (else `HOME`) and keeps the manifest under `<state>/setup/`. A Codex installation records no permission; everything below about the allow rule applies to Claude only. The manifest records version, scope, exact original bytes, the effective installation baseline, owned group fingerprints, a unique installation ID, and a prepared/installed phase. The installation ID appears as a shell comment in the exact owned command, leaving executed argv unchanged. The manifest is published atomically before settings replacement. A failed replacement leaves a prepared record: retry composes with current unrelated settings, while removal can discard an uninstalled preparation. A partial temporary manifest is never published. If settings were published before the phase update, retry recognizes the marked hook and refreshes the removal baseline from current unrelated settings. An independently added unmarked hook is never adopted. The same installation owns one permission allow rule, `Bash(herdr-threads *)` (`claude::HERDR_THREADS_ALLOW_RULE`). It lets Claude run, without a prompt, any single Bash command whose first word is `herdr-threads` (every subcommand, any arguments); a chained segment is still checked separately. It exists because print mode denied the hook's ready commands without it (native Claude demo 2, P6). The ready commands, fallback and diagnose argv use the bare argv0 `herdr-threads` (`cli::hook::CLI_ARGV0`), and a test renders every form with the hook's renderer and checks it against `claude::bash_rule_covers`, a model of Claude's documented Bash rule matching. The manifest records the rule with a fingerprint. An identical rule already in the baseline is recorded as `pre_existing`: it is never duplicated or removed. A manifest recorded before any rule existed is not reported installed, and re-running setup adds the rule through the prepared-intent path. The retired rule `Bash(export HERDR_THREADS_CALLER_CONTEXT=*)` (`claude::CALLER_CONTEXT_ALLOW_RULE`) matched only the `updatedInput` rewrite prefix, which the production hook never emits; a manifest that records it reports `allow_rule.ownership: superseded`, and re-running setup records the owned retired rule as `superseded_permission` in a prepared intent, removes it, and adds the declared rule (a user's own copy stays). A hand-removed recorded declared rule makes re-setup refuse rather than re-add it; a hand-removed retired rule does not block the upgrade. `remove_user_settings` removes only the unchanged owned group and the owned rule (plus, for an interrupted upgrade, the owned retired rule), retaining current unrelated hooks and permissions; changed or missing installed hook entries fail closed, while an owned rule that is already gone does not block removal. `inspect_user_settings` reports the rule's ownership and presence in `HookInspection::allow_rule`. When nothing else changed, removal restores the exact effective baseline bytes. Paths containing spaces remain argv values and are shell quoted only for the command hook. The file replacement retains the settings file's permissions.

The public CLI no longer uses the session-scoped Codex path (`plan_codex`, `codex_session_manifest`, `inspect_codex_session`, `uninstall_codex`); those remain library seams for a session-flag launch. Codex is installed at user level like Claude, and `launch` adds no hook arguments. The installed hook command carries `--host-endpoint`, and the hook exits 0 silently, in a session that is not a pane of that Herdr instance (`cli::hook::foreign_session`); the one thing it still does there is the evidence note described under "Version evidence". Both inspectors return independent `installed` and caller-supplied `observed` values. A `ConfiguredHook` descriptor is present only when required owned declarations match, and its fingerprint describes the currently inspected Claude bytes or Codex groups. `Observed` must come from separate native evidence and is never inferred from a settings file or fixture.

These are provisional setup interfaces against the current declaration surfaces. The Codex and Claude adapter task dependencies still need final declaration and native recipe acceptance. The file operations check exact bytes before replacement, but an unrelated noncooperating writer (including the harness itself, for example Codex recording trust in `config.toml`) can still race the final rename; avoid running setup while the harness is editing its own configuration. The scoped setup tests are deterministic and do not certify a live native callback or receipt.

## Payload contract

Each harness declares the native hook payload it consumes as data: `claude::CONTRACT` and `codex::CONTRACT` (type `harness::contract::HarnessContract`) list, per event kind, the fields the parsers read, their JSON types and whether each is required. The declaration sits next to the parsers; the drift tests in `tests/harness/contract.rs` fail when a parser requires a field the contract does not declare, or when a declared required field is not actually required by a parser.

The contract carries structure only. Value constraints are not contract terms: string length and control-character limits, the enumerated `source` values (Codex `fork` is valid input that the parser refuses), the Bash `tool_name` filter and the `agent_id`/`agent_type` pairing rule. A payload that satisfies the contract but fails those is the parser's concern, never a contract violation.

`contract_id` is the first 16 hex characters of SHA-256 over the contract's canonical JSON: keys in byte order, events sorted by name, fields sorted by path, no whitespace. It depends only on the declaration, so it is stable across builds and toolchains. A declaration change changes the id and must be deliberate (the pinned-id test fails first). `herdr-threads contract-id [--harness claude|codex]` prints `<harness> <id>` lines; with `--json` it prints `{"claude": ID, "codex": ID, "normalize": {...}}` (one harness with `--harness`). It is local and never contacts the daemon.

`harness::contract::classify(contract, registered_event, stdin)` returns `Ok`, `Violation { event, field }` or `Malformed`. A violation is a well-formed JSON object for a known event kind that is missing a required field or has one of the wrong type; truncated or unparseable JSON, a non-object, oversized input and an unknown event kind are `Malformed`, never a violation. The event is the one the hook was registered for (below), not the payload's own discriminator: a missing, renamed or non-string `hook_event_name` under a registered event is a violation on that field. Without a registration (a legacy hook) the payload's discriminator selects the event.

The canonical harness version is the bare `MAJOR.MINOR.PATCH` (`harness::contract::normalize_version`): `2.1.286 (Claude Code)` becomes `2.1.286` and `codex-cli 0.158.0` becomes `0.158.0`. A pre-release such as `0.160.0-alpha.1`, any other shape and an unknown harness are not recognized. `herdr-threads harness-version normalize <harness> <raw>` prints it (exit non-zero with `unrecognized <harness> version: <raw>` otherwise), so the canary and operators use the same function.

**`--event` registration.** `setup` registers each hook group with its event on the command line: `... hook claude --event SessionStart`, placed after the harness word and before the ` # herdr-threads-owner:<id>` marker. The hook entrypoint accepts an optional `--event NAME` (1 to 63 ASCII letters and digits) after the harness word. Hooks installed before this keep working: they carry no `--event`, still count as installed (`launch` still starts), and classify through the payload discriminator. `doctor` reports them as informational (`setup.event_registration: "legacy"`, never a limitation) and suggests re-running `herdr-threads setup <harness>`, which rewrites the groups with `--event`. For Codex, re-running setup changes each hook command, and Codex keys hook trust by a hash of the hook: review and trust the new hooks once in Codex (the next interactive `codex` start lists them, or open `/hooks`).

### Version evidence

Hooks send bounded observations using the existing nullable `HarnessEvidence` transport and `hook.harness_evidence` negotiation. Each note names harness, optional attributed version or absence reason, contract, event, outcome and session; no raw payload is sent. Reporting is best effort to an already-running compatible daemon and cannot authorize an account mutation, start a daemon or manufacture receipt/runtime proof. Explicit exact-version evidence remains historical and separate from current core operation.

**When.** A per-session gate file, `<state>/harness/evidence/<harness>-<16 hex of sha256(session id)>.json` (directory 0700, file 0600, at most 4 KB, files older than 24 h pruned), decides before any socket I/O:

| Payload | Sent when |
| --- | --- |
| `SessionStart` | always |
| other event, `ok` | the session has sent no `ok` note and the daemon has not said `verified`; or an hour after the session's last `ok` note (a heartbeat, exempt from the verified gate, that keeps a long session in the daemon's recent-evidence window) |
| `violation` | once per session, event and field |
| `malformed` | once per session and event |

Without a session id the hook cannot gate: `SessionStart`, violations and malformed payloads are sent, `ok` only for `SessionStart`. The verified gate suppresses `ok` only; a violation after verification is always reported.

**Where the daemon keeps it.** Exact attributed rows remain in `harness_version_evidence`, with their original lifecycle/tool milestones and sticky violations. `harness_unattributed` retains bounded absence reasons. Unknown runtime creates no synthetic version/build row. For an actual unavailable-runtime violation with a nonempty session, migration 24 adds `harness_contract_diagnostics`, keyed by `(harness, session_id, contract_id)`: first event, field and timestamp are sticky, subsequent violations advance last time, and success cannot clear it or verify a runtime.

Storage retains at most **256 rows per harness**, reads at most **20**, and expires rows after **30 days** since last violation. Eviction uses descending last/first time then ascending session/contract for deterministic ties. Expiry or capacity eviction can retire failures; no new reset/repair command exists. Report projects one newest retained failure through existing `unattributed.reason/at`; Health projects at most one actual failure per harness within **24 hours**. Missing/empty session or malformed input uses bounded parse/reason diagnostics without inventing a session.

Codex rollout `cli_version` is optional creator metadata only, including startup; it never identifies the current managed target. Known-resume suppression remains, and Codex unattributed startup is never held for creator-based credit. Claude's optional runtime-written transcript evidence and held-start behavior remain separately scoped; neither supplies default rich capabilities. See [transcript scope](harness-transcript-version.md).

**Capability.** The note is a daemon capability, `hook.harness_evidence`. A daemon that does not advertise it receives nothing and the hook leaves its gate file alone, except that a Codex resume is marked in the gate file before any socket I/O.

### User-visible states

Historical exact-version diagnostics retain three states; these are advisory and never core admission or capability authority. Every (harness, version) the daemon has evidence for has one of three states, derived by one pure function (`harness::state::derive`, first match wins):

1. a local violation (a payload broke the contract): **broken**;
2. the version is older than every recipe's minimum (the ladder's "below the floor" row): **broken**, action `upgrade <harness>`;
3. it is inside a recipe's `known_broken` range: **broken**. If local evidence verified it, doctor also notes that it has worked here; this remains a historical advisory verdict;
4. local evidence verified it (a lifecycle and a tool payload under the same contract): **working**. A manifest-only `known_broken` row does not override it; doctor notes that it has worked here;
5. the manifest reports it `known_broken` for the same `contract_id` (canary or manual row): **broken**;
6. the manifest has a `verified` row for it under the same `contract_id`: **working**;
7. a recipe lists it: **working**;
8. anything else (optimistic, schema-matched, unlisted and not below the floor): **new**. A new version is never refused and adds nothing to Health; it becomes working when a lifecycle and a tool payload verify it.

A version newer than every recipe is therefore never `broken` just for being unlisted. Manual and canary manifest rows derive identically; doctor prints which one a verdict came from.

**Historical diagnostic action** on a broken verdict (except below the floor), first match: `upgrade herdr-threads to X (supports <harness> <version>)` when the manifest has a `verified` row for this version under another `contract_id` whose `supported_since` is newer than the running release (X is that `supported_since`); else `pin <harness> to <= Y`, Y being the newest version below this one verified on this machine (local evidence, same contract), else the manifest's `last_working`, else (a recipe range) the recipe's newest working version; else `report: <url>`, the row's `issue_url` or the repository's issues page.

**What Health shows.** Actual local payload failures remain limitations. Historical recipe floors, known-broken manifest rows, old admission caches and unavailable version metadata alone add no limitation or repair action. A historical `working` label is not proof of the current runtime, and absence of diagnostics cannot establish Working. Available core contracts remain cooperative with explicit runtime/native-receipt uncertainty.

**What doctor shows.** Exact-version blocks are historical diagnostics, with advisory action/manifest text separated from current configuration and actual input failures. No installed runtime is probed or synthesized. When the daemon advertises `harness.states`, doctor asks it and prints one block per harness: `harness <h>: <state> <version> — <source>` for the newest row and `  <h> <v>: <state> — <source>` for each other row in the Health window, the verdict line of a broken one, each note, `issue: <url>`, `version evidence unavailable: <reason> (<time>)` when the latest unattributed reason is newer than the newest row, `hook payloads not understood: <n>` when non-zero, then the manifest policy and cache lines. The source is one of `local evidence (lifecycle + tool payloads)`, `local evidence: violation in <event>/<field>`, `canary manifest row (<evidence>)`, `manual manifest row`, `recipe tables`, `below the recipe floor`, `no evidence yet`. With `--json` the report has `harness_states` (or `null` with `harness_states_unavailable` when the daemon is absent or too old).

## Harness canary

`scripts/harness-canary.sh` installs each newer Claude Code and Codex release into a throwaway home and checks that herdr-threads still works with it. It runs daily from `.github/workflows/harness-canary.yml` (cron `17 6 * * *`) and on manual dispatch. The workflow selects `--harness both` (Claude Code and Codex) unless a dispatch names another selector: `all` also selects exact-runtime adapters (Hermes), which need a `--runtime-command-file` the workflow never supplies, so they always end inconclusive and fail the run. `both` is a fixed Claude Code and Codex selection, so a new npm-release adapter needs a selector change to join the daily run. It never touches `~/.claude`, `~/.codex` or aisw profiles.

### What each tier checks

- **Tier 0 (no model, always).** Per probed version: the binary reports the installed version (`t0.version`); `setup` installs and `unsetup` removes the owned hooks (`t0.setup`, `t0.unsetup`); `doctor` reports `contract_declared` through the core evaluator (`t0.admission`, no exact-runtime/native proof); Codex loads the config setup left (`t0.config-load`); a session started against a local stub API fires the SessionStart hook and the captured payload parses with the Rust parsers (`t0.hook-fires`, `t0.payload-parse`); every launch flag herdr-threads passes still appears in the harness help (`t0.launch-flags`); plus the isolation check. Codex also records warn-only signals: payload schema `drift` (`t0.schema`), an npm-shim admission mismatch (`t0.npm-shim-admission`) and unknown subcommands or value options (`t0.launch-tables`). Warns appear under "signals" in the summary and never file an issue.
- **Tier 1 (model, only when the key exists).** One cheap prompt per harness on a fresh home without herdr-threads setup: SessionStart and Bash PreToolUse payloads are captured, the model must echo both context nonces back, and the payloads parse (`t1.*`). `--model-tier auto` skips tier 1 for a harness whose key (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`) is empty, `off` never runs it, `required` makes a missing key an infra error. A tier-1 failure is retried twice before the probe counts as failed.

**Core versus historical admission.** Live `chk_t0_admission` and saved `--check-admission DOCTOR PROBE` use `admission.py evaluate-core`. Only `contract_declared` passes; missing executable is infra, malformed/missing/unknown or historical admission labels fail. Optional metadata is diagnostic only. The saved consumer uses the probe harness and preserves the required historical-expectation field, without comparing it to core admission or requiring a schema result.

`evaluate-historical` (legacy `evaluate` alias) retains ladder/schema diagnostics and explicitly rejects `contract_declared`, even with an equal or unasserted expectation. The historical expectation generator, probe fields/schema shapes and gated Rust captured-payload/schema/help diagnostics remain separate. Neither a core pass nor an offline fixture guard proves a native canary run succeeded.

With `--bisect`, a failing newest version is bisected over the candidates between the last verified version and the newest, then confirmed. The result assumes the break is monotone and says so in the report when versions were never probed.

Candidates and contracts. In `since-verified` mode the baseline (`verified_max`) and the `known_broken` exclusions are taken under the tested tree's contract (`herdr-threads contract-id`); rows with a null `contract_id` (manual and recipe-listed rows) count for every contract. A version that is `known_broken` under another contract and not under the current one is re-probed on every run (probe role `reprobe`), so it gains a row under the current contract, and `supported_since` once a release carrying that contract ships; re-probes never change the verdict, the exit code or the issues. Without a buildable herdr-threads the selection is contract-agnostic and nothing is re-probed.

### Running it locally

```sh
scripts/harness-canary.sh --self-test                      # offline; no network, npm or build
scripts/harness-canary.sh --harness both --versions latest --model-tier off --out "$TMPDIR/hc-latest"
scripts/canary/file_issues.py --dry-run --repo OWNER/REPO --report "$TMPDIR/hc-latest/canary-report.json"
python3 scripts/canary/test_file_issues.py                 # the issue-filing cases, offline
```

`--out` must be outside the checkout (or git-ignored). Exit codes: `0` every harness `all_pass`, `no_candidates` or `known_broken_persists`; `1` any `break` or `inconclusive`; `2` any `infra_error`, bad arguments or an isolation refusal.

### Reading the report

The workflow uploads `canary-report.json`, `summary.md` and probe logs as the `harness-canary-report` artifact (30 days) and appends `summary.md` to the job summary. Per harness the verdict is one of:

| Status | Meaning | Issue |
|---|---|---|
| `all_pass` / `no_candidates` | nothing new, or everything new passes | none |
| `break` | `first_bad` is the lowest failing version, `last_good` the version below it; `failing_checks` carry the details | `harness-canary: <harness> <first_bad> breaks herdr-threads` |
| `inconclusive` | results contradict monotonicity, or the baseline failed on confirmation; every probe is listed | `harness-canary: <harness> inconclusive above <last_good or verified_max>` |
| `infra_error` | install, npm or isolation failed (exit 2); the run says nothing about compatibility | none; the failed run is the signal |
| `known_broken_persists` | the failure continues above a declared `known_broken` range | none |

`scripts/canary/file_issues.py` files one issue per harness with `break` or `inconclusive`, deduplicated on the exact title among open issues labelled `harness-canary`. A repeat run with the same result digest is a no-op, a changed digest adds one comment, and it never closes or edits issues or opens PRs. Close the issue by hand once the fix has merged.

### From an issue to a fix

1. Reproduce with the issue's version: `scripts/harness-canary.sh --harness <h> --versions <first_bad> --model-tier off --out "$TMPDIR/hc"` and read the failing check's detail.
2. If the harness changed shape, add or extend an adapter recipe for `>= first_bad` and add the version to `harness-versions.json` once its native recipe is verified.
3. If no recipe can land soon, paste the report's `known_broken_snippet` into the recipe's `known_broken` list (`known_broken: &[VersionSet::Interval { min: Some(Version::new(a, b, c)), max: None }]`; `max` is the newest failing version probed). The explicit historical diagnostic ladder then refuses that range (current core admission remains independent), and the canary reports `known_broken_persists` instead of a new issue until a different version breaks.

### Version manifest

`docs/compatibility/harness-versions.json` is the version manifest (schema 2). The in-repo copy is generated from the recipe tables (`cargo test versions_json_guard`; `HT_BLESS=1` regenerates) and is embedded in the binary; release builds first replace it with the canary's published copy from the `harness-manifest` branch (file `harness-versions.json` at the branch root, raw URL `https://raw.githubusercontent.com/alepar/herdr-threads/harness-manifest/harness-versions.json`) when that is valid schema 2 within the size cap.

Document: `schema_version` (2), `generated_from`, `generated_at`, `latest_release`, `contracts` (`{harness: contract_id}`), `rows`. A row is keyed by (`harness`, `version`, `contract_id`) and carries `status` (`verified` | `known_broken`), `evidence` (`live` | `no_model` | `schema`), `source` (`canary` | `manual`), `supported_since`, `broken_event`, `broken_field`, `last_working`, `issue_url`, plus the recipe fields `recipe` and `known_broken` that the canary scripts read. The in-repo generator writes `status: verified`, `source: manual` and null for every canary-only field (`generated_at`, `latest_release`, `contract_id`, `supported_since`, `broken_event`, `broken_field`, `last_working`, `issue_url`); a row with a null `contract_id` never supplies a status to the daemon. The daemon takes a row's status only when its `contract_id` equals the daemon's own contract; release-pointer fields (`latest_release`, `supported_since`, `last_working`, `issue_url`) are read for (harness, version) from any row. A `schema_version` other than 2 means no manifest (the canary's reader upgrades a schema-1 file on read).

Invariants (`src/harness/manifest.rs`; the canary writer enforces them): the file is at most 256 KB (`MAX_MANIFEST_BYTES`); the writer keeps per harness the newest 50 versions plus every `known_broken` row and every recipe-listed version, and fails above 80% of the cap; a `known_broken` row carries `broken_event` and `broken_field`; files from the writer and from the in-repo generator both pass the daemon's reader.

When the daemon fetches: only from its recording path, when (a) a harness version has no local evidence and no row in the cached or embedded manifest, or (b) a fresh violation is recorded; at most once per day per harness (a failed attempt counts). The fetch runs on a detached thread (`curl -fsS --max-time 5`, 256 KB cap, `If-None-Match` with the stored ETag when a valid cache exists) and never blocks the caller. It is a plain GET: nothing about the user, the machine or the project is sent. A missing `curl` is the same as offline. A body that is not schema 2, is too large or is invalid is logged and ignored; it never replaces a valid cache. Readers use the cache (`<instance>/harness-manifest/harness-versions.json` with `meta.json` holding the ETag, fetch time and last attempt per harness) and fall back to the embedded copy.

Opt out: set `"harness_manifest": "off"` in `<instance>/settings.json` or `HERDR_THREADS_OFFLINE=1` in the daemon's environment. Both are read once at daemon start, so run `herdr-threads daemon stop` then `ensure` for a change to apply. `settings.json` rejects unknown keys (the daemon refuses to start and names the file), so downgrading herdr-threads to a release that does not know a key requires removing the key. `herdr-threads doctor` prints the effective policy and the cache state (informational, never a limitation).

### Manifest publishing

The canary's `publish-manifest` job writes the manifest to the `harness-manifest` branch (file `harness-versions.json`) by a direct commit from `github-actions[bot]`; it is the only job with `contents: write`, and it runs serialized (`concurrency: harness-manifest`). Only the default branch publishes: a scheduled run (always on the default branch) or a manual dispatch of the default branch. A dispatch from any other branch runs the canary and uploads the `harness-canary-manifest` artifact, but the publish job is skipped, and the job itself refuses (exit 1, no push) if `GITHUB_REF` is not the default branch reported by the API. The writer is `scripts/canary/manifest.py write`: baseline is the branch file (the in-repo file until the branch exists; a schema-1 baseline is upgraded on read), output is always schema 2.

- **Which outcomes write rows.** Only a payload-contract violation (a well-formed payload of a known event that breaks the declared contract) writes a `known_broken` row, with `broken_event`, `broken_field` and `last_working` (the newest version below it that verified under the same contract, else the baseline's newest verified version). A probe that passed with every captured payload `ok` writes a `verified` row (`evidence: live` when a `PreToolUse` payload was among them, else `no_model`). Everything else stays issue-only and writes nothing: tier-0 failures, schema fingerprint drift, infra errors, inconclusive bisects, flaky probes, malformed-only payloads. An existing `known_broken` row stays until a later run verifies the same version under the same contract. A row under a contract other than the tested one does not exclude the version; it is re-probed (see "Candidates and contracts"). Version keys come only from `herdr-threads harness-version normalize`; a version it refuses is skipped with a warning.
- **Two live contracts and `supported_since`.** The canary keeps one row per live contract: the current tree's (`herdr-threads contract-id` at the tested commit) and the latest release's. `scripts/canary/release_contract.sh <tag> <out>` builds that release in a git worktree, asks it for its contract id and replays its `canary_payloads` over the kept probe captures. When the release's contract equals the current one its probes fold into the same rows; when it differs each version gets a second row keyed by the release's id. A release that predates contract ids is recorded as unsupported and contributes nothing. Only a release whose `contract-id` cannot answer is unsupported. A release that cannot be checked out or built, or whose lookup or tag fetch fails (infrastructure), is not: it writes `{"tag", "error"}`, the previous release-contract rows are kept, the workflow annotates a warning and the job stays green (its exit code comes only from the canary step). Tier-0 rule: a probe whose last attempt failed a tier-0 check other than `t0.payload-parse` ran in a broken setup, so a payload violation in it is issue-only and writes no `known_broken` row; a violation with only `t0.payload-parse` failing still does. For every `verified` row the release's contract also passed, `supported_since` is set (once) to the release tag. Rows of any other contract are dropped; they are not live.
- **Retention and size.** After each run the writer keeps the newest 50 versions per harness plus every `known_broken` row, every recipe-listed row and every manual row. It refuses to write (and the canary job fails) when the document would exceed 80% of the 256 KB cap (209715 bytes).
- **Manual edits.** `python3 scripts/canary/manifest.py validate PATH` checks a manifest against the schema-2 invariants (exit 1, one line per violation). `python3 scripts/canary/manifest.py set --file PATH --harness H --version V --status verified|known_broken ... --binary target/debug/herdr-threads` upserts a row with `source: manual`, validates and writes atomically. The canary never modifies or removes a manual row (it logs `kept manual row`). Commit the edited file to the `harness-manifest` branch.
- **Release embed.** `release.yml` fetches the branch file and runs `manifest.py embed`, which copies it over `docs/compatibility/harness-versions.json` only when it is schema 2, at most 256 KB and passes `validate`; otherwise it prints a notice and the in-repo file is embedded.
- **Prerequisite: repository rulesets.** The publish job's token can write any ref of the repository, so the repository must have an active ruleset on the default branch that blocks deletion and non-fast-forward updates, and an active ruleset on `refs/tags/v*` that blocks deletion and update. The job lists the rulesets through `gh api` and runs `manifest.py check-ruleset` before it pushes; a missing ruleset (or a 403/404 from the API) fails the job without pushing. Create them under Settings, Rules, Rulesets.

### Schedule liveness

In a public repository GitHub disables scheduled workflows after 60 days without repository activity. A disabled canary files no issues, so it looks exactly like a passing one, and nothing in the workflow can detect that. Check it by hand, and before every release:

```sh
gh workflow view harness-canary.yml     # state must be active
gh run list --workflow harness-canary.yml --event schedule --limit 3   # a recent scheduled run
```

If the workflow is disabled, re-enable it with `gh workflow enable harness-canary.yml`. An automated keepalive is deferred.
